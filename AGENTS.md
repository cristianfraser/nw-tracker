## Language and i18n

- **UI copy via i18n (es + en)**: all user-facing strings live in **`client/src/i18n/master.json`** — the single source of truth, nested like the locale files, every leaf holding both languages: `{ "en": "Save", "es": "Guardar" }`. `locales/es.json` / `locales/en.json` are **generated** by `npm run i18n:generate -w nw-tracker-client` (`client/scripts/i18n-generate.mjs`); never hand-edit them — `client/src/i18n/localeSync.test.ts` fails on drift. The master stays nested because some leaf keys contain literal dots (e.g. `panelAccounts.addAccount."accountType.equity"`). No hardcoded Spanish or English labels in components except via `t('…')` / `i18n.t('…')`.
- **Translation keys in English**: dotted paths such as `dashboard.cards.netWorth`, `brokerage.groups.mutual_funds`. Code identifiers use English slugs (`mutual_funds`, `real_estate`); display copy lives in `master.json`.
- **Shared labels**: use helpers in `client/src/i18n/index.ts` (e.g. `ccExpenseCategoryLabel`, `flowsPlBucketLabel`; a nav node's label is the server's, resolved with `resolveNavTreeLabel`) so sidebar, cards and charts read the same keys.
- When adding UI text, add the key (both languages) to `master.json` first, run `npm run i18n:generate -w nw-tracker-client`, then reference it. Migrate hardcoded strings when touching an area.
- **UI language preference**: `client/src/languagePreference.ts` (localStorage `nw-tracker.language`), seeded once from `navigator.language` (Spanish → `es`, else `en`; non-browser/vitest contexts stay `es` so label assertions are deterministic), then the stored value is authoritative. Changed from `/panel/settings` via `DisplayPreferencesContext.setLanguage` (calls `i18n.changeLanguage`, persists, syncs `<html lang>`; re-renders `AppTree` top-down). The decimal separator is an independent setting. **Do not cache `t()` results** in `useMemo`/state without the language in the deps — translate at render time.
- **Dates**: numeric dates render as ISO `YYYY-MM-DD` (timestamps `YYYY-MM-DD HH:MM`) in every language — never `dd-mm-yy` / `toLocale*` short styles. Month-name labels (`dic 2026` ↔ `Dec 2026`, ticks `dic 16` ↔ `Dec 16`) go through `client/src/formatDateLabel.ts`, which reads `i18n.language` at call time — same no-caching rule as `t()`.
- **Enforced by `npm run check:conventions`** (root; also runs at the end of root `npm run typecheck`): flags accented Spanish in client string literals/JSX (comments exempt), `Intl.NumberFormat` outside `format.ts`, hardcoded-locale `toLocaleString` without date options, month-name tables outside `formatDateLabel.ts`, `isFetching` / `isRefetching` in `client/src/components` / `pages` (see «Loading states»), and ticker-suffix parsing (`.endsWith(".SN")`, `lastIndexOf(".")` on a ticker, `\.SN$` regexes, `LIKE '%.SN'`) in `server/src` / `client/src` / `ingest/src` outside `server/src/priceProviders/` (see «Instrument registry and price providers»). It also flags currency hardcoding (docs/any-currency-plan.md): `formatClp` / `formatUsd` (and `formatUsdFine`) in `client/src/components` / `pages`, a unit or currency compared with a literal code, fixed currency lists and `"clp" | "usd"` unions outside `rates.ts` / `valueConvert.ts` / `displayUnits.ts`, and `_clp` / `_usd` / `_eur` keys in `server/contracts/src/dto`; every hit fails unless its line says why the currency is native to its source (`// convention-ok: <reason>`: an F22 figure is pesos by law, a Santander feed has a peso and a dollar side, a card's billing frame is pesos), and a migration above 312 with `CHECK (… IN ('clp' …))` fails outright (reference `currencies(code)`). There is no ratchet baseline. «Is this pesos?» is `isHomeCurrency` (`HOME_CURRENCY` in the contracts' `dto/apiConstants.ts`, re-exported by the server's `displayUnits.ts`); a client figure one currency by nature formats through its named wrapper in `client/src/formatNative.ts` (`formatF22Pesos`, `formatCardBillingPesos`, `formatMortgagePesos`, …), a display-unit value through `formatMoney` / `formatCurrency`. Every currency prints from its `currencies` row (symbol, its side — `symbol_after`, the UF «1.234,00 UF» —, `display_digits`; migration 364): `formatMoney(m, { precision: "full" })` prints up to the digits it is counted in (a cuota's UF parts, 4), `{ digits: n }` a fixed count (the UF in pesos, 2); there is no UF-only formatter. Escape hatch: `// convention-ok: <reason>` on the line.
- **Dependency guard, also in `npm run check:conventions`** (`scripts/check-deps.mjs`, baseline `scripts/check-deps.baseline.json`). Builds the TypeScript import graph of `server/src`, `client/src`, `ingest/src` and `server/contracts/src` (tests excluded, type-only imports counted, `.js` resolved to `.ts`/`.tsx`, `nw-tracker-contracts` to its `index.ts`) and fails when a file joins an import cycle the baseline does not list, when a new edge crosses a forbidden boundary (contracts → server/client/ingest, client ↔ server, ingest ↔ server: `server/contracts` is the only shared code), or when `cacheRegistry.ts` imports a module it did not. Prints the largest cycle, the edge count vs the baseline and the top fan-in, fan-out and transitive-reach files. Cycles may only shrink: after a change that shrinks them, `node scripts/check-deps.mjs --write-baseline` locks it in (docs/untangle-plan.md F1). Shared formats (numbers, dd/mm and ISO days, day arithmetic, year-months and Spanish month names, accent folding, RUT and account numbers, merchant text, the zod building blocks) live in `server/contracts/src/formats/`, each rule pinned by a case file in `server/contracts/data/` (`npm run test -w nw-tracker-contracts`); the Python parsers assert the same files.
- **Number formatting**: all numbers (CLP, USD, UF, units, percents) share one decimal-separator convention from `client/src/numberFormatPreference.ts` (localStorage `nw-tracker.decimalSeparator`, seeded from the IANA timezone; toolbar toggle overrides). Always format via `client/src/format.ts` helpers — never `Intl.NumberFormat` / `toLocaleString` with a hardcoded locale for numbers. A separator change re-renders (not remounts) via `AppTree`; **do not cache formatted strings** in `useMemo`/state unless `decimalSeparator` is in the deps — memoize raw numbers, format at render. **Typed numbers:** every number field reads through `parseNumberInput` / `parseNumberInputOrThrow` (format.ts). A number that fits one convention is read that way («1500,5», «1.500.000», «1,234.56»); only a single mark followed by exactly three digits («1.500») is decided by the setting (1500 with comma decimals, 1.5 with period decimals); anything else is rejected with `common.numberInvalid`; forms keep their own sign/range/integer rules. Prefills and placeholders use `formatNumberInput`. Never `Number()` / `parseFloat` / `.replace(/\./g, "")` on typed text, and no `type="number"` inputs (the browser parses those by its own locale). The flows amount filter (`flowsAmountFilter.ts`) also takes an amount copied from the table: a leading `$` / `US$` and the negative «($500)».

## An account's value: what it holds, converted once (`docs/holdings-currency-plan.md`, `accountValue.ts`, `holdingPrices.ts`, `valueConvert.ts`, `rates.ts`)

- **Value at a date = quantity of what the account holds, converted ONCE into the display unit.** `accountHolding(id)` (`holdings.ts`): a currency (pesos, dollars; property and mortgage in UF), a stock (quote currency), a coin (dollar price series), fund cuotas (peso-priced) or a card. `accountHoldingQtyAt(id, ymd)` = quantity; `holdingPriceAt(instrument, ymd)` = unit price in its quote currency (past day: stored observation on/before, history tier; today: live quote in session, held print after close, display-session bar, newest bar; a fund's live/per-date Risky Norris proxy); `accountValueAt(id, ymd, unit)` = qty × price → `convertValue` (`valueConvert.ts` over `rates.ts`). Never build pesos and convert back. Historical stack `accountHistoricalQtyMark` (`accountMarkClpAtYmd.ts`: branches return quantities; an instrument is the asset only on days its price is on file, else fall through); `accountMarkClpAtYmd` = that in pesos.
- **Spread side = what closes the position.** Assets: foreign → CLP at bid, CLP → foreign at ask; liabilities flip (`accountIsDebt` / `kindIsDebt`, `accountProfile.ts`). UF and EUR have no spread. Stored days read `fx_daily` with bid/ask observed that day or later, else mid ∓ half `FX_BID_ASK_SPREAD_CLP`. Flows convert per event at their own day's stored rate (`flowEventInUnit` / `convertFlow`: pesos → dollars at the buy rate, any other pair at the day's mid); benchmark levels convert at the mid.
- **Today reads the live rate** (every pair with a live rate while the fx day is open: `shouldUseLivePairQuote` / `livePairRateForDay` in `fxLive.ts`, read by `rates.ts`). `accountTodayValue(id, opts) → {value_clp, native_value, native_currency, side, as_of_date, priced_on}` is the one today value (dashboard row, header, today's mark, perf live row, every chart live point); other units convert the NATIVE value with `todayValueInUnit(id, v, unit)`. `priced_on` is informational only.
- **`accountValueInUnitFromClp(id, clp, ymd, unit)`** (`accountValue.ts`) converts a peso-native account value at the account's side and re-reads a value native in another currency (`accountValueCurrency`) from its holding. `clpToUnitAt(clp, ymd, unit, {side})` is for amounts that aren't one account's value (cards netted from cash, liability totals at `side: "debt"`). Bucket/net-worth sums in a unit = Σ each account's value in that unit per day (`buildDashboardBucketDailySeriesInUnit`, daily series, overview, ATH) — never Σ pesos ÷ one rate.
- **A card's value in a unit goes through one seam, `cardValueInUnit.ts`**: the card's sub-balances per currency (`ccOwedByCurrencyAtYmd`) each convert on their own, at the debt side while owed and the asset side while in credit; a card with no walk on file is its peso owed alone. The property and mortgage are still the depto ledger's pesos (peso quantities) until the loan phase.
- **Stored valuations are in any currency (migration 260, `valuationValue.ts`).** A `valuations` row is a quantity in `currency` (any lowercase code). Generic readers convert once on the row's date at the account's side (`storedValuationInUnit`: `valuationLatest.ts`, `bookValuations.ts`, `valuationTimeseries.ts`); the historical stack (`accountMarkClpAtYmd.ts`) carries book marks in pesos, so a non-peso book mark with a carry window throws. Kind-specific readers assert their currency (`assertValuationCurrency`: card CLP anchors, AFP/Fintual peso marks). Property rows are UF appraisals, left out by every mark reader (`valuationsAreAppraisals`); the mortgage has none (migration 261; the depto ledger values it, and property/mortgage chart month-ends come from the ledger, `augmentChartDatesForDeptoAccounts`). `GET /api/accounts/:id/valuations` returns `value` + `currency`; `POST` writes pesos and refuses a property, a mortgage and a crypto account.
- **The daily cache stores quantities** (`markSeriesStore.ts` cells `{qty, asset}`); unit values are built at read from memoized day price and rate (`accountValueSeriesOnGrid`), one series for every unit. Rate rows (`fx_daily`, `fx_daily_bid_ask`, `uf_daily`) trim only accounts whose quantity is a rate-built peso figure (cards — from the row's own day —, the depto ledger, book marks), never shares, coins, cuotas, options or foreign-currency ledgers (the series' `rate_independent`, `trimRateDependentMarkSeries`). Price rows (`equity_daily`, `fund_unit_daily`) trim their holders (which asset a day holds depends on price availability).

**Display units are currencies** (migration 312, `displayUnits.ts`, `rates.ts`, `fxPairsSync.ts`, `docs/any-currency-plan.md`). The toggle offers every **core** currency in `currencies` (CLP, USD, EUR; `GET /api/currencies` → code, symbol, minor digits, tier, read by the picker and formatters). Requests name `?unit=<code>` (`requestDisplayUnit`; `include_usd` / `include_uf` ignored) and every payload is built in that one unit — no `*_usd` twins, fixed-unit `Record`s or `unit === "usd"` branches outside `rates.ts` / `valueConvert.ts` (dashboard rows, nav cards, value map, bundles (`nav_strip` 21, `group_shell` 3), valuation/daily series, performance, Rentabilidad, benchmarks, export, all flows payloads, latest movements, cards/liabilities, ticker, watchlist, market series, projections, wealth percentile). **Rates:** `rates.ts` tries a direct pair, then via USD, then via CLP (UF and Banco Central EUR/CLP are peso pairs). EUR/USD is in `fx_rates` (Yahoo `EURUSD=X` from the portfolio start, write-once, dated on the London day, due after London midnight; source `fx_pairs`, `scripts/sync-fx-pairs.ts`); EUR/CLP reads `eur_daily`. Every core pair has a live rate (see «Every core pair has a live rate»); today's EUR/CLP crosses EUR/USD × USD/CLP. A flow converts at its day's rate (`flowEventInUnit` / `convertFlow`: own dollar leg in USD, buy rate pesos → dollars, day mid otherwise). **Native currencies are not display units:** a card's foreign sub-balances, `facturado_foreign`, the card billing ledger and facturaciones (pesos), the tax return and 1040, groceries, fx bid/ask gaps. `zeroCloseEps(unit)` (`perfKernel.ts`) is the unit's smallest coin. EUR projections use the USD inflation default (2,5 %). **Fx coverage** (`fxCoverage.ts`; `fx_coverage` on the bundle and market series; the rates page's `RatesCoverageNotices`) checks every pair the conversion into the unit walks from each held currency (both movement legs, valuations, plus pesos and dollars; walk = `conversionPairs`, rows `pairStoredDates` / `pairHasStoredQuote`): `{unit, pairs: [{base, quote, complete, first_missing_date, …}], …}`, copy naming pair and unit. Warmers build every core currency (`warmedDisplayUnits`). The synthetic market writes EUR/USD ~1,10 and EUR/CLP = USD/CLP × EUR/USD; the demo's real market loads EUR/USD and its asset carries `fx_rates` (asset schema 2 — publish a new asset from the home server before the next demo release).

## Data provenance (`DataOrigin`)

API payloads must **not** use top-level `source: "db"` / `"csv"` — the client always reads SQLite. Provenance describes how data entered:

| Layer | Field | Examples |
|-------|--------|----------|
| Account | `accounts.import_key` (identity; `notes` = same string as human provenance) | `import:excel|key=mortgage`, `credit_card_master|santander|<last4>`, `import:panel|ticker=QQQ|key=…` |
| Row | DTO `origin` | `import_document`, `manual` (from `cc_installment_purchases.source`: `pdf` → `import_document`) |
| Market data | (future) | `api_sync` / `api_yahoo` for `equity_daily` |

Shared type: `server/src/dataOrigin.ts` (`import_document` \| `manual` \| `api_sync`).

## Import sources vs runtime

**Rule:** files under `cfraser/` are **import inputs only**. HTTP, dashboard, valuation, and sync read **SQLite**; missing data → error or “run import”, not a silent file fallback.

- **Depto:** one movement ledger per property (`loadDeptoLedgerForProperty(id)`, cached `depto.ledger|rows|<property id>`; `deptoLedgerForAccount` / `deptoLedgerForLoan` / `loadAllDeptoLedgers`). Pairs come from `propertyLoanPairs()` (`accountRoles.ts`: a `property` role holder and its `loan_of` account); extra properties are `import:property|key=<k>` / `import:loan|property=<k>` (`propertyAccountImportKey` / `loanAccountImportKey`; migration 299's triggers seed the roles). Every reader («Próximos pagos», valor/hipoteca overlays, mortgage sections, card pairing, real-estate mortgage rows) loops over the pairs; the lender portal reading names its loan by `lender_pattern`. The ledger joins property-account movements with **`loan_payments`** (migration 258; docs/holdings-currency-plan.md phase 4): one row per payment movement, `leg` `property` | `loan`, `loan_account_id`, cuota, origin, and the bank's figures in its own currency — `balance_after`, `min_payment`, `max_payment` in `loan_currency` (UF); `principal`, `extra_principal`, `interest`, `insurance_fire`, `insurance_life` in `payment_currency` (pesos); readers throw on any other pair. Nothing derived is stored (parts' UF = pesos ÷ UF día, 4 decimals, the pago 5; net equity; `pagado_neto_uf`; `pago_acumulado_clp`; deltas/acumulados are computed from `uf_daily`). The appraisal is a **`valuations` row of the property account in UF**, forward-filled by the ledger; a property's valuations are its appraisals (`valuationsAreAppraisals`, `valuationValue.ts`), so generic mark readers skip them and its chart samples month-ends from its first ledger row (`augmentChartDatesForDeptoAccounts`); its value is net equity (`deptoNetEquityUfBySnapshotDates`). Rows are **sequential daily balances**: order = `deptoLedgerChronoCompare` (date, then decreasing crédito restante for same-day prepago+cuota); `assertDeptoPrepagoSequencing` fails when a prepago raises the balance (regular cuotas may: grace-period capitalization); snapshot fills use exact-date cutoffs with prepagos included — never a month-end cutoff expansion or a prepago skip (one-day equity spikes, ± P/L couplets). `mortgagePaymentCreate` writes the movements (human notes, mortgage `flow_kind`) plus both `loan_payments` rows; manual-payment recompute updates in place. No `depto_snapshot`: the RE card synthesizes valor/hipoteca from the property + mortgage rows. **The mortgage group page** (`GET /api/portfolio-groups/:slug/mortgage-glance?unit=`, `mortgageGroupGlance.ts`) reads each loan's own `depto_glance` from its cached account bundle, so a loan's figures are its page's, and sums them in the display unit (whatever each loan's currency): today's balances as the loan pages value them, the chart's balances at each date's rate, original / paid / prepaid at today's rate, the next cuotas from their payment-currency figures at today's rate, financing cost summed per period and year; `payments` merges the loan pages' payments lists into one when the loans share their loan and payment currencies (else `payments` is null and `payments_mixed_currencies` says why; the rest of the page serves), the day figure is null when any loan's is, and `GET /api/portfolio-groups/:slug/mortgage-prepayments` merges their prepaid-vs-invested comparisons (`computeMortgageGroupPrepaymentComparison`, totals by the shared `prepaymentTotals`).
- **Account identity:** `accounts.import_key` (unique, nullable; migration 159) is the find-or-create key and well-known lookup (`import:excel|key=mortgage`, `import:fintual|cert|key=…`, `credit_card_master|<issuer>|<last4>`, `import:panel|…`); every creator writes it; `notes` holds the same string for humans, never read by code. Card→account resolution uses `credit_card_account_config.card_last4` (every master has a config row).

Runtime code must not use `fs.readFile*` on `cfraser/` except in `server/scripts/` and import helpers. The import-sync documents route (`GET /api/import-sync/documents/:accountId/:month/file|sheet`, `importSyncDocumentFile.ts`) is the only request path that serves a document's bytes or an xlsx's cells: it resolves the file on the server from the column and month (never a client path; the real path must be a regular file inside that kind's document folders, or the cell and the route throw); a preview over 20 MB or 200 000 cells is a 413. The coverage route (`GET /api/import-sync/document-coverage`) only lists the files and reads the parsed-cartola JSON for the matrix.

## Server runtime modes (local vs hosted demo)

One binary, env-driven (`server/src/httpSecurity.ts`, root `.env` loaded at boot):

- **The primary runs as LaunchAgent `com.user.nw-tracker-server`** (`server/com.user.nw-tracker-server.plist`, installed by `server/scripts/install-server-agent.sh`, which refuses while the port is taken): `tsx src/index.ts` without watch, KeepAlive, log `cfraser/server.log`. Restart: `launchctl kickstart -k gui/$(id -u)/com.user.nw-tracker-server` (alias `nw-server-restart` bootstraps it if unloaded). Its scheduler owns the nightly ingest runs (`docs/ingest-split-plan.md`), so it must not depend on a terminal.
- **The primary is a home server deploying from GitHub `main`** (`scripts/server-deploy.sh`, agent `com.user.nw-tracker-deploy` via `scripts/install-deploy-agent.sh`). An always-on Intel MacBook Pro (`pmset disablesleep`) runs server and ingest service; the laptop runs no agents and no live DB (dev servers use test/demo data or a snapshot copy with `BACKGROUND_JOBS_ENABLED=0`). Every 3 min the agent fetches `origin/main`; on a move it enqueues a `deploy` job (see «The job queue»; one queued, moved to the newest commit) and polls its claim ~150 s, else leaves it for the next run (stale after 15 min, so a dead agent can't drain the queue forever). The claim needs nothing else running (`server-restart`): in-flight ingest finishes, nothing new starts once it is due, and after the restart the executor holds every job until the agent completes (or the 20-min lease lapses → lost, badged). Then: snapshot `before-deploy-<sha>`, fast-forward, `npm ci` only when a package file changed, build into `client/dist.next` and swap with two renames (old kept as `dist.prev`; never build into `client/dist` in place — the live server 404s meanwhile), restart the server (and the ingest service when `ingest/`, `server/contracts/` or a package file changed), wait for `/api/health` to report the commit, complete; on failure roll back, complete as failed, never retry that commit. With the server down it deploys without the queue. Refuses commits not on `origin/main` or modified tracked files. Outcomes in `cfraser/deploy.log`, the job and app messages (failure = notification); `scripts/server-deploy.sh --check` dry-runs. Read-only deploy key. Machine differences a deploy must not undo: poppler/qpdf from MacPorts (`/opt/local/bin`, on the installed plists' PATH; tracked plists carry laptop paths, adapted at install), Intel builds of `ingest/python/.pdf_deps` / `.numbers_deps` (`pip install --target`), and npm 11 skipping unallowed install scripts (the deploy checks `better-sqlite3` loads).
- **Open tabs reload onto a deployed client** (`server/src/clientBuild.ts`, `client/src/clientBuild.ts`): the live-quotes stamp poll carries `client_build` = the served `client/dist/index.html`'s hashed `/assets/` script/stylesheet URLs, sorted, space-joined (cached on mtime+size; null without a served client). The tab compares its own boot-time id (both sides assert `server/src/test/clientBuildIdCases.json`) and, when different, reloads at its next in-app navigation or once hidden, never under a form. One reload per build (sessionStorage `nw-tracker.clientBuildReloadedFor`); a still-differing tab only warns. Production builds only.
- **`HOST`** — default `127.0.0.1` (keeps the unauthenticated API off the LAN); the demo sets `0.0.0.0`.
- **`CORS_ALLOWED_ORIGINS`** — comma-separated allowlist; default Vite dev/preview (`localhost:5173`/`4173`). Never reflect any origin — any website could read the API.
- **`DEMO_MODE` is the only access control; there is no login.** Local mode relies on `127.0.0.1`; the demo is **read-only**: `demoReadOnlyMiddleware` (`httpSecurity.ts`, mounted with `DEMO_MODE=1`) answers `403 { error: "demo_read_only" }` to non-GET/HEAD/OPTIONS `/api` requests, which the client maps to `demo.readOnly` (`client/src/api.ts`). Exempt: the analytics beacon (`USAGE_PAGE_VIEW_PATH`) and the edit allowlist («The demo is writable, a little»). **Never put real data behind `DEMO_MODE`.**
- **`DB_BACKUP_ENABLED` / `DB_BACKUP_KEEP` / `DB_BACKUP_DIR` / `DB_BACKUP_DIR_KEEP`** — daily snapshot while the server runs (`dbBackupScheduler.ts`; default on). Retention (`dbSnapshotRetention.ts`, pure): one per day for `DB_BACKUP_KEEP` days (30), then one per month, for every label (`auto-daily`, `before-deploy-<sha>`, hand-made `db:snapshot`). The second copy in `DB_BACKUP_DIR` (`~/Documents/backups/nw-tracker`, root `.env`) keeps `DB_BACKUP_DIR_KEEP` days (60). Pruned after each snapshot; by hand `npm run db:prune-snapshots -w nw-tracker-server [-- --dir=<folder> --apply]` (report-first).
- **A snapshot proves itself** (`dbSnapshot.ts`: the daily backup, `db:snapshot`, the deploy's `before-deploy-<sha>`): written as a hidden `.<name>.db.tmp` beside its final name, it must pass `PRAGMA quick_check` on a read-only open before it is renamed; a failed copy is deleted and the call throws; a killed run's temp files (untouched for an hour) go at the next snapshot. The listing and retention never see a temp file. The second copy in `DB_BACKUP_DIR` is temp + rename into a folder that must already exist (an unmounted volume is an error, never recreated on the local disk); the primary folder is pruned whatever happens to the copy; a failed snapshot or second copy raises an app notification once per Chile day per kind (`dbBackupScheduler.ts`).
- **`app_messages` is pruned once per Chile day, right after that day's snapshot** (`pruneAppMessagesAfterDailySnapshot` in `dbBackupScheduler.ts`, `pruneAppMessages` in `appMessages.ts`): `log` rows older than 30 days and read notifications older than 180 days go; unread notifications never do, nor the newest row of any title (the daily-run and sync-log state reads the latest row per title). With backups off, nothing is pruned.
- **Late documents** (`lateDocuments.ts`, migration 382, flag `LATE_DOCUMENT_CHECK_ENABLED`, off under `BACKGROUND_JOBS_ENABLED=0` and never on the demo): daily at 09:00 Chile (a boot past the slot catches up once, 10 min after start) the import-sync coverage is built and every `missing` (column, month) is late from a fixed day of the following month — the 25th for a cartola, the 7th for a card statement (matrix month = the close's) — when that day is at most 60 days back; each newly late pair raises one «Document not received» notification and a `late_document_notifications` row (account, kind, currency — a cartola's and a one-column card's are pesos —, month), so it never notifies again. A coverage build that throws raises «Document check failed» once per Chile day and the check waits for the next slot.
- **Scheduler and outbound bounds.** A job whose `next()` throws is asked again every 5 minutes (`NEXT_ERROR_RETRY_MS`, `schedulerKernel.ts`) and raises one notification per failure streak. Every `fetchOut` call is bounded (60 s, `OUTBOUND_TIMEOUT_MS` in `httpOut.ts`, combined with the caller's signal; `OutboundTimeoutError` names the label and host).
- **Graceful shutdown** (`gracefulShutdown.ts`): on SIGTERM / SIGINT the server stops every scheduled job (`stopAllScheduledJobs`), stops accepting, waits up to 10 s for in-flight requests, flushes the usage log, runs `wal_checkpoint(TRUNCATE)`, closes the database and exits (0, or 1 when a step failed); a second signal exits at once.
- **Other websites stay out** (`httpSecurity.ts`; both off under `DEMO_MODE`). `hostAllowlistMiddleware`: a request whose `Host` (port ignored, raw header, never `X-Forwarded-Host`) is not `localhost` / `127.0.0.1` / `[::1]`, a `CORS_ALLOWED_ORIGINS` host or an **`ALLOWED_HOSTS`** entry (comma-separated hostnames; a URL refuses to boot) gets `421 { error: "host_not_allowed" }` — DNS rebinding. The home server's `.env` lists its public name and its private-network address. `crossSiteWriteGuardMiddleware`: an `/api` write answers `403 { error: "cross_site_write" }` unless the browser says `Sec-Fetch-Site: same-origin`, its `Origin` is a CORS origin, its own `Host` or on an `ALLOWED_HOSTS` name, or it carries no `Origin` and is not `cross-site` (curl, ingest, the deploy agent).
- **Deploy rollback** (`scripts/server-deploy.sh`): the old commit is checked out, `npm ci` runs only when a package file changed, the replaced client is swapped back from `client/dist.prev` (rebuilt only without one), each failed step is named in the notification, and the job is completed as failed even when the rollback is unhealthy. The database is never restored automatically: the notification lists the migrations that stay applied and the `before-deploy-<sha>` snapshot to restore by hand.
- **`CACHE_WARM_ENABLED`** — dashboard cache warmer (`dashboardCacheWarmer.ts`; default on): rebuilds page bundles at boot, at 00:05 Chile, on an external `data_version` change, and 30 s after in-process invalidations; not on live price moves (the requesting request rebuilds, see «Polls follow the market clock»). The warmed object is the served response (`dashboard.page_bundle|<unit>`). CC billing detail is cached as `cc.billing_detail|<accountId>` (day/data_version fresh, dropped by a logged change that names the card: the change log in `cacheRegistry.ts`, families in `cacheFamilies.ts`; nothing invalidates a cache by hand). **Requests go first** (`apiRequestsInFlight.ts`): warm steps start only after 250 ms with no `/api` request in flight (health, beacon, `/api/ingest`, `/api/jobs` don't count; the stamp poll does; requests >20 s stop counting; a wait caps at 60 s). Only gaps between steps wait — a request may be awaiting the step's promise. **The warm never holds the event loop long** (the demo's half CPU and its 5 s health check): it builds the inputs ahead of each payload, each its own cached entry, with the loop given back between them (`warmSlicer`, `WARM_SLICE_MS` = 40 ms of work per stretch, then once no request is in flight) — account rows step by step (a card's billing base, monthly perf rows, the row; `warmDashboardAccountRows`), the groups' daily returns, the ATH's linked-card owed by year (`warmNetWorthAllTimeHigh`), then the bundle, which finds them cached. A stretch opens its own ALS memos (tree index, valuation memo): nothing read before a gap reaches an entry built after it. A value with no cached pieces is built with `warmAggregationInPieces` (`cacheRegistry.ts`; the expense lines, source by source and step by step: `warmFlowsExpenseLines`): nothing is cached while it builds, and it is stored only if no drop happened in its gaps (else rebuilt, after 3 tries in one go). Request handlers keep their synchronous builders.
- **Flags are parsed once by `server/src/config.ts`** with the contracts' flag rule (`parseEnvFlag`, `formats/flags.ts`, shared with the ingest service): `1/true/yes` on, `0/false/no` off, unset/empty default, anything else refuses to boot; precedence explicit env > demo defaults > background-jobs defaults > built-in. `initServerConfig()` runs after `loadRootDotenv()`, so a flag change needs a restart (credentials `BCENTRAL_*`, `COINGECKO_API_KEY`, `INGEST_TOKEN` are read live). Leaf modules read `deploymentProfile()` (demo, read-only API, sources never run, AFP source, market awake gate, usage-log file), never `DEMO_MODE`.
- **`BACKGROUND_JOBS_ENABLED=0`** defaults `GLOBAL_SYNC_ENABLED` / `LIVE_QUOTES_SYNC_ENABLED` / `DB_BACKUP_ENABLED` / `CACHE_WARM_ENABLED` / `USAGE_LOG_ENABLED` / `LATE_DOCUMENT_CHECK_ENABLED` to 0 (an explicit per-job flag wins) and turns off the ingest scheduler and job-queue executor regardless. Set on every `.claude/launch.json` server so agent dev servers never sync or back up the shared DB.
- Express 5 forwards a rejected async handler to the terminal error middleware; new routes need no `asyncHandler` (GUIDELINES.md).
- **Write routes read typed bodies.** A route that reads a JSON body declares its shape as a zod schema in `server/contracts/src/requests/<area>.ts` (exported as `nw-tracker-contracts/requests/*`, each with its inferred input type) and reads it with `parseBody(schema, req)` (`routes/shared.ts`) inside `writeHandler`; never cast `req.body`. A refused body throws an `InputError` (400) whose message names the first failing field (`requestIssueMessage`, `requests/issues.ts`). Schemas state shape only (types, required fields, enums, day and month formats, positive ids); rules that need the database stay in the route or the function it calls. Fields are JSON types: a number sent as a string is refused. The client imports the same request types (type-only) for its bodies.

## Schema baseline (fresh DBs)

`initSchema()` runs `server/src/schemaBaseline.ts` (full schema as of migration 155, all `IF NOT EXISTS`) and marks ≤ 155 applied on a new DB; those files are deleted (copies in `~/Documents/backups/nw-tracker/{removed,squashed}-migrations/`). Only the 8 reference-row seeds in `BASELINE_REFERENCE_DATA_MIGRATIONS` (db.ts) remain and run on fresh DBs. Recorded-but-missing files are harmless, so numbering gaps are expected; 156+ apply normally. A migration may pair with a `POST_MIGRATION_HOOKS` entry in `db.ts` (pure TS, inside the migration transaction; the hook files live in `server/src/migrationHooks/` — e.g. `legacyNoteBackfills.ts` for 157). A table a migration drops must also leave the baseline, or every boot recreates it empty. To squash: `npx tsx scripts/regenerate-schema-baseline.ts --last <newest-migration>` (from `server/`), then delete the covered files (keep the seeds). Migration SQL is split naively on `;` — no triggers or `;`/`--` inside literals; use a post-migration hook.

**Runner checks.** After every `FOREIGN_KEYS_OFF_MIGRATIONS` migration (and its hook) the runner runs `PRAGMA foreign_key_check` inside the migration's transaction and throws, rolling back, on any violation (`assertNoForeignKeyViolations`, db.ts). `npm run check:conventions` fails when two files in `server/migrations` share a number (the historical `226_*` pair is allowlisted). A migration is identified by its full filename: never rename or renumber one that may have been applied anywhere, it would run again.

## Server Vitest (SQLite)

- Vitest uses **`server/data/nw-tracker.test.db`**, never `nw-tracker.db` (both gitignored, `server/data/*.db`).
- **`NW_TRACKER_TEST_DB`** is set in `server/vitest.config.ts` (`test.env`) and the server **`npm run test`** script, before `db.ts` loads.
- **`server/src/vitest.globalSetup.ts`** generates the **Vitest person** when the test DB is missing (`generate-demo-data.ts --test`, `testPerson`); tests must not depend on personal data. It is never refreshed automatically: a stale pre-synthetic copy keeps being used (symptom: missing `demo:*` fixture accounts or real-data invariants) — delete it to rebuild. `NW_TRACKER_TEST_FROM_DEV=1` copies the local `nw-tracker.db` instead (reproducing against real data).
- **`server/src/vitest.setup.ts`** → **`server/src/test/vitestDbSeed.ts`**: ensures the isolated master `credit_card_master|santander|vitest-fixture` for merge/import tests.
- **One database per fork** (docs/test-speed-plan.md; `server/src/test/workerTestDb.ts`). The default run (`NW_TRACKER_TEST_DB=nw-tracker.test.db`) treats that file as a read-only **base**: the global setup generates it when missing, applies newer migrations to it and checkpoints it; each fork then clones it (APFS clone, instant) to `nw-tracker.test.r<run>.w<N>.db` (`<run>` = the Vitest host pid, `N` = `VITEST_POOL_ID`) in `src/vitest.workerDb.ts`, which must stay the first entry of `setupFiles`. Files run in parallel on `NW_TRACKER_TEST_FORKS` forks (default: one per physical core — hyperthreads only stretch single tests toward Vitest's 5 s limit); every run starts from the base, two runs in one checkout never share a clone, and a run's clones are deleted at its end (a killed run's at the next run's start). `pool: "forks"` stays: better-sqlite3 segfaults in worker threads at teardown.
- **Cleanup rules for a test file**, since files share a fork's clone in sequence: create your own synthetic fixtures (prefixed) and remove them in `afterAll`; never change rows of accounts you did not create; pin dates against fixed values or `TODAY`-relative values that stay in their intended month (two `TODAY − n` closes can fall into one billing month); restore any `process.env` you set. **File order is random** (`sequence.shuffle.files`; the seed is printed — reproduce with `--sequence.seed=<seed>`), so a file that only passes after another one has a bug.
- **Files of a fork share one process and its loaded modules** (`server/vitest.config.ts`, two projects). Root `poolOptions.forks.isolate: false` reuses each fork's process across files; project **`shared`** (every file without a mock) also keeps the module graph, so a module is loaded once per fork, not once per file. Project **`isolated`** holds every test file whose source contains `vi.mock(` / `vi.doMock(` — found by scanning, no list to keep — and drops the module graph and mocks before each file (a mock left in a shared graph reaches the next file: `No "x" export is defined on the mock`). A module that reads env or other state once at import sees the first file's value in every later file of the fork: read it at call time instead (like `serverConfig()`). **Reset rules** (`src/vitest.setup.ts`, which runs again before every file): after each file `process.env` goes back to what the file found, fake timers, spies (`vi.spyOn`) and `vi.stubGlobal`/`vi.stubEnv` are undone, `globalThis.fetch` is put back (stub a global only with `vi.stubGlobal`, never by assignment), and the card-line write frame and the expense-link no-op are registered again; in-process caches are cleared before every test (`clearAggregationCache`). Anything else a file changes in module state (a `register…` hook, a module-level map) it restores itself in `afterAll`, like `cards/lineWriteSession.test.ts`. Never start a timer or server a file does not stop: the process outlives the file. A test helper that runs once per process (a module-level «done» flag) runs once per fork, not once per file — make it idempotent and run it every call. **Shake out leaks with `NW_TRACKER_TEST_FORKS=1`** (every file through one process) on a few seeds. `initServerConfig` is never called by tests (only `index.ts`), so `serverConfig()` reads the live env.
- Override with `NW_TRACKER_TEST_DB` (absolute path, another basename under `server/data/`, or `:memory:`): that is one database, so the run falls back to a single fork with no clones.
- **Scripts** (server and client): `npm run test` runs the typecheck and Vitest **concurrently** (`scripts/run-parallel.mjs`, `[typecheck]` / `[vitest]` prefixes) and fails if either fails — the full check before a commit. `npm run test:vitest` = Vitest alone. `npm run test:related -- <files>` = only the test files that statically import those sources, for quick feedback while iterating, never the final check: a change to a migration `.sql`, `scripts/generate-demo-data.ts` / `src/demoData`, the schema baseline or JSON fixtures reaches every DB test but selects none of them.
- **Typechecker = TypeScript 7** (`typescript-7` alias of `typescript@7.x` in the root devDependencies), called only through `scripts/tsc.mjs` (every `typecheck` and `build` script): both TypeScript packages ship a `tsc` bin, so never call `tsc` / `npx tsc` directly. `typescript` 5.x stays only for typescript-eslint (client lint), which needs the classic API.
- **Pre-push hook** (`.githooks/pre-push`, enabled by the root `prepare` script via `core.hooksPath`): typechecks the workspaces a push touches (a `server/contracts` or root package/tsconfig change = all four) in parallel plus `npm run check:conventions`, and fails over a 30 s budget, naming the slow step; it runs no tests. Agents never push with `--no-verify` — fix the error or the slow step.
- Clean fixture rows out of **`nw-tracker.db`**: `sqlite3 server/data/nw-tracker.db < server/scripts/cleanup-cc-vitest-pollution.sql`.
