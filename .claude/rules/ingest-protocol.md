## Ingest API (plan in `docs/ingest-split-plan.md`)

- **Two packages meet here.** `ingest/` (workspace `nw-tracker-ingest`) reads the outside world; the server applies what it sends and is the only DB writer. They share only **`server/contracts`** (`nw-tracker-contracts`): the envelope (`schema_version`, `feeder_id`, `source {channel, ref, label?, fetched_at?}`, `payload`), result / error bodies, the kind registry `INGEST_KINDS`, a typed client (`createIngestClient`, validates before sending) and a JSON Schema export (`npm run schema -w nw-tracker-contracts`). Neither package imports the other.
- **Kinds are canonical, never bank-shaped:** a kind says what the data means; bank decoding lives in the feeder. One `schema_version` per kind; a change old payloads would not satisfy bumps it. **A currency is any lowercase ISO 4217 code** (`currencyCodeSchema`, `server/contracts/src/formats/schemas.ts`); the server holds each code to `currencies` on receipt (`server/src/ingestCurrencies.ts`: `requireLoadedCurrency`; `pesosOrDollars` / `dollarsOnly` where a handler takes only those — card sub-balances, bank and broker cash, mirrors, wires): unknown → 422 `unknown_currency`, known but unsupported → 422 `unsupported_currency` (`IngestRefusal`, rolled back, never a 500). `payment.processor_receipts` keeps any code unchecked.
- **`POST /api/ingest/<kind>`** (`routes/ingest.ts`) checks envelope → version → payload (4xx `unknown_ingest_kind` / `unsupported_schema_version` / `invalid_envelope` / `invalid_payload`), then the **receiver** (`ingestReceiver.ts`) runs the kind's handler from `INGEST_HANDLERS` (`ingestHandlers.ts`; a kind without a handler is a compile error) in one IMMEDIATE transaction and answers `{status: applied | duplicate | conflict, kind, schema_version, retry, dry_run, message?, conflicts?, details?}`. Handlers return `{details, retry?}` and never pick a status. **Store once:** a kind declares `ref: document | read` (`defineIngestKind`); a `document` kind's ref + payload sha256 is kept in `ingest_documents` (migration 269) once applied with a final outcome — the same payload again answers `duplicate` with the first details (nothing runs), another payload under the ref `conflict`; a `read` kind runs every send. Rows a resend must restate identically go through `storeOnce` (field-by-field, collects every disagreement). **Conflict:** a handler throws `IngestConflict` (`{at: <table>:<key>, fields, message}` + details); the document rolls back, never a 500. **Dry run:** only the envelope's `dry_run` (`client.send(..., {dryRun})`; payloads carry no `apply`) — runs the handler and rolls back; process caches are bypassed inside a transaction (`dbInTransaction`) so nothing a dry run read outlives it. `retry: true` tells the feeder to keep the document staged; `rolledBack(fn)` is the same rollback for tests and report scripts. `GET /api/ingest/kinds` lists kinds.
- **Access (`ingestAuth.ts`; rule `ingestAccessRefusal` in `server/contracts/src/access.ts`, shared with the ingest service's `/runs` and `/parse`, as are `DEFAULT_SERVER_PORT` / `DEFAULT_INGEST_SERVICE_PORT`):** local connections only (socket address, never `req.ip`); `INGEST_TOKEN` requires `Authorization: Bearer`; `INGEST_ALLOW_REMOTE=1` (refused at boot without a token) lets a remote feeder in. `DEMO_MODE` refuses everything (`ingest_disabled`). Ingest bodies up to 32 MB (rest of the API 2 MB).
- **Unanswered requests are resent (`createIngestClient`, `server/contracts/src/client.ts`).** A connection-level failure is retried at 2 s, 8 s, 20 s (`DEFAULT_CONNECTION_RETRY_DELAYS_MS`; logged by `ingestClient()` in `ingest/src/serverApi.ts`), then thrown as `IngestConnectionError`, named by `describeIngestFailure`. An HTTP answer never retries. Resending is safe by contract (`duplicate`, tasks idempotent, a double report refused as `run_not_waiting`). The service's `reportWithRetry` adds a 15-minute loop for a server that stays down.
- **Run protocol (switched on by `ingest/switch-schedule.sh to-server`).** The server decides WHEN and WHAT: `ingestRunScheduler.ts` ticks every 30 s on the wall clock (timers stall in sleep, the clock does not) and `decideIngestRun` (`ingestRunPolicy.ts`, pure) picks the nightly for the latest 22:00 Chile slot (answered by an `ingest_runs` row, a queued job, or any daily run after it; skipped when a daily run finished < 60 min ago), else the hourly for the latest :30 slot, and queues it (a run in flight makes it wait, never skip). An hourly may carry the Santander **balance poll** (`decideSantanderBalancePoll`): every hour unless the login is latched, the bank was tried < 35 min ago, or 22:00 is < 45 min away; input = the feeder's `santander_state` from the latest report. Requests go to `INGEST_URL` (default `http://127.0.0.1:3002`); a run not taken is `not_started` and its job returns to the queue (offered again 30 s later); a nightly badges «Ingest service unreachable» once per slot, only on the slot's second unreachable answer. **Idempotent per run id:** a retry carries the same id; the service answers 202 for the run it is running, `already_ran` (409) for one finished; the server reads both — and a «busy» naming its own run — as started, and accepts a report for a `not_started` run. **Recording:** `completeIngestRun` → `recordDailyRun` / `recordHourlyEmailRun` (a dry run or quiet hourly records nothing); a run whose job stops heartbeating for its 5-minute lease is `lost`, recorded as failed (3 h / 90 min timeouts only for pre-queue rows, `job_id` null). `ingest_runs` (migrations 200–201) is one row per (kind, slot); `GET /api/ingest/runs`. **The ingest service** (`ingest/src/service/`, LaunchAgent `com.user.nw-tracker-ingest`, GUI session) takes one run at a time (409 busy) with the only runners, `ingest/src/runner/` `runNightly` / `runHourly`; each step runs one ingest command (`npm run <script>` in `ingest/`, server tasks via `server-task`, never the root pass-throughs) and returns the `StepResult` the command wrote (`ingest/src/stepResult.ts`, `{staged, inserted, fetch, differs, read_brokers}` to the file in `NW_INGEST_STEP_RESULT`) — gates read structured results, never stdout. Logs `cfraser/daily-run.log` / `email-run.log` (hourly rotates at 5 MB). It may veto a requested bank fetch (latched login, bank tried < 35 min — `vetoed`, not an attempt), raises the desktop alert on a failed nightly, reports to `POST /api/ingest/runs/<id>/complete`. `INGEST_RUN_DRY=1` = every run dry. **Run now (`startManualIngestRun`, `POST /api/import-sync/ingest-runs`, «Corridas de banco y correo»):** queues an hourly or nightly as a job (slot = request instant, `not_before` now, reason `manual: …`; an already-queued run of that kind is moved up), carrying the extras `runRequestExtras` decides at START (the one rule for slot and manual runs: balance poll, AFP UNO, AFC, payslips, MetLife). It answers the slot it overlaps. Refused only where the scheduler is off (the primary must know the run id). `GET` same path lists in-flight, latest per kind, next slots; the page polls every 5 s during a run. **Enabling:** `INGEST_SCHEDULER_ENABLED=1` only in the INSTALLED server plist (set by the switch script, kept by `install-server-agent.sh`), never root `.env`; off whenever `BACKGROUND_JOBS_ENABLED=0`. `switch-schedule.sh to-server` removes retired timed agents; `status` shows what is loaded.
- **The job queue (`docs/job-queue-plan.md`, migration 246, `jobQueue.ts`, `jobQueuePolicy.ts`, `jobQueueExecutor.ts`, `jobClaims.ts`).** Every long job of the primary (nightly, hourly, «Run now», deploy) is a `jobs` row; exclusion is the resources a job holds (`ingest-service`; `server-restart`, exclusive), never clock windows; each kind's priority, resources, lease, dispatch and run kind are one `JOB_KINDS` row. A job that cannot start waits and runs late, never dropped. **`pickNextJobs`** (pure): a running job silent past its lease (`heartbeat_at` or `claimed_at` + `lease_ms`) is `lost`; a queued job past `stale_after` is `superseded`; the rest by priority (deploy 100 > nightly 50 > hourly 40), then `not_before`, then age; a job starts when none of its resources is held; `server-restart` only when nothing runs, nothing starts while held, and once due nothing of lower priority starts (so hourlies cannot starve a deploy). **Coalescing:** at most one QUEUED job per `dedupe_key` (`ingest.nightly`, `ingest.hourly`, `deploy`; partial unique index); re-enqueue updates it (newest payload/reason, earliest `not_before`, newest `stale_after`). A running job is never modified. **Producers:** `ingestSchedulerTick`, `startManualIngestRun`, the deploy agent (`POST /api/jobs`). **Executor** (`startJobQueueExecutor`, `JOB_QUEUE_EXECUTOR_ENABLED`, default = the ingest scheduler's flag): 30 s tick plus one on every enqueue/completion (`notifyJobQueue`); writes off lost jobs (ingest → run `lost`, failed run; other → «Job lost: <kind>» notification), supersedes stale ones, dispatches ingest jobs (claim as `ingest-service`, write the `ingest_runs` row with `job_id` and extras, `POST /runs`; busy/silent → `releaseJob`, not an attempt). At start a SCHEDULED job a daily run already covered is superseded (a nightly with a daily run after its slot or < 60 min ago; an hourly whose slot predates the last daily run). **Workers:** the ingest service heartbeats `POST /api/jobs/<id>/heartbeat` each minute (lease 5 min) and its report completes the job (a report for a released `not_started` run completes it too); the deploy agent claims (`POST /api/jobs/claim`), heartbeats, completes (`POST /api/jobs/<id>/complete`; lease 20 min). Worker endpoints use the ingest access rules. **Page:** «Cola» (`GET /api/import-sync/jobs`, `JobQueuePanel`): running, queued with structured WHY (`resource` + holder, `exclusive`, `draining`, `not_before`; worded by the client), latest finished; Cancel (queued only; cancelled slot recorded `skipped`, not re-queued) and Retry (failed/lost ingest run → manual run). `scripts/replay-job-queue.ts` replays slots (`--deploy` instants) through the policy. `ingest_runs` stays the detail table.
- **Server tasks and the inbox pipeline.** Run steps that work on the server's own data are server tasks, `POST /api/ingest/tasks/<task>` (`contracts/tasks.ts`, `server/src/ingestTasks.ts`, ingest access rules): `cc_payment_mirrors` (`dry_run`), `synthetic_cc_payments_check`, `cc_bank_cupo_check` (`recheck`), each `{task, ok, report}`. `npm run server-task -w nw-tracker-ingest -- <task>` calls one; root `convert:cc-payment-mirrors`, `check:synthetic-cc-payments`, `check:cc-bank-cupo` point there. `import:cfraser-inbox` is an ingest command (`ingest/src/inbox/pipelineMain.ts`, manifest `inbox/organizeManifest.ts`): loads the root `.env` (qpdf reads PDF passwords from it), runs the ingest commands in order and asks for the tasks — it never opens the database. Market data is synced by the server's scheduler; `npm run sync:all -w nw-tracker-server` is a manual tool.
