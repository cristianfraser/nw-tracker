# Ingest sources and the bank runs (nw-tracker)

> Moved verbatim from `AGENTS.md`, whose «Topic rules» index lists the sections of every file under
> `.claude/rules/`. A section named in «…» that is not in this file is in `AGENTS.md` or in the file
> that index names for it.

## Ingest kinds, one per source (protocol in `ingest-protocol.md`)

- **A Gmail session that loses its connection is rerun (`withImapSession`, `ingest/src/email/imapSession.ts`).** Every IMAP fetcher goes through it: a connection failure (`ECONNRESET`, imapflow `ETIMEOUT`, `NoConnection`; never an answer with a server code like `AUTHENTICATIONFAILED`) reruns the whole session after 15 s then 60 s; imapflow's `error` event has a listener so it cannot crash the process. Safe because each document is written and ledgered before the next is read, and read-only fetchers clear their list at session start.
- **`bank_account.movements` v2: the checking «últimos movimientos» xlsx and the dollar account's feed.** A partial listing: `{ account: {issuer, product: "checking", currency: clp | usd, number?}, movements: [{date, description, currency, amount (signed), document_no, wire_reference}], rejected_rows }`; `wire_reference` = the bank's reference on an incoming-wire credit. `ingest/src/santander/checkingMovements.ts` decodes the workbook (Fecha dd-mm-yyyy · Detalle · Cargo · Abono; a future date is the bank's posting day, kept); `import:checking-movements` (spawned by `import:cfraser-inbox`) sends each file, archives it under `cfraser/checking-ultimos-movimientos/imported/`, and fails the step after archiving when a row could not be read. Server: `applyBankAccountMovements` → `importCheckingPartialMovements` (`PartialBankMovement`, shared with the cuenta-vista paste) + a `checking_recent_xlsx` batch. **A row the bank dated after the fetch day is stored on the fetch day** (Chile date of the envelope's `source.fetched_at`; a peso listing without it is refused, 422 `missing_fetched_at`; the browser upload and the cuenta-vista paste pass the request time): the fetch day is the latest day the money could have moved, the bank's date is kept as its posting (`recordBankPosting` with basis `fetch`, migration 329), and the note key, cartola supersede, transfer-leg and mail matches keep reading the bank date. Rows on or before the fetch day are unchanged. Backfill of rows stored before: `npm run dump:checking-listings -w nw-tracker-ingest -- --out=<json>` (the archived workbooks with their mtimes) then `server/scripts/redate-forward-posted-checking-rows.ts --listings=<json> [--apply]` (report-first; the earliest listing showing a row is its fetch day; rows absorbed into transfers and UI uploads are reported, not guessed). **Uploads go through the service:** the server hands the file to `POST /parse/santander.checking_xlsx` (`requestFeederParse`, `ingestFeeder.ts`; `parse.ts`: 200 `{kind, schema_version, payload}` or 422 `not_this_format` / `unreadable`); `not_this_format` (a monthly cartola) falls to the server's cartola-xlsx path. Needs the service running (503 otherwise). Ingest reads numbers and dates through the contracts' `formats/` (no copies).
- **`card.payment_receipt` v1: Santander's card-payment receipt mails.** `{ issuer, paid_on, debt_currency: clp | usd, amount_clp, amount_usd, card_last4 }`; source ref = message id (keys the synthesized payment, so a resend never writes a second). Decoded by `ingest/src/santander/paymentReceipts.ts`; `import:santander-receipts` (spawned by the inbox pipeline) sends each and archives to `processed/` unless the server answers `ambiguous`. Server: `applyCardPaymentReceipt` → `applyPaymentReceipt` (re-date the next-workday debit, or synthesize the transfer + plant the card line). The overdue alarm is `check:synthetic-cc-payments`, run after the receipts on every pipeline run.
- **`broker.movements` v1: the Racional crawl.** One read = one crawl stamp in `cfraser/racional-movements/`: list rows (`movements-<stamp>.json`, decoded by `ingest/src/racional/movements.ts`) plus, in reads staged before 2026-11-18, the dividends API record (`dividends-<stamp>.json`); either may be missing. **Since the app's 2026-11 rebuild the crawl reads Racional's own data, not the page (`ingest/src/racional/appData.ts`, `steps.ts`):** the app's server functions (`app.racional.cl/_serverFn/<hash>`, seroval-encoded, recognised by shape — hashes change per build) answer the movements list (newest first, 100 rows, ISO instants, «USD 1.234,56» / «CLP 1.234» amounts) and each movement's detail (a buy's shares / price / order, a dividend's gross / tax / net, a Retiro's positions sold and caja). Only navigation inside the app asks: a page loaded by URL arrives server-rendered with no answer on the network, so the crawl opens «Movimientos» from the menu and clicks each new row at its position (label and amount checked first). A staged row keeps the old print and key (`US$…` / `$…`, class `buy` / `dividends` / `contribution` / `withdrawal` / `commissions` / `corporate_action`, Chile day), so stored cursors still match, and carries `created_at`, `fill`, `dividend`, `liquidation`. **A new session needs a person:** after the password Racional asks for this device's passkey («Confirma que eres tú», `/passkey`); the login stops there with a message, a supervised run is confirmed at the screen, «Mantener sesión» keeps it for the scheduled runs. `import:racional-movements` (`--apply`) sends staged reads oldest first; the server (`applyRacionalRead`, `racionalMovementsImport.ts`) plans them (day-sum dedupe, cash legs left for mirror pairs, a blocked row holds back the whole list, conflicts and ledger-less dividends reported as `problems`), writes, stores dividend breakdowns, moves its coverage. Ingest moves its crawl cursor when the list applied and archives to `imported/` when nothing is left to fix; otherwise the read stays staged. A row it cannot decode is never sent and fails the step. **A portfolio liquidation is booked from the row's detail view**, because the list cannot tell it from cash sent to a bank: it is one «Retiro» row (class `pending-withdrawal` until the money lands two days later, then `withdrawal`). The crawl opens every withdrawal row's detail (stages its `status`); `racionalWithdrawalLiquidation` reads a `portfolio_sell` detail's positions sold, its caja and the «Acciones vendidas» step's day (`parseRacionalLiquidationDetail` reads the same from the detail text of reads staged before the rebuild); `racionalRowToMovements` emits one `sell` per position plus a `portfolio_cash_withdrawal`. A detail without sold amounts stays the cash `withdrawal` (manual); a Retiro the crawl could not open is `incomplete` and blocks its read. The server plans the sell as `stock_sell` ETF → Racional CLP with units (`racionalEquityAccountId`: bare Bolsa symbol → `.SN`) and the caja pesos as a transfer caja → Racional CLP, deduped by the day-sum rule (re-reads and hand-booked liquidations are duplicates); an emptied caja ends the comisión nudge. The list key strips `pending-` (`racionalRowKindClass`; stored cursors compared via `normalizeRacionalListRowKey`); the list amount may differ from the printed sale; a key no longer found re-stages the window, absorbed by dedupe. `accountUsesEquityMtm` exempts `isClpCashAccount` as well as USD cash (a `stock_sell` into CLP cash must not make the wallet an equity account); `stockUnitsInflowByMonthEnd` is gated on it.
- **`broker.movements` for Fintual: the dollar wallet's cash interest, read live.** Alpaca's monthly sweep profit sharing has no mail (the Alpaca cartola prints it later; `brokerDividendStatementApply` only reports it). `import:fintual-wallet` (`ingest/src/fintual/walletInterest.ts`, `--apply`) asks Fintual's `/gql/` for `stocksWalletCashInterests` (operation `WalletMovements`) with `FINTUAL_COOKIE` and sends each credit as `broker.movements` broker `fintual` (contract accepts only `interest` movements and a dividends record from Fintual). The server (`fintualWalletInterestApply.ts`) books a missing credit as single-leg `savings_earnings` on Fintual USD on Fintual's day; same day + same cents = duplicate, different amount that day = problem, nothing written. Runs every hourly and in the nightly beside the Fintual mail imports, under `NW_TRACKER_FINTUAL_APPLY`. An expired cookie fails the step.
- **`broker.notifications` v1: Fintual and Racional money mails.** `ingest/src/brokers/brokerEmail.ts` classifies `cfraser/broker-emails/scan-*.json`, collapses copies by Message-ID and emits what each mail STATES (`kind`, `ticker`, `fund_name`, `goal_name`, `amount` / `gross_amount`, `units`, `price`, `clp_amount`, `paid_to` bank | broker_balance, subject as provenance). `import:fintual-emails` / `import:racional-emails` (`--apply`) send a broker's WHOLE staged set each run (idempotent; an unbookable notification retries by being resent). The server (`brokerNotificationsApply.ts`) runs `planFintualEmailBatch` / `planRacionalEmailMovements` and decides what the mail does not say: bookability (`brokerNotificationIsBookable` — a gross-only dividend never is) and whether the Racional crawl must open (`racionalFetchDecision`: nudges after the newest clean read in `broker_read_coverage`, plus the monthly comisión). `details` carry the plan, Fintual retiros synthesized from a mail whose bank credit never appeared (command exits 1) and the crawl decision, written to `cfraser/.broker-email-decision.json` (removed first, so a failed send never opens the browser). `check:broker-emails` is a local report. **Fintual deposits and dollar purchases:** «Recibimos tu depósito» (`deposit`) books checking → «Fintual CLP» (a bank debit already on file is left for a human to convert); «Compraste dólares» (`wallet_funded`) books Fintual CLP → Fintual USD as `fx_exchange` with the dollars as counter leg; a buy of a fund no account holds creates the stock account in the Fintual stocks' bucket. Wires to Fintual go through Fintual CLP; historical deposits stay checking → goal.
- **A broker adapter (`brokerAdapter.ts`).** Per broker: cash account by currency, the account holding a printed ticker (Racional's bare symbol → `.SN`), dividend ↔ `dividend_payout` distance (Fintual ±5 days, `BROKER_SETTLEMENT_WINDOW_DAYS`, the one Fintual settlement window; Racional ±2), where a deposit mail may already be in the ledger. Rules written once against it: `planDepositFromMail` (checking → broker pesos; same-pesos transfer in the lead days = duplicate, a plain checking debit in the debit window = for a human) and `pairDividendPayout`. Checking is found via `checkingAccountId`, never a legacy import key. `brokerPlanRow` is the one report row. **Two accounts may hold one ticker (`accountIdForEquityTicker(ticker, { brokerCashAccountId })`, `accountsWithEquityTickerAtBroker` in `accountEquityTicker.ts`):** among several holders the lookup keeps the one traded against the broker's cash account (`equityBrokerHoldings.ts` evidence); one holder resolves without it, none or several at that broker throws. Fintual passes Fintual USD for dividends and multi-holder buys.
- **`bank_account.statements` v1: Santander's monthly cartolas.** `{ account: {issuer, product: checking | demand_deposit}, apply, force_reimport, statements: [{document, period_month, period_from, period_to, opening_balance, closing_balance, month_closing_balances, movements: [{date, branch, description, document_no, amount}], skipped_rows, notes}], unreadable: [{document, error}] }`. Ingest reads the corriente's xlsx (`ingest/src/santander/checkingCartolaXlsx.ts`, saldo identity checked) and both accounts' PDFs (`ingest/python/parse-checking-cartola-pdfs.py`, `parse-cuenta-vista-cartola-pdfs.py`, `cartola_layout.py`); `import:checking-cartolas` / `import:cuenta-vista-cartolas` (`--dry-run`, `--force-reimport`, `--skip-pdf-parse`, `--only-pdf=`; corriente also `--xlsx-only`, `--only-xlsx=`, `--dir=`) send one payload per account; the inbox pipeline calls them after `organize:checking-cartola-xlsx`. Server: `applyBankAccountStatements` (`bankAccountStatementsApply.ts`) → `importCartolaList` + `finishCartolaImportRun` (period dedupe, phantom months, cuenta vista month split, anchor re-derivation). Ledger wipe: `npm run wipe:cartola-ledger -w nw-tracker-server` (report-first; fails on FK children on the real DB). The monthly xlsx upload parses via `/parse/santander.checking_cartola_xlsx`. **A stored month is replaced only by count** (`cartolaImportShouldReplaceExisting`: more movements, or any where it had none) — don't decide by reading the stored PDF for «sin movimientos»: annual cartolas print it for empty months and would re-import (renumber) them every run.
- **`bank_account.transfer_notices` v1: who each checking transfer was with.** Cartolas truncate the payee; the bank's mails state name, RUT, bank, account, e-mail, comment. `fetch:santander-mail-archive --from --to` stages transfer / payment / facturado mails under `cfraser/santander-mail-archive/`; `ingest/src/santander/transferMails.ts` decodes every layout since 2015 into `{kind: outgoing | incoming | between_own_products | schedule_created, date, amount, from, to, comment}`; `import:transfer-mails` (nightly after the card feed, 21 days; `--archive=`, `--days=`, `--dry-run`) sends them. The server (`bankTransferNotices.ts`, migration 214) stores each notice once (`bank_transfer_notices`) and rebuilds every pairing each apply (`movement_transfer_notices`, one notice per movement side): same amount on the account the mail names (`bank_account_numbers`), posted from the mail's day to 6 days later, mails in sending order, each bank row once — so an own transfer's echo and a schedule notice pair with nothing. Same-day preference: a transfer to the counterparty's own account (`transfer_counterparty_accounts`, by RUT or account number; personal data, live DB only), then a single-leg row, then a transfer elsewhere; ties differing only by id are twins paired in order, other ties reported and unpaired. **Banco de Chile mails, and movements written from a mail (`ingest/src/bancochile/transferMails.ts`, `transferNoticeMovements.ts`, migrations 219–220):** `import:transfer-mails` also reads `serviciodetransferencias@bancochile.cl` (mails the recipient; the Rut and account printed are the recipient's) and pairs all mailers' notices against every numbered account. Hourly runs `--days=2`. A notice mailed in the last 3 days whose bank row has not arrived gets its movement from the mail (`mailMovementForNotice`): `incoming` → a credit; between two numbered accounts → one transfer (the second mail of a transfer to an own account at another bank is an incoming notice to an unnumbered account and writes nothing); to a known counterparty → a transfer into its landing account (`landingAccountFor`: its only account, or its one `import:panel|kind=clp|` balance; card numbers left to payment receipts); else a debit. A broker's own deposit mail (Racional's duplicate check reaches 5 days back) writes the same transfer when first and recognizes it when second. Confirmation via the importers' transfer-leg skip (`confirmTransferNoticeMovementForTransferLeg`). The row is dated the mail's day, noted `import:<issuer>-mail|<sent at>|Transf a <payee> (<bank>)` / `Transf. de <sender>` (+ ` — <message>`), recorded with signed pesos in `transfer_notice_movements`, never written twice for one mail even after deletion. Both checking importers keep it and skip the bank's listing as `superseded_by_mail` (same signed pesos, mail day from the business day before the bank day through it, or already confirmed on that bank day), stamping the bank's day as posting day and its description; unlisted within 2 business days fails the step (`overdue`). Its note carries the sender's name, not RUT digits, so `propose-card-reimbursements.ts --payer-note-token` must name the sender for such rows. **A bank row listed after the mail's day is dated the mail's day** (`redatePairedRowsToMailDay`, after each pairing rebuild): only inside Santander's posting window (`bankDateMatchesTransferDate`), each paired side keeps its bank day as posting, so the pairing holds on every later apply. A row another document dated (`movement_bank_postings` with basis `evidence`) on another day is a `redate_conflicts` entry and fails the step; a listing's fetch day (basis `fetch`) is replaced by an earlier mail day, and a mail on the same day turns its basis to `evidence`; a transfer whose other side is a numbered bank account or card without its own posting is left on its date (`redate_skipped`). Details carry `redated`, `redate_conflicts`, `redate_skipped`; historical rows are re-dated by the next apply.
- **`bank_account.incoming_wires` v1 (`incomingWires.ts`, migration 228): dollar withdrawals booked from mail.** Santander USD has no feed, so a Fintual dollar withdrawal comes from three mails. Fintual's «Retiro en dólares confirmado» (`broker.notifications` `withdrawal_requested`: net, gross, destination, pay day — `due_on` = next date with the printed day of month) can be cancelled, so it is only stored (`broker_withdrawal_requests`). Banco Security's «Envío de Transferencia» (MT103 copy: 32A value date and amount, 50K ordering customer, 59F beneficiary) and Santander's «AVISO DE LIQUIDACION DE ORDEN DE PAGO RECIBIDA» (order number, amount; no account → the bank's one declared dollar account) are `incoming_wire_notices` (resend must restate), decoded in `ingest/src/wires/`, sent by `import:transfer-mails` (hourly `--days=2`, nightly 21 days; `--issuer=wires` only these). A wire = notices of one transfer (same account via `bank_account_numbers`, leading zeros ignored; same cents; value dates within 2 days; one per side). A request pairs with the one wire into its destination for exactly its net, from request day to 7 days past pay day, with no notice naming another ordering customer; the pair writes broker cash → account for the net on the value date plus a `cash_fee` of gross − net on broker cash (hand-entered ones in the window count). Every apply re-pairs everything; `incoming_wire_bookings` records each request once and survives movement deletion. A request 3 days past pay day with no wire fails the step; an unclaimed wire is reported.
- **`payment.processor_receipts` v3: who a processor charge actually paid.** A processor-only charge («PAGOS.FLOW.CL (WEB)», «FLOW *…», «PAGO FACIL») is explained by the receipt mail: payee (name, RUT, e-mail), amount, time, order, concept, descriptor. `archiveMails` (`ingest/src/email/santanderMailArchive.ts`) stages a sender's mails; `ingest/src/payments/paymentReceiptMails.ts` has one decoder per processor (Flow, both layouts; Pago Fácil, dated by the mail); a non-receipt from the sender decodes to null, an unreadable receipt throws; `import:payment-receipt-mails` (nightly after transfer mails, 45 days; `--days=`, `--from= --to=`, `--archive=`, `--dry-run`). Stored once (migration 215, `payment_processor_receipts`); paired with expense lines **when the lines are built** (`withPaymentReceipts`, `paymentProcessorReceipts.ts`, last step of the expenses payload), never stored, because card line ids change on re-import: same pesos (an interest plan's line by its printed principal, `ccInstallmentInterestForAccount`), purchase day from the day before payment to five after, receipts in payment order, each line once, nearest day first, then a merchant naming the processor; identical lines are twins paired in order, other ties unpaired. Every line of a paired purchase (cuotas too) carries `payment_receipt`. Another processor or platform = one decoder (+ a merchant hint for a processor).
  - **Shop order confirmations** ride the same kind. Shopify «Confirmación de pedido» (shop domain or `t.shopifyemail.com`, fetched by Gmail query — `archiveMails` takes `gmraw`) → platform `shopify`: shop (subject bracket, else text before «Pedido #…», else sender name), items, «Total $X CLP». Orders and processor receipts pair separately (`matchPaymentReceiptsToExpenseLines`); a charge can have both and the line shows the order. Shops' own confirmations (`ORDER_CONFIRMATION_SOURCES`): Calvin Klein (VTEX; Total must equal the payment block's Valor), adidas («hemos recibido tu pedido» / «Gracias por tu pedido»; preparing/shipping/pick-up mails null), Club Dominó (branch in payee, printed time, total with tip), Eventbrite (only a CLP total; free orders null; untested on a real paid mail), miCoca-Cola («Hemos recibido tu pedido … con éxito» / «Pago Aprobado», contacto@micoca-cola.cl; DispatchTrack mails have no amounts; total = subtotal + descuentos + despacho).
  - **Dollars** (`currency: usd`, migration 216; DynaVap): pair only with a line of the same dollars to the cent — never a peso line at the day's rate, which any purchase of the week could fit.
  - **MercadoLibre: split charges and amountless receipts** (migration 221, `decodeMercadoLibreOrder`). A multi-seller order is charged per seller: «Pagaste $ 15.725 1x $ 8.865 y 1x $ 6.860» → `charges` (`payment_receipt_charges`, must sum to the amount); its lines pair all or none, each showing «n/N»; «6x $ 9.245» alone is one charge in cuotas. An `amount: null` receipt pairs after every amount-bearing one, with the unclaimed line on the nearest day (−1…+5) whose merchant is the store's statement name (`STATEMENT_NAME_FOR_AMOUNTLESS`: «MERCADO LIBRE», «*N PRODUCTOS») or a seller (`SELLER_NAMED_CHARGE`: «MERCADOPAGO *TIENDAUNO») — never a bare «MERPAGO*», which is also MercadoPago's in-person payments; a printed amount stays a hard check. **A MercadoPago-prefixed charge** («MP *MERCADOPAGO …», or the listing's cut «MP *MERCADO»; `MERCADOPAGO_PREFIX_CHARGE`, `receiptStatementNames.ts`) is taken by an amountless MercadoLibre receipt only when no store-named or seller-named charge fits and it is the single unclaimed such charge from the day before to five days after the receipt day (a plan's «Total» line included); two candidates link nothing, a bare «MERPAGO*» never qualifies. Risk: an in-person MercadoPago payment alone in that window is linked to the order. A line so linked reads as the catalog's MercadoLibre, the seller staying its link label. **A refund whose purchase structured state names** (a prepayment's credit, an annulment, a paired nota) carries `refund_of` (the purchase's final names, link label and receipt; «Reembolso · <purchase>», ⓘ shows the purchase's receipt) and its merchant is no evidence for the cut-merchant name rule (`cardMerchantsByAccount`).
  - **Amazon: a receipt per shipment**, because Amazon charges the dollar side once per shipment, the day it ships, for the shipment's total (not the order total). `amazon` receipts are the shipping mails (`decodeAmazonShipment`: «Shipment Total» / «SHIPMENT TOTAL» / «Shipment total», «Total» in the «Shipped: "…"» layout; $0 → null). Shipments of one order no line carries singly pair with one line of their sum, from the latest. Order confirmations are `amazon_order` (`ORDER_SUMMARY_OF`): read only for an order none of whose shipments paired, up to 30 days after placing; a confirmation priced by Amazon's currency converter → null.
  - **LATAM, Uber, subscriptions (migration 233).** LATAM purchase mails (`ingest/src/payments/latamMails.ts`, all layouts incl. «E-Ticket Confirmation» in dollars) → `latam` (itinerary, booking); a fare-difference change → `latam_change`. Uber (`uberMails.ts`): `uber` trips carry `trip` (from, to, Chile-clock start/end, km; the line shows each address up to its first comma, `trip_label`), `uber_eats` the restaurant as payee, `uber_one` with `subscription: true`; amount = what the card was charged (Uber Cash legs dropped); another-currency ride/order → null. Summary mails (`uber_trip_summary` / `uber_eats_summary`) are read only for a trip/order no receipt paired (`ORDER_SUMMARY_OF`, keyed by printed start or xid). A peso Uber receipt also pairs with a dollar line naming Uber at the day's rate within 4 % (`PESO_RECEIPT_CHARGED_IN_DOLLARS`; exact amount ranks first). **A subscription's charge reads «Suscripciones»** (`withSubscriptionCategory`, last step of the expense lines) when only the bank's name decided its category (merchant rule or none, `resolveCcExpenseCategory`'s `fromBankName`) and its link says subscription (App Store receipt whose items all renew, a charge inferred from a cycle or monthly run, Uber One); an «Único» row or line-level category stays.
  - **Receipts abroad, Despegar, stays (migration 234).** Any currency (`currency`). Dollar statement lines carry the original amount (`amount_orig`, `amount_orig_currency` = clp / usd or null): a foreign receipt pairs with the dollar line whose original amount matches to the cent (never by conversion); a peso receipt also pairs with a dollar line whose peso origin is its amount. Uber receipts abroad decode in their currency, dated by the mail. Despegar (`despegarMails.ts`) states airline and own charge apart → `charges`. Lodging (`stayMails.ts`): `booking`, `airbnb` (card rows only; credit-paid → null), `stripe`, `accor`, each with `stay` {check_in, check_out, city}. A Booking stay has no descriptor and pairs from the mail's day to five days past check-out, nearest to mail day or check-in; only a reservation's latest Booking mail pairs (`ONE_MAIL_PER_ORDER`); a line printing the receipt's reference wins a tie. A stay no line carries at its amount links as a guess («≈», `guess_basis`) to every untaken line from the day before check-in to the day after check-out whose merchant has the property's first distinctive word (≥4 letters, accents folded, lodging words and the city excluded).
  - **Vehicle permits (migration 268, `ingest/src/payments/vehiclePermitMails.ts`).** Maipú's PDF (`permisocirculacion@maipu.cl`; `PaymentProcessor.pdfAttachment` stages it with `pdftotext -layout` text) has no labels: fields by position and shape, each agreeing with its copies (folio, year, payment day, plate `AB1234-5` / `ABCD12-K`, two accounting parts summing to the amount, amount printed three times, tasación, expiry, car). Expiry 31/08 = cuota 1 of 2; 31/03 next year = cuota 2 of 2, or the whole year when paid before August (cuota 2 payable only from August). Sent as `municipalidad_maipu` with `vehicle_permit` {permit_year, plate, cuota, cuotas, expires_on} (optional; `permit_*` columns), payee «Municipalidad de Maipú», concept «Permiso de circulación <year> · 1ª cuota» = the link label (no category rule per permit).
  - **Ticket vendors and the event (migrations 255–256, `ingest/src/payments/ticketMails.ts`).** `event` {name, starts_on, starts_at, ends_on, venue} (optional; `event_*`): `puntoticket` (event layout or event-less add-on; items + despacho = total), `toliv` (tolivmarket.com / toliv.com; tickets + comisión = total; guest-list without payment block → null), `ticketmaster_cl` (yearless date = first on/after the mail, weekday checked), `ticketmaster_nz` (NZ$), `paylogic` (euros; re-mails on every state change, so only an order's FIRST mail pairs — `ONE_MAIL_PER_ORDER`, where Booking keeps the latest), `aitickets` and `ticketplus` (no amount: pair by charge name «TICKETPLUS» on its day; courtesy/invitations null). Free orders null. ## Unattended daily bank run

- **The nightly run** (the ingest service's `runNightly`, asked for by the server's scheduler at 22:00 Chile, see «Run protocol»): fetch Santander → the mail fetches → `import:cfraser-inbox` → the card feeds (Santander, Lider BCI), payment mirrors and bank checks → the mail imports → broker mail → Racional, AFP UNO, AFC, payslips when asked → `import:santander-statements`. The service must be a LaunchAgent in the GUI session (`com.user.nw-tracker-ingest`), because headless Chrome is blocked upstream and the fetcher needs a window server. Personal specifics live in PARSERS.md. **Mail is read by one fetcher (`ingest/src/email/mailFetcher.ts`):** every search on All Mail uses a DST-safe `SINCE` (`searchMailSince`); the six document sources (`SANTANDER_DOCS_SOURCE`, `LIDER_BOLETAS_SOURCE`, `LIDER_STATEMENT_SOURCE`, `FINTUAL_ACCIONES_SOURCE`, `APPLE_MAIL_SOURCE`, `AFC_CARTOLAS_SOURCE`) only DECLARE the sender, the subject → document kind and each mail's documents, and `fetchMailDocuments` walks the window (`DEFAULT_MAIL_WINDOW_DAYS`), skips what the document ledger holds, writes and records; `fetch:<source>` is `email/fetchMailMain.ts <source>`. `archiveMails` (the text archives the transfer, receipt, wire and utility decoders read) lives beside it; MIME helpers are `email/mime.ts`. - **The BCI Lider facturación arrives by mail: `fetch:lider-statements`** (`ingest/src/email/liderStatements.ts`) pulls the monthly «Estado de Cuenta Tarjeta Lider Bci Visa» PDF from `estadodecuenta@correo.tarjetaliderbci.cl` into `cfraser/inbox/` — the card's only automated statement path. **The ledger key is the mail date + message id, NOT the attachment filename** (the santanderDocs rule inverted), because BCI reuses the same attachment name every month (a client number) and a filename key would silently skip every month after the first; the saved inbox name is date-prefixed for the same reason. The statement is the bare-number PDF attachment — the «Inserto Seguros.pdf» insert must never reach the inbox (a non-statement PDF there aborts the organizer), and any other attachment shape is an ERROR (non-zero exit), never a guess. The PDF is encrypted (`LIDER_CC_STATEMENT_PDF_PASSWORD`); the pipeline decrypts, and the organizer names it from the peeked close (`peek_bci_lider_meta`). Don't add a bare `PAGAR HASTA` fallback to that peek: it matches the anterior section's «a Pagar … Hasta» and names the statement after the previous month's close.
- **PDF/JSON statement imports never dedupe against web-paste lines.** `importCcStatementsMerge` skips a row whose key/fuzzy twin already exists on the account, but an open web-paste bucket line is NOT durable evidence for a PDF import: the same merge's `reconcileOpenWebPasteAfterPdfImports` deletes the bucket's in-period lines right after the line loop, so a skip against one would delete the purchase from BOTH places. The dedupe/fuzzy scans take `excludeWebPasteSources`, set per statement from its own source (`ccExpenseLineDedupe.ts` / `ccCrossImportDedupe.ts`); web-paste imports keep full scans, since deduping a re-paste against its own bucket and against PDF lines is their point. The BCI `monto_facturado` import check is a HARD gate (no escape hatch; `pdf_total_operaciones` is collected from a single text rendering in `cc_statement_reconcile.py`, never the concatenated dual rendering, which doubles it). The gate's identity: `parsed_operaciones + parsed_cargos_abonos = Monto Total Facturado` — BCI section-3 rows (parser layout `bci_lider_cargos`) net into cargos_abonos by LAYOUT, not the Santander merchant regex (which misses «IMPUESTO DL» and merchant-named abonos like a Lider.cl return nota); PAGOs count as mid-period payments, never cargos.
- **Santander is split by document rhythm: the web session is DAILY MOVEMENTS ONLY, the monthly PDFs come from Gmail.** `fetch:santander` runs three steps — `card-movements`, `checking-movements`, `card-statements` (the facturación **JSON**; the PDF endpoint never succeeds, and the step does not click «Ver estado de cuenta» — the page requests the PDF by itself on each view and the step only logs that answer). The summary lists the skip as an ok step with its reason. There is no `cartola` step. Both monthly documents arrive as mail attachments from `mensajeria@santander.cl`, fetched by **`npm run fetch:santander-docs`** (`ingest/src/email/santanderDocs.ts`, same IMAP/Keychain app-password path as the broker-email detector): «Estado de Cuenta Tarjeta de Crédito» (the card facturación) and «Cartola Mensual de Cuentas.» (cuenta corriente + the cuenta vista accounts). Attachments are written to `cfraser/inbox/` under the **bank's own filenames**, which is the entire contract — the organizer recognises Santander's attachment naming (`1_<seq>_<account>_<date>_CC.pdf` cuenta corriente, `_CM` cuenta vista, `_LC` línea de crédito) and classifies `80_*` credit-card statements by peeking the PDF text. Mail costs no bank session, no 2FA and no window server.
  - **CC payment receipts register the payment the day it happens.** Santander mails a receipt for every card payment — «Pago Deuda Nacional TCR» (CLP debt, `Monto del pago`) and «Comprobante Pago (abono) de la deuda facturada en dolares» (USD debt; carries `Equivalente en pesos`, the exact checking leg, plus USD amount and fx) — and `fetch:santander-docs` stages the body text as JSON under `cfraser/santander-payment-receipts/` (message-id-keyed in the document ledger). `import:santander-receipts` (ingest decodes it, `ingest/src/santander/paymentReceipts.ts`, and sends a `card.payment_receipt`; the server applies it in `santanderCcPaymentReceipts.ts`; `check:synthetic-cc-payments` raises the overdue alarm; the inbox pipeline always runs both, the receipts after the xlsx import) does one of two things. **No bank row yet** (the daily xlsx only arrives with the nightly session): the checking → card `pago_tarjeta` transfer is **synthesized from the receipt**, dated the payment day (cross-currency shape for the dollar abono: CLP from-leg = the receipt's pesos, USD counter leg = the abono), recorded in **`santander_synthetic_cc_payment_transfers`** (migration 181, twin of the Fintual retiro table), and the card's own credit line («PAGO» / «ABONO DE DIVISAS», built through `santanderReceiptCardLine` → `listingLineFromCardListingLine` so it is byte-identical to the feed's row) is planted in the open web-paste bucket (batch kind `cc_santander_receipt`), so checking balance, deposits line and owed walk read the payment during the day.   - **The ledger key is the attachment FILENAME, not the month.** The facturación arrives as **two same-day mails** (CLP and USD), so a month-keyed ledger would mark the month done on the first and never download its sibling. The bank's filename carries its sequence number and document date, a stable per-document identity, and each month brings fresh sequence numbers: due when the mail lands, retried daily until it does, never fetched twice. `--force` ignores the ledger, `--dry-run` lists without writing, `--days=N` widens the search window (default 45).
- **Hourly e-mail poll:** the ingest service's `runHourly`, at :30 past every hour — the mail fetches (`fetch:santander-docs`, `fetch:lider-statements`, `fetch:lider-boletas`, `fetch:fintual-docs`, `fetch:apple-mail`, `fetch:emails`) and, **when a fetch staged something new this hour** (the fetches' `staged` step result), the full inbox pipeline (`import:cfraser-inbox` — so a monthly facturación imports the hour its mail lands, with the receipts import and the payment-mirror task) and the broker e-mail imports (`import:fintual-emails` / `import:racional-emails` under the plist's apply gates). The gate also counts a photo waiting in `cfraser/grocery-receipts/inbox/` (the one input no fetch stages); the grocery stage is incremental (per-receipt import stamps). Everything else stays nightly (Racional, statement JSONs), and the nightly inbox pipeline is the unconditional retry backstop for anything staged-but-unimported. The server records it (`recordHourlyEmailRun`, `dailyRunLog.ts`) under its **own titles** («Hourly e-mail poll») — never the daily ones, which `lastDailyRunAt` reads for the 22:00 repeat skip. A quiet hour records nothing; failures record every run but only the first of the Chile day badges (`notification`) — the nightly, which runs the same e-mail steps, remains the alerting authority.
- **The hourly Santander balance poll (`bankProductSummaryApply.ts`, `ingest/src/santander/balancePoll.ts`, migration 266).** Every hourly poll logs in to Santander (`fetch:santander --balance-poll`, the Chrome window visible — the runners do not pass `--background`), sends the login's product summary (card cupos + deposit-account balances, `cruceProductosOnline`) as **`bank.product_summary`** v1, and reads only the listings the server names: the server records the summary as a cupo capture and a balance snapshot (source ref `balance-poll-<stamp>`), judges each product at once and answers `fetch` — the card feed for a card that disagrees (or a summary without card rows), the peso checking xlsx for the cuenta corriente, the dollar account's capture for Santander USD; a cuenta vista has no listing and is only reported. The summary carries no feed close, so a card is compared without one; a close the app has not seen reads as a mismatch, costs one card-feed read and settles itself. The step prints `balance poll fetch: <list|none>` (and a `differs:` line per product), which the runner reads to import what was staged (card feed + mirror converter, the USD capture, the inbox pipeline for the xlsx) and then runs `check:cc-bank-cupo -- --recheck`. **A difference that survives its listing is a notification** («Bank balance differs from the app», `ingestTasks.ts`), once per difference: a fresh mismatch notifies when the latest EARLIER observation of the same product agreed or differed by another amount (`previousBankCupoVerdict`, the deposit verdict's `previous`, both by `observed_at` so the summary and the card feed of one session are one observation); the cupo and balance checks do not fail their step on a mismatch (the nightly's included) — only a feed with no summary does. There is no catch-up or payday fetch; old `ingest_runs` rows may carry `catch-up` / `payday` requests.
- **Dividends are booked NET; the gross and the withholding tax live in `movement_dividend_details` (migration 183, writer `movementDividendDetails.ts`).** A `dividend_payout` transfer (equity → cash) carries what the broker CREDITED — the only figure the balance walk and every P/L reader need, and the only one every source agrees on. The tax year needs the gross and the tax withheld abroad (Chile credits it against the local tax on the gross), so each dividend movement may carry one satellite row: `gross_amount`, `withholding_amount`, `withholding_rate_pct`, `withholding_jurisdiction`, `tax_residency_country`, `per_share_amount`, `position_qty`, `record_date`, `pay_date`, `broker_event_id`, `source` (`racional_api` | `fintual_cartola` | `fintual_certificado` | `ibkr_statement` | `manual`), `source_ref` — every nullable field filled only when the document prints it, a rate never computed from gross and tax. The writer (`upsertMovementDividendDetail`) is the one choke point: it throws when gross − withholding is not the movement's amount (a movement booked GROSS), when two documents disagree about the same dividend, and otherwise lets a richer document replace a poorer one (`SOURCE_RANK`: statement/API > certificado > manual) while a poorer one only fills nulls; a same-rank document from another file is provenance only (no rewrite, so the nightly re-read cannot churn). **Sources:** Racional's dividend detail (`grossAmount`, `taxAmount`, `netAmount`, since the 2026-11 rebuild; read for each new dividend row, `racionalDividendRecord`), and before it the `/users/movements/dividends` API (`DIV` gross, `DIVTAX`, `amount` net), whose `dividends-<stamp>.json` files the importer still reads — `import:racional-movements` writes the breakdown on insert, on duplicates, and from those files for history; Fintual's **Alpaca monthly cartola** («Cartola mensual de Acciones», `fetch:fintual-docs` → `cfraser/fintual-acciones/cartolas/`, message-id ledger because the attachment is named after the month only) whose Income section prints `Cash DIV @ <per share>, Pos QTY: <qty>, Rec Date: <d> $<gross>` plus `Div. Adj(NRA Withheld) … at 15% for tax country CHL; w8w9: w8 -$<tax>` (a dividend with no NRA line was credited in full), and the on-request **certificado de transacciones y eventos de capital** (`…/certificados/`, bruto / impuestos / neto) — `import:fintual-acciones` (ingest: `fintual/accionesDocs.ts` parsers; server: `brokerDividendStatementApply.ts`, through `broker.dividend_statement`) pairs each printed dividend with the ledger's `dividend_payout` at the printed NET within ±5 days (the DRIP-day skew every Fintual source shares) and fails the step on a dividend with no row or several; sweep interest is reported, not booked. A future IBKR statement (Dividends + Withholding Tax sections) writes the same rows. **Trap:** the «Recibiste USD $X en dividendos de T» Racional mail states the GROSS dividend while Racional credits the net after the 15% US withholding — never book the subject figure. Both Racional dividend templates are nudges (`gross_amount` on the event, never `amount`), and the crawl importer's day-sum mismatch is a **`conflict`** that fails the step (`requires_manual` stays for the by-design cash legs). Nothing reads the table on a request path yet; a tax-year rollup is a later tranche.
- **The checking xlsx download never goes through Chrome's download handling.** The SPA builds the xlsx in the page and clicks an `<a download href="data:…;base64,…">`, and Chrome 152+ crashes (SIGSEGV/SIGTRAP on CrBrowserMain) handling that data-URL download under CDP. `browser.ts` installs an init script that catches `a[download]` clicks carrying a `data:`/`blob:` href (both `a.click()` and a dispatched MouseEvent, the FileSaver style), keeps the bytes on `window.__nwInlineDownloads`, and `downloadTo` (wait.ts) races that stash against Playwright's download event and writes the file itself — the bank's filename is preserved, and a real HTTP download still takes the native path. The relaunch-once logic stays for whatever else can kill the browser.
- **The Santander session survives a Chrome crash and a homepage modal.** `runSantander` detects a gone browser (`page.isClosed()` or Playwright's closed/crashed wording), relaunches Chrome **once** per run and retries the same step before continuing (`MAX_BROWSER_RELAUNCHES`; the persistent profile keeps the bank session, so the relaunch normally skips the password login — kept at one so a deterministic crash can't become a burst of logins; a failed relaunch marks the remaining steps skipped). The public homepage can open a marketing modal (`div.modal-overlay[role=dialog]`) whose overlay swallows the click on «Ingresar»; `login.ts` sweeps the fraud banner and any dialog's own close button (`SELECTOR.closeModal` — never an arbitrary button) before the click and retries once after a blocked click. **The private site logs an idle session out:** the SPA overlays «vamos a cerrar tu sesión por inactividad — ¿Necesitas más tiempo?» with a 10-second countdown, and long waits do not count as activity; `sessionKeepAlive.ts` polls every 2 s beside the running step and clicks «Mantener sesión» (never «Cerrar sesión»), and the step runner re-logs-in when `isLoggedIn` is false before a step. Chrome is launched with `--hide-crash-restore-bubble` so the post-crash «Restore pages?» bubble never invites a human to restore old tabs into a scraper session. **When the scraper reports a closed page/browser, check the crash reports (`~/Library/Logs/DiagnosticReports/`) before touching selectors.** **The card carousel is advanced by a swipe when its arrow does nothing (`swipeToNextCard` in `cards.ts`):** after an arrow click that produces no `consultaUltimosMovimientos` call within 5 s the step drags across the active tile and waits again; «neither the arrow nor a swipe produced a new movements call» is the stop. **The session waits for the call each view makes, never for networkidle (`docs/santander-session-trim-plan.md`)**, because the SPA's analytics traffic never goes idle. The login waits for the login button and then for a logged-in URL plus the landing's `cruceProductosOnline`; the card step reads whichever currency a card opens on, clicks the other tab once and never restores it (the carousel keeps the tab), and stops once every card of the product summary was visited (the swiper does not disable its arrow) — **and fails when a card the summary says owes money was never listed (`unlistedCardsWithDebt`)**: no file is written, so the next poll fetches again, instead of the cupo check failing on the bank's side; the statements step follows the same pattern after «facturados» resets to Pesos and reads the tab bar only once rendered; the checking step waits for the peso `transactions` call and the download button. **A rejected login never hangs the run:** `openSession` closes the context it launched when the login (or a relaunch) fails, `main.ts` force-exits ten seconds after the run is over if anything still holds the event loop (logged, so a leak stays visible instead of becoming a hang), and `login` polls for the rejection toast (`TEXT.loginRejected` — it renders in the top-level page beside the `#login-frame` iframe, not inside it) while the redirect is pending, failing with the bank's own words instead of a 90-second navigation timeout. **A failed login leaves evidence and a wrong clave latches logins off:** every login failure (including «login form never appeared after opening the panel») writes a screenshot plus the frame and page text under `cfraser/scraper-diagnostics/`, quotes the frame text in the error, and records whether the `#login-frame` iframe element existed and its src (the frame loads from the private-app host, so a stall there is indistinguishable from a panel that never opened). When the panel renders the bank's «No fue posible ingresar a tu banco en línea — Comprueba tu conexión a internet» card in place of the iframe (typical right after a wake from sleep, while the network is coming back), `login` clicks its «Volver a intentar» once and restarts the 45-second form wait (a second card fails with the bank's words), and `openSession` probes both login hosts before launching Chrome (`waitForHosts` in `ingest/src/network.ts`: any HTTP answer counts, up to 90 s, a wake younger than five minutes named in the log). The toast «Alguno de los datos ingresados es incorrecto» means the stored Clave Digital is wrong, and presenting it nightly is how a bank blocks a clave — so `loginLatch.ts` records the rejection in `cfraser/.santander-login-rejected.json` and `runSantander` refuses to open a browser while it stands, failing the step loudly with the fix in the message. The latch clears itself when the Keychain item's modification date is later than the rejection (`readKeychainItemModifiedAt` — attributes only, never `-w`), on a successful login, or for one run with `--force`.
- **The payment-mirror converter runs twice per nightly run**: inside the inbox pipeline (after the receipts step) and again after `import:santander-movements`, because the card's PAGO / ABONO DE DIVISAS evidence for a same-day payment only lands with the feed. A run with no step recorded is a failure (`runStepsSucceeded`).
- **The 22:00 run skips only right behind another run.** The scheduler supersedes the nightly when a daily run finished less than 60 minutes ago (`DAILY_RUN_REPEAT_WINDOW_MINUTES`, `ingestRunPolicy.ts`). Don't skip it on any earlier run that Chile day: an afternoon manual or wake-up run would cancel the evening's run and leave the afternoon's card movements for the next night.
- **Racional import: one read never blocks another (through `broker.movements`).** Rows missing units or instrument are `incomplete`, dedupe runs first, and only an incomplete row that would be written blocks its own read (nothing from its list written, the crawl cursor does not move past it, step exits 1; later reads and their dividends still apply). The crawl cursor is ingest's (`cfraser/.racional-crawl-cursor.json`, `crawlCursor.ts`): the list key (`racionalListRowKey`, the crawl's own `rowKey`) of the first row of the newest read whose list the server applied, forward-only. A Racional e-mail nudge retires once a read that started after the mail applied cleanly (`broker_read_coverage`, migration 202). Details in PARSERS.md «Racional (brokerage)».
- **The bank's own cupo is checked every night (migration 188, `santanderBankCupo.ts`, `ccOwedByCurrency.ts`, `ccBankCupoCheck.ts`).** Santander's landing page requests a product summary once per login (`cruceProductosOnline`); its `TCR` rows state each card's cupo / utilizado / disponible in CLP and in USD (18-digit strings with two implied decimals in both currencies). The fetcher keeps them in the card-movements file (`cupos`, or `cupos: null` + `cuposError` when the session got none — the movements step never fails over it). `import:santander-movements` validates them before writing anything (cupo = utilizado + disponible to the cent; bank account and plastic route to the same master; one row per master and currency) and records them after the lines (`cc_bank_cupo_captures` / `cc_bank_cupo_snapshots`, idempotent per file). The step «CC bank cupo check» (`check:cc-bank-cupo`, nightly after the payment-mirror pass and after the hourly poll's import) judges the latest capture once against the app's owed per currency (`ccOwedByCurrency`: `clp` and a `foreign` entry per currency the card owes in; each line in its own currency): the last closed facturación's billed total (statement header, or the feed's SALDO INICIAL on a provisional close) + plan cuotas not billed yet over every plan bought through that day (`installmentRemainderAfterFacturacionClp` — no calendar month-end cut, unlike `installmentRemainingClpByCalendarMonth`) + every line filed under a later facturación (charges +, payments and notas −, cuota lines left to the plans). That is the bank's own identity (utilizado = SALDO INICIAL + saldo capital cuotas + unbilled feed rows), so pesos and dollars agree exactly (tolerance 0): a plan's unbilled remainder is its principal (BCI: the cuota lines' printed «Monto operación», below N × cuota) less the cuotas already billed, and Santander's unprinted cuotas follow its own split (`CC_ISSUERS.cuota_split`: round half up, the last cuota absorbs); a card that stopped billing uses its last statement close; a snapshot whose feed states another close than the app's latest is `indeterminate`. The report with both sides and the app's terms is a **log** (import sync; verdicts in `cc_bank_cupo_checks`); a mismatch is a notification once per difference and does not fail the step (see «The hourly Santander balance poll»); a feed without a summary fails once. **A row the listing shows twice is two charges (`webPasteListingDedupeKeys`):** a pasted table or the nightly feed is the complete «movimientos no facturados» list, so identical rows in it are twins, never one row listed twice — the Nth one gets the parser's `#dupN` one-shot key and imports (the merge treats a fresh `#dup` key with a colliding computed key as an affirmed twin and skips the fuzzy match for it), re-pasting matches each twin on its own key, the feed close's move-forward and the mirror (one-to-one) see the twins too, and the statement's `#dup` lines settle them at the close. Don't collapse repeated paste rows: that leaves the app one charge short until the statement. The card page shows the bank's figures and the verdict under «Cupo» (`bank_cupo` on the card payload; the «Cupo» value itself mixes CLP with the dollars in pesos).
- **The bank's own deposit-account balances are checked nightly too (migration 212, `bankAccountBalances.ts`, kind `bank_account.balances`).** The same product summary lists the client's deposit accounts (`CCC` cuenta corriente in pesos and dollars, `CCM` cuenta vista; `MONTODISPONIBLE` is the balance). The fetcher keeps those rows in the card-movements file (`accounts`), `import:santander-movements` sends them after the card listing (same source ref), and the server records every row; only numbers declared in `bank_account_numbers` (account ↔ issuer + number + currency, set on the live DB — personal data) are judged, inside the «CC bank cupo check» step: the ledger in the account's own currency at the observation's Chile day (display readers) must equal the bank to the cent, each snapshot judged once, the report a log, a mismatch a notification once per difference. A row in any code of `currencies` is recorded and judged in the account's own currency to its coin — pesos against the peso checking ledger, any other against the cash ledger held in it (`ledgerBalanceInOwnCurrency`; a declared account held in another currency throws); the product summary asks for a listing only in the currencies the session reads (`CHECKING_LISTING_BY_CURRENCY`: pesos, dollars), any other mismatch is reported with no listing. The summary balance is live, so a post-cutoff wire is in it as soon as it happens — the same moment the ledger counts the forward-posted row.
- **Fail-soft, but never silent.** Steps do not abort the run as a group — one bank being down still lets the rest import — so the outcome is *recorded*, not just logged: `recordDailyRun` (`server/src/dailyRunLog.ts`, from the run report `completeIngestRun` receives) writes an `app_messages` row per run — a plain `log` when every step passed, a **`notification`** (which the app badges unread) plus a macOS alert from the service when any failed; a run whose job stops heartbeating is recorded as a failed run (`lost`). **The first clean run after a badged failure is a `notification` too** — under the clean title (the titles drive `lastDailyRunAt` / `staleDailyRunDays`; kind is read by none of them), with a «Recovered: the previous run (YYYY-MM-DD HH:MM) had failed.» line, because the notifications tab lists notifications only and a resolved outage would otherwise sit there unresolved. Same rule for the hourly poll, where the recovery records even when the poll was quiet (`lastRunFailureToRecoverFrom` in `dailyRunLog.ts`); the next clean run finds a success on top and is a plain log again. **A recovery is a notification only when its outage was badged:** the poll badges one failure per Chile day, so a second outage of the day is logs only and its recovery is a log too (recorded, with the «Recovered» line, so import sync shows the outage end).
- The message body names each step and its duration **and the days since the last successful run** — the failure a per-run status cannot express is the run that never happened (machine asleep at 22:00, agent unloaded). `staleDailyRunDays()` is the read side for any surface that wants to show it.

## Import rules per source

- **CC installments:** `import:cc-parsed` / PDF → `cc_installment_*` / `cc_statements`; no runtime CSV.
- **CC parse is incremental.** The per-PDF parse cache key is **(PDF sha256, parser version) only** — never mtime/size (they drift on copies). A cache hit never reads the PDF: the readability peek/OCR and qpdf repair run on misses only, and the hit validates cached meta (`require_statement_meta`). Two downloads of the same facturación under different names make the incremental import ping-pong the statement's row between source names: put exact duplicates (and a re-download named by its pay-by date) in the card slot's `duplicates/` (excluded by `is_excluded_cc_pdf_path`, like `pending-review/`). `server/scripts/remove-cc-duplicate-download-statements.ts` (report-first) removes copies stored as their own closes.
- **Scanned documents use one OCR model (`ingest/python/ocr_tessdata.py`).** A different `eng.traineddata` build reads scans differently (and fails the reconcile). `use_expected_tessdata()` (card, payroll, checking-cartola OCR) takes `TESSDATA_PREFIX`, else the first standard folder (Homebrew, MacPorts, `/usr/local`, `/usr`) whose model has the expected sha256, else throws listing each folder. The home server keeps a copy of the laptop's model and sets `TESSDATA_PREFIX` in its ingest plist. Changing the model = re-parse every scan, then update the hash.
- **CC statement import is incremental (migrations 171, 292).** The import (`card.parsed_statements`; `import:cc-parsed` by hand) skips a statement whose `import_fingerprint` is unchanged: a hash of the statement's and each line's stored columns (`cards/statementStorage.ts` defines it; `ccStatementFingerprint.ts` filters), written by `importCcStatementsMerge` because only it knows which row the statement resolved to (the close-date fallback can match another `source_pdf`). It hashes what the ledger keeps, so two renderings of one statement hash alike; identity, derived columns (kind, origin label, dedupe keys, ids) and lines dropped as repeats stay out. A parser change touching only unstored fields (plan principal columns, layout, canonical row id) needs `--full`. A statement that does import gets the full reconcile. **`--full`** forces the from-scratch pass (`import:cfraser-inbox -- --full` passes it through).
- **CC statement source ownership:** `cc_statements` is UNIQUE on (account_id, card_group, source_pdf, statement_date), so two sources for one facturación would duplicate it. Ownership is per (close, currency) and **the PDF outranks the JSON** (`ccStatementJsonSource.ts`) — the JSON arrives first but is thin (the international endpoint is dateless with all-NULL headers, so a JSON USD statement has lines only), and first-writer-wins would lose the later PDF. `npm run import:santander-statements [-- --apply]` (ingest sends `card.statement`; server `cardStatementApply.ts` over `santanderStatementImport.ts`) cross-checks PDF-owned closes (report only) and writes unowned ones through `mergeCardStatements` as `import:santander-json|<currency>|<close>`; a later PDF supersedes a JSON-owned close inside that merge (JSON rows deleted, lines cascade, `json_closes_superseded_by_pdf`; their keys go into `replaceStatementKeys` so the reconcile doesn't count them). The cross-check (`pairStatementLines`) pairs by normalized merchant + |amount|, then amount + merchant prefix («matched by prefix»: the PDF layout can glue the charge-type column, «… COMPRAS P.A.T.»; the parser is left alone because a version bump re-parses the corpus), then by rendering (`matched_by_rendering`: a JSON-only trailing 4-digit terminal code, punctuation). JSON statements are real statements elsewhere: they count for facturación close and open-web-paste supersede (`isStatementSourceKind` = not a listing), join traspaso links, and dedupe in a `json|`-prefixed key space. The import refuses when the bank's Cuenta→master disagrees with the registry's plastic routing (`assertNoCardRoutingConflict`) and skips an international response that re-serves an older cycle (`usdStatementIsStaleEcho`). **Currencies pair on (account, NumExtracto)** (`assembleSantanderStatementBatch`, `ingest/src/santander/statementJson.ts`): the international file takes close, pay-by, next close and titular card only from the same extracto's national (extracto from the staged name `<Cuenta>-extracto-<NNN>-…` or a capture's `requestBody.INPUT.NumExtracto`; none or `extracto-0` throws); without a twin it is «unpaired»; the batch throws only when ambiguous (one extracto with two closes or differing copies, two extractos for one close). Writes go per (account, close); `--apply` archives a superseded, fully verified facturación (not the account's newest extracto) into `santander-statement-json/archive/`; dirty groups stay («KEPT»).
- **Per-card CC behavior is config:** redirects, superseded masters and classification tokens load from gitignored `cfraser/cc-cards.json` (`server/src/ccCardRegistry.ts`, `ingest/python/cc_cards.py`; missing = empty registry for demo/CI). Tests use `server/src/test/ccCardsFixture.json` (`NW_TRACKER_CC_CARDS`, in `vitest.config.ts`); never hardcode real last4s. Real values: PARSERS.md.
- **Fintual certificado:** `npm run import:fintual-cert` (ingest sends `fund_account.transactions`; server `fintualCertImport.ts`), run by `import:cfraser-inbox` (report only) when one lands. Non-destructive: `--apply` only ADDS rows no flow covers (matching includes mirror-merge/manual transfer legs, exact amount ±5 days); never deletes or overwrites, keeps externally-set flow kinds (the APV-A state bonus looks like a personal deposit there). Deposit kind goes to `movements.flow_kind` at import (state bonus / traspaso; plain deposits NULL). The account ensure sets `fund_series_key`.
- **Fintual retiros are synthesized from the mail.** «Pagamos tu retiro» states amount, payment date, goal and cuotas, so `import:fintual-emails` writes the goal→checking transfer at once (else the NAV drop sits in P/L until the bank leg; the hourly poll can't fetch it). One row whichever side lands first: an imported credit is **promoted in place** (`fintualWithdrawalPairing.ts`); a synthesized transfer absorbs the bank's later row through the checking importers' `superseded_by_transfer` skip (`findMatchingInternalTransferLegId`, signed amount + posting window) in xlsx and cartola. Syntheses are recorded in **`fintual_synthetic_retiro_transfers`** (migration 177, message-id UNIQUE; leaf `fintualSyntheticRetiros.ts` avoids an import cycle); the skip stamps `confirmed_on` (the only trace, since it inserts nothing). `import:fintual-emails` exits non-zero when a synthesis is unconfirmed past paid_on + 2 Chile business days (else the next anchor re-derivation silently absorbs a phantom credit). Last-business-day retiros are synthesized too; the next-month bank row records its posting day (see «Bank posting day»). **Retiro to the Fintual balance** («… quedaron disponibles para invertir en Fintual … equivalente a N cuotas»): `paid_to: "fintual"`, goal → «Fintual CLP» (`import:panel|kind=clp|key=fintual_clp`) with the cuotas, no synthesis record. «Devolvimos tu saldo» (balance wired back after 7 days) is manual.
  - **Gmail IMAP `SINCE` returns nothing on a DST-transition day** (evaluated in the account's zone): `fetchBrokerEmails` searches from watermark − 1 day, then − 2 if empty (`searchSinceCandidates`); the exact-timestamp filter drops seen mails.
  - **Scan files overlap, so mails collapse by Message-ID** before sending (`collapseBrokerEmailEventsByMessageId`, `ingest/src/brokers/brokerEmail.ts`; the `broker.notifications` contract refuses a repeated message id): `SINCE` is day-granular and `stagedScans.ts` concatenates every `scan-*.json`, and a duplicated retiro would promote twice and roll back the batch. The fetcher drops messages `<= last_seen_at` (`fetch.ts`); `refusePromoteCollisions` sends a second in-batch claim on a credit to `requires_manual`. **The pairing window is `[paid_on, paid_on + 5]`** (`findUnpairedCheckingCredit`): a wire never posts before payment, and a two-sided window claims unrelated earlier credits. Repair: `server/scripts/unpromote-checking-credit.ts --movement-id=NN --note='<original partialMovementNote key>'` (report-first, `--apply`; the note is the xlsx dedupe identity, byte-exact), then re-import.
- **AFP UNO:** cuota ledger built from the full-history Certificado de Movimientos and the SP's official valor cuota, one account per fund manager (`server/scripts/split-afp-ledger-into-fund-accounts.ts`; see «The AFP account's ledger and price»). Cuotas = Σ `units_delta` + transfer legs, no snapping. New rows from the nightly certificate read (`pension_account.certificates`), price from `afp_uno`.
- **Statement line sections are one rule set:** `server/contracts/data/ccStatementLineRules.json` (payment literals, ABONO DE DIVISAS, traspaso tokens, CLP/USD section-3 patterns, garbled-row pattern, layout lists), read by `ccStatementLineRules.ts` and `ingest/python/cc_statement_line_rules.py`; `classifyCcStatementLine` / `classify_statement_line` place every non-installment line for the import gate and the parse check; both suites assert `ccStatementLineSectionCases.json`. A USD payment line is never section 3; BCI section-3 rows net by layout. The file is in the parse-cache version (editing it re-parses once).
- **A charge named «PAGO …» is a charge** (`_is_printed_payment`, `parse-cc-statement-pdfs.py`): «PAGO FACIL», «PAGOS.FLOW.CL (WEB)», «PAGOS.F*COMUNIDAD …», «PAGOS MASIVOS …» print positive. A payment is an exact payment name, or opens like one and prints negative. The reconcile's operaciones check is skipped when the period had a payment, so **`operaciones_shortfall`** (`cc_statement_reconcile.py`) fails a text-read Santander peso statement whose operaciones fall more than a peso short of «TOTAL OPERACIONES» (more is a refund set aside; OCR scans exempt).
- **Two identical-ish lines on one statement are two charges:** `oneShotLineFuzzyMatchExists` ignores lines this import wrote into the same statement (`excludeLineIds`); lines already on file still dedupe re-imports.
- **Stale copies from an old card-group assignment** (`scripts/replace-stale-cc-statement-copies.ts`, report-first, IMMEDIATE): the card group comes from the file name, so a regrouped statement gets a second copy keyed by the new group while dedupe leaves the lines on the old one (double-counted). The script deletes the stale rows and re-imports the twins in full, carrying assignments, failing when a paired payment loses evidence. Statements the parse reads as zero rows keep their old rows (the only record).
- **International rows come from whole printed lines:** a vertical chunk is a line only with exactly one line's two amounts and no «N DE M» counter; otherwise it is `VERTICAL_MULTI_LINE`, keeps its merge slot (stable row ids and fingerprints) and is dropped unless a whole row replaces it (else page numbers, other lines' US$, or a payment's origin become charges). In the layout reader PAÍS is the two-letter cell before the two amounts, and it is the merchant's country, not the charge currency. Cleanup: `server/scripts/remove-cc-intl-extraction-artifacts.ts` (report-first, `--apply`).
- **Payroll labels read their own line:** `amount_after_label` never crosses a line break and skips a rate before the amount («Isapre 7%»); Talana header columns go through `amount_in_header_column` (0 when blank). After a parser change review `import:payroll-liquidaciones -- --dry-run`.
- **Card line origin currency is decided by value, on import (`ccOriginCurrency.ts`):** the parser writes MONTO MONEDA ORIGEN as printed and leaves `orig_currency` empty (column kept so peso fingerprints don't move); `importCcStatementsMerge` labels with `ccLineOriginCurrency`: `usd` when origin = US$ to the cent, `clp` when origin ÷ US$ is within 5 % of `fx_daily` on/before the date (+ half a cent ÷ |US$|), else null — never by country — and refuses pre-labelled records. The JSON writes its origin as the same Chilean cell (`ccOriginAmountCsvCell`); web paste has none. Nothing computes with these fields. Relabel stored lines with `scripts/relabel-cc-line-origin-currency.ts [--origins-csv=…] [--apply]` after the parse + import that follow a parser change.
- **One parser per format.** dd/mm/yyyy → ISO: `parseDdMmYyToIso` (`server/contracts/src/formats/dates.ts`; card code via `normalizeTransactionDateIso`; a line's date is `statementLineDateIso`, transaction else posting, `ccInstallmentPayBy.ts`) and Python `parse_dd_mm_yy_to_iso` (`ingest/python/statement_values.py`), both asserting `server/contracts/data/ddMmYyToIsoCases.json` (one case file per format in `server/contracts/data/`); ISO → dd/mm/yyyy: `ddMmYyyyFromIso` (throws on non-ISO). Far-future fixtures use ISO dates (a dd/mm year past 2038 reads as a jammed token). Numbers: each source declares its style, never guessed from separators — `parseChileanNumber` / `parseUsNumber` (`formats/numbers.ts`, throw; `isChileanNumber`, `parseOptionalChileanInteger`) and Python `parse_clp_amount` (ties-to-even). Own copies remain in BCentral, Quetalmi, `ingest/src/brokers/brokerEmail.ts`, the Racional crawl (`ingest/src/racional/steps.ts`, `movements.ts`).
- **Cartola rows without a year** (`cartolaMovementDateIso` in `server/contracts/src/formats/dates.ts`, `cartola_row_date` in `ingest/python/cartola_layout.py`): candidates are the years DESDE→HASTA where dd/mm is a real date in the period; exactly one, else error (both assert `server/contracts/data/cartolaMovementYearCases.json`). PDF parsers add `PdfCartolaRowDates`: an ambiguous row (annual cartolas) takes the earliest candidate on/after the previous row, else the parse fails naming file and row. The XLSX never spans a year and has the base rule only.
