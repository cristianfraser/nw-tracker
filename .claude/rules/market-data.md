# Market data: sync and live quotes (nw-tracker)

> Moved verbatim from `AGENTS.md`, whose «Topic rules» index lists the sections of every file under
> `.claude/rules/`. A section named in «…» that is not in this file is in `AGENTS.md` or in the file
> that index names for it.

## Global sync scheduler

- In-process scheduler (`server/src/globalSyncScheduler.ts`): polls every 15 minutes **only while any source is stale**; when all are fresh, stops polling and wakes at the earliest source `next_sync` wall time.
- **One scheduler kernel, one source table, one config (`schedulerKernel.ts`, `globalSyncStale.ts` `SYNC_SOURCES`, `publisherSchedule.ts`, `config.ts`, `outboundFetch.ts`; docs/untangle-plan.md F14).** Every background job — the global sync, the live-quote poll and its two companions (the watchlist history depth, the sync dimming check), the ingest scheduler's 30 s tick, the job queue's executor, the warmer's 00:05 rollover and data-version check, the hourly backup check, the usage flush — is a `ScheduledJob`: it says when it next wants to run (a wall-clock instant) and what a run does; the kernel owns one timer per job, suspend detection (how late the timer fired, or the wall clock running ahead of the monotonic one), the network grace after a wake, the bounded retry budget refilled by a success (`every failure` for the live poll, `only while recovering from a wake` for the global sync), the in-flight guard and the enabled / awake gates. A sync source is one row of `SYNC_SOURCES` (label, configured, stale rule, publisher lag and its dimming hour, wake time, day kind, whether a forced run survives a still-stale success); the status rows, the scheduler's stale list, the dimming list and the step labels are read from it, and the ids live in the leaf `syncSourceIds.ts`. A business-day publisher is a `PublisherSchedule` (`{publishHour, lagBusinessDays}`): the SP (AFC, and the AFP read from the SP) lag 1, UNO's own API lag 2; the evening publish hour of Fintual, the AFP and the AFC is one constant, `EVENING_PUBLISH_HOUR_CHILE`, and the publisher-lag verdict is one function (`publisherLagFromPoll`). Every sync fetch goes through `fetchOutboundText` (user agent, a 60 s timeout unless stated, Latin-1 or UTF-8, Banco Central's rate gate).
- **Only the user's primary app instance runs background jobs.** Any secondary dev server sharing the real DB — every `.claude/launch.json` server config (already set) or an ad-hoc `npm run dev -w nw-tracker-server` — must set **`BACKGROUND_JOBS_ENABLED=0`**: two in-process schedulers on one SQLite file double-run every due sync (duplicate `Sync` rows in `app_messages`, identical diffs) and race writes ("database is locked"). See the env bullet under Server runtime modes.
- **Crypto EOD** (`crypto_eod`): due from 23:55 Chile; `equity_daily` trade dates are **UTC** days. Source: CoinGecko daily USD (includes weekends). Due close = last **completed** UTC day at sync time (never the in-progress UTC calendar day). Stale carryover persists after midnight Chile until that day is in DB (`cryptoEodDueUtcYmd` in `equityEodSync.ts`). Backfill: `npm run backfill:crypto-coingecko-eod -w nw-tracker-server`.
- Manual “Marcar desactualizado” calls `notifyGlobalSyncScheduler()` to start polling immediately.
- **IPC is the Banco Central's base-2023 spliced index, checked against its own monthly variation (`ipcSeries.ts`, `fetchIpcMonthsVerified` in `bcentralApi.ts`).** `ipc_daily` stores the index only (`G073.IPC.IND.2023.M`, first-of-month dates, 1998 →); every fetch also reads the published variation (`G073.IPC.VAR.2023.M`) and throws unless each month's index ratio matches it within 1e-5 points. Both print plain decimals and go through `parseUsNumber` — never the generic `parseBcentralNumber`, which reads «133.823492253» as 133.823.492.253. The sync re-fetches the last stored month and `writeVerifiedIpcRows` throws when a stored month differs (a revision or rebase is never spliced on); reload with `npm run backfill:sbif-utm-ipc -w nw-tracker-server -- --replace-ipc`. The splice is not the INE's official variation in every month (the UF, which moves with the official one-decimal variation, disagrees with the rounded spliced variation around base changes and rounding edges), so a tax reajuste that must follow the SII's figures cannot assume them equal.
- **The official IPC variation lives apart, in `ipc_official_monthly` (migration 196, `siiOfficialIpc.ts`).** The INE's monthly variation as the SII prints it (`sii.cl/valores_y_fechas/utm/utm<year>.htm`, one decimal) — what the UF follows and what the SII reajusta with — plus the index as printed in the base of its day (ratios across the 2019 and 2024 base changes are meaningless; reajustes chain the variations, `officialIpcVariationPctBetween`). Every month is checked against the UF (growth from the 9th of the next month to the 9th of the one after, rounded to one decimal); only the two latest months may wait for their UF, anything older throws, and a stored month whose figures change throws. Filled by `server/scripts/backfill-sii-official-ipc.ts` (from 2016, since `uf_daily` starts mid-2015); the monthly `sbif_ipc` sync step fetches this year's page (and last year's until its December is stored).
- **The AFP account's ledger and price (`afpUnoOfficialSync.ts`, `afpDisplayFrame.ts`, `pensionLedgerShape.ts`, `spAfpFundUnits.ts`, migration 206).** The price is the Superintendencia de Pensiones' official valor cuota (`vcfAFPxls.php`, one fund per file, every AFP, yearly blocks with their own header — UNO from 2019-10 — and a «Valores Provisorios» block that reprints the current month), stored with the SP's own date in `pension_fund_unit_official` (every AFP, fund A; a stored value the SP prints differently is replaced and noted). **`afp_uno_cuota_a` is the display frame:** the official value of Chile business day D shows from the next business day (`AFP_UNO_DISPLAY_LAG_BUSINESS_DAYS` = 1), the day it is published (the SP prints ~18:30–18:50; nothing changes at 00:00). The `afp_uno` sync is due from 18:00 Chile on each business day (`EVENING_PUBLISH_HOUR_CHILE` in `publisherSchedule.ts`, the same hour as Fintual so the two funds go stale together) until the previous business day's value is stored, re-reads the current year each run, re-derives the last 60 display days and writes rows only through the day the latest published value shows (a pending value is never pre-written as a carry); a late SP is publisher lag («Esperando publicación», dims from 18:00). No uno.cl homepage scrape and no Quetalmi (both wrote a 00:00 frame). **The ledger** is one row per day a certificate price first shows in that series (`pensionLedgerShape.ts`: rows netted per day, withdrawals their own row, provisions cancel; a price is looked for from six months before its período to eighteen after, since late cotizaciones can be credited much later), so cuotas enter on the day their price does and a contribution never reads as a gain or loss. **One account per fund manager and fund (migration 242, `afpAccounts.ts`, `pensionCertificateChain.ts`, `server/scripts/split-afp-ledger-into-fund-accounts.ts`; plan `docs/afp-fund-accounts-plan.md`):** «PlanVital-A», «Modelo-A» and «UNO-A» each hold the cuotas their certificate rows print, priced by their own fund's official valor cuota in the display frame — series `afp_<afp>_cuota_<fund>` (`afpDisplaySeriesKey`), declared on `accounts.fund_series_key`, which `cuotaLedgerSeriesKeyForAccount` reads (null means the kind's live series, `afp_uno_cuota_a`); `import_key` is `import:afp|afp=<afp>|fund=<fund>`. **A fund switch is a transfer between two fund accounts carrying both cuota counts:** `units_delta` the cuotas sold (the from-leg), `counter_units_delta` the cuotas bought (the to-leg; migration 242, read through `transferToLegUnits` / `transferFromLegUnits` in `movementTransfer.ts`, accepted by the create validation only on a transfer between two units accounts), `flow_kind = 'afp_fund_switch'`, `amount` the pesos the sale produced, dated the day the receiving fund's credit price shows; the sending fund's series ends on the day its sale price showed, so while the money is in transit the account keeps exactly the pesos that left (an on-or-before read), no phantom P/L couplet. When the receiving fund credits more than was sent, the difference shows as its P/L on its first day. **The live UNO account is the afp account whose series is `afp_uno_cuota_a`** (`liveAfpUnoAccountId`): the nightly reads, the sync, the stale rule and the `account_sync_sources` inference resolve it that way, never by import key. A cuota-ledger account with no stored `valuations` gets its chart dates from its units events (`augmentChartDatesForCuotaLedgerAccounts`); the position ticker is `<AFP>-<FUND>`. The 2027 generational fund is one more account, series and switch. The chain is built from the full-history certificate by `server/scripts/split-afp-ledger-into-fund-accounts.ts --cert=<rows.json> [--apply --live]` (report-first; input from `npm run parse:afp-uno-certificate -w nw-tracker-ingest -- --pdf= --out=`; the locating, pairing and per-fund net checks live in `pensionCertificateChain.ts`): each row's pesos must be its cuotas × its official price, each fund's rows plus the switch into it must net to the cuotas it sold, and Σ cuotas today must be unchanged.
- **AFC Fondo de Cesantía (CIC) is a cuota ledger priced by the Superintendencia de Pensiones' public daily valor cuota (`afcCicSeries.ts`, `cuotaLedgerAccounts.ts`).** Source **`afc_cic`** reads the SP's yearly CSV (`vcfAFCxls.php?aaaa=YYYY` — semicolon, Latin-1, Chilean numbers, one row per CALENDAR day with weekends/holidays as flat carries of the prior close, history since 2002, no auth; the parser fail-fasts on any header/row shape change) into `fund_unit_daily` series `afc_cic` (CIC column only — the FCS is the solidarity fund). The trailing month is «provisorio», so every run re-reads the whole current year (plus the previous one while its Dec 31 is missing) and **replaces** a differing stored value, reporting it as a step note («restated …») — the SP is the authority. **Due rule:** the SP publishes on Chile business days only: from **18:00 Chile** (`EVENING_PUBLISH_HOUR_CHILE`, the one hour Fintual's cuota, the AFP and the AFC share, so the three dim together) a business day's publication prints the previous business day's row, so the expected row is the business day before the latest publish day (`expectedPublishedDay`: Friday's row from Monday 18:00, Thursday's all weekend), and the schedule wake is the first business day whose publication expects a row beyond the latest in DB (`nextPublishDue` / `publisherNextSync`). Don't expect the business day before TODAY: every weekend would then wait on Friday's row and dim the AFC until Monday evening. **Publisher lag:** each fetch records its time and the CSV's last printed day (`afcCicLastCheckedAt` / `afcCicLastPublishedYmd` in the sync state); a stale row whose fetch is under 30 min old, whose DB holds that printed day and whose printed day is still before the expected one is the SP's lag (`afcCicPublisherLag`, the panel shows «Esperando publicación»), and it dims only from 18:00. Disabled when no account carries `fund_series_key = 'afc_cic'`; migration 182 rebuilt the CHECK-enumerated `account_sync_sources` with the value and declared the AFC account (`import:excel|key=afc`) on the series. **Valuation:** `isCuotaLedgerKindSlug` (afp | afc) covers every cuota-ledger branch — position meta (`getAccountPositionMeta`, ticker «AFC CIC»), historical marks (`accountMarkClpAtYmd`), today's live value (`accountTodayValue`: AFC reads its ledger BEFORE the stored rows — those are the pre-ledger benchmark, not a mark; AFP keeps stored-first because its sync stamps a today row from the same cuotas × px), chart live last points, perf cuota inflows, and the dashboard/detail overrides — with `cuotaLedgerSeriesKeyForAccount` resolving both from `accounts.fund_series_key` (an AFP account without one prices with `afp_uno_cuota_a`); an `afc` account WITHOUT a series key is not modeled in cuotas and keeps the plain stored-mark path (demo/CI). Manual AFC creates require `units_delta` (`movementUnitsPolicy`, unit «cuotas», reconciled against the series like AFP/Fintual), so the book-ledger edit is off for it. Full-history backfill: `npm run backfill:afc-cic -w nw-tracker-server`. The rates page has an «AFC CIC» chart (`market_display_series` builtin, rates only — the marquee renders a fixed set of fund chips).
- **The AFC ledger is rebuilt from the AFC documents, not derived (`afcCertImport.ts` on the server, ingest's `afc/documents.ts` reading the PDFs through `unemployment_fund.documents`; `npm run import:afc-cert -- --cert=<pdf> [--cartola=<pdf> …] [--replace-excel-rows] [--drop-ids=…] [--apply]`).** The AFC prints no cuotas anywhere, and none are needed: the CIC is valued at the SP valor cuota, each cotización is credited at the valor cuota of its **fecha de pago**, and the AFC's commission is deducted in cuotas (the one thing the SP series does not carry). So (1) the **certificado de cotizaciones previsionales acreditadas** (every cotización with período, empleador, monto, fecha de pago; two legs per período — trabajador 0,6 % + empleador 1,6 % — closed by a `TOTAL` line the parser must reproduce) becomes ONE movement per (período, pay date) with `units_delta = monto ÷ valor cuota(pay date)`, identity = note key `AFC cotización — período YYYY-MM (pago YYYY-MM-DD)` (idempotent re-imports; a changed printed amount is a `mismatch`, never overwritten); (2) withdrawals are priced at the valor cuota of their date, except one after which the account's own next stored valuation reads 0 with nothing else moving the ledger before it — that one **closes** with exactly the cuotas held; (3) each **estado cuatrimestral** yields a true-up per printed saldo: `units = saldo ÷ valor cuota(day) − ledger through the day`, `flow_kind = cash_fee` when the ledger sits above the saldo (the commission) or `savings_earnings` below — both are P/L to every deposit reader, never capital — refused when the period's cotizaciones in the ledger differ from the cartola's «Total de cotizaciones» (the certificate import is incomplete; a true-up must not absorb missing cotizaciones as «commission»), and closing withdrawals are re-measured after the true-ups. Without `--apply` the whole transaction is rolled back after printing, so the report IS the post-import ledger. The pesos ÷ valor cuota derivation script (`afc:derive-cuotas`) remains only as a benchmark tool for a ledger with no certificate.
- **Stale vs the publisher's lag.** `isFintualSyncStale` deliberately keeps the source stale while the cuota expected for a publish day has not appeared, so the scheduler keeps polling; `fintualPublisherLag` (`globalSyncStale.ts`) classifies a stale Fintual row as the PUBLISHER's lag when the last poll is recent (`PUBLISHER_LAG_MAX_POLL_AGE_MS`, two scheduler intervals — read from the goals snapshot's `fetchedAt`), nobody forced a run, the API's latest published day is behind the first expected publish day, and every held fund's bar for that published day is in the DB; anything else (sig mismatch, unreconciled positions, a missed poll) stays plain stale. The status row carries `publisher_lag {expected_ymd, published_ymd, last_checked_at}`; the sync panel shows «Esperando publicación» with the two dates and the last check instead of «Desactualizado». **The dimming list is `stale_dimming`** (`staleDimmingSources`; `dashboardAccounts` dims from it, `stale` itself is unchanged): our own staleness always dims, a publisher-lag source dims from **18:00 Chile** (`EVENING_PUBLISH_HOUR_CHILE` in `publisherSchedule.ts`, the one constant the stale rule, the schedule wake and the dim rule share) until the cuota is applied; before 18:00 — pre-open, the live proxy, the post-close hold — every Fintual account stays normal because the display holds all the publisher has. A value still missing at midnight stays overdue: a lag whose expected day is before today dims at any hour (every publisher-lag source, the AFP and the AFC included), until the value is applied. **A cuota already in hand needs no same-day poll:** Fintual forward-publishes a holiday block's flat carries, so on a publish day whose cuota is already applied (`fintualLastAppliedPublishYmd >= today`, signature unchanged, positions reconciled) `isFintualSyncStale` is false without a poll that day. In `syncSourceSchedule.ts` «fintual» the next wake is the first publish day whose 18:00 is still ahead (today before 18:00, else from tomorrow — a block-closing Sunday counts) and skips past an applied day; never jump to the publish day after the next one, since the scheduler sleeps until the earliest `next_sync` when nothing is stale and would miss that 18:00. The applied day is threaded in explicitly (`fintualNextSync(cl, appliedPublishYmd)` in `syncSourceSchedule.ts`, handed the state's `fintualLastAppliedPublishYmd` by the source's definition), never read from the state file inside the schedule, so the schedule stays a pure function of its inputs.
- **Fintual's closure day never moves the sync state backwards (`runFintual`).** When a poll reports a closure day older than `fintualLastAppliedPublishYmd` (2026-11-24 23:20: 11-22 after 11-23), that day's cuotas are written under it (the caches drop only when a value changed) and nothing else follows: the goals snapshot, `fintualLastPublishYmd`, the applied day and both signatures stay, since the settled, stale and reconcile checks read them. The source stays stale and keeps polling for the day it is waiting on; with no fresh snapshot the wait reads as our staleness, not «Esperando publicación», after 30 minutes.
- **A skipped Fintual day is a stand-in at the next value, healed from the public serie on any day (`fundUnitDaily.ts` `gapFill`, `fintual_official_serie`).** Fintual publishes day D's cuota the evening of D (the "D+1" rule is the public serie's), and over a weekend / holiday block a second value dated the block's LAST día inhábil, a few days of fee accrual below the last business day's. When the evening poll misses a day and the next poll finds only a later value, the gap days must not be copies of the PREVIOUS cuota (a carry would put the missed day's whole move into the next day's P/L). `upsertFundUnitSpotPreservingHistory` takes `gapFill: "stand_in_new"`: the Fintual path writes every skipped day at the NEW value as `fintual:stand-in|from=<observation day>` (a placeholder to `isFintualCarryForwardFundUnitNote`, never published, so the verifier replaces it unconditionally, the RN composition anchor skips it and the newest-bar check ignores it); other callers keep the carry (`fintual:carry-forward`). `fintual_official_serie` is its own sync source (the goals poll is not due on a weekend once the block value is applied): stale from 12:00 Chile, at most every 2 h (`fintualOfficialSerieLastCheckedAt`), while a mapped series holds a placeholder dated within the last 7 days and on or before yesterday; the goals poll's check stamps the same field so the two never run minutes apart. **Global sync waits for the network after a wake and retries (`schedulerKernel.ts`):** a suspend is measured from a late timer or wall-vs-monotonic clock divergence, a tick that follows one waits 10 s, and a failed post-wake sync is retried after 60 s and 180 s, the budget refilled by a success; a failure with no wake keeps the 15-minute poll.
- **Fintual valor cuota = Fintual's own share count, verified against the official serie.** The evening poll prices each goal's fund from the site's `/gql/` «latest accrued balance» queries (`clReserveLatestAccruedBalance` / `clApvAGoalLatestAccruedBalance` / `clApvBGoal…` / `clGoal…`, cookie-authed like `GET /api/goals`; builder + parser in `server/src/fintualRealAssetNav.ts`): `investmentClosureDate` is the publish day, `portfolioSharesBalance.sharesBreakdown[].sharesQuantity` is Fintual's share count (APV-A sums the user-owned and state-bonus portfolios), and valor cuota = ticker valuation ÷ those shares — **never ÷ the ledger's cuotas**, because the ledger lags Fintual whenever cash is in transit (a retiro sells cuotas days before the «Pagamos» mail lands the transfer on payday). The goals-API `nav` counts the payout (`reservePendingBalance.pendingPaymentWithdrawalsAmount`), so ledger cuotas × true price equals it by identity until payday, and `expectedGoalsApiNavClp` = shares + pending deposits + pending payouts is what a «mismatch» log line compares against. A goal with no Fintual price this poll (empty, or its closure day lags the publish day) writes **nothing** for its v2 account (`syncFintualFundUnitsFromResolutions` skips; no NAV ÷ cuotas inference for v2) and the missing-bar carry re-polls; a `/gql/` fetch or shape failure throws (never a guessed date or price); a goal holding several funds throws (one series per account). **Next-day verifier (`server/src/fintualPublicSeriePrice.ts`):** after every goals poll, `runFintualOfficialSeriesCheck` re-reads the last 14 days of the OFFICIAL public serie prices — `GET https://inversiones.fintual.com/api/managed_funds/serie/share_price?fund_serie=<id>&start_date&end_date`, no auth, history since inception, weekends included, publishes day D on D+1 so it can never serve the evening write — for every mapped series (`FINTUAL_PUBLIC_SERIE_BY_SERIES_KEY`: reserva2 → serie 1 Very Conservative Streep A, apv_a/apv_b → 7 Risky Norris APV, risky_norris → 6 Risky Norris A; ids from the fund-page bundle's `FINTUAL_MANAGED_FUNDS`): fills days no poll wrote (an EMPTY goal never publishes, so this keeps the RN-proxy anchor series current), replaces carry-forward placeholders, and **corrects** a published bar beyond `FINTUAL_PUBLIC_SERIE_TOLERANCE_REL` = 1e-4 — as a change line plus a **step error** («Errors:» in the sync log), because a correction means the evening derivation was wrong. Manual: `npm run fintual:backfill-cert-fund-units -w nw-tracker-server -- [--from=YYYY-MM-DD] [--series=…] [--apply]` (report-first). Provenance notes: `fintual:gql:shares-publish|<import notes>` (evening), `fintual:public-serie:publish|serie=<id>` (official), legacy `fintual:real_assets:publish`; `isFintualPublishedFundUnitNote` is the one predicate that protects them from carries and the unreconciled-inferred cleanup.

## Live market quotes (intraday)

- **Scheduler** (`server/src/liveMarketQuotesScheduler.ts`): polls Yahoo every **2 min** while a priced market is open and every **5 min** otherwise, on the wall clock (see «Polls follow the market clock»). HTTP handlers read **`live_market_quotes` only** — no on-demand Yahoo from client requests. The tick also runs `ensureWatchlistEquityHistoryDepth()` (watchlist.ts): `equity_daily` history to the watchlist YTD/YoY anchors (~400d) for watchlist + composite tickers, one Yahoo attempt per ticker per Chile day — `GET /api/watchlist` serves DB only and never fetches.
- **Prices come from Yahoo's price stream; the poll is the backstop (`yahooPriceStream.ts`, `yahooPricingData.ts`, `liveQuotesFlushPolicy.ts`).** The server (never the browser) keeps one socket to `wss://streamer.finance.yahoo.com/?version=2` (unofficial, no key) subscribed to the watchlist series keys plus every live exchange-rate pair's Yahoo symbol (`CLP=X`, `EURUSD=X`: `liveFxPairs`, see «Every core pair has a live rate»); frames are `{"type":"pricing","message":"<base64 protobuf PricingData>"}`, decoded by hand: field 1 id, 2 price (float32, rounded to the priceHint), 3 time (sint64 ms), 7 marketHours (plain enum — 6 and 7 are NOT zigzag: 0 pre, 1 regular, 2 post), 12 change (previous close = price − change; the stream sends no previous close for equities); every other field is skipped by wire type, and a frame without id / price / time throws and drops the socket. Only regular-session prints of today's session inside the readers' own gates are kept (`streamTickInSession`: NYSE / Santiago session, crypto always, an exchange rate while its fx day is open), so the post-close held print and the fx day end keep the poll's rules. **Write rule (user's choice): a flash is a real move** — each second, every unit whose price differs from what it last wrote and whose last write is ≥ 30 s old is written, several together when several moved, but never sooner than `LIVE_QUOTES_FLUSH_GAP_MS` (default 5 s; 15 s on the demo, `render.yaml`) after the previous write that moved something, since each one rebuilds the caches. A unit is a symbol, except the Risky Norris basket's ETFs, written together so the APV marks move once per interval. Writes go through `writeStreamQuotes` (`liveMarketQuotesSync.ts`): the poll's rows, change test, stamp and scoped invalidation. A symbol with a kept tick in the last 5 min is **covered**: the poll skips it (`liveStreamCoverage` → `syncAllLiveMarketQuotes(now, {skipTickers, skipLiveFxPairs})`) and the stream re-stamps its row every 3 min at the same price (no change, no invalidation) so the 10-min freshness window never lapses on a quiet `.SN` or the dollar; anything uncovered (a closed market, a quiet symbol, a dead socket) is the poll's. While connected the poll keeps the 5-min cadence in session too (the open tick stays). Reconnects back off 2 / 10 / 30 / 60 s; 3 min with no frame while a subscribed market trades closes the socket. The client polls the stamp every 5 s and refetches by `X-Live-Inputs` (see «Polls follow the market clock»). The hosted demo connects only while awake. `LIVE_QUOTES_STREAM_ENABLED=0` = polling only; `LIVE_QUOTES_STREAM_URL` overrides the endpoint.
- **Wake and wholesale-failure handling (`schedulerKernel.ts`).** A poll that fires an interval or more late (or after the wall clock ran ahead of the monotonic one) waits 10 s before fetching, because right after a wake the network is not back and every request fails. A poll where NO equity request succeeded (`tickFailedWholesale` — partial failures are Yahoo throttling and never retry; the fx leg is not consulted because its EOD fallback reports ok) retries after 15 s then 45 s: the budget refills only when a poll succeeds, so a continuous outage costs two extra attempts in total, a success cancels a pending retry, and a thrown sync (a bug, not the network) never retries.
- **Post-close hold + the mark date's fx frame (`equityHeldSessionQuote` in `equityQuote.ts`).** Between a session's close and the EOD sync landing its bar the live gate (`shouldUseLiveEquityQuote`) is off, so a session that has closed for the day (`equitySessionClosedForDay` — NYSE after 16:05 New York, Santiago after 17:05 Chile, never crypto) and has no bar yet **holds the session's last stored print** in `live_market_quotes` (Yahoo's `regularMarketPrice` re-serves the official close after the bell, so the print IS the close; freshness is not required, the session match is). Without it every reader falls to the PREVIOUS bar and reads a 0 day P/L until the EOD run. One choke point, consumed by the quote resolver (marquee/watchlist), `equityBrokeragePositionMeta` (dashboard rows) and `equityTodayNativeValue` through `holdingPriceAt` (today's marks). **Paired fx rule:** a today mark's fx is the mark date's rate through `rates.ts` (`convertValue`) in every branch — live CLP=X while the mark date's fx day is open (until 17:05 New York, `shouldUseLivePairQuote`), the stored close after — and `computeEquityMtmClp` converts at `asOfYmd` whatever the price source (a historical date never matches the live row's session, so it reads the stored row). Don't price today's bar at the stored row on or before today (`storedPairRate`): between the NYSE close and the fx day end that is the previous day's close, which re-frames every USD holding by the day's fx move. The dashboard row's value in another unit converts the native value by the same rule (`todayValueInUnit`). Pre-open: the prior bar at the prior day's stored fx (USD cash floats from Chile midnight, equities from the open — a known asymmetry, left as is).
- **Polls follow the market clock; the client refetches when prices move (`nextLiveQuotesTickAtMs`, `liveQuotesStamp.ts`).** Ticks sit on wall-clock multiples of the cadence (not a `setInterval` from boot, which leaves minutes of each session's start on yesterday's close) — **`LIVE_QUOTES_SESSION_INTERVAL_MS` (default 2 min) while a market the watchlist prices is in its regular session** (NYSE, Santiago; crypto keeps the base), `LIVE_QUOTES_INTERVAL_MS` otherwise — and each open minute gets its own tick 20 s later (`OPEN_TICK_DELAY_MS`). **A moved price is rebuilt on demand, and the client refetches only what read it:** a write that moves a price (stream or poll) publishes the live-quotes stamp at once and logs what moved (`noteLiveQuotesChanged(at, {tickers, fx, dimming, all})`, `fx` the pair keys that moved, a 500-entry log); the warmer does not react to `live_tail` (that would rebuild mostly what nobody looks at), so the first request that needs a dropped response rebuilds it on top of the cached history. `GET /api/live-quotes/stamp?since=<stamp>` answers `{stamp, moves}` — the union of what moved after `since`, `all` when the log cannot tell (a `since` from before this process or before the log's oldest entry). Every GET API response carries **`X-Live-Inputs`** (`liveInputsHeader.ts`): the request runs in its own dependency node (`cacheDependencies.ts`; cache and live-tier hits link their entry's node, so a cached response names the same inputs as its build) and the header lists the tickers whose live quote it read plus one token per live rate (`$fx` = USD/CLP, `$fx:EUR_USD` any other pair) and `$dimming`, or `none`. The client keeps the inputs on each payload under a non-enumerable symbol (`client/src/liveInputs.ts`; `j()` attaches them, a default `structuralSharing` keeps them) and `useLiveQuotesStampInvalidation` (polled every 5 s while the tab is visible) invalidates only the queries whose inputs meet the moves; a payload with no inputs (a scalar, no header) refetches on every move. A response reads live prices only where it shows them: group-page line and row order is by **yesterday's close**, not today's value (`sortNavNodesByMarkDesc`, `orderGroupTabRowsBucketMajor` — an order read live would put every price into the sidebar and the flows lists; it holds for the day), and the account page bundle builds only its own dashboard row (`buildDashboardAccountRow`), not the whole listing. So the sidebar, messages, reminders, benchmark list and flows lists answer `none` and never refetch on a price move, and a stock or coin page refetches only for its own ticker, the dollar and the sync dimming. To see where a response reads live prices, record the stack of each `noteLive*Read` call while building it.
- **A tick drops only what read a moved price (`cacheDependencies.ts`; the store is `cacheRegistry.ts`, see `docs/cache-registry.md`).** Every aggregation-cache entry and live-tier memo builds inside a dependency node that records the live inputs it read — a ticker (the live-quote row readers and the gates that decide whether to read them: `shouldUseLiveEquityQuote`, `equityHeldSessionQuote`, `getLatestLiveEquityQuoteRow`) or a live exchange rate by its pair key (`noteLiveFxRead("USD_CLP")`: `shouldUseLivePairQuote`, the live fx row, the observado window average; `EUR_USD` the same way); a lookup links the entry's node into whatever is built around it, hit or miss. The poll passes what moved (`publishLiveInputChange` / `invalidateMarketDataAggregations("live_tail", moves)`): among the entries an unscoped tick drops, only those that read a moved price, or whose inputs are unknown, go. A poll that also wrote the day's `fx_daily` close drops everything a tick can reach. A new reader of `live_market_quotes` must report through those functions. **So must every switch decided by the clock or the sync state** — a session, a publish hour, a holiday hold, a settled cuota: it reports what it would read whatever it decides (e.g. the Risky Norris proxy gate `shouldUseRiskyNorrisProxyMtm` reports the basket and the dollar), or entries cached before the switch survive every tick and read 0 day P/L. Two inputs that are not prices: the dashboard's sync dimming (`stale_dimming`, turning at 18:00 Chile) is reported with `noteSyncDimmingRead` and dropped when the dimmed set changes (`syncDimmingWatch.ts`, checked on every live-quotes tick, which also publishes the refetch stamp); and a global sync run whose Fintual poll changes the sync-state fields valuation reads without writing a row clears the caches after saving (`fintualValuationStateFingerprint`). A process-lifetime memo of database state belongs in `dbStateMemo`, never a plain Map. **Inside a transaction the memo is the transaction's own:** an entry lives while the transaction does (`dbTransactionEpoch` in `db.ts` moves when an outermost transaction begins or ends, when any transaction function throws — its savepoint rolled back — and on every `exec`) and until the change log records a write of a logged table (`mark_input_changes`, which the triggers fill inside the transaction too; a write that changes no logged row keeps it). Without it, ingest handlers (which run inside the receiver's transaction) rebuild the nav-tree model on every expense-line build, costing minutes per request. Chart-inactive (`accountChartInactive`) reads no price at all: an account valued from units (shares, coins, cuotas), a dollar account or a peso ledger (checking, a broker's peso balance, a portfolio caja) is inactive when its ledger holds none today; only the other accounts (the property, the mortgage, stored marks) read their month closes. An empty position reads no quote either: today's mark of a stock with no shares, or a coin account with no coins, is its sold-out 0, and the stock's position (`equityBrokeragePositionMeta`) carries no mark, all from the quantity alone, so their pages do not drop on their ticker's tick. Parity: `liveTickIncrementalRebuild.test.ts`, `cacheDependencies.test.ts`.
- **Response caches beside the bundle (families in `cacheFamilies.ts`).** The card ledgers (`cc.ledger|`, per card and per group), an account page's bundle, a group page's valuation / tables / monthly P/L / Rentabilidad (`dashboard.page_bundle|account_detail|`, `…|group|`), the dashboard account rows (`…|account_rows|`, shared by the home bundle, the nav snapshot and the account bundle) and a group's daily-series response (`daily.series|response|group|`) are cached; every API write drops them too (`index.ts`, request kinds `api-write` / `machine`), since labels, notes and card config sit beside the logged tables. The group endpoints share one consolidation per (group, unit, account set) (`groupConsolidatedMonthlyRaw`). The card page payload carries no statements with their lines, stored balance snapshot, per-purchase proxy or per-purchase payment rows (the page draws none of them). The warmer rebuilds the pages the usage log says are opened, most visited first (`visitedPagesWarm.ts`).

- **Cache invalidation (F2; `docs/cache-registry.md` is the full account).** One store (`cacheRegistry.ts`), every key in a family declared once in `cacheFamilies.ts`, one write signal: triggers log every change of a logged table, from any connection, into `mark_input_changes` (`markInputTriggers.ts`: `mark` rows carry the account and raw date a historical mark reads, `write` rows any other change; a table in neither list fails `cacheRegistry.test.ts`). The registry applies the log before a cached read, after every API write and on the warmer's poll; mark rows trim the per-account mark series (`markSeriesStore.ts`) and each family drops what read the change (a family declaring `marketReads` ignores the market tables it does not list: a close never drops the flows inputs). Market writers of this process add a notice (`invalidateMarketDataAggregations`), so same-connection sync writes, which do not bump `data_version`, still reach the caches; a value no table holds (the live dollar rate the expense lines priced unpaid dollars at) is a declared input (`dropFamiliesWhenInputChanged`). A new cache is a family plus a key builder built through `getAggregationCached` — no invalidation call anywhere; a new table is a migration adding its triggers.
- **Risky Norris proxy MTM is framed on the NYSE session day, never the Chile calendar day (`riskyNorrisProxyMtm.ts`).** The RN / APV Fintual accounts value today through the live/EOD basket proxy (`shouldUseRiskyNorrisProxyMtm`) from the NYSE open until the Fintual evening sync settles the cuota that reflects that session, then read the official cuota until the next open. "Settled" is asked about `nyseWallClock(now).ymd` (`fintualGlobalSyncSettledForChileDay`), and the Chile-holiday hold classifies that same session day: Chile runs 0–2 h ahead of New York depending on the two DST calendars, so between Chile midnight and New York midnight the Chile day has rolled while the settled session has not — asking "settled for Chile today" there re-arms the proxy for the gap. **The pending-cuota hold keeps a session's close until the cuota that reflects it is in the database (`sessionCuotaPending`):** a session's cuota day is the session day itself when Chile worked that day, else the next Chile business day (Fintual prints flat carries for a non-business block), and the cuota is pending while the series' latest PUBLISHED row (`latestPublishedFintualCuotaDay`, never a carry or a stand-in) is dated before it. `inPendingCuotaProxyHold(series, now)` asks that of the session the proxy is holding (today's once open, else the previous NYSE session) and is consulted before the trading-day gate: a Friday holiday keeps Friday's close on screen through the weekend and Monday pre-open, then Monday's live session, then Monday's cuota; a business day whose cuota is late (2026-11-24: none by midnight) keeps its close past New York midnight and through the next morning. A normal weekend after a published Friday never holds. **The hold is per DATE, not just today:** `riskyNorrisProxyAppliesOnYmd(series, ymd)` applies the same test to the NYSE session on or before a historical date, and `getAccountPositionMeta` / `fundPriceAt` then value that date through `riskyNorrisProxyCuotaForMtm(series, now, asOfYmd)`, which carries the value on the SESSION the date reflects (live session, else the held one — never the calendar day), so every day of a held block values identically and its «Día» P/L is 0 by construction; without it the next day reads the held proxy against a bar that never saw the session and shows the move a second time, under the wrong day. When the cuota is written the predicate turns off and the dates read the official bars — the row's insert trims the marks from its day and the apply's `invalidateMarketDataAggregations` drops the rest. **The test reads the series' own rows, never the sync state:** `fintualLastAppliedPublishYmd` follows whatever closure date the last poll reported (Fintual reported 11-22 after 11-23 on 2026-11-24 23:20), and `fintualGlobalSyncSettledForChileDay` also asks whether TODAY's positions reconcile with the last poll's NAV (false for hours whenever cash is in transit, which once valued every historical Chile holiday through today's basket — a 500 where a basket ETF had no bar that far back). A series with no published row at all (demo data) has nothing pending; a later published cuota closes every earlier session, so a day Fintual skipped keeps its stand-in until the official serie replaces it. **The proxy's fx leg is the dólar observado frame (`fxObservadoFrame.ts`)**, because Fintual values day D with day D's US closes and day D's CHILEAN INTERBANK fx — the Banco Central observado published on D+1 (`fx_daily_bcentral` is keyed by publication date), an average of trades in a market that closes 14:00 Chile — and Yahoo's 17:05-New-York CLP=X close tracks it worse (late-afternoon peso moves enter the proxy one day and leave the next). `proxyClpFromMeta` resolves BOTH fx legs (composition_date anchor and valuation day) through `observadoFrameFxForDay`: the first observado row dated after the day (a gap wider than 7 days throws); while that publication is pending (today, or yesterday before the 18:00 `sbif_usd` sync) the running average of the live CLP=X prints inside the 09:00–14:00 Chile window (≥3 prints), else the frame's most recent observation on an earlier day — yesterday's window estimate while its publication is pending too, else the last published observado (never carry the last PUBLISHED row past a pending estimate: it pairs today's basket with an interbank fx two sessions old); a head older than 7 days throws (stale sync). `anchor_fx_clp` on `watchlist_composite_meta` is informational (the frame value at sync time). **The composition anchor is the cuota's own session, never Fintual's positions date (`resolveCompositionAnchor` in `fintualRiskyNorrisComposition.ts`)**, because the basket's price base and the cuota must belong to the same session: the anchor day is the latest Chile business day on or before the positions date carrying a published (non-carry-forward) Risky Norris cuota, the APV cuota must exist on that exact day (an APV serie that exists but lacks it throws; only a serie absent altogether yields null), and `composition_date` IS that day, so `basketReturnForHoldings` / `observadoFrameFxForDay` resolve on the session the cuota embeds. **The sync refreshes serie 6 and serie 7 from the official public prices first** (`RN_COMPOSITION_REFRESH_SERIES_KEYS`, the same verifier the Fintual poll runs), since the empty RN goal never publishes in the evening poll, and runs **once per slot — 10:00, 12:00, 15:00 and 18:30 Chile — on Chile business days and the day after one** (`rnCompositionSlots.ts`: `FINTUAL_RN_COMPOSITION_SLOTS_CHILE`, `isFintualRnCompositionDueDay`; a Friday's cuota publishes on Saturday, a Sunday brings nothing; the state stamps the slot served, `fintualRnCompositionLastSlot`, and a missed slot is one run, never a catch-up per slot). The extra slots measure when Fintual publishes (each run logs «as of <positions date>, anchored <day>»; a run that finds nothing new re-anchors on the same day, which changes nothing); trim them once the log shows which ones find something new. **Self-check on every run** (`compositionSelfCheck`): the previous anchor's EOD prediction for the new anchor day vs the official cuota, as a step note, and a step error beyond `RN_COMPOSITION_SELF_CHECK_ERROR_BP` = 40 bp. The anchor only sets the proxy's level; its day change cancels it in the ratio. The live USD/CLP rate / `fx_daily` (through `rates.ts`) stay the frame for every USD cash/equity account — only the RN/APV proxy embeds the observado.
- **The proxy basket is kept per Fintual positions date (migration 238, `watchlistCompositeHistory.ts`).** `watchlist_composite_meta` / `_holdings` carry only the latest basket (delete + insert on every sync); `watchlist_composite_positions` (+ `_position_holdings`) holds one basket per (bucket, positions date — Fintual's «as of», the holdings' `synced_at`) in **Fintual's own tickers** (`holdingsAsStated`; the SPXS → SPY price mapping is pricing only — Fintual's SPXS is the Invesco S&P 500 UCITS ETF, the fund holds no real SPY), write-once through `recordCompositePositions`: a repeat statement is `unchanged`, the same positions date with other weights a `conflict` — the sync keeps the first statement, still re-anchors on the new one, and logs a step error; the sync's note names what entered and left against the latest recorded basket, and the change line compares holding counts. Nothing on a request path reads it. Older history recovered from DB snapshots by `server/scripts/backfill-rn-composition-history.ts` (report-first, `--apply`; `source = 'snapshot'`; opens each snapshot through the `sqlite3` CLI with `immutable=1`, because better-sqlite3 cannot open a WAL snapshot read-only). **Before the sync existed the record is the regulator's (migration 239, `cmfFundPortfolio.ts`, `server/scripts/import-cmf-rn-composition.ts`):** the CMF's monthly «Cartera de inversiones extranjeras» of every fondo mutuo (`ffm_cartera.php` → `ffm_download.php`, `cartera=EXTR`, file `FFM_INV_EXTR_YYYYMM.txt`, columns per Circular 1333; Risky Norris is RUN 9570 «NORRIS») lists each holding's nemotécnico («SPXS LN», «FTEC US») and its share of fund assets (the last column). The importer (`--fetch` downloads the months missing under `cfraser/cmf-ffm-cartera/`, report-first, `--apply`) records one `source = 'cmf'` basket per month-end — weights renormalized to the foreign-ETF sleeve, `etf_weight_sum` = the sleeve's share of assets — and leaves a date Fintual already stated alone. **The filing is also a nightly cross-check (`cmf_rn_portfolio` global-sync source, `cmfRnPortfolioSync.ts`):** from 09:00 Chile, once a day while the previous calendar month's filing is not on record (`cmfRnPortfolioLastMonth` / `cmfRnPortfolioLastCheckYmd` in the sync state; the first run reads the latest `cmf` month from the history), the sync asks the CMF for it, records it as a `cmf` basket (kept out when Fintual stated that very day) and saves the raw file under `cfraser/cmf-ffm-cartera/`, then compares it with the latest Fintual-stated basket of the fortnight before the month-end: a ticker one side lacks, or a weight more than 3 points apart (`CMF_RN_CROSS_CHECK_WEIGHT_ALARM`), is a step error, the gap otherwise a note. A month the CMF has not published yet is a note («not published yet»), retried the next day.
- **USD/CLP floats on the forex calendar (`forexDay.ts`).** Yahoo **`CLP=X`** is fetched by every live-quotes tick while the **fx day is open — a weekday before 17:05 New York**, US and Chilean holidays included — and every CLP↔USD reader for today goes through `rates.ts` (live while `shouldUseLivePairQuote`, `fxLive.ts`), so USD holdings move with the rate from Chile midnight to the New York close. At the day end the first closed tick writes the day's close into **`fx_daily`** from the same quote the readers froze on (`catchUpFxDailyIfMissingDueSession` → `syncYahooFxUsdFromYahoo`; the `yahoo_fx_usd` source is the nightly backstop, due at the same instant with carry-over), and **rows are write-once** (`insertFxRowsIfMissing`): Yahoo's daily bars — whose close is the London-midnight open, not the day's last print, and which disagree with its intraday feed — only fill days never observed and never revise a row, so yesterday's P/L does not move overnight. **Weekends read Friday's close**: no Saturday/Sunday rows (Yahoo labels its Monday week-open bar by the New York date of the bar start, i.e. Sunday — the ingest skips weekend dates, because Sunday rows would put weekend news moves into Sunday-dated month-ends). Banco Central dólar observado is stored separately in **`fx_daily_bcentral`** (reference only; synced by `sbif_usd` from 18:00 Chile). Backfill (gap-filler, existing rows kept): `npm run backfill:yahoo-fx-usd -w nw-tracker-server`; `npm run backfill:sbif-fx-eur -w nw-tracker-server` (BCentral reference + EUR).
- **Every core pair has a live rate (migration 323, `fxLive.ts`, docs/any-currency-plan.md C6).** A live pair is USD/CLP plus every core currency `currencies` loads from a Yahoo pair (`yahoo_pair_symbol`: EUR/USD from `EURUSD=X`), listed by `liveFxPairs()` and named by its pair key `<BASE>_<QUOTE>` (`USD_CLP`, `EUR_USD`): its `live_market_quotes` symbol (kind `fx`, value = quote units per base unit), its dependency token (`noteLiveFxRead(key)`) and its `X-Live-Inputs` token (`$fx` for USD/CLP, `$fx:EUR_USD`). **One session for every pair: the forex day of `forexDay.ts`** (a weekday, Chile calendar, before 17:05 New York) — EUR/USD trades round the clock on weekdays, but the day the app values is the one the dollar's fx day frames, so a euro and a dollar figure built at the same instant read rates of the same day. The poll fetches each pair while it is open (`fetchYahooLivePairRate`; skipped when the stream covers it, `skipLiveFxPairs`), the stream subscribes to each pair's Yahoo symbol under the same gate and coverage / re-stamp rules (`liveStreamCoverage().fxPairs`), and the first closed tick writes a pair's day close into `fx_rates` from the last live rate of that session (`writeLivePairDayCloseIfMissing`, source `live:EURUSD=X`, write-once like `fx_daily`; dated the Chile day, which is the London day at 17:05 New York, so the London-midnight Yahoo bar of `fx_pairs` finds the day stored and keeps it; a session with no live row is left to that bar). A day close drops everything a tick can reach, as the `fx_daily` close does. `rates.ts` reads a pair's live rate for today exactly as USD/CLP's (`livePairRateForDay`, fresh row, session on or before the date, else the stored close); a FLOW of today converts at the stored rate (`convertFlow` passes `storedOnly`), as pesos → dollars at the stored buy rate does, so the daily series' past part (a history-tier value, which must read no live input) stays live-free in EUR. **EUR/CLP today:** Banco Central's `eur_daily` carries no quote of today until it is published, so while EUR/USD has a quote dated today (live, or the written close) today's EUR/CLP is EUR/USD × USD/CLP of today (a mid; reported as both pairs); without one it reads `eur_daily` as every past day does.
