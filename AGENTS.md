## Language and i18n

- **UI copy via i18n (es + en)**: all user-facing strings live in **`client/src/i18n/master.json`** — the single source of truth, nested like the locale files, every leaf holding both languages: `{ "en": "Save", "es": "Guardar" }`. `locales/es.json` / `locales/en.json` are **generated** by `npm run i18n:generate -w nw-tracker-client` (`client/scripts/i18n-generate.mjs`); never hand-edit them — `client/src/i18n/localeSync.test.ts` fails on drift. The master stays nested because some leaf keys contain literal dots (e.g. `panelAccounts.addAccount."accountType.equity"`). No hardcoded Spanish or English labels in components except via `t('…')` / `i18n.t('…')`.
- **Translation keys in English**: dotted paths such as `dashboard.cards.netWorth`, `brokerage.groups.mutual_funds`. Code identifiers use English slugs (`mutual_funds`, `real_estate`); display copy lives in `master.json`.
- **Shared labels**: use helpers in `client/src/i18n/index.ts` (e.g. `ccExpenseCategoryLabel`, `flowsPlBucketLabel`; a nav node's label is the server's, resolved with `resolveNavTreeLabel`) so sidebar, cards and charts read the same keys.
- When adding UI text, add the key (both languages) to `master.json` first, run `npm run i18n:generate -w nw-tracker-client`, then reference it. Migrate hardcoded strings when touching an area.
- **UI language preference**: `client/src/languagePreference.ts` (localStorage `nw-tracker.language`), seeded once from `navigator.language` (Spanish → `es`, else `en`; non-browser/vitest contexts stay `es` so label assertions are deterministic), then the stored value is authoritative. Changed from `/panel/settings` via `DisplayPreferencesContext.setLanguage` (calls `i18n.changeLanguage`, persists, syncs `<html lang>`; re-renders `AppTree` top-down). The decimal separator is an independent setting. **Do not cache `t()` results** in `useMemo`/state without the language in the deps — translate at render time.
- **Dates**: numeric dates render as ISO `YYYY-MM-DD` (timestamps `YYYY-MM-DD HH:MM`) in every language — never `dd-mm-yy` / `toLocale*` short styles. Month-name labels (`dic 2026` ↔ `Dec 2026`, ticks `dic 16` ↔ `Dec 16`) go through `client/src/formatDateLabel.ts`, which reads `i18n.language` at call time — same no-caching rule as `t()`.
- **Enforced by `npm run check:conventions`** (root; also runs at the end of root `npm run typecheck`): flags accented Spanish in client string literals/JSX (comments exempt), `Intl.NumberFormat` outside `format.ts`, hardcoded-locale `toLocaleString` without date options, month-name tables outside `formatDateLabel.ts`, `isFetching` / `isRefetching` in `client/src/components` / `pages` (see «Loading states»), and ticker-suffix parsing (`.endsWith(".SN")`, `lastIndexOf(".")` on a ticker, `\.SN$` regexes, `LIKE '%.SN'`) in `server/src` / `client/src` / `ingest/src` outside `server/src/priceProviders/` (see «Instrument registry and price providers»). It also flags currency hardcoding (docs/any-currency-plan.md): `formatClp` / `formatUsd` (and `formatClpUfDay`, `formatUsdFine`) in `client/src/components` / `pages`, a unit or currency compared with a literal code, fixed currency lists and `"clp" | "usd"` unions outside `rates.ts` / `valueConvert.ts` / `displayUnits.ts`, and `_clp` / `_usd` / `_eur` keys in `server/contracts/src/dto`; every hit fails unless its line says why the currency is native to its source (`// convention-ok: <reason>`: an F22 figure is pesos by law, a Santander feed has a peso and a dollar side, a card's billing frame is pesos), and a migration above 312 with `CHECK (… IN ('clp' …))` fails outright (reference `currencies(code)`). There is no ratchet baseline. «Is this pesos?» is `isHomeCurrency` (`HOME_CURRENCY` in the contracts' `dto/apiConstants.ts`, re-exported by the server's `displayUnits.ts`); a client figure one currency by nature formats through its named wrapper in `client/src/formatNative.ts` (`formatF22Pesos`, `formatCardBillingPesos`, `formatBillPesos`, …), a display-unit value through `formatMoney` / `formatCurrency`. Escape hatch: `// convention-ok: <reason>` on the line.
- **Dependency guard, also in `npm run check:conventions`** (`scripts/check-deps.mjs`, baseline `scripts/check-deps.baseline.json`). Builds the TypeScript import graph of `server/src`, `client/src`, `ingest/src` and `server/contracts/src` (tests excluded, type-only imports counted, `.js` resolved to `.ts`/`.tsx`, `nw-tracker-contracts` to its `index.ts`) and fails when a file joins an import cycle the baseline does not list, when a new edge crosses a forbidden boundary (contracts → server/client/ingest, client ↔ server, ingest ↔ server: `server/contracts` is the only shared code), or when `cacheRegistry.ts` imports a module it did not. Prints the largest cycle, the edge count vs the baseline and the top fan-in, fan-out and transitive-reach files. Cycles may only shrink: after a change that shrinks them, `node scripts/check-deps.mjs --write-baseline` locks it in (docs/untangle-plan.md F1). Shared formats (numbers, dd/mm and ISO days, day arithmetic, year-months and Spanish month names, accent folding, RUT and account numbers, merchant text, the zod building blocks) live in `server/contracts/src/formats/`, each rule pinned by a case file in `server/contracts/data/` (`npm run test -w nw-tracker-contracts`); the Python parsers assert the same files.
- **Number formatting**: all numbers (CLP, USD, UF, units, percents) share one decimal-separator convention from `client/src/numberFormatPreference.ts` (localStorage `nw-tracker.decimalSeparator`, seeded from the IANA timezone; toolbar toggle overrides). Always format via `client/src/format.ts` helpers — never `Intl.NumberFormat` / `toLocaleString` with a hardcoded locale for numbers. A separator change re-renders (not remounts) via `AppTree`; **do not cache formatted strings** in `useMemo`/state unless `decimalSeparator` is in the deps — memoize raw numbers, format at render. **Typed numbers:** every number field reads through `parseNumberInput` / `parseNumberInputOrThrow` (format.ts). A number that fits one convention is read that way («1500,5», «1.500.000», «1,234.56»); only a single mark followed by exactly three digits («1.500») is decided by the setting (1500 with comma decimals, 1.5 with period decimals); anything else is rejected with `common.numberInvalid`; forms keep their own sign/range/integer rules. Prefills and placeholders use `formatNumberInput`. Never `Number()` / `parseFloat` / `.replace(/\./g, "")` on typed text, and no `type="number"` inputs (the browser parses those by its own locale). The flows amount filter (`flowsAmountFilter.ts`) also takes an amount copied from the table: a leading `$` / `US$` and the negative «($500)».

A definitionally-CLP DTO field like `value_clp` is fine; the target is DB storage and parallel `_clp`/`_usd` branches. Precedent: `equity_daily` / `live_market_quotes` (migration 152) — select `value` + `currency`, **throw on unexpected currency**. Migrate opportunistically; no big-bang renames.

## An account's value: what it holds, converted once (`docs/holdings-currency-plan.md`, `accountValue.ts`, `holdingPrices.ts`, `valueConvert.ts`, `rates.ts`)

- **Value at a date = quantity of what the account holds, converted ONCE into the display unit.** `accountHolding(id)` (`holdings.ts`): a currency (pesos, dollars; property and mortgage in UF), a stock (quote currency), a coin (dollar price series), fund cuotas (peso-priced) or a card. `accountHoldingQtyAt(id, ymd)` = quantity; `holdingPriceAt(instrument, ymd)` = unit price in its quote currency (past day: stored observation on/before, history tier; today: live quote in session, held print after close, display-session bar, newest bar; a fund's live/per-date Risky Norris proxy); `accountValueAt(id, ymd, unit)` = qty × price → `convertValue` (`valueConvert.ts` over `rates.ts`). Never build pesos and convert back. Historical stack `accountHistoricalQtyMark` (`accountMarkClpAtYmd.ts`: branches return quantities; an instrument is the asset only on days its price is on file, else fall through); `accountMarkClpAtYmd` = that in pesos.
- **Spread side = what closes the position.** Assets: foreign → CLP at bid, CLP → foreign at ask; liabilities flip (`holdingIsDebt`). UF and EUR have no spread. Stored days read `fx_daily` with bid/ask observed that day or later, else mid ∓ half `FX_BID_ASK_SPREAD_CLP`. Flows convert per event at the mid (`flowEventInUnit`, `convertTs`, `clpToUnitAtMid`), as do benchmark levels.
- **Today reads the live rate** (USD/CLP while the fx day is open, `fxForLiveMtm` in `rates.ts`). `accountTodayValue(id, slug, opts, now) → {value_clp, native_value, native_currency, side, as_of_date, priced_on}` is the one today value (dashboard row, header, today's mark, perf live row, every chart live point); other units convert the NATIVE value with `todayValueInUnit(id, v, unit)`. `priced_on` is informational only.
- **`accountValueClpToUnitAt(id, clp, ymd, unit)`** converts a peso-native account value at the account's side and re-reads a value native in another currency (`accountValueCurrency`) from its holding. `clpToUnitAt(clp, ymd, unit, {side})` is for amounts that aren't one account's value (cards netted from cash, liability totals at `side: "debt"`). Bucket/net-worth sums in a unit = Σ each account's value in that unit per day (`buildDashboardBucketDailySeriesInUnit`, daily series, overview, ATH) — never Σ pesos ÷ one rate.
- **A card's value in a unit goes through one seam, `cardValueInUnit.ts`** (owed walk in pesos at the debt side); the card phase will replace it with per-currency sub-balances. The property and mortgage are still the depto ledger's pesos (peso quantities) until the loan phase.
- **Stored valuations are in any currency (migration 260, `valuationValue.ts`).** A `valuations` row is a quantity in `currency` (any lowercase code). Generic readers convert once on the row's date at the account's side (`storedValuationInUnit`: `valuationLatest.ts`, `bookValuations.ts`, `valuationTimeseries.ts`); the historical stack (`accountMarkClpAtYmd.ts`) carries book marks in pesos, so a non-peso book mark with a carry window throws. Kind-specific readers assert their currency (`assertValuationCurrency`: card CLP anchors, AFP/Fintual peso marks). Property rows are UF appraisals, left out by every mark reader (`valuationsAreAppraisals`); the mortgage has none (migration 261; the depto ledger values it, and property/mortgage chart month-ends come from the ledger, `augmentChartDatesForDeptoAccounts`). `GET /api/accounts/:id/valuations` returns `value` + `currency`; `POST` writes pesos and refuses a property.
- **The daily cache stores quantities** (`markSeriesStore.ts` cells `{qty, asset}`); unit values are built at read from memoized day price and rate (`accountValueSeriesOnGrid`), one series for every unit. Rate rows (`fx_daily`, `fx_daily_bid_ask`, `uf_daily`) trim only accounts whose quantity is a rate-built peso figure (cards — from the row's own day —, the depto ledger, book marks), never shares, coins, cuotas or dollar ledgers (`setRateIndependentAccountsResolver`). Price rows (`equity_daily`, `fund_unit_daily`) trim their holders (which asset a day holds depends on price availability).

## Data provenance (`DataOrigin`)

API payloads must **not** use top-level `source: "db"` / `"csv"` — the client always reads SQLite. Provenance describes how data entered:

| Layer | Field | Examples |
|-------|--------|----------|
| Account | `accounts.import_key` (identity; `notes` = same string as human provenance) | `import:excel|key=mortgage`, `credit_card_master|santander|<last4>`, `import:panel|ticker=QQQ|key=…` |
| Row | DTO `origin` | `import_document`, `manual` (from `cc_installment_purchases.source`: `pdf` → `import_document`) |
| Market data | (future) | `api_sync` / `api_yahoo` for `equity_daily` |

## Import sources vs runtime

**Rule:** files under `cfraser/` are **import inputs only**. HTTP, dashboard, valuation, and sync read **SQLite**; missing data → error or “run import”, not a silent file fallback.

- **Depto:** one movement ledger per property (`loadDeptoLedgerForProperty(id)`, cached `depto.ledger|rows|<property id>`; `deptoLedgerForAccount` / `deptoLedgerForLoan` / `loadAllDeptoLedgers`). Pairs come from `propertyLoanPairs()` (`accountRoles.ts`: a `property` role holder and its `loan_of` account); extra properties are `import:property|key=<k>` / `import:loan|property=<k>` (`propertyAccountImportKey` / `loanAccountImportKey`; migration 299's triggers seed the roles). Every reader («Próximos pagos», valor/hipoteca overlays, mortgage sections, card pairing, real-estate mortgage rows) loops over the pairs; the lender portal reading names its loan by `lender_pattern`. The ledger joins property-account movements with **`loan_payments`** (migration 258; docs/holdings-currency-plan.md phase 4): one row per payment movement, `leg` `property` | `loan`, `loan_account_id`, cuota, origin, and the bank's figures in its own currency — `balance_after`, `min_payment`, `max_payment` in `loan_currency` (UF); `principal`, `extra_principal`, `interest`, `insurance_fire`, `insurance_life` in `payment_currency` (pesos); readers throw on any other pair. Nothing derived is stored (parts' UF = pesos ÷ UF día, 4 decimals, the pago 5; net equity; `pagado_neto_uf`; `pago_acumulado_clp`; deltas/acumulados are computed from `uf_daily`). The appraisal is a **`valuations` row of the property account in UF**, forward-filled by the ledger; a property's valuations are its appraisals (`valuationsAreAppraisals`, `valuationValue.ts`), so generic mark readers skip them and its chart samples month-ends from its first ledger row (`augmentChartDatesForPropertyAccounts`); its value is net equity (`deptoNetEquityUfBySnapshotDates`). Rows are **sequential daily balances**: order = `deptoLedgerChronoCompare` (date, then decreasing crédito restante for same-day prepago+cuota); `assertDeptoPrepagoSequencing` fails when a prepago raises the balance (regular cuotas may: grace-period capitalization); snapshot fills use exact-date cutoffs with prepagos included — never a month-end cutoff expansion or a prepago skip (one-day equity spikes, ± P/L couplets). `mortgagePaymentCreate` writes the movements (human notes, mortgage `flow_kind`) plus both `loan_payments` rows; manual-payment recompute updates in place. No `depto_snapshot`: the RE card synthesizes valor/hipoteca from the property + mortgage rows.
- **Account identity:** `accounts.import_key` (unique, nullable; migration 159) is the find-or-create key and well-known lookup (`import:excel|key=mortgage`, `import:fintual|cert|key=…`, `credit_card_master|<issuer>|<last4>`, `import:panel|…`); every creator writes it; `notes` holds the same string for humans, never read by code. Card→account resolution uses `credit_card_account_config.card_last4` (every master has a config row).

Runtime code must not use `fs.readFile*` / `readSemicolonCsv` on `cfraser/` except in `server/scripts/` and import helpers. Import-sync document coverage (`GET /api/import-sync/…`) may list files for admin tooling only.

## Server runtime modes (local vs hosted demo)

One binary, env-driven (`server/src/httpSecurity.ts`, root `.env` loaded at boot):

- **The primary runs as LaunchAgent `com.user.nw-tracker-server`** (`server/com.user.nw-tracker-server.plist`, installed by `server/scripts/install-server-agent.sh`, which refuses while the port is taken): `tsx src/index.ts` without watch, KeepAlive, log `cfraser/server.log`. Restart: `launchctl kickstart -k gui/$(id -u)/com.user.nw-tracker-server` (alias `nw-server-restart` bootstraps it if unloaded). Its scheduler owns the nightly ingest runs (`docs/ingest-split-plan.md`), so it must not depend on a terminal.
- **The primary is a home server deploying from GitHub `main`** (`scripts/server-deploy.sh`, agent `com.user.nw-tracker-deploy` via `scripts/install-deploy-agent.sh`). An always-on Intel MacBook Pro (`pmset disablesleep`) runs server and ingest service; the laptop runs no agents and no live DB (dev servers use test/demo data or a snapshot copy with `BACKGROUND_JOBS_ENABLED=0`). Every 3 min the agent fetches `origin/main`; on a move it enqueues a `deploy` job (see «The job queue»; one queued, moved to the newest commit) and polls its claim ~150 s, else leaves it for the next run (stale after 15 min, so a dead agent can't drain the queue forever). The claim needs nothing else running (`server-restart`): in-flight ingest finishes, nothing new starts once it is due, and after the restart the executor holds every job until the agent completes (or the 20-min lease lapses → lost, badged). Then: snapshot `before-deploy-<sha>`, fast-forward, `npm ci` only when a package file changed, build into `client/dist.next` and swap with two renames (old kept as `dist.prev`; never build into `client/dist` in place — the live server 404s meanwhile), restart the server (and the ingest service when `ingest/`, `server/contracts/` or a package file changed), wait for `/api/health` to report the commit, complete; on failure roll back, complete as failed, never retry that commit. With the server down it deploys without the queue. Refuses commits not on `origin/main` or modified tracked files. Outcomes in `cfraser/deploy.log`, the job and app messages (failure = notification); `scripts/server-deploy.sh --check` dry-runs. Read-only deploy key. Machine differences a deploy must not undo: poppler/qpdf from MacPorts (`/opt/local/bin`, on the installed plists' PATH; tracked plists carry laptop paths, adapted at install), Intel builds of `ingest/python/.pdf_deps` / `.numbers_deps` (`pip install --target`), and npm 11 skipping unallowed install scripts (the deploy checks `better-sqlite3` loads).

## Schema baseline (fresh DBs)

`initSchema()` runs `server/src/schemaBaseline.ts` (full schema as of migration 155, all `IF NOT EXISTS`) and marks ≤ 155 applied on a new DB; those files are deleted (copies in `~/Documents/backups/nw-tracker/{removed,squashed}-migrations/`). Recorded-but-missing files are harmless, so numbering gaps are expected; 156+ apply normally. A migration may pair with a `POST_MIGRATION_HOOKS` entry in `db.ts` (pure TS, inside the migration transaction — e.g. `legacyNoteBackfills.ts` for 157). A table a migration drops must also leave the baseline, or every boot recreates it empty. To squash: `npx tsx scripts/regenerate-schema-baseline.ts --last <newest-migration>` (from `server/`), then delete the covered files (keep the seeds). ## Usage and performance log (migration 247, `usageLog.ts`, `usageReport.ts`, `usageDb.ts`, `/panel/usage`)

- **Recorded so optimization follows real use** (primary and demo). Every `/api` request (`usageLogMiddleware`, mounted first): duration to last byte, status, pre-compression size (`res.locals.usageBodyBytes` from `jsonResponse.ts`, else `Content-Length`; none for 304), cache outcome (`requestCacheStats.ts` per-request `AsyncLocalStorage`; `getAggregationCached` reports each lookup: warm = all hits, cold = any miss, neither = none). Aggregated per UTC hour × method × route pattern (`req.baseUrl + req.route.path`, `(unmatched)` for 404) × work-changing params (`USAGE_KEY_QUERY_PARAMS`: `unit`, `days`, `period`, `portfolio_group`, …; never `account_id` or free text) into `usage_endpoint_hourly` (count, total/max ms, 4xx/5xx, bytes, warm/cold, 15-bucket histogram `USAGE_HISTOGRAM_BOUNDS_MS`, `h00..h14`, for p50/p95). Every route change (`useUsagePageTiming`, `client/src/usagePageTiming.ts`, beacon `POST /api/usage/page-view`, untimed) into `usage_page_views`: path, route (numeric segments → `:id`), first-page flag, settle time (route change, or page start for the first, to the last query fetch once 400 ms quiet; left/hidden/still fetching after 60 s = no time, `outcome`). Only the path is stored (plus the daily `visitor` hash on the demo).
- **Requests only touch memory:** flushed once a minute in one transaction (`flushUsageLog`, upserting the hour); endpoint rows >90 days deleted daily; page views kept.
- **Where:** `usageDb()` — main DB on the personal instance, `DEMO_ANALYTICS_DB` on the demo. `USAGE_LOG_ENABLED` (default on) defaults to 0 under `BACKGROUND_JOBS_ENABLED=0` so dev servers never write the primary's DB; the demo defaults it to 1. When off, the beacon answers 204.
- **`/panel/usage`** (`GET /api/usage/report?days=1|7|30|90`, `GET /api/usage/endpoint-trend?method=&route=&params=&days=`): top pages (views, exact settle p50/p95/max, unsettled views, mean queries), endpoints by p95 (count, p50/p95/max, total time, warm share, errors, mean size), and a picked endpoint's daily trend over every Chile day. The server computes all figures. Demo: 404 `usage_report_not_public` (use `npm run demo:visits`).

## Dashboard performance profiling

- **`npm run profile:dashboard`** (from `server/`): sequential builder timings on the test/dev DB (`NW_TRACKER_TEST_DB` or `server/data/nw-tracker.test.db`).
- **`DEBUG_PERF=1`** (or `DEBUG_VERBOSE=1`) logs `[heavy]` spans during requests.
- **`GET /api/dashboard/page-bundle`**: the home page's one call, served from `dashboard.page_bundle|<unit>` (built by the warmer; the cached value is the in-flight promise so concurrent cold requests share a build). Dropped by every explicit invalidation (`invalidateCcBillingDetail`, `invalidateMarketDataAggregations`); only requests in an invalidation→rewarm gap pay the build.
- **`GET /api/dashboard/nav-context`** (sidebar/group pages): account rows, card metrics, value map, no net-worth series; fetched on group/liabilities routes and account pages whose nav node has routable children (home uses the bundle). **Scoped** by required `?root=<nav node slug>` (`navContextScope.ts`): card metrics of the subtree and of groups its nodes host (`linked_card_slugs`), the account rows those nodes hold plus every liability account (the property card names the mortgage), the value map under the node; bucket totals, layout and liabilities breakdown whole. The Pasivos tree is searched first (net worth has a childless `liabilities` node). The client keys on the root and merges into the stored nav snapshot (`mergeNavContextIntoSnapshotCache`; never writes without one — a slice doesn't cover the tree); the warmer builds visited group pages' slices. It is requested beside the page's own requests and the strip shows as soon as it lands, dimmed until then.
- The dominant cost is usually the portfolio-group totals inside **`getDashboardValuationTimeseries`** / **`getGroupValuationTimeseries`** (`@heavy` in source).
- **JSON is serialized once and compressed** (`jsonResponse.ts`): `jsonResponseMiddleware` replaces `res.json` on `/api` with the same body, `Content-Type` and weak ETag (over uncompressed bytes, so 304s work across encodings); bodies ≥1 KB get `Vary: Accept-Encoding` and brotli (preferred on q ties; browsers offer it on HTTPS only) or gzip, never over an existing `Content-Encoding` or `no-transform`. A payload marked with `markJsonResponseCacheable` keeps bytes, ETag and compressed forms in a WeakMap keyed by the object (lives and dies with the cache entry). Marked: group and account daily-series responses (`groupDailySeriesResponse.ts`; account as `daily.series|response|account|`, dropped by API writes), `cachedGroupResponse`, the page bundle, nav snapshot/context, the account detail bundle, both card ledgers. **Only immutable cached objects may be marked** (a mutated object serves stale bytes); others are stringified per response at gzip 1 / brotli 1 (cached ones gzip 6 / brotli 5, once per build).
