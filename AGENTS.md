## Topic rules (`.claude/rules/`)

## Language and i18n

- **UI copy via i18n (es + en)**: all user-facing strings live in **`client/src/i18n/master.json`** — the single source of truth, nested like the locale files, every leaf holding both languages: `{ "en": "Save", "es": "Guardar" }`. `locales/es.json` / `locales/en.json` are **generated** by `npm run i18n:generate -w nw-tracker-client` (`client/scripts/i18n-generate.mjs`); never hand-edit them — `client/src/i18n/localeSync.test.ts` fails on drift. The master stays nested because some leaf keys contain literal dots (e.g. `panelAccounts.addAccount."accountType.equity"`). No hardcoded Spanish or English labels in components except via `t('…')` / `i18n.t('…')`.
- **Translation keys in English**: dotted paths such as `dashboard.cards.netWorth`, `brokerage.groups.mutual_funds`. Code identifiers use English slugs (`mutual_funds`, `real_estate`); display copy lives in `master.json`.
- **Shared labels**: use helpers in `client/src/i18n/index.ts` (e.g. `ccExpenseCategoryLabel`, `flowsPlBucketLabel`; a nav node's label is the server's, resolved with `resolveNavTreeLabel`) so sidebar, cards and charts read the same keys.
- When adding UI text, add the key (both languages) to `master.json` first, run `npm run i18n:generate -w nw-tracker-client`, then reference it. Migrate hardcoded strings when touching an area.
- **UI language preference**: `client/src/languagePreference.ts` (localStorage `nw-tracker.language`), seeded once from `navigator.language` (Spanish → `es`, else `en`; non-browser/vitest contexts stay `es` so label assertions are deterministic), then the stored value is authoritative. Changed from `/panel/settings` via `DisplayPreferencesContext.setLanguage` (calls `i18n.changeLanguage`, persists, syncs `<html lang>`; re-renders `AppTree` top-down). The decimal separator is an independent setting. **Do not cache `t()` results** in `useMemo`/state without the language in the deps — translate at render time.
- **Dates**: numeric dates render as ISO `YYYY-MM-DD` (timestamps `YYYY-MM-DD HH:MM`) in every language — never `dd-mm-yy` / `toLocale*` short styles. Month-name labels (`dic 2026` ↔ `Dec 2026`, ticks `dic 16` ↔ `Dec 16`) go through `client/src/formatDateLabel.ts`, which reads `i18n.language` at call time — same no-caching rule as `t()`.
- **Enforced by `npm run check:conventions`** (root; also runs at the end of root `npm run typecheck`): flags accented Spanish in client string literals/JSX (comments exempt), `Intl.NumberFormat` outside `format.ts`, hardcoded-locale `toLocaleString` without date options, month-name tables outside `formatDateLabel.ts`, `isFetching` / `isRefetching` in `client/src/components` / `pages` (see «Loading states»), and ticker-suffix parsing (`.endsWith(".SN")`, `lastIndexOf(".")` on a ticker, `\.SN$` regexes, `LIKE '%.SN'`) in `server/src` / `client/src` / `ingest/src` outside `server/src/priceProviders/` (see «Instrument registry and price providers»). It also flags currency hardcoding (docs/any-currency-plan.md): `formatClp` / `formatUsd` (and `formatClpUfDay`, `formatUsdFine`) in `client/src/components` / `pages`, a unit or currency compared with a literal code, fixed currency lists and `"clp" | "usd"` unions outside `rates.ts` / `valueConvert.ts` / `displayUnits.ts`, and `_clp` / `_usd` / `_eur` keys in `server/contracts/src/dto`; every hit fails unless its line says why the currency is native to its source (`// convention-ok: <reason>`: an F22 figure is pesos by law, a Santander feed has a peso and a dollar side, a card's billing frame is pesos), and a migration above 312 with `CHECK (… IN ('clp' …))` fails outright (reference `currencies(code)`). There is no ratchet baseline. «Is this pesos?» is `isHomeCurrency` (`HOME_CURRENCY` in the contracts' `dto/apiConstants.ts`, re-exported by the server's `displayUnits.ts`); a client figure one currency by nature formats through its named wrapper in `client/src/formatNative.ts` (`formatF22Pesos`, `formatCardBillingPesos`, `formatBillPesos`, …), a display-unit value through `formatMoney` / `formatCurrency`. Escape hatch: `// convention-ok: <reason>` on the line.
- **Dependency guard, also in `npm run check:conventions`** (`scripts/check-deps.mjs`, baseline `scripts/check-deps.baseline.json`). Builds the TypeScript import graph of `server/src`, `client/src`, `ingest/src` and `server/contracts/src` (tests excluded, type-only imports counted, `.js` resolved to `.ts`/`.tsx`, `nw-tracker-contracts` to its `index.ts`) and fails when a file joins an import cycle the baseline does not list, when a new edge crosses a forbidden boundary (contracts → server/client/ingest, client ↔ server, ingest ↔ server: `server/contracts` is the only shared code), or when `cacheRegistry.ts` imports a module it did not. Prints the largest cycle, the edge count vs the baseline and the top fan-in, fan-out and transitive-reach files. Cycles may only shrink: after a change that shrinks them, `node scripts/check-deps.mjs --write-baseline` locks it in (docs/untangle-plan.md F1). Shared formats (numbers, dd/mm and ISO days, day arithmetic, year-months and Spanish month names, accent folding, RUT and account numbers, merchant text, the zod building blocks) live in `server/contracts/src/formats/`, each rule pinned by a case file in `server/contracts/data/` (`npm run test -w nw-tracker-contracts`); the Python parsers assert the same files.
- **Number formatting**: all numbers (CLP, USD, UF, units, percents) share one decimal-separator convention from `client/src/numberFormatPreference.ts` (localStorage `nw-tracker.decimalSeparator`, seeded from the IANA timezone; toolbar toggle overrides). Always format via `client/src/format.ts` helpers — never `Intl.NumberFormat` / `toLocaleString` with a hardcoded locale for numbers. A separator change re-renders (not remounts) via `AppTree`; **do not cache formatted strings** in `useMemo`/state unless `decimalSeparator` is in the deps — memoize raw numbers, format at render. **Typed numbers:** every number field reads through `parseNumberInput` / `parseNumberInputOrThrow` (format.ts). A number that fits one convention is read that way («1500,5», «1.500.000», «1,234.56»); only a single mark followed by exactly three digits («1.500») is decided by the setting (1500 with comma decimals, 1.5 with period decimals); anything else is rejected with `common.numberInvalid`; forms keep their own sign/range/integer rules. Prefills and placeholders use `formatNumberInput`. Never `Number()` / `parseFloat` / `.replace(/\./g, "")` on typed text, and no `type="number"` inputs (the browser parses those by its own locale). The flows amount filter (`flowsAmountFilter.ts`) also takes an amount copied from the table: a leading `$` / `US$` and the negative «($500)».

## Page grid and tiles (`docs/layout-grid-plan.md`, `styles/tokens.css`, `shell.css`, `page-grid.css`, `cards.css`)

- **The shell is two tracks; only the content carries the column grid.** `.layout--with-sidebar` is `var(--sidebar-w) minmax(0, 1fr)`: the sidebar a fixed 11.625rem (sized to the widest nav label), sticky, outside the columns, its own `--sidebar-bg` (a shade above `--bg`), no border. **Its rows (`AppSidebar.tsx`, `AppSidebar.module.css`):** text sits on one column per depth (`--sidebar-text-x` + depth × `--sidebar-indent`, 8px); every net-worth group with rows under it (one that shows a chevron; a sub-bucket shown as a leaf has none) carries a 6px square in its card pill's colour (`markerRgb`, `mutedPillBackgroundRgb`) in the margin left of its text, and «Gastos» the expenses favicon's red down-pointing triangle (`EXPENSES_FAVICON_SPEC` in `favicon.ts`, the one definition both read), drawn in the selected chart style (`RoughSwatchBox` / `RoughSwatchTriangleDown` through `SketchMarker`, every style but plain; imported directly, as `Pill` imports `PillScribble` — lazy-loading them paints flat marks and bare pills until the chunk arrives). The open page's row has an inset rounded highlight and the groups above it read bright; a group opens/closes from a chevron in the same margin, which replaces its square on hover or keyboard focus (a group without a square shows it while closed, and always on touch; on touch the square stays and is itself the button). No carets, rails, hyphens or accent bar. An account that holds nothing today (`accountChartInactive`, dollar cash included) is not in the nav tree. Content is capped at `--page-max` (105rem from 1440, left-aligned beyond). Tokens on `:root`: `--content-cols` (4 on a phone, **12 from 880** on both desktop tiers, so a tile's span never changes between them), `--gutter` (1rem, 1.5rem from **1440**), `--row-gap` (= gutter), `--row-unit` (1.5rem, one UI line), `--margin-inline` (0.75rem phone, 1rem small desktop, 1.5rem big), derived `--content-w` / `--col-w`, plus `--hairline`. Media queries cannot read custom properties, so the two tier lines are literals wherever a stylesheet needs them; 880 is also the tables' narrow line (`useIsNarrowViewport.ts`), so the app has one small-desktop line. `.layout-main` (track 2) reserves the ticker's strip at the top and keeps `overflow: auto`, so anything wider than the content scrolls inside the main column, not the page; a table never should — it shows its cards instead (see «UI tables — desktop/mobile sync»). `.layout-main>.content` is the column grid; every page's `<main>` is one child spanning it. The ticker: on a phone a full-viewport bar and on the small desktop a bar across the content's width, both with the content reserving its strip (`.layout-main` padding-top); on the big desktop it covers the content's last 8 columns (5–12) and the content starts at the top. The prefs dock's max-width derives from the tokens.
- **Whatever a route renders is on the grid by itself:** `page-grid.css` makes the content region's direct child (a page's `<main>`, or a layout's) a subgrid of the content columns (`row-gap: var(--row-gap)`), so a page root declares nothing. A container INSIDE a page that holds tiles of its own says so with `.page-grid` (same subgrid): a Loadable shell (`GroupInfoBase`, `AccountDetailSharedLayout`, the tax return), a page inside the flows or panel layout with its own root (groceries), a tile grouping sub-tiles. Each section is a **`PageGridTile`** (`components/layout/PageGridTile.tsx`: `<section data-tile=… class="page-tile">`) with its heading INSIDE it, so the row gap is the only space between sections — no outside margins (`.page-tile>:is(h2,h3,h4,.chart-panel-title-row):first-child { margin-top: 0 }`, `.chart-panel-title-row>:is(h2,h3,h4) { margin: 0 }`; no inline `marginTop` / `margin` / `fontSize` on sections). A `.chart-grid` is a subgrid where it is a page-grid child (two panels on six columns each from 880; `--full-line` all of them) and a plain 12-column grid with the same gutter elsewhere. Chart titles and surface controls use `.chart-panel-title-row`; control styles live in `styles/controls.css`. **Account pages are on the grid (`AccountDetailSharedLayout`):** the content shell is a page grid, the strip a `page-grid` tile, and every section a tile (position, charts as `chart-grid` tiles, returns, detalle, cartola months, each credit-card table, mortgage form / sheet / scenarios / prepayments, capability forms, flows); a section made of several tiles (the card's cuotas block, the Pasivos credit-card and mortgage sections, the depto ledger block) is a `page-grid` container with one dim marker, so the same components sit on the Pasivos group pages inside `GroupInfoBase`.
- **A card's title is a pill in its bucket's colour (`DashboardCardTitleRow` `colorRgb`):** the nav node's own `color_rgb` (the colour its chart lines use, set from the panel), drawn with the shared `Pill` on a muted version of it (`mutedPillBackgroundRgb`: lightness ×0.9, chroma ×0.8 in OKLCH); small, not uppercase, the text the pill's own colour with only its lightness moved (`tintedTextOnRgb`: dark on a light pill, light on a dark one). A card with no colour keeps plain text.
- **Card numbers flash on a change (trial; `numberChangeEffect.ts`, `AnimatedNumberFlow` `changeEffect`):** when a strip card's balance or breakdown line changes in the same display unit after a settled render, the digits switch at once and the cell flashes green or red by direction (`flashOnChange`): instant on, ~200 ms hold, 2 s fade; a new change restarts it. The four P/L figures and the summary cards' balances (the page's own total in row 1 and an account page's hero, `CompactEntityCard`) do not flash; they keep the rolling digits. A currency switch, or a dimmed placeholder giving way to live figures, keeps the rolling digits. `NUMBER_CHANGE_FLASH_ENABLED = false` brings the rolling digits back everywhere.
- **Cards have no chrome and touch** (no padding, background, border or radius, no inset yet — aligning card text with the container edge is the next step; `--card-radius` only skins popovers and the modal). A strip is `.cards-strip` (`PortfolioEntityCardsStrip`: one `.cards.cards--summary` block over one `.cards.cards--detail` block; the accounts table a sibling `.cards-strip__table`), a subgrid of the content columns; each `.cards` block is **four equal columns of its own** across the strip with no gap (not a subgrid of the page columns: the gutters would split across the cards and make the outer ones narrower, misaligning the rows). A row the cards do not fill closes with a line just outside its last card (`box-shadow`), on the pixel the next row's card draws its left border on; dividers are per-card borders stripped by a **fixed 4-up count** (`nth-child(4n+1)` no left border, `nth-child(n+5)` a top border; never auto-fill), the one line between the blocks the detail block's border-top. The summary row is the same 4-up block with two cells empty. Below 880 cards are 1-up, 2-up between 600 and 879. A bare `.cards` outside a strip (the flows periods, the mortgage / credit-card summary rows) is a plain 4-column grid with the same dividers. `.chart-box`, `.chart-box--pending` and `.table-wrap` have no chrome (the pending chart frame is the title row plus the reserved height).

Below 1440 the two containers are `display: contents` and the tiles are page-grid items ordered by `--tile-order` = `DASHBOARD_LAYOUT[id].s.y` (`client/src/dashboardLayout.ts`, the one table of tile rectangles per tier in react-grid-layout's own shape — `GRID` is its `Responsive` props; `dashboardLayout.test.ts` asserts reading order, spans and big-desktop placement). In the rail a `.cards` block is 2-up (a `.cards--list` block — «Próximos pagos» — stays one card per row there and at 600–879; a `.cards--pair` block — the «Flujos» periods — stays 2-up below 600 too) and a parallel table shows its mobile rendering by the rail's width (`@container rail (max-width: 40rem)`). The home «Flujos» section is two tiles: `DashboardFlowsPeriods` (rail) and `DashboardFlowsChart` (main), on the same react-query entry. On the small desktop (880–1439) the periods and «Próximos pagos» share a row, half the columns each (`SMALL_PAIRS` in `dashboardLayout.ts`, `PageGridTile` `smallSpan`; the periods' cards 2-up), and below the big desktop the tiles take their reading-order index (`dashboardTileOrder`), not a `y`. ## Per-surface display controls

- **Período/Rango are per-surface, not global.** Every chart owns a compact Período (D/M/Y) + Rango control and every perf/flows period table a Período-only control (tables always cover FULL history and paginate at every grain). State: `client/src/surfaceDisplayPrefs.ts` — `useSurfacePrefs(surfaceId, defaultPeriod, defaultRange)` persists partial `{period, range}` JSON under `nw-tracker.surface.<pageKey>.<surfaceKey>` (missing field = caller default; per page instance; deliberately no cross-tab sync). UI: `components/ui/SurfaceControls.tsx` in `ChartPanelTitleRow`/heading rows. The global toolbar (`AppDisplayPreferencesBar`) carries the display unit only; the old `nw-tracker.metricsPeriod`/`.timeRange` keys are cleared at boot. Bullets elsewhere that say "toolbar Período/Rango" mean this per-surface pair.
- **Defaults**: home value charts + group/account/Pasivos valuation = Diario+3y; every P/L combo, flows chart and the CC charts = Mensual+3y (the CC ledger surfaces are independent controls — `CreditCardLedgerSurfaces.tsx`, one implementation for the card page (`cc.<id>.*`) and the Pasivos / credit-card group section (`liab.cc.<slug>.*`): `.historial` is D/M/Y + Rango and the `.detalle` table M/Y period only; the group pages get Diario through the daily-series CC block summed over the merged ledger's masters, see «CC per-day owed + daily extras»); tables = Mensual (+ full history); proportional charts = Mensual+Todo (the Pasivos root's coverage chart, which takes that slot, Mensual+3y); rates = range-only 1y. **A Rango of N days is N days ending today, today included, on both sides:** `timeRangeCutoffYmd` = today − (N − 1), the same as the server's day windows (daily series points, flows overview day rows). Every client clip goes through `clipPointsToTimeRange` / `clipRowsToTimeRange` (no inline `>= cutoff` filters).
- **Axes.** Every value chart's Y axis starts at 0 for non-negative data and spans 0 for mixed-sign data — one helper, `buildNiceYAxis` (`client/src/components/charts/chartLayout.ts`). Two deliberate exceptions: the Rates page keeps `buildNiceYAxisPositiveBand` (a quote series is about the move; a 0-anchored UF axis is a flat line) and the wealth-percentile top-% axis is a reversed log scale that cannot contain 0. X ticks are **phased on January**: month strides are divisors of 12 (1/2/3/4/6) walked from the first month index that is a multiple of the stride, so a 4-month stride reads ene/may/sep whatever month the series starts in; the day-grid helper phases its month-first ticks the same way, and multi-year strides land on round years (even years for 2, 2015/2020/2025 for 5). Only the first-data-point push (year branch) and the appended last point may sit off-phase. Known residue: on a daily grid whose first month is partial, a tick that phases onto that month sits on the first grid day, not the 1st (`computeRegularMonthXAxisTicks` cannot tell a daily grid from a month-end series with a live last point).
- **Cards show all three periods at once** (no card period anywhere): metrics grid = Mes and Año deposits + P/L rows, a divider, then the dimmed Total row (lifetime deposits + P/L); the Día P/L sits on the balance row beside the main value, with no day deposits figure (`DashboardCardGroupMetrics.tsx`); then breakdown. There is no title balance-Δ chip / `title_delta`. Chart-inactive visibility = any-period activity.
- **Composition charts are proportional** (100%-stacked areas at every grain, own controls; no pies): server-built share series in `server/src/proportionalSeries.ts` — per date base = Σ max(value, 0) over member lines (negatives floor to 0, base 0 → null; Σ shares == 1) — emitted pre-clip as `group_allocation_proportional` + `nav_grouped_proportional`/`liab_grouped_proportional` (group payloads), `allocation_proportional` (home bundle + overview-daily) and `proportional`/`grouped_proportional` (`/api/daily-series`). Client renders via `ProportionalAreaChart` (shares are unit-invariant — keep-prev passes them through unscaled). **One level only:** the home chart stacks one level below the «big» buckets of the net_worth nav tree (`compositionBigBuckets`, `dashboardComposition.ts`: net_worth's children, where a `nav_bucket` without a `dashboard_bucket_slug` — Inversiones — is replaced by its own children; liability and reference groups skipped). Its lines are each big bucket's first-level children — a child group is one line (Σ of its `listAccountsForGroupTab` accounts), a direct account one line (name, account colour) — in nav order; label, i18n key and `color_rgb` come from the nav node and the client colours by the payload colour. Values are the dashboard's marks: monthly `slugMarkTotalsAtDatesClp` at the chart dates only (reusing the primary-lines totals for the same group), daily `accountMarkClpSeriesOnGrid` — so they agree at month-ends — computed in CLP since shares are unit-invariant. The linked credit-card netting (`cashNetOfLinkedCreditCards`) is subtracted from the savings line (`isCashSavingsNavNode`, same as the value map); the builder throws unless exactly one line carries it, if an account sits in two lines, or if a bucket account is in none. A group page's chart is always its direct children (`nav_grouped_proportional` is that single block) whatever the Agrupado toggle says, a leaf page its accounts; there is no `ungrouped` proportional block. Pasivos is separate (unchanged by this rule).
- **Value map («Mapa», `navValueMap.ts`).** A finviz-style treemap in the composition chart's slot on the dashboard and on every net_worth group page with something to tile — sub-groups or accounts of its own (leaf pages too, even with a single account; Pasivos keeps its chart); a «Composición / Mapa» select in the panel title row (stored per surface as `view` beside `<pageKey>.proportional`; the map's own Día/Mes/Año return window is `<pageKey>.map`, default Día; Rango does not apply). The server emits ONE tree, `value_map` (+ `value_map_color_bounds`), beside `card_metrics_by_slug` in the page bundle, nav-context and nav-snapshot payloads; the client picks the page's subtree by slug (`valueMapRootForPage`). Nesting is the net_worth nav tree: a group with GROUP children is a frame (header strip with name + %, when there is room), a group without is the smallest tile, which carries its accounts (`leaf_accounts`): a leaf group opens into them at any depth when it holds two or more, a single account stays the group's own tile except on the page's own first level, which always opens — the page root opens into its own accounts even with one; the client decides by depth from the page root. A mixed group (stocks beside sub-buckets) shows its own accounts as tiles beside the sub-group tiles, and those sub-groups are leaves exactly as the sidebar shows them (`mapNode` / `asLeaf` in `sidebarNavFromApi.ts`): one block, no `leaf_accounts`. Liability and reference groups are not in the map. **Additivity:** tile values are Σ of account rows' current values, each account claimed by one tile (a duplicate throws), so frames add up; the one non-row figure is the linked credit-card total, which the cash card nets (`cashNetOfLinkedCreditCards`) and whose footer sits on the savings card, so the SAVINGS tile carries it (checking is a sibling leaf group and stays raw) and the cash frame equals the cash card value. Every node carries its TRUE value, negatives included (a frame = Σ of all its children); a node worth ≤ 0 is left out of the payload but still counts in every ancestor (so a card bigger than savings + checking hides the whole cash bucket, and the root stays net worth). The client sizes a frame's area by its visible children; tooltips show the true value. The map shows whenever it is the selected view: during a unit switch or a refetch it keeps drawing the last data it had (`useHeldValueMap`), never swapping back to the composition chart. Size = value in the display unit; colour = the node's flow-adjusted % for the period (`row_pct` rule over the node's rows, a single row for an account tile; an empty member with no delta does not blank a group's %) against FIXED per-period bounds the server emits (day ±3%, month ±8%, year ±25%; null % = neutral). The layout is our own squarified treemap (`treemapLayout.ts`) — Recharts' `Treemap` cannot reserve a frame header — drawn by `ValueTreemap.tsx` with CSS tokens `--treemap-*`. Every frame keeps its header: a frame squarified smaller than its minimum (header + a body, and for a frame holding frames, room for their minimum too) is grown at its siblings' expense, and each node's area is its value at one global px-per-value plus the area its headers and padding take (re-measured over a few passes), so a tile inside a frame has the same area per value as one outside. A tile's label shows only when it fits whole (text measured on hidden spans): name over % from ~36 px tall, one row from ~22 px, else none; a header drops its % first, then shortens the name. The tooltip always shows value, % and P/L; a click goes to the node's route.
- **A group valued through one proxy basket maps as the basket's holdings (`proxyBasketBreakdown.ts`, the `proxy` input of `navValueMap.ts`).** When every positive account a node claims sits on the same proxy bucket (`proxyBucketSlugForSeriesKey` in `riskyNorrisProxyMtm.ts` — the Fintual APV accounts → `fintual_risky_norris_proxy`), the node becomes a frame of `kind: "holding"` tiles, one per ETF the fund STATES in its latest `watchlist_composite_positions` row (Fintual's tickers, e.g. SPXS, not its SPY price proxy; `price_ticker` is the Yahoo one), sized by stated weight × the sleeve's share of assets, plus a neutral «Otros» tile (`valueMap.otherSleeve`) for the non-ETF sleeve (`1 − etf_weight_sum`); accounts on the same proxy merge into one breakdown, accounts on different proxies or without one keep their own tiles, and a click goes to the node's route. A holding's colour is its time-weighted return over the days the fund HELD it inside the card period (day / month / year, the cards' anchors): each positions date resets the weights, weights step between dates, disjoint holding windows chain and days out of the basket contribute nothing. The tooltip adds the holding's contribution to the fund (plain Σ weight × daily return, unlinked) and «held N/M days»; the CLP leg goes through the observado frame, like the proxy itself. Fail-fast: a positions row in force without `etf_weight_sum`, a missing close, a non-USD price ticker or a period starting before the first recorded basket throws. Client: `holding` on the value-map DTO, tooltip rows.
- **Flows period tables do not clip by range** (tables include all); the «en el rango» companion totals follow the CHART's Rango. Table Diario views fetch `days=0` (full-history daily; the first build is a known one-time server cost).
- **Yearly charts start with a partial first year.** Every M/Y chart applies Rango then Año through `clipMonthsThenRollup` (`client/src/timeRange.ts`): months are cut at the range start (month-end ≥ cutoff), then rolled up, so a mid-year Rango's first yearly point covers only that year's months inside the range — flows pages, proportional charts and every P/L combo alike — a yearly bar adds up to the monthly bars of the same window, and each «en el rango» total reads the same at M and Y. Running levels are sampled at year-end, never re-summed (`rollupChartPointsByYear` `levelKeys`; `rollupPerfPointsYearly` `accumKey`). Flows payloads (`/api/flows/deposits`, `/api/flows/pl`, `/api/flows/expenses/real-estate`, the dashboard's `inversiones_deposits_chart`) carry monthly blocks only; yearly rows roll up client-side (the P/L year table too). Tables stay full history.
- **The /flows P/L page is market P/L of the deposit accounts (`FLOWS_PL_BUCKETS` in `flowsPl.ts`).** Four buckets: brokerage, retirement, cash (cash_eqs WITHOUT the accounts under Checking accounts — their P/L is the plan fee and the dollar account's fx, a gasto or cash) and real estate (the property's P/L with its mortgage interés + seguros added back — `flowsMortgageCarrying.ts` — since gastos counts them, so it reads the UF revaluation); the chart, the month/year table (desktop + mobile cards) and the per-account blocks (the property's row carries the carrying back too) all show them, Diario included (cash without checking has its own daily scope `flows.pl:cash_eqs`, the others share `pg:<slug>`). The flows overview's P/L is this builder's monthly / daily total.
- **The flows overview is built on the server (`flowsOverview.ts`, `GET /api/flows/overview?unit=clp|usd&installment_mode=split|total[&days=N]`).** Per calendar month (and day, for Diario): `income` (incl. the payroll deductions counted as gastos), `expenses` (gasto del mes of the mode; refunds negative), `savings` = income − expenses, `deposits` = the deposit events of every account NOT under Checking accounts (`accountIdsUnderCheckingAccounts`: corriente, vista, the dollar account, MACH — their own events are cash; money back into checking is negative; the linked mortgage deposit keeps its amortización), `deposits_pre_tax` (AFP/AFC cotizaciones), `card_spent` (the card lines' part of expenses, plus the amortización of a mortgage dividendo a card paid, on the depto payment day in both modes — a financing projection spreads only its gasto), `card_paid` (transfers checking → card master — `pago_tarjeta`, divisas at the pesos that left checking, the dollar account's at its dollars — less card → checking top-ups; card-to-card is not cash; `flowsOverviewCash.ts`), `cash_change` (the checking accounts' ledger change, Σ `accountMarkClpAtYmd` through the mark cache, today for the month in progress), `cash_fx` (the fx result on what the checking accounts hold in another currency than the unit — Σ over days of the holding at the end of the previous day × the day's change of its rate into the unit, the card's revaluation rule (`ccRevaluationCostByDate`) on the asset side, `checkingCashByDay` in `flowsOverviewCash.ts`: in pesos the dollar checking accounts at the sell rate, live today through `fxForLiveMtm`, in dollars the peso accounts at a peso's dollar value; one quantity and one rate per account and day serve both the value and the leg, so Δvalue = fx leg + the day's flows at the day's rate and days add up to the month; the checking accounts' own P/L, which `pl` leaves out by design), `cash_unexplained` = cash_change − (savings − deposits + card_spent − card_paid + cash_fx) — shown on /flows, never forced to zero (what is left is a checking debit in no leg, e.g. a «deposits»-tagged debit whose deposit differs, an overdraft-line payment; or a dollar flow's spread between the mid the legs count it at and the sell rate the dollars are held at), `pl` (the /flows P/L page's own builder, `buildFlowsPlChartMonthly` / `buildFlowsPlDailyChartSeries` in `flowsPl.ts`, so the two read the same total every month — the checking accounts' own P/L is out, the property's mortgage carrying is added back), `investments_change` = deposits + deposits_pre_tax + pl (= Δ value of those accounts, checked to the peso) and `net_worth_change` = savings + deposits_pre_tax + pl + cash_fx. Cash leaves when a card is paid, not when it is used: the card line reads card_spent − card_paid. Full-history `totals`, `closed.{last_month,last_12_months}` — closed months only on the Chile clock (the month in progress reads as a deficit until its salary lands on the last business day) — and `days` (Diario rows inside the `days` window) only when asked; totals and every rollup sum the base legs and re-derive the rest. The /flows overview (table + «Fx de caja» + «Sin explicar») and the home dashboard's flows card (`DashboardFlowsSummary`, surface `dashboard.flows`: Ingresos, Gastos | Ahorro, Depósitos, Tarjetas gastado − pagado, Variación de caja | P/L, Variación inversiones, Variación patrimonio — no «Fx de caja» line: its nine lines are pitched to the strip cards' divider on the big desktop, and the leg reaches the card through Variación patrimonio) only pick rows, clip them to their Rango and roll years up (`flowsOverviewRows.ts`). **The client holds no copy of the derived-field rule:** each derived figure is linear in the legs, so a yearly row and the «en el rango» total are a field-by-field Σ of the server's rows; the income page reads its month rows, day points and total from `/api/income?unit=` `aggregates` (`buildFlowsIncomeAggregates`, the overview's own per-kind income buckets), and the deposits page its day points (`chart_daily*`) and category subtotals from the server. The /flows/deposits page reads the same deposits: the checking accounts out and the mortgage carrying taken back out of the property's dividendo deposits as negative `mortgage_carrying` rows (`buildFlowsDepositsPayload({ excludeCheckingAccounts, withMortgageCarrying })`; the dashboard bundle's own call keeps every account and no carrying rows), so its total is the overview's deposits + deposits_pre_tax month by month (tested), shown split as post-tax / AFP+AFC (`post_tax_total_*`, `pre_tax_total_*`, `isPreTaxDepositRow`). The carrying is one list for the three readers (`flowsMortgageCarrying.ts`: from the line that is the payment, once per link — a financing projection is skipped — on the depto payment day in both installment modes). Cached as `flows.overview|<unit>|<mode>|<days>` over a shared `flows.overview.inputs|` (income, expense lines — `flows.overview.inputs|lines`, the carrying `…|carrying|<unit>` — deposits, card payments): a live-quote tick drops only the payloads; writes and historical market data drop both, and so does any API write once answered (category / income edits touch no other funnel) — but not the queue's and run log's machine traffic (heartbeats, claims, run reports), which drops nothing (`requestDropsResponseCaches` in `requestContext.ts`); the warmer builds the CLP and USD month payloads. **Income has a `rent` bucket:** `buildFlowsIncomeAggregates` sums the income kind `rent` (a tracked place's rent) into its own bucket — `rent_clp` on the month rows, `rent` on the chart points — beside salary, severance, parent_gift and other; the income chart and month table draw it (`income.chart.rent`), the client only picks.

## Loading states (`components/ui/Loadable.tsx`, `components/charts/ChartEmptyState.tsx`)

- **No view is ever replaced by a loading screen.** Every page renders its real layout at once; while a query is pending each component renders its frame with the values it has — zero placeholders, held prior data, an empty table — and dims (`Loadable` / `loadableClass`: `.loadable.is-loading`, opacity .55, inert, `aria-busy`; nested markers never compound, and `.chart-panel-title-row` stays clickable inside a dimmed surface so a Período/Rango/view change is a new request, never blocked). The only loading text is a button label while its mutation runs; never a bare «Cargando…» paragraph, `null`, or a page re-gated on a Diario/unit change. **Eager pages, lazy charts, idle prefetch (`App.tsx`, `lazyChunks.ts`, `components/charts/lazyCharts.tsx`):** the dashboard, group, Pasivos and account pages plus the flows and panel layouts ship in the entry chunk, so a document load paints the page's own layout; the chart engine (recharts) is one lazy chunk reached only through `lazyCharts.tsx` (`chartsBundle.ts` re-exports the chart components the eager pages use), whose Suspense fallback is the chart's own frame — title row with live controls plus the pending box — so a chart slot never shows text; secondary pages stay lazy behind a `null` fallback (`v7_startTransition` keeps the previous page during in-app navigation; the flows and panel layouts wrap their `Outlet` in their own `Suspense` so a direct load keeps the h1 and tabs), and `useIdleChunkPrefetch` imports every registered chunk — charts first — in an idle callback after first paint, after which navigation and charts are synchronous (`lazyComponent` renders a loaded module directly). The entry chunk must carry no recharts. **A first-ever visit (no cached nav tree) is blank, not a message:** the sidebar shows the Net worth link and the Panel footer; the dashboard and the group / Pasivos pages (`GroupInfoBase` `coldStripShape`) draw `PlaceholderCardsStrip` — nameless cards (blank title, value and metric rows at the real rows' height, same grid and shells) in the shape `client/src/coldPageShape.ts` states (`DASHBOARD_COLD_STRIP` 2 summary + 4 bucket cards, `GROUP_COLD_STRIP` 1 summary card; a guess for the paint before the tree arrives, never routed through `requireNavCardMetrics`); a page title with no name yet (`PageTitleRow`) keeps a title's height, so the account placeholder is a blank title, not «Cuenta #id».
- **The home panels paint from the browser's last copy (`queries/persistedPayloadCache.ts`).** «Flujos» (its two closed periods, per unit and expense mode), «Próximos pagos» and «Últimos movimientos» (per unit) keep their last live payload in localStorage and show it, undimmed, until the server answers, like the strip's nav snapshot, the sidebar tree and a group page's shell. One key scheme for all of them, `nw:cache:<name>:v<version>[:<scope>…]`, the version being the payload's `schema_version` (`DTO_SCHEMA_VERSIONS` in contracts) or, for a shape the client builds itself, the client's own; older versions and keys of earlier conventions are swept at boot (`sweepPersistedPayloads`). A held payload of the other unit is never stored; an entry whose shape the client does not read (`isValid`) is ignored.
- **A background refetch never dims (`queryShowsLoading` in `queries/pageShapeReady.ts`).** A query-backed view's `loading` is `isPending || isPlaceholderData` — no data yet (a disabled query included), or the previous page / filter held — never `isFetching`, because the live-quotes stamp invalidates queries on each price move and everything would dim on every tick. `isLoading` is not the signal either: it is false while placeholder data is shown and for a disabled query. `npm run check:conventions` flags `isFetching` / `isRefetching` in `components/` and `pages/`. **A failed background refetch never hides data either (`queryLoadError`, same file):** react-query keeps the last data and sets `error` when a refetch fails; a view shows its error instead of its content only when it has no data (`queryLoadError(q)` = `q.error` while `q.data` is undefined) — a server restart must not replace a page with an error.
- **Every data component takes `loading?: boolean`** (charts, tables, sections, the CC surfaces, `PeriodReturnsWithBenchmark` with `data: … | null`) and dims its own root. A chart's empty branch is `ChartEmptyState`: while loading an empty `.chart-box--pending` at the chart's size (`boxStyle` for the fixed-height ones), otherwise the «no data» copy — loading and absence never share a message. Tables render their header with no rows while loading; the empty label is for a loaded, empty result.
- **A Diario chart never draws the monthly data.** In day mode a chart shows its pending frame — the title row with its live controls over an empty box of the chart's size (`ChartEmptyState` with `loading`) — until its own daily payload for the current unit has arrived (query neither pending nor placeholder, `queryShowsLoading`); the page passes it no points (an empty block, `null`, `[]`), never `dailyBlock ?? monthlyBlock`. Monthly and yearly modes are unaffected. Applies to the dashboard overview, composition and Δ combo, the group and Pasivos valuation / composition / coverage / P/L charts, the Pasivos mortgage combos, the card historial and the account valuation and P/L combos. The home net-worth chart shows the same pending frame in Mensual and Anual until the real bundle is in (the placeholder bundle's zero lines are not drawn, since they only flash before the lines' draw-in). A group's P/L combos stay mounted in day mode whatever their points say (`PortfolioGroupChartsSection`), so the controls can switch back.
- **Recharts is patched (`patches/recharts+3.10.1.patch`, applied by the root `postinstall: patch-package`).** A Line's first draw-in never recorded reaching the end (its final frame, elapsed 1, renders after `isAnimating` turns false, so `useAnimatedLineLength` is never asked for it, and its 4-decimal rounding can leave even that frame short of `getTotalLength()`), so the first data update redrew the right edge of every line. Changes (both builds, `es6` and `lib`): `Line.js` passes the final frame to `getVisibleLength`; `useAnimatedLineLength.js` counts elapsed 1 as full; `LineDrawShape.js` gives an unmeasured line (length 0 on first render) `stroke-dasharray: 0px 1px` (hidden) instead of `0px 0px`, which the browser draws solid, flashing every line in full before its wipe-in. Still needed in 3.11; drop the patch once Recharts fixes it, and re-check it on any Recharts upgrade (patch-package fails the install when it no longer applies). The deploy re-runs `npm ci` when `patches/` changes (`needs_ci` in `scripts/server-deploy.sh`). Separately, `LineChartPanel` keeps its plotted rows across refetches (`useStableChartRows`: unchanged rows keep their objects, a rebuild that changes nothing passes the same array).
- **Loading is not absence.** A server-stated absence (an explicit `null`, an empty list after load, a capability schema such as `movement_create`) hides the subview; a pending query must not read as one. `period_returns` is `undefined` while loading and `null` when the server says none (`useGroupInfoConsolidatedTables`, `useAccountDetailPageData`); the account placeholder takes its category and title from the cached nav row / nav node (`placeholders/accountDetailPlaceholders.ts`), so category-keyed blocks mount right at first paint; the card strip mounts on a cold cache from `buildPlaceholderNavStripDash` (zero `card_metrics_by_slug` for every nav group node, so `requireNavCardMetrics` holds). Accepted pop-ins, because the client cannot know them before the bundle: the CC/mortgage sections and perf combos of a group that turns out to have none, the capability forms. The dashboard's `chart_shape` and the group pages' `chart_buckets` are the nav-time hints for the patrimonio/perf panels and the grouped toggle, and `chart_coverage` (`groupHostsLiabilitiesCoverage`) marks the Pasivos root so the coverage chart mounts from first paint instead of the composition chart swapping out when the payload lands.
- **Keep-previous-data is scoped to the entity** (`displayUnitQueryBehaviorFor(queryKey, entityKeyLength)` in `queries/displayUnitQueries.ts`): a unit, period, range, page or filter change holds the previous payload (the page dims it; `isPlaceholderData` means held data of the SAME group/account/scope), while a different group, account or daily scope starts from its placeholder (bare `keepPreviousData` would show account A's bundle, undimmed, under account B's title). **A held prior-unit payload is never fx-converted:** a unit switch shows the target unit's own react-query data when still warm, else the dimmed zero placeholders for charts and tables — and for the CARD STRIP the previous unit's cards, dimmed and in THEIR unit, which flip to the new values once they land (the dashboard from its held bundle; the group, Pasivos and account pages through `useHeldNavStrip`, the previous unit's nav context or stored snapshot, the account hero from its held detail row — `AccountDetailPageData.stripUnit`); the target unit's stored snapshot wins when it has one; a blank strip only when neither unit has anything. The nav snapshot and nav context queries are keyed on the unit (entity length 2) so neither holds one unit's payload under another; the dashboard cards always animate. The ticker, watchlist and Flows P/L keep previous data across their unit/window changes too. Pages gate `notFound` / `loadFailed` / `<Navigate>` on the nav query having settled, never while it is pending.

## Rentabilidad benchmark row (migration 207, `benchmarkLevels.ts`, `benchmarkComparison.ts`)

- **One definition of a period's % (`periodPctDailyChain.ts`).** Every % the app shows is the scope's daily flow-adjusted `pct` (its own daily series) compounded over the period — a day is one step; 1W, a month, a year, YTD, the 1A/3A/5A windows and the all-time Total compound the days in them; a day with no return is flat, a period with none null. Readers: the Rentabilidad cells, 1D/1W included (`withDailyChainedReturns`, applied after `withShortHorizonCells`); the «Detalle por mes / año» rows of accounts (`monthlyPerfForAccountDisplay`) and groups (`withGroupDailyChainedMonthPct`, `detalleDailyChainedPct.ts`; a year is the compound of its months, so of its days); the dashboard account rows' `pct_*` (`withDailyChainedAccountRowPcts`) and the nav groups' `row_pct` / `parent_pct` (`withChainedGroupPct`, the accounts table and the value map's colours); the home class Δ chart's % view. Don't apply the one-step `flowAdjustedPct` at a surface's own grain: it counts a whole month's or year's flow from its first day, so card, Rentabilidad and detalle disagree whenever money moves mid-period. Kept on the one-step rule: a scope of liabilities only (its P/L is a cost, not a return; Pasivos pages, card and mortgage rows) and the legacy group sub-tab. P/L acumulado ÷ net deposits rides beside the compounded Total (`pct_total_on_deposits_*` on account rows, `on_deposits_*` on a group's total cell) and shows as the Total %'s tooltip. Every non-liability account and portfolio group therefore needs its full-history daily series in both units; `rentabilidadDailyWarm.ts` warms all of them. **The chains keep only each day's pct (`dailyPctSeries.ts`):** `groupDailyPctPoints` / `accountDailyPctPoints` / `dailyPctPointsForScope` build the full series uncached (its past part still from the history tier) and cache `{as_of_date, pct}` per day under the daily-series family (`daily.series|<scope>|<unit>|0|pct|…`); the full payload is built and cached only when a page's day view asks for it. Don't make % readers hold the full cached payload: it exhausts the heap (the demo's Render Starter instance, ~256 MB V8 heap, crash-looped on it). The warm's log line prints heap used and limit; `scripts/profile-cache-memory.ts` lists what each warm step retains and the largest keys; `render.yaml` starts the server with `NODE_OPTIONS=--max-old-space-size=320` on the start command, not as a service env var (that also reaches the build, and the client's Vite build aborts at 320 MB). Parity: `inversionesPerfPct.test.ts`, `dailyPctSeries.test.ts`.
- **The month windows (MTD → TOTAL) are chained from DAILY returns** (`periodReturnsDaily.ts`): each day's flow-adjusted `pct` of the page's own daily series (`resolveAccountDailySeries` / `resolveGroupDailySeries`, full history), from the month-end before the window's first month through today; the pesos and the window bounds stay the monthly rows'. (Monthly chaining counts a month's deposits from its first day and misstates months with large mid-month flows.) The full-history daily series behind every Rentabilidad table are warmed in CLP after the page bundles (`rentabilidadDailyWarm.ts`, one scope per macrotask).
- **Every Rentabilidad table (account pages, investment group pages, Inversiones) has a second row comparing it with a selectable benchmark**, default the mortgage, choice remembered per surface (`<pageKey>.returns`, `useSurfaceBenchmark`). Fetched apart from the page payloads (`GET /api/benchmark-comparison?benchmark=&unit=&account_id=|portfolio_group=`, `GET /api/benchmarks`), so a change of benchmark refetches only the row.
- **The row is a shadow portfolio:** for each window it starts with what the account or group was worth at the window start (1D/1W: the marks on the anchor day; month windows: the first month's `prior_closing`, the figure the real P/L starts from) and receives the same flows on the same days (`loadMergedDisplayDepositInflowEvents`, `flowEventInUnit` — transfers between a group's members cancel), all in the benchmark. Cells: the benchmark's own return over the window (L(end) ÷ L(start) − 1, comparable with the real time-weighted %), the shadow P/L, and Δ = the real cell's P/L − the shadow's. A window that starts empty measures from its first flow; a benchmark with no level at the start or on a flow day leaves the cell empty, never a guess. Levels are in the display unit at each day's rate (live fx today).
- **Benchmarks are rows of `benchmarks`, one per kind:** `equity_with_dividends` (`equity_daily` closes, each `equity_dividends` dividend reinvested at its ex-date close net of `withholding_pct`; SPY at 15%), `fund_unit` (a `fund_unit_daily` series; Risky Norris = `fintual_cert_risky_norris`), `index_plus_rate` (UF compounded at `rate_pct`: the mortgage at 4,95%, UF at 0, a DAP at 2% — migration 208). A level read on or before its date throws when the observation is over 10 days old (a stale series, not a weekend). A new benchmark of an existing kind is a row, not code. **`portfolio_group` (migration 209)** names one of the user's own groups (`portfolio_group_slug`; seeded Brokerage, Acciones, APV, Crypto): its level is the group's time-weighted return, each day's flow-adjusted `pct` from its own daily series chained (`chainDailyReturns`), in the display unit; offered under «Tus portafolios» in both selectors and only while the group exists. It is chained DAILY, so it differs from the group's Rentabilidad TOTAL, which chains monthly returns (every month's flows counted from day 1). In the prepayments comparison, payments that predate a benchmark's history are listed without an invested value and left out of both sides of the totals (`covered_payments` / `covered_from`).
- **`equity_dividends` is write-once** (Yahoo `events=div`): `stocks_nyse` fetches it with the closes for every NYSE ticker and benchmark tickers are always in that sync; a restated amount is a sync note, never overwritten. History: `npm run backfill:equity-dividends -w nw-tracker-server [-- --ticker=SPY --dry-run]`.
- Check: the SPY account against the SPY benchmark differs by tens of pesos over YTD/1A (ex-date vs pay-date reinvestment).
- **Both rows carry the money's IRR** (`real_irr_pct` / `shadow_irr_pct`, `irr.ts`): the rate that turns the window's starting value and every flow, on its date, into the end value — yearly on windows of 365 days or more, over the window on shorter ones (`irr_annualized`; annualizing a day is noise). Solved by a grid scan plus bisection; null when no rate or several rates fit (e.g. a shadow the same withdrawals leave below zero). Don't use a Modified Dietz money-weighted %: it inflates on long windows with large flows both ways.
- **The mortgage page's «Prepagos vs invertir»** (`mortgagePrepaymentComparison.ts`, `GET /api/mortgage-prepayment-comparison?account_id=&benchmark=&unit=`) follows every peso paid above the minimum cuota (`loan_payments.extra_principal` on the `loan` rows: the `prepago` rows and the extra in each regular payment) to today two ways: prepaid, at the `mortgage` benchmark; invested the same day in the selected benchmark (default SPY, `account.<id>.prepayments`). Δ = invested − prepaid; totals carry both IRRs. Before tax; the insurance that shrinks with the balance is left out.

## Pasivos liabilities coverage (`referenceCoverage.ts`)

- **On the Pasivos root page the composition chart's slot shows «Cobertura de los pasivos»** (`CoverageLineChart`): each chart-host reference line («Disponible», «Disponible total») ÷ the total owed on the same date — every liability account on the page (`isLiabilityKindSlug`: the mortgage balance plus the cards' owed-on-date) — as a percent with a dashed 100% line (where that money would clear every debt). The cards are netted inside «Disponible» through cash, so they sit on both sides — deliberate: the chart reads «what I have against everything I owe». A date without positive debt has no point. **The axis is capped at 200% (`COVERAGE_AXIS_CAP_PCT`):** card-only years read in the thousands of percent and would flatten the mortgage era on a 0-anchored axis, so each line is DRAWN clamped to the cap (`|drawn` key) along the top edge, with its clamped run overlaid in a darker shade of its colour (`|capped` key, `cappedStroke`); the rows keep the true values under the series' own keys and the tooltip reads those (`mapPayload`). Not `allowDataOverflow`: without it Recharts grows the domain back to the data, and with it the line leaves the plot. **In Diario it shows its pending frame until its daily series lands** (see «A Diario chart never draws the monthly data» under «Loading states»).
- **Server-built at both grains, same block shape as the proportional ones** (`dates` + `series[].values`, fractions): the monthly group valuation payload's `reference_coverage` (from the block's own reference lines and liability lines, `liabilitiesCoverageFromBlock`) and the daily series' `reference_coverage` (from `reference_lines` and the liability accounts' daily lines). Data-driven: emitted only where the page hosts reference lines AND holds a liability account, so Efectivo (which hosts «Tarjeta de crédito») and the sub-pages keep their composition chart. It reuses that slot's Período/Rango (`liab.<slug>.proportional`).

## Daily series — calendar-day grid deltas (`dailySeries.ts`)

- **`getBucketDailySeries(accounts, { unit, days, now?, includeAccounts? })`** (`server/src/dailySeries.ts`): one point per **Chilean calendar day** ending today (`chileWallClockAt(now).ymd`; `days: 0` = since `portfolioStartYmd`; `DAILY_SERIES_MAX_DAYS` 7400 is a sanity bound, not a product cap — full-history daily is a user choice). Values are true levels via `bucketValueInUnitAt` (→ `accountMarkClpAtYmd`) — each account's mark is flat on its own closed days (weekend/holiday), so **per-account market-calendar attribution falls out of level deltas** (a `.SN` line moves on Chilean days, USD stocks on NYSE days, crypto/UF every day) with no session-window bookkeeping. Each point carries **`market_day`** (`isNyseTradingDay || isChileBusinessDay`; false = weekend/shared holiday — the detalle table dims those rows). Flows use the same deposit-event accounting as `netDepositFlowBetween`, bucketed per `(prev_day, day]` (bulk `loadMergedDisplayDepositInflowEvents`, USD cash included). `pl = delta − flow`; missing legs → null, never a fake 0. Grid helper: `chileCalendarDaysListEndingAt` (in-file).
- **Money without a value gives no return (`unvaluedMemberDays`).** A bucket sums only the members that have a mark that day, so a member whose money arrived before its first valuation would read as money in without its value (huge ± swings that collapse a daily-chained TOTAL). A run of unmarked days that money entered and that ends in a mark — and the day the mark appears — has `pl` and `pct` null (flat in a chain). Never-valued (not yet open) and no-longer-valued (closed) members are not flagged.
- **Liquidation-edge conventions:** (1) **USD-cash deposits are event-based, native-frame** — `loadForeignCashCapitalSortFlows` (`equityBrokerageCapitalFlows.ts`) emits every balance-affecting non-interest movement as a deposit event (USD sign = `signedNativeDeltaForAccountMovement`, so Σ event USD ≡ balance − interest by construction); the CLP frame is per event, never a re-priced aggregate: compra counter legs at their real pesos, equity legs (`stock_buy`/`stock_sell`/`dividend_payout`) mirror the stock side's attribution exactly (intra-bucket transfers net to the peso), legless USD at the event date's sell rate. **A wire shared by same-day buys is split pro rata (`wireProRataFlows`):** with exactly one CLP→USD conversion on the cash account that day, no buy equal to it, and the day's buys needing at least its dollars, each buy carries `wire pesos × buy / Σbuys` at face plus the dollars the wire did not cover (USD already held, e.g. a swept dividend) at the reference rate — the last buy takes the rounding, so the pieces add up to the wire; one buy larger than the wire is the wire + residual composite. (Without the split, the buys fall to the reference rate while the wire comes in at its real pesos, and the conversion spread reads as a −100% month on the cash account instead of sitting in the stocks' cost.) There is no balance − interest re-pricing anywhere (flows deposits windows, valuation dep maps, daily telescoping, `usdCashMonthlyPerfRows`): a no-event window reads 0 deposits in both frames; fx moves on held USD land in P/L like equities. CLP ledger cash and checking accounts follow the same rule: the group consolidation sums their merged deposit events per month through `ledgerCashNetFlowBetween` (events load once per account via `netDepositFlowWindows`), and `valuationTimeseries` has no CLP-cash balance − interest branch, so the aportes line, both performance tables, the card and the daily series read the same events. In pesos the events sum to balance − interest on every day; fx moves on pesos held are USD P/L. These monthly rows (USD cash included) give the first month P/L = close − flow, as the account performance builder does. (2) **`pct_month` is sign-guarded** (`flowAdjustedPct(nominal, prior, netFlow, close, eps)` in `periodReturns.ts` — accountPerformance's closed months, live current-month row and first months, both consolidations, the dashboard pcts (closing at the row's current value), the daily series `pct`, the 1D/1W cells and the equity position's return on deposited all use it). **A period that ends at zero** (`|close| ≤ eps`) on a net withdrawal divides by `prior` (the start frame's `prior + netFlow` is then exactly `−nominal`, which would read every emptying sale as −100%); withdrawing exactly the prior close reads 0%, ending at zero with no prior close (bought and sold inside the period) reads null, and ending at zero on a net deposit keeps −100% (everything at work was lost, never below −100%). **Zero is the unit's coin** (`ZERO_CLOSE_EPS`: 1 peso, 0,01 USD, 0,0001 UF; `flowAdjustedPct` takes the unit) on every grain: a close, prior or start base at or below it is no capital, so a one-peso dust balance reads null instead of dividing the day's fx move by a peso. **Group periods carry each member's zero close** (`endChargedFlow` / `groupStartFrameFlow`): a member that ends at zero on a net withdrawal has it charged at the period end, capped at the group's own net withdrawal so a transfer between members is not counted twice — in `consolidateGroupMonthlyPerf` (rows carry `end_charged_flow`, summed by the yearly rollup), the net-worth / inversiones bucket sums (re-capped), the daily series and the 1D/1W cells; a period where no member empties is unchanged: when `prior + netFlow ≤ eps` (a liquidation withdraws intra-month gains too) the denominator falls back to `prior` — otherwise a close-at-0 month reads exactly −100% by the identity `nominal = −(prior + netFlow)` and poisons every chained Rentabilidad window. (3) **Daily chart lines clip as units** (`trimDailyLineEdges`): a never-held-in-window line nulls its `deposits_acum` too, aggregated bucket lines re-trim after summing, and the daily payload carries **`chart_end_ymd`** (mirror of the monthly block's) when every account line ended — the client trims valuation-chart points only (`buildDailyValuationBlock`); `points` stay full-length for P/L bars and the detalle table. (4) **Grouped bucket aportes aggregate from PRE-trim deposits:** `groupDailySeriesAccounts` sums each bucket's `deposits_acum` from the series' internal `deposit_cums_raw` (every member's raw cums — wound-down and never-held-in-window included — then the aggregate edge-trims as a unit), never from the display-trimmed member lines: summing trimmed lines makes an active bucket with a liquidated member lose that member's terminal net deposits at its clip day, jumping the aportes line by the dead member's withdrawals. A bucket line's terminal aportes equal that bucket's own leaf-page `deposits_acum_total` by construction; `deposit_cums_raw` is stripped from HTTP payloads at the `/api/daily-series` route.
- **One conversion for deposit and flow events (`flowEventInUnit`, flowsDeposits.ts).** Every merged-deposit reader (dashboard totals, `netDepositFlowBetween`, the flows deposits page, monthly/daily aportes, the daily grid incl. mortgage and derived card flows, the fx scan) and the depto ledger payments (mortgage card, performance table, daily view — the property's payments too) convert each event at its own date's rate: a carried leg as is (CLP `amt`, a recorded `amt_usd`), CLP→USD at the buy rate on/before the date (`clpToUsdAtPayment`, unrounded), CLP→UF at that day's UF. Unrounded; a missing rate throws, never a skipped event or a null total, and the flows deposits payload has no `fx_conversion_error`. Never convert a month's sum at the month-end rate (it disagrees with the card and the daily view). Test fixtures a USD reader converts must sit inside the test person's market window (about two years back). Summary «Depositado», chart aportes and dashboard deposits all read personal capital (`movementCountsAsPersonalDeposit`: APV-A's state bonus is not a deposit). Not yet on the rule: the deposits reconciliation, and UF window flows (converted at the window end, the ledger-cash group tables included). A CLP event converts at the buy rate while balances use the mid, so on a cash account a deposit reads a small +USD P/L in its month and a withdrawal a small −P/L; they cancel over a round trip.
- **Group consolidations get each account's payload whole.** Both paths into `consolidateGroupMonthlyPerf` (the cached group consolidation, which also feeds net worth, inversiones and flows P/L, and the group tables' `consolidateFromAccountMonthly`) pass the account payload whole — don't rebuild it field by field: dropping `import_key` makes a Fintual certificate account's month-end mark fall back to its perf rows (already in the requested unit) and the USD path divides them by fx again. `monthEndCloseForAccountInUnit` converts only the mark (`monthEndMarkClpForAccount`) and takes the perf-row fallback as it is, already in the rows' unit; it converts to UF too, and the live current-month row reads UF (close at today's UF, the month's flow at today's UF).
- **Cached wrapper** `getBucketDailySeriesCached(scopeKey, …)` (real clock only) → `daily.series|<scope>|<unit>|<days>|<ids>` keys, dropped by `invalidateCcBillingDetail` (the account/CC write funnel) and `invalidateMarketDataAggregations` via `invalidateDailySeries()`.
- **Book-value carry for manual-marked accounts** (`storedMarkFlowCarry.ts`): the terminal stored-`valuations` forward-fill (historical branch in `accountMarkClpAtYmd` + both generic stored returns in the `accountTodayValue` stack) returns stale mark **+ net personal flows since its date** (`netDepositFlowBetween`, the same reference as the daily/d1 flow legs) — so a deposit day steps the value with `pl = 0` by construction, and the next mark day carries the clean inter-mark P/L. A mark dated the flow day has an empty carry window (no double count). **Never applied to CC or mortgage balances** (kind-gated: CC owed-on-date has its own derivation; a mortgage payment's balance effect is amortization only). This makes the Rentabilidad d1/w1 cells and today's dashboard values deposit-aware for these accounts. In the today stack, depto property/mortgage UF marks resolve **before** the stored return (first in `accountTodayValue`), so a stale property valuation cannot shadow the live ledger mark.
- **Known limits:** monthly-marked accounts (DAP, cuenta ahorro) render P/L as steps — the mark day carries the accumulated inter-mark P/L (carry only moves flows, never fabricates intraperiod returns). A full-history daily build is the expensive one. The depto property/mortgage ledger is memoized (`depto.ledger|rows`, dropped by `invalidateCcBillingDetail`); the remaining hot spot is CC `latestCreditCardValuationRowAsOf`.
- **The account page header shows the dashboard card's value (`accountTodayValue.ts`).** Both read `accountTodayValue` — the value `accountMarkClpAtYmd` returns at Chile today, every dashboard row, liabilities included, so today shares a frame with the prior-day and month-end marks — which carries one override: accounts valued from units × price (cuota ledgers, Fintual cert funds, crypto) show their position's mark, the position asked at TODAY. Don't add a second value ladder for the header.
- **Per-account mark cache + live-tail re-pricing:** marks dominate a daily build, so each account's mark series is cached on the calendar-day grid (`server/src/accountMarkDailyCache.ts`, `accountMarkClpSeriesOnGrid`; the cells are quantities, see «The daily cache stores quantities») and the daily consumers — `getBucketDailySeries`, `buildDashboardBucketDailySeriesClp`, the overview payload's liabilities leg — read it instead of calling `accountMarkClpAtYmd` per account per day. **Only days strictly before Chile today are cached**; today always recomputes (live quotes, intraday fx). That split is what makes the live-quote poll cheap: no historical mark reads `live_market_quotes` (`accountMarkClpAtYmd`'s live stack is gated on `asOfYmd === today`, `computeEquityMtmClp` only reaches `fxForLiveMtm` when handed an explicit live price, and `computeCryptoMtmClp` reads `fxForLiveMtm(asOfYmd)` whatever the price source — a historical date never matches the live row's session, so it reads `fx_daily`), so a live tick drops the daily *aggregations* and keeps the marks. The series **extends** in both directions as wider windows are requested (a later wider view pays only the missing prefix), in their own store (`markSeriesStore.ts`); grids must be contiguous ascending calendar days (checked O(1), throws) and a length/range mismatch throws rather than silently shifting values by days.
- **Mark-cache waterfall (migration 211, `markInputTriggers.ts` + `cacheRegistry.ts`).** The per-account mark series live in their own store (`markSeriesStore.ts`), not the aggregation cache, so they survive the Chile day rollover (a past day's mark does not depend on the date it is read) and every write that does not touch an account's inputs. Each table a historical mark reads has a trigger spec (movements, valuations, the card statement / line / installment / traspaso tables, mirror merges, loan payments, fx (+ bid/ask, observado), UF, fund units, equity closes, the proxy basket, accounts, asset/portfolio groups, market symbols) logging `(account or NULL = every account, raw date)`; the registry trims each affected series to the days before the change by the spec's rule (`backDays` / `recentDays` / `rateTable`: a card's dollar lines read the fx of their pay-by, so an fx row reaches 75 days back for cards; a statement header its billing period; the proxy's observado 7 days; a fund cuota 10 days; the proxy basket 30 days) and drops the daily aggregations and input memos built on them. An equity close logs its ticker's holders only (every account when the ticker is in the proxy basket; nothing for a watchlist-only ticker). The depto property and mortgage accounts are trimmed together (`declareAccountsTrimmedTogether`). A movement that is its account's first units row logs the whole history (it switches the valuation method). `clearAggregationCache()` drops everything, marks included. A source with no spec throws.
- **A live-quote tick rebuilds only today (the history and live tiers in `cacheRegistry.ts`).** A tick drops the page bundle, the monthly-perf / consolidation / flows payloads and the daily aggregations, but what they are built from survives it: the **history tier** (`historyTierMemo`, the `hist.` family) memoizes every input a live quote cannot move — a past day's `accountMarkClpAtYmd` (the month-end marks every monthly builder walks; the daily mark store keeps its own days and bypasses it), the merged deposit timelines (`buildMergedDepositMap`), the ledger month closes before today (`balanceOnlyMonthlyRowsAsc`), equity / crypto MTM at a past day (`computeEquityMtmClp` / `computeCryptoMtmClp` without a live price or `now`), the linked-card netting by past day, a past day's USD / UF rate and USD-cash dollars in the daily series (`pastDayUnitConverter`). It is dropped wholesale by every other invalidation — a write row of any logged table, `historical` market data, a mark row of any connection, the day rollover and `data_version` — so outside a tick it is as fresh as the rest of the cache; a new entry may read only mark-input tables or rows one of those funnels covers, never a live quote, the live fx row or the clock beyond the Chile day. Inside a transaction both tiers hand out throwaway maps (report-only imports read rows they roll back). The **live tier** (`liveTierCached`) memoizes `accountTodayValue` on the real clock for the rest of the UTC minute and is dropped by every invalidation, a tick included. The wall clocks (`chileWallClockAt`, `nyseWallClock`) are memoized per UTC minute (minute resolution, whole-hour offsets, so exact). A tick also drops the cached card billing-detail bundles (`cc.billing_detail|<id>`, not their satellites), because an unpaid facturación prices its dollars at the live rate (`usd_rate_source: live`). Parity: `liveTickIncrementalRebuild.test.ts` (synthetic DB, frozen trading afternoon; rebuild after simulated ticks must equal a rebuild from an empty cache; covers the flows overview too). **The flows overview's inputs follow the live dollar rate, not the tick (`syncFlowsInputsWithLiveUsdRates` in `flowsMortgageCarrying.ts`):** the expense lines price an unpaid facturación's dollars at that same live rate, so the inputs (`flows.overview.inputs|`) record the live rates they used (the cards' facturaciones with `usd_rate_source: live`) and are dropped when a reader finds the cards' current ones differ — a tick that moves only stocks or coins, or one after the fx day closed, keeps them. (The receipt matcher's day arithmetic is memoized and windowed by day, the display dedupe buckets purchases by account/facturación/pesos/day, and the nota-cancelled plan ids sit in the history tier.) Not done: trimming the history tier by date on `historical` invalidations (the mark-series waterfall's rule) instead of dropping it.
- **A dropped payload rebuilds only today's part (`docs/performance-plan.md` «A-F as built»).** On top of the tiers above, the expensive builders keep their past in the history tier: the daily series' past part (`daily_series_past` in `dailySeries.ts`: each account's value in the unit on every grid day but the last, the flow legs, deposit cumulatives and market-day flags), the ledger accounts' closed-month rows (`ledger_closed_month_rows`), a plain account's raw valuation-chart mark on a past date (`valuation_chart_past_raw_clp`; never the trailing or today point, never the card / mortgage / property lines), a card's statement list (`cc_statements_by_account`, frozen rows) and the deposit-event buy rate (`fx_buy_rate_on_or_before`, rates found only). A card's billing detail is two cached parts: the base (`cc.billing_detail|<id>|base`: ledger payload, detalle, facturaciones without their dollar rates), which a scoped tick drops only when it read a moved price, and the bundle, which copies the facturaciones and applies the rates (`withFacturacionUsdRates`), so a dollar tick re-applies only the rates. Each Pasivos reference source's totals are a cached group-response part (`reference_source_totals`). **`buildHistoryTierValue(what, build)`** (`cacheRegistry.ts`) runs a history-tier part in its own dependency node and throws if it read any live input (a quote, the live dollar, or a gate deciding whether to read one) — use it for new parts; the valuation-chart memo is the one exception, because the equity MTM consults the live-dollar gate even for a past day (it reads the stored close there; `equity_mtm_clp` relies on the same rule). Parity: `liveTickIncrementalRebuild.test.ts` runs a coin-only tick on a Bitcoin account it adds, besides the dollar ticks.
- **Group/account page per-account lines: plain stored-valuation accounts use the mark:** plain stored-valuation accounts — manual marks, DAP, cuenta ahorro, the pre-Fintual «Principal» predecessor accounts — value each chart date through `accountMarkClpAtYmd` (stored + net flows since; null before the first mark), matching the daily series; don't forward-fill the last stored `valuations` row without the flow carry (`buildPointsForAccounts`), or a deposit or liquidation after the last mark leaves the line stale. **Guarded to plain-stored only**: equity/crypto/cash MTM, credit_card, mortgage, afp, property, and Fintual cert keep the raw their own branches compute (those framings are intentional — AFP ledger×px transit months, the Fintual cert freshness gate). **Fintual cert accounts read the live mark** (cuotas × fund-unit price, the certificado value) at every date; they have no stored `valuations` rows, and `augmentChartDatesForFintualCertAccounts` derives their chart date grid from the cuota history (month-ends from the first cuota event, which must include **transfer legs**: aportes are mostly modeled as checking→fund transfers, so a single-leg-only MIN would miss the start). **Edge trims on per-account lines:** both grains null each line's **leading** run of 0/null so a late-starting account begins at its first holding (equity reads null pre-holding; crypto's zero-unit mark is a finite 0 — the trim makes them agree), and the daily mirrors the monthly's **trailing** clip (`trailingZeroRunClipStartIndex`, shared out of `timeseriesTailClip.ts`): a sold-out account keeps one plotted zero — one DAY at this grain vs one month-end at the monthly's — then ends, with `deposits_acum` clipped alongside its value exactly as `applyTrailingZeroTailClipToBlock` bundles them. **Display-only**: bucket `points` (the P/L legs, which read the untouched `wealthByAccount`) keep their true zeros. Residual by construction: the monthly's kept zero lands on a month-end and the daily's a day earlier, so one cell per sold-out account reads monthly-0 vs daily-null at month-end comparisons. **AFP:** its stored historical rows are a **write-once cache no scheduled job refreshes** (the `afp_uno` sync only upserts a today spot row via `upsertAfpSpotValuationWithExplicitPx`; `revalueAfpAccountFromCuotas` is manual, its script `afp-uno-apply-valuation` in `server/scripts/archive/`) — after a ledger rebuild, revalue the stored rows first, then trust the chart. The diamond takes no pointer events; the docked tooltip appends an ATH footer line (diamond glyph, `charts.athTooltip` date framed like the title, value) while the hovered row is within `athTooltipIndexTolerance` of the peak's row (≈1,2% of the plotted rows, never less than the adjacent row), bright on the peak's own row and muted on the neighbours.
- **Pending current bucket carries forward:** `LineChartPanel` densify-extends every valuation chart's x-axis through Chile today, so when the day/month/year turns before fresh data loads, the extension bucket would render as a fabricated 0 on every line (the trailing-zero coercion flips the synthetic all-null row). `carryForwardTrailingPendingRows` (`chartDensifyTimeSeries.ts`) copies the last real row into trailing synthetic rows before `coerceKeptTrailingZeroMonth`, but only keys with a finite NON-ZERO value at the last real row — the server tail clip ends a sold-out series in one kept 0 (or nulls), so ended lines are never resurrected and the `[…, x, 0]` sold-out plot survives. Complement: `useChileDayRolloverInvalidation` (mounted in `AppTree`) watches `chileTodayYmd()` (60s interval + focus/visibilitychange) and invalidates ALL react-query caches on day rollover, so day-baked payloads refetch right after midnight instead of waiting out `staleTime`/`refetchInterval`; server caches clear on Chile-day rollover (`cacheRegistry.ts` day epoch), so the first post-midnight fetch is correct.
- **CC per-day owed + daily extras:** between stored anchors, `accountMarkClpAtYmd`'s CC branch returns anchor + **post-anchor signed line activity** (charges +, PAGOs −, `postCloseLiveBalanceAdjustmentClp` — the same evidence stream the month-end writer applies post-cierre). **Installment purchases ramp daily:** the daily walk and the daily CC netting pass `includeInstallmentPurchases` — each contract adds its full `cc_installment_purchases.total_amount_clp` on its `purchase_date` (cupo is consumed at purchase, matching the printed «cupo utilizado en cuotas»), so cuota-heavy months ramp instead of stepping at the next anchor; per-month cuota billing lines stay excluded (billing moves debt between facturado/por-facturar, it doesn't change owed) and anchors still snap to evidence. The month-end writer must NOT pass the flag — its `balance_total` is cupo-based at month-end and already contains post-cierre contracts (passing it double-counts them). The normalized line stream is memoized under the `cc.billing_detail|<id>|postclose_lines` satellite key (per-account `invalidateCcBillingDetail` prefix-deletes `<key>|`). **Header-only payments:** the Santander CLP format prints the previous facturación's payment as a dated «MONTO CANCELADO» row that the parser drops by design (the amount lives in the statement header), so the stream synthesizes the PAGO event from `cc_statements.monto_pagado_anterior` + `monto_pagado_anterior_date` (migration 166; the parser captures the printed date when exactly one body row matches the header amount) — without it the between-anchors walk only climbs. Statements whose payment exists as a real line are skipped (no double count); duplicate statement versions collapse on the shared `hdr-pago|` key. The cash_eqs linked-CC netting uses the same daily convention at historical dates (`liabilityTree.linkedCreditCardBalanceTotalClpAsOf`). **Range selector**: `Rango: 30d/60d/90d/6m/1y/3y/5y/10y/Todo` (`client/src/timeRange.ts`; per surface, see «Per-surface display controls»). Daily fetches send `days = timeRangeToDays(range)` (0 = total); **M/Y charts clip client-side** (a yearly chart cuts its months first, then rolls up — `clipMonthsThenRollup`, see «Yearly charts start with a partial first year») to the same range inside `LineChartPanel` + `MonthlyPerformanceComboChart` (`clipPointsToTimeRange`; when the clip removes leading history the initial zero anchors are skipped — no false left-edge dive to 0). **Agrupado daily**: `/api/daily-series` emits `grouped_accounts` (`groupDailySeriesAccounts` over the nav/liabilities `ChartBucketPlan` — synthetic ids match the monthly grouped blocks, so the client builder reuses that block's metadata); Pasivos pages (`LiabilitiesGroupPage`) swap to the daily chart too (per-card buckets). **Sin-agrupar daily:** nav pages also get `ungrouped_accounts` + `ungrouped_proportional` from the `grouped: false` plan (one nav level deeper — on the Inversiones hub the second-level buckets, matching the monthly toggle-off view), **only when that plan's bucket keys differ from the grouped plan's**; on leaf pages both plans are identical, so the client reuses `grouped_accounts` for the toggle-off view (absence-means-identical rule in `GroupInfoPage`'s three daily memos — valuation pairs with `nav_grouped_blocks.ungrouped`, P/L bars with `nav_grouped_bars.ungrouped`). **CC chart window:** the historial (on the card page AND the Pasivos / credit-card group pages) windows on its OWN Rango across all three period modes — `[max(range_cutoff, first_data − 0.2·span), max(today, plan_end)]` (`client/src/chartRangeWindow.ts`: `rangeWindowStartYmd` keeps a 20% empty lead before the data as a truncation cue and never reaches past the range, `total` starts flush; `windowMonthRows` left-clips the monthly rows AND pads empty leading months so M/Y match the dense daily grid's left edge). The daily historial reads a server-built **CC block** (`ccDailyHistorialBlock.ts`, attached to `/api/daily-series` on CLP requests only — the chart is CLP-native and the client asks for clp): **`cc_owed`** (saldo total = Σ of the scope's CC-master lines, the per-day owed walk — never the bucket `points`, which on the Pasivos root include the mortgage), **`cc_installment_debt`** (Σ per master), **`cc_facturacion_bars`** (each card's facturación bar on its close date, see «Historial bars») and **`cc_plan_tail`** (`ccInstallmentPlanTailClpForAccounts` in `ccInstallmentDebtDaily.ts`) over `today+1 .. plan_end` (= the LATEST member's last cuota pay-by; every member with a schedule walks the shared grid, so a settled member's open-cycle carry still rides until its own pay-by and the today→tomorrow seam stays continuous), CLP-only. **Group scope:** the Pasivos root and the credit-card group get the same block summed over the masters `resolveCcMasterAccountIds` gives the merged monthly ledger (`creditCardGroupLedger.ts`) — one membership for both grains; a card page passes its single id through the same builder. `plan_debt_clp` continues the daily `buildCcInstallmentDebtDailySeries` walk; `balance_clp` = plan debt + the unpaid non-installment carry (`owed_today − plan_debt_today` via `accountMarkClpAtYmd`, frozen at today) until it is paid, then the two lines coincide — **split by facturación:** while the latest closed facturación (statement or provisional) is still ahead of its pay-by, the open cycle's own charges (`facturadoClpFromOpenMonthStatementLines` — tagged cuota purchases excluded, they ride in the plan debt — clamped to the carry) leave on the open pay-by and the rest on the closed one's (`closedFacturacionAheadOfPayBy`), reproducing the monthly projected rows (`balance_total = cupo` once facturado is null) at each projected month-end within a small daily-vs-monthly rounding residue. Daily mode marks `today` with a dashed «Hoy (proyección →)» reference line where the real owed walk hands off to the projection.
- **Traspaso de deuda links:** a «traspaso de deuda internacional» reclassifies USD debt onto the CLP side of the same card — the USD statement's abono leg and the CLP statement's cargo leg of one facturación are a single event, no cash moves, total debt unchanged. **`cc_traspaso_deuda_links`** (migration 170) stores the pair with the bank's hard conversion (implied rate = `amount_clp / amount_usd`); `normalizedPostCloseLines` values a linked USD leg at **minus the CLP leg's booked pesos**, so the pair nets to exactly zero in the owed walk / daily CC netting / flow legs instead of leaving an fx residue. Links are **derived state, rebuilt per account inside every PDF statement import** (`relinkCcTraspasoDeudaLinksForAccount` in `ccTraspasoDeudaLinks.ts`; statement-line replacement cascades old rows away) and the relink **throws on an unpairable leg** — one CLP + one USD leg per statement close, signs validated, rate sanity band — so importing a facturación with only one of its two statement currencies fails loudly when a traspaso is present. Web-paste bucket lines never participate (a pasted leg can legitimately arrive alone; it keeps today's fx conversion until the PDF import links the real pair). Manual re-check/backfill: `npx tsx server/scripts/relink-cc-traspaso-deuda.ts [--apply]`.
- **Strip 1D/1W + ticker displayPL:** the Rentabilidad short-horizon cells are calendar-framed — 1D = today (live) vs **yesterday**, 1W = vs 7 calendar days ago (`periodReturnsShortHorizon.ts`; MTD keeps its live badge). The 1D cell equals the daily table's last row by construction, every day incl. weekends. Money surfaces (strip, dashboard day cells, daily table, bucket cards) always show **real** calendar-day PL; per-instrument day changes (marquee, watchlist 1D, RN-proxy composite) go through **`displayDayPct`** (`tickerDayDisplay.ts`) — hard 0 on the instrument's closed days (NYSE calendar for USD tickers, Chile for `.SN`/fund cuotas, weekends for fx; crypto/UF always real). Tickers only: a US-holiday fx drift on a USD stock stays visible as real P/L in money surfaces while its marquee chip reads 0. **Marquee and watchlist follow the display unit:** `GET /api/market-ticker?unit=` and `GET /api/watchlist?unit=` (the query key carries the unit; `watchlistDisplayUnitParam`) express every value AND every change column in the display unit, converted leg by leg in `watchlistStatsForRow` — the current value at the fx of its observation day (live while that fx day is open), each anchor at the fx on or before the anchor's own date (`watchlistAnchors.ts`, shared with the composite proxy), the day anchor at the fx of the calendar day before the observation — so in CLP mode a USD ticker's chip is price × fx and equals the account row's day P/L. A series already quoted in the requested unit is untouched; the USD/CLP row is never converted (it is the rate, CLP per USD in every mode), nor are the other rate rows (kind `fx_pair`, migration 313, `series_key` `eur_usd` / `eur_clp`, read through `pairRateOnOrBefore` in `rates.ts`: quote units per one base unit, on the marquee as the payload's `fx_pairs` and on the rates page as `/api/market-series`'s `eur_usd`); the marquee payload is built from the same row stats (`uf`/`uno_a`/`risky_norris`/`risky_norris_proxy` = `{day, value, currency, delta_pct}`, equities `{value, currency}` = the display unit), so strip and page cannot disagree. The closed-day hard 0 stays keyed on the instrument's calendar.
- **Group/account daily views:** `GET /api/daily-series?portfolio_group=|account_id=&unit=&days=` serves the bucket daily series **plus per-account chart lines** (`getBucketDailySeries({ includeAccounts })` — same marks, zero extra cost; group scope resolves via `listAccountsForGroupTab`, so the Pasivos tabs work too). In day mode the group/account valuation chart swaps to those lines (`buildDailyValuationBlock` in `client/src/dailySeriesChart.ts` reuses the monthly block's account metadata so series identities/colors survive the M↔D toggle), including the **aportes acum. companions** (`deposits_acum` per account + `deposits_acum_total` = full-history cumulative deposits at each day, same event source as the flow legs) — the Aportes acumulados toggle behaves identically to the monthly view and the detalle table becomes **`DailyPerfDetailTable`**. The last daily row equals the Rentabilidad 1D cell by construction (shared legs).
- **Chart-host reference overlays in day mode:** the Pasivos «Disponible»/«Disponible total» and Efectivo «Tarjeta de crédito» lines are weighted sums of OTHER nav groups (`portfolio_groups.group_kind = 'reference'` + `linked_group` items — data-driven, never a slug list), so the daily payload carries **`reference_lines: [{dataKey, values}]`** built by `dailyReferenceLinesForChartHost` (`server/src/dailyReferenceLines.ts`) and the client pairs them with the monthly block's `lines` metadata (same borrow-the-metadata rule as `grouped_accounts`; unknown dataKey → skipped, never a synthesized label). Both paths pick the host through one helper, `chartHostSlugForValuationGroup`, so monthly and daily can't drift. Source totals are read **on-or-before**: `groupTabValuationTotalFromBuilt` keeps every point of the source's own chart and `forwardFillTotalsToChartDates` picks per host date — don't intersect with the host's dates first (that drops a source's mid-month point, e.g. Fintual/APV snapshots on flow days, and carries the previous month). **A cash source must be CC-netted** (`linkedCreditCardClpForCashCardByDates`): the monthly chart Total for cash_eqs comes from the consolidated cierre via `applyConsolidatedTotalToGroupTabBlock`, which nets the linked card — without it the daily overlay sits a whole card balance above the monthly one. **Each source reads that group's OWN daily series** — `getBucketDailySeriesCached` under the same scope key, rows and options the `/api/daily-series` group branch uses (`pg:<slug>`, `includeAccounts: true`, rows filtered only by `account_id > 0`), so one build serves both. Keep those three inputs identical or the key silently stops matching and both sides rebuild. A thin per-unit `daily.refsrc|<slug>|<unit>|<days>` map caches the netted result on top (the CC netting is not free to redo per request); everything drops under the `daily.` prefix. Reference sources must resolve by **raw slug** (the daily route's convention, equal to the monthly `portfolioGroupApiForValuation` sets). Marks dominate a daily build, so a values-only source build saves little. Expected D↔M gap: the monthly composer only reads source rows whose date is a chart date and forward-fills the rest, so a month-end where a source has no row shows a stale monthly value while the daily marks the real one.

## Options (contracts as accounts)

- **A listed option series is its own account at intrinsic value** (migration 304, `optionContracts.ts`, `optionPosition.ts`, `optionFlowKinds.ts`, `optionAssignment.ts`; `docs/demo-app-features-plan.md` §3). `option_contracts` (account → underlying, right C|P, strike, expiry, multiplier 100, OCC symbol); `accounts.equity_ticker` is NULL (EOD sync, watchlist, `accountsWithEquityTicker` never see it); the profile picks `QuantitySource {kind: "option_contracts"}` BEFORE the share branch; holding `{kind: "option", …, quote: "usd"}` (non-dollar underlying throws). Contracts are SIGNED (short = −n): `unitsDeltaForAccountMovement` per kind (`option_sell_open`/`_sell_close` −|n| on the from-leg, `option_buy_open`/`_buy_close` +|n| on the to-leg, single-leg `option_expire`/`option_assign` −held as stored), `optionContractsThroughDate`, `qtyMarkNativeValue` × multiplier — a short's value is NEGATIVE (`positionMarkFromMeta`, `units_kind: "contracts"`). **Price = intrinsic from the underlying's close** (`holdingPriceAt`: as-traded past close, today's price today; `max(0,S−K)` call, `max(0,K−S)` put, 0 from expiry); time value is not priced (no contract history; stated on the page); a missing underlying close THROWS and no ladder falls back to a book mark. Closed/expired/assigned = 0, chart-inactive. `option_contracts` is a mark input (`OPTION_CONTRACTS_SPEC`, whole-history revalue); `option_assignments` links an assignment's two rows.
- **Flow kinds** (`OPTION_UNITS_FLOW_KINDS`, in `BROKERAGE_FLOW_KINDS`, `BROKERAGE_NON_CASH_FLOW_KINDS`, the reconciliation's non-capital list, `intraDayFlowRank`, client `brokerageFlowKinds.ts`): `option_sell_open` (contract → USD cash, −n), `option_buy_open` (cash → contract, +n), `option_buy_close`, `option_sell_close`, `option_expire` (single-leg, amount 0, −held) and `option_assign` (single-leg, −held) + a `stock_sell` at the strike (`stock_buy` for an assigned put; exercised long reversed), linked in `option_assignments`, written together by `assignOptionContract` (`POST /api/accounts/:id/option-assignments`; a bare `option_assign` is refused). `validateBrokerageTransferEndpoints`: premiums settle in USD cash, whole contracts, direction fits that day's position (open never closes the other side, close never past zero, nothing after expiry); `option_expire` must reach exactly zero on/after expiry. Forms: `STOCK_ACCOUNT_FLOW_KINDS` vs `OPTION_CONTRACT_FLOW_KINDS` (units required, «contratos»).
- **A premium is capital** (`equityBrokerageCapitalFlows.ts`): received = capital out of the contract (`dividend_payout` mirror), paid = in (`stock_buy` mirror), at the day's USD reference rate; the USD-cash loader mirrors it negated so they cancel in the bucket; expiry/assignment move no money. So value − aportes is the position's P/L (fixture `optionContracts.test.ts`). **`loadForeignCashCapitalSortFlows`'s generic branch THROWS on an unlisted kind** (`USD_CASH_GENERIC_CAPITAL_FLOW_KINDS`: kind-less transfer, cash deposits/withdrawals, conversions, `other`, `pago_tarjeta`, `carga_tarjeta`); a new instrument's leg needs its own rule, never "deposit".
- **Creating:** `POST /api/accounts` `account_type: "option"`, `option: {underlying, right, strike, expiry, multiplier?}`: underlying must quote USD; OCC symbol derived (`occSymbol`); default name «SPY 2025-06-20 C 600»; leaf `brokerage_opciones__<occ slug>` under `brokerage_opciones` (kind_slug `options`, `/inversiones/brokerage/opciones`, seeded by `seedNavTree`, hidden when empty); `import_key` `import:panel|option=<occ>|key=<slug>`; never moves buckets. **Tax lots** (`taxLots.ts`, `optionTaxLotEvents.ts`): short lots (`open_short`/`close_short`, own pool; `realizeTaxLots` returns `shortCloses`, `openShortLots`; `dispose` with no long lot throws — shorts are declared, never inferred; `taxLotTerm`: short always short-term §1234(b), long long-term after > 1 year). `optionTaxLotEventsFromRows` / `loadOptionTaxLotEvents` map sell-open → open_short, buy-close → close_short, expiry → close_short/dispose at 0, buy-open → acquire, sell-close → dispose; `optionLotResults` gives slices. Assignment/exercise has no gain of its own; the premium adjusts the share trade (Pub. 550: short call +proceeds, short put −cost, long call +cost, long put −proceeds) via `optionAssignmentAdjustments(stockAccountId)` into `equityTaxLotEventsFromRows` / `loadEquityTaxLotEvents` (optional input). Still open: the Schedule D / F1040 wiring that reads these results (no report calls them yet), the demo's option events, a live chain price. **Their tax:** lots reach Form 8949 / Schedule D via `us1040/wired.ts` (assignment premium into the share's basis/proceeds, 1040 equity walk only); on the F22 an option movement in a Chilean-resident window throws (Ley 20.544 not modelled, `assertNoOptionsInResidentWindow`, `f22/blocks.ts`), in a non-resident window it is `excluded` (`options`, `nonresident`, `taxFacts/options.ts`).

- **Demo options wheel** (`demoData/optionsWheel.ts`, `simulate.ts` `runWheel`, `generate.ts` `createOptionContractAccounts`, `invariants.ts` `checkOptionsWheel`). At IBKR from 2025-01, every third month (15th or next NYSE day), as US resident: cash-secured put ~5 % below close, or covered call ~5 % above while holding 100 assigned shares, on the monthly expiry nearest 45 days (Thursday if Friday closed); premium = 0,04 % of strike per day to expiry — story assumptions, no pricing model. Underlying = on the first securable sale day, the largest NYSE dollar ticker of the broker list (SGOV excluded) whose 100 shares fit the collateral (cash + SGOV reserve) — never hardcoded; an unsecurable put is not written. Outcome = close on expiry (put assigned below strike, call above), never forced. Written through the real model: `Ledger.optionContracts`, `option_sell_open` series → IBKR USD, `option_expire` rows, `DirectMovement` `option_assign` → `assignOptionContract` in date order (SGOV sold first if cash is short); series accounts created per pass after `simulate` (the reset drops them). Assigned shares are IBKR's holding of the ticker's ONE stock account (`heldUnits` keyed `ticker|cash`). Invariants: 0 contracts from expiry, −1 from sale, premiums/legs equal the story to the cent, one 100-share link per assignment, IBKR dollar cash never negative.

## Checking / cuenta vista ledger anchor

- A checking balance is **derived from movements**; a synthetic **anchor** movement (`import:cartola|anchor|<period>|saldo final`, dated before the first real movement) carries the opening balance so the walk lands on the latest cartola's `saldo_final_clp`. `ensureCheckingLedgerAnchor` re-derives it when an import advances the latest cartola period.

- **Bank posting day (migration 199, `movementBankPostings.ts`).** `occurred_on` = best evidence of when money moved; `movement_bank_postings(movement_id, account_id, posted_on, occurred_on_basis)` keeps the day a bank document filed it on one account when different, and what `occurred_on` rests on (migration 329: `evidence` = a document stated the day; `fetch` = the listing's fetch day, an upper bound a transfer mail may move earlier) (Santander's 14:00 cutoff → next workday, possibly next month). ## An account's value: what it holds, converted once (`docs/holdings-currency-plan.md`, `accountValue.ts`, `holdingPrices.ts`, `valueConvert.ts`, `rates.ts`)

- **Value at a date = quantity of what the account holds, converted ONCE into the display unit.** `accountHolding(id)` (`holdings.ts`): a currency (pesos, dollars; property and mortgage in UF), a stock (quote currency), a coin (dollar price series), fund cuotas (peso-priced) or a card. `accountHoldingQtyAt(id, ymd)` = quantity; `holdingPriceAt(instrument, ymd)` = unit price in its quote currency (past day: stored observation on/before, history tier; today: live quote in session, held print after close, display-session bar, newest bar; a fund's live/per-date Risky Norris proxy); `accountValueAt(id, ymd, unit)` = qty × price → `convertValue` (`valueConvert.ts` over `rates.ts`). Never build pesos and convert back. Historical stack `accountHistoricalQtyMark` (`accountMarkClpAtYmd.ts`: branches return quantities; an instrument is the asset only on days its price is on file, else fall through); `accountMarkClpAtYmd` = that in pesos.
- **Spread side = what closes the position.** Assets: foreign → CLP at bid, CLP → foreign at ask; liabilities flip (`holdingIsDebt`). UF and EUR have no spread. Stored days read `fx_daily` with bid/ask observed that day or later, else mid ∓ half `FX_BID_ASK_SPREAD_CLP`. Flows convert per event at the mid (`flowEventInUnit`, `convertTs`, `clpToUnitAtMid`), as do benchmark levels.
- **Today reads the live rate** (USD/CLP while the fx day is open, `fxForLiveMtm` in `rates.ts`). `accountTodayValue(id, slug, opts, now) → {value_clp, native_value, native_currency, side, as_of_date, priced_on}` is the one today value (dashboard row, header, today's mark, perf live row, every chart live point); other units convert the NATIVE value with `todayValueInUnit(id, v, unit)`. `priced_on` is informational only.
- **`accountValueClpToUnitAt(id, clp, ymd, unit)`** converts a peso-native account value at the account's side and re-reads a value native in another currency (`accountValueCurrency`) from its holding. `clpToUnitAt(clp, ymd, unit, {side})` is for amounts that aren't one account's value (cards netted from cash, liability totals at `side: "debt"`). Bucket/net-worth sums in a unit = Σ each account's value in that unit per day (`buildDashboardBucketDailySeriesInUnit`, daily series, overview, ATH) — never Σ pesos ÷ one rate.
- **A card's value in a unit goes through one seam, `cardValueInUnit.ts`** (owed walk in pesos at the debt side); the card phase will replace it with per-currency sub-balances. The property and mortgage are still the depto ledger's pesos (peso quantities) until the loan phase.
- **Stored valuations are in any currency (migration 260, `valuationValue.ts`).** A `valuations` row is a quantity in `currency` (any lowercase code). Generic readers convert once on the row's date at the account's side (`storedValuationInUnit`: `valuationLatest.ts`, `bookValuations.ts`, `valuationTimeseries.ts`); the historical stack (`accountMarkClpAtYmd.ts`) carries book marks in pesos, so a non-peso book mark with a carry window throws. Kind-specific readers assert their currency (`assertValuationCurrency`: card CLP anchors, AFP/Fintual peso marks). Property rows are UF appraisals, left out by every mark reader (`valuationsAreAppraisals`); the mortgage has none (migration 261; the depto ledger values it, and property/mortgage chart month-ends come from the ledger, `augmentChartDatesForDeptoAccounts`). `GET /api/accounts/:id/valuations` returns `value` + `currency`; `POST` writes pesos and refuses a property.
- **The daily cache stores quantities** (`markSeriesStore.ts` cells `{qty, asset}`); unit values are built at read from memoized day price and rate (`accountValueSeriesOnGrid`), one series for every unit. Rate rows (`fx_daily`, `fx_daily_bid_ask`, `uf_daily`) trim only accounts whose quantity is a rate-built peso figure (cards — from the row's own day —, the depto ledger, book marks), never shares, coins, cuotas or dollar ledgers (`setRateIndependentAccountsResolver`). Price rows (`equity_daily`, `fund_unit_daily`) trim their holders (which asset a day holds depends on price availability).

## Import sources vs runtime

**Rule:** files under `cfraser/` are **import inputs only**. HTTP, dashboard, valuation, and sync read **SQLite**; missing data → error or “run import”, not a silent file fallback.

- **Depto:** one movement ledger per property (`loadDeptoLedgerForProperty(id)`, cached `depto.ledger|rows|<property id>`; `deptoLedgerForAccount` / `deptoLedgerForLoan` / `loadAllDeptoLedgers`). Pairs come from `propertyLoanPairs()` (`accountRoles.ts`: a `property` role holder and its `loan_of` account); extra properties are `import:property|key=<k>` / `import:loan|property=<k>` (`propertyAccountImportKey` / `loanAccountImportKey`; migration 299's triggers seed the roles). Every reader («Próximos pagos», valor/hipoteca overlays, mortgage sections, card pairing, real-estate mortgage rows) loops over the pairs; the lender portal reading names its loan by `lender_pattern`. The ledger joins property-account movements with **`loan_payments`** (migration 258; docs/holdings-currency-plan.md phase 4): one row per payment movement, `leg` `property` | `loan`, `loan_account_id`, cuota, origin, and the bank's figures in its own currency — `balance_after`, `min_payment`, `max_payment` in `loan_currency` (UF); `principal`, `extra_principal`, `interest`, `insurance_fire`, `insurance_life` in `payment_currency` (pesos); readers throw on any other pair. Nothing derived is stored (parts' UF = pesos ÷ UF día, 4 decimals, the pago 5; net equity; `pagado_neto_uf`; `pago_acumulado_clp`; deltas/acumulados are computed from `uf_daily`). The appraisal is a **`valuations` row of the property account in UF**, forward-filled by the ledger; a property's valuations are its appraisals (`valuationsAreAppraisals`, `valuationValue.ts`), so generic mark readers skip them and its chart samples month-ends from its first ledger row (`augmentChartDatesForPropertyAccounts`); its value is net equity (`deptoNetEquityUfBySnapshotDates`). Rows are **sequential daily balances**: order = `deptoLedgerChronoCompare` (date, then decreasing crédito restante for same-day prepago+cuota); `assertDeptoPrepagoSequencing` fails when a prepago raises the balance (regular cuotas may: grace-period capitalization); snapshot fills use exact-date cutoffs with prepagos included — never a month-end cutoff expansion or a prepago skip (one-day equity spikes, ± P/L couplets). `mortgagePaymentCreate` writes the movements (human notes, mortgage `flow_kind`) plus both `loan_payments` rows; manual-payment recompute updates in place. No `depto_snapshot`: the RE card synthesizes valor/hipoteca from the property + mortgage rows.
- **Account identity:** `accounts.import_key` (unique, nullable; migration 159) is the find-or-create key and well-known lookup (`import:excel|key=mortgage`, `import:fintual|cert|key=…`, `credit_card_master|<issuer>|<last4>`, `import:panel|…`); every creator writes it; `notes` holds the same string for humans, never read by code. Card→account resolution uses `credit_card_account_config.card_last4` (every master has a config row).

Runtime code must not use `fs.readFile*` / `readSemicolonCsv` on `cfraser/` except in `server/scripts/` and import helpers. Import-sync document coverage (`GET /api/import-sync/…`) may list files for admin tooling only.

## Dashboard performance profiling

- **`npm run profile:dashboard`** (from `server/`): sequential builder timings on the test/dev DB (`NW_TRACKER_TEST_DB` or `server/data/nw-tracker.test.db`).

- **JSON is serialized once and compressed** (`jsonResponse.ts`): `jsonResponseMiddleware` replaces `res.json` on `/api` with the same body, `Content-Type` and weak ETag (over uncompressed bytes, so 304s work across encodings); bodies ≥1 KB get `Vary: Accept-Encoding` and brotli (preferred on q ties; browsers offer it on HTTPS only) or gzip, never over an existing `Content-Encoding` or `no-transform`. **An expense line's money is its own currency** (`lineMoney.ts`, `wireExpenseLine.ts`, contract `Money` / `LineConverted`). Wire: `amount: {value, currency}`, `converted: {value, currency, rate_source} | null` in the requested unit (every lines endpoint takes `?unit=`; null when already in it), `value_clp` (pesos, for peso documents: facturación/month modal totals, financing candidates). `rate_source`: `native`; `paid` / `live` / `pay_by` (card dollars at the facturación's paid rate, today's while unpaid, pay-by − 1 when none on file: `facturacionUsdRateWithSourceResolver`; a dollar payment line at the pesos paid, `usdPaymentLineClpResolver`); `day`. Into a third currency a line goes through its pesos and keeps their source. `amount_clp` / `amount_usd` / `amount_usd_at_expense` are server construction data (in-pipeline matchers read them); finished-line readers use `lineValueIn(l, unit)` / `lineAmount(l)` / `linePesos(l)`. The client never converts: `formatLineAmount` / `MoneyAmount` show native + converted («US$13,30 (≈ $13.083)», «≈» = `live`), only converted below 450 px of list width (container query). A peso document (utility bill, demo place bills) matches only peso lines; real-estate bills and declared recurring payments still read a dollar line's pesos. Manual expenses may be any core currency (migration 316; flow triggers read the row's amount and currency).

**A card payment is named by what it paid** (`expensePaymentNames.ts`, `payment_name` on lines, `display_brand` on `CC_ISSUERS`), from payment records, never bank text: a one-shot charge paying another card's facturado (`cc_facturado_payment_charges`) and every line of a `finances_facturado` plan («Total» and cuotas) → «Pago <brand> ·<last4>» (`pays_card`); the paid card's payment line → «Pago con tarjeta <brand> ·<last4>» (`paid_by_card`) when it is the whole facturado, or, paid in parts, one payment per charge/plan summing to it, dated within `MATCH_WINDOWS.financing_payment` of the latest paying day and matched by `ccPaymentEvidenceKey` (so a statement PAGO replacing a planted one keeps the name); the card leg of a `pago_tarjeta` from a bank account → «Pago desde <account>» (`paid_from_account`; a divisas abono by its dollars). Ambiguity names nothing. The client words it via i18n (`expenses.creditCard.paymentName.*`, `expensePaymentName`) in place of the merchant; the ⓘ card keeps store and bank text.

**Expense category rules are global, keyed on the vendor** (migration 252, `expenseCategoryRules.ts`, `bankMerchantName.ts`): `expense_category_rules` holds a general rule per vendor and specific rules per vendor + link. The vendor (`vendorRuleKey`) is the catalog brand of the bank text (a `branch` entry without its branch — every Jumbo is «JUMBO»; processor prefix off — «PAYU \*UBER EATS» = «UBER EATS»), else the cleaned name; a rule learned on a cut name reaches the full one (`vendorRuleKeyCandidates`). The link is a receipt's store (by brand), an App Store app, or a transfer recipient (RUT, else name); recipient rules ignore the transfer wording (vendor `TRANSFERENCIA`). Precedence: the line's own category («Único», per-line override) > specific rule > general rule > «sin categoría»; the general rule applies in `resolveCcExpenseCategory`, the specific one late, once the link is known (`withSpecificCategoryRules`, after the subscription step, for card and checking lines whose category only the bank name decided, including an «Único» row without category). Lines carry `category_link` (kind, key, label, `specific_default`) and `category_specific`; the picker's «Específico» checkbox (default on, off for food delivery: Uber Eats, Rappi) picks which rule a change writes, sent as `rule_link`. `server/scripts/report-expense-category-rule-migration.ts --db=<file>` lists migration 252's merge of the old per-account rules and its conflicts (read-only).
