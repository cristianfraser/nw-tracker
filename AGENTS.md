## Language and i18n

- **UI copy via i18n (es + en)**: all user-facing strings live in **`client/src/i18n/master.json`** — the single source of truth, nested like the locale files, every leaf holding both languages: `{ "en": "Save", "es": "Guardar" }`. `locales/es.json` / `locales/en.json` are **generated** by `npm run i18n:generate -w nw-tracker-client` (`client/scripts/i18n-generate.mjs`); never hand-edit them — `client/src/i18n/localeSync.test.ts` fails on drift. The master stays nested because some leaf keys contain literal dots (e.g. `panelAccounts.addAccount."accountType.equity"`). No hardcoded Spanish or English labels in components except via `t('…')` / `i18n.t('…')`.
- **Translation keys in English**: dotted paths such as `dashboard.cards.netWorth`, `brokerage.groups.mutual_funds`. Code identifiers use English slugs (`mutual_funds`, `real_estate`); display copy lives in `master.json`.
- **Shared labels**: use helpers in `client/src/i18n/index.ts` (e.g. `ccExpenseCategoryLabel`, `flowsPlBucketLabel`; a nav node's label is the server's, resolved with `resolveNavTreeLabel`) so sidebar, cards and charts read the same keys.
- When adding UI text, add the key (both languages) to `master.json` first, run `npm run i18n:generate -w nw-tracker-client`, then reference it. Migrate hardcoded strings when touching an area.
- **UI language preference**: `client/src/languagePreference.ts` (localStorage `nw-tracker.language`), seeded once from `navigator.language` (Spanish → `es`, else `en`; non-browser/vitest contexts stay `es` so label assertions are deterministic), then the stored value is authoritative. Changed from `/panel/settings` via `DisplayPreferencesContext.setLanguage` (calls `i18n.changeLanguage`, persists, syncs `<html lang>`; re-renders `AppTree` top-down). The decimal separator is an independent setting. **Do not cache `t()` results** in `useMemo`/state without the language in the deps — translate at render time.
- **Dates**: numeric dates render as ISO `YYYY-MM-DD` (timestamps `YYYY-MM-DD HH:MM`) in every language — never `dd-mm-yy` / `toLocale*` short styles. Month-name labels (`dic 2026` ↔ `Dec 2026`, ticks `dic 16` ↔ `Dec 16`) go through `client/src/formatDateLabel.ts`, which reads `i18n.language` at call time — same no-caching rule as `t()`.
- **Enforced by `npm run check:conventions`** (root; also runs at the end of root `npm run typecheck`): flags accented Spanish in client string literals/JSX (comments exempt), `Intl.NumberFormat` outside `format.ts`, hardcoded-locale `toLocaleString` without date options, month-name tables outside `formatDateLabel.ts`, `isFetching` / `isRefetching` in `client/src/components` / `pages` (see «Loading states»), and ticker-suffix parsing (`.endsWith(".SN")`, `lastIndexOf(".")` on a ticker, `\.SN$` regexes, `LIKE '%.SN'`) in `server/src` / `client/src` / `ingest/src` outside `server/src/priceProviders/` (see «Instrument registry and price providers»). It also flags currency hardcoding (docs/any-currency-plan.md): `formatClp` / `formatUsd` (and `formatClpUfDay`, `formatUsdFine`) in `client/src/components` / `pages`, a unit or currency compared with a literal code, fixed currency lists and `"clp" | "usd"` unions outside `rates.ts` / `valueConvert.ts` / `displayUnits.ts`, and `_clp` / `_usd` / `_eur` keys in `server/contracts/src/dto`; every hit fails unless its line says why the currency is native to its source (`// convention-ok: <reason>`: an F22 figure is pesos by law, a Santander feed has a peso and a dollar side, a card's billing frame is pesos), and a migration above 312 with `CHECK (… IN ('clp' …))` fails outright (reference `currencies(code)`). There is no ratchet baseline. «Is this pesos?» is `isHomeCurrency` (`HOME_CURRENCY` in the contracts' `dto/apiConstants.ts`, re-exported by the server's `displayUnits.ts`); a client figure one currency by nature formats through its named wrapper in `client/src/formatNative.ts` (`formatF22Pesos`, `formatCardBillingPesos`, `formatBillPesos`, …), a display-unit value through `formatMoney` / `formatCurrency`. Escape hatch: `// convention-ok: <reason>` on the line.
- **Dependency guard, also in `npm run check:conventions`** (`scripts/check-deps.mjs`, baseline `scripts/check-deps.baseline.json`). Builds the TypeScript import graph of `server/src`, `client/src`, `ingest/src` and `server/contracts/src` (tests excluded, type-only imports counted, `.js` resolved to `.ts`/`.tsx`, `nw-tracker-contracts` to its `index.ts`) and fails when a file joins an import cycle the baseline does not list, when a new edge crosses a forbidden boundary (contracts → server/client/ingest, client ↔ server, ingest ↔ server: `server/contracts` is the only shared code), or when `cacheRegistry.ts` imports a module it did not. Prints the largest cycle, the edge count vs the baseline and the top fan-in, fan-out and transitive-reach files. Cycles may only shrink: after a change that shrinks them, `node scripts/check-deps.mjs --write-baseline` locks it in (docs/untangle-plan.md F1). Shared formats (numbers, dd/mm and ISO days, day arithmetic, year-months and Spanish month names, accent folding, RUT and account numbers, merchant text, the zod building blocks) live in `server/contracts/src/formats/`, each rule pinned by a case file in `server/contracts/data/` (`npm run test -w nw-tracker-contracts`); the Python parsers assert the same files.
- **Number formatting**: all numbers (CLP, USD, UF, units, percents) share one decimal-separator convention from `client/src/numberFormatPreference.ts` (localStorage `nw-tracker.decimalSeparator`, seeded from the IANA timezone; toolbar toggle overrides). Always format via `client/src/format.ts` helpers — never `Intl.NumberFormat` / `toLocaleString` with a hardcoded locale for numbers. A separator change re-renders (not remounts) via `AppTree`; **do not cache formatted strings** in `useMemo`/state unless `decimalSeparator` is in the deps — memoize raw numbers, format at render. **Typed numbers:** every number field reads through `parseNumberInput` / `parseNumberInputOrThrow` (format.ts). A number that fits one convention is read that way («1500,5», «1.500.000», «1,234.56»); only a single mark followed by exactly three digits («1.500») is decided by the setting (1500 with comma decimals, 1.5 with period decimals); anything else is rejected with `common.numberInvalid`; forms keep their own sign/range/integer rules. Prefills and placeholders use `formatNumberInput`. Never `Number()` / `parseFloat` / `.replace(/\./g, "")` on typed text, and no `type="number"` inputs (the browser parses those by its own locale). The flows amount filter (`flowsAmountFilter.ts`) also takes an amount copied from the table: a leading `$` / `US$` and the negative «($500)».

## Page grid and tiles (`docs/layout-grid-plan.md`, `styles/tokens.css`, `shell.css`, `page-grid.css`, `cards.css`)

- **The shell is two tracks; only the content carries the column grid.** `.layout--with-sidebar` is `var(--sidebar-w) minmax(0, 1fr)`: the sidebar a fixed 11.625rem (sized to the widest nav label), sticky, outside the columns, its own `--sidebar-bg` (a shade above `--bg`), no border. **Its rows (`AppSidebar.tsx`, `AppSidebar.module.css`):** text sits on one column per depth (`--sidebar-text-x` + depth × `--sidebar-indent`, 8px); every net-worth group with rows under it (one that shows a chevron; a sub-bucket shown as a leaf has none) carries a 6px square in its card pill's colour (`markerRgb`, `mutedPillBackgroundRgb`) in the margin left of its text, and «Gastos» the expenses favicon's red down-pointing triangle (`EXPENSES_FAVICON_SPEC` in `favicon.ts`, the one definition both read), drawn in the selected chart style (`RoughSwatchBox` / `RoughSwatchTriangleDown` through `SketchMarker`, every style but plain; imported directly, as `Pill` imports `PillScribble` — lazy-loading them paints flat marks and bare pills until the chunk arrives). The open page's row has an inset rounded highlight and the groups above it read bright; a group opens/closes from a chevron in the same margin, which replaces its square on hover or keyboard focus (a group without a square shows it while closed, and always on touch; on touch the square stays and is itself the button). No carets, rails, hyphens or accent bar. An account that holds nothing today (`accountChartInactive`, dollar cash included) is not in the nav tree. Content is capped at `--page-max` (105rem from 1440, left-aligned beyond). Tokens on `:root`: `--content-cols` (4 on a phone, **12 from 880** on both desktop tiers, so a tile's span never changes between them), `--gutter` (1rem, 1.5rem from **1440**), `--row-gap` (= gutter), `--row-unit` (1.5rem, one UI line), `--margin-inline` (0.75rem phone, 1rem small desktop, 1.5rem big), derived `--content-w` / `--col-w`, plus `--hairline`. Media queries cannot read custom properties, so the two tier lines are literals wherever a stylesheet needs them; 880 is also the tables' narrow line (`useIsNarrowViewport.ts`), so the app has one small-desktop line. `.layout-main` (track 2) reserves the ticker's strip at the top and keeps `overflow: auto`, so anything wider than the content scrolls inside the main column, not the page; a table never should — it shows its cards instead (see «UI tables — desktop/mobile sync»). `.layout-main>.content` is the column grid; every page's `<main>` is one child spanning it. The ticker: on a phone a full-viewport bar and on the small desktop a bar across the content's width, both with the content reserving its strip (`.layout-main` padding-top); on the big desktop it covers the content's last 8 columns (5–12) and the content starts at the top. The prefs dock's max-width derives from the tokens.
- **Whatever a route renders is on the grid by itself:** `page-grid.css` makes the content region's direct child (a page's `<main>`, or a layout's) a subgrid of the content columns (`row-gap: var(--row-gap)`), so a page root declares nothing. A container INSIDE a page that holds tiles of its own says so with `.page-grid` (same subgrid): a Loadable shell (`GroupInfoBase`, `AccountDetailSharedLayout`, the tax return), a page inside the flows or panel layout with its own root (groceries), a tile grouping sub-tiles. Each section is a **`PageGridTile`** (`components/layout/PageGridTile.tsx`: `<section data-tile=… class="page-tile">`) with its heading INSIDE it, so the row gap is the only space between sections — no outside margins (`.page-tile>:is(h2,h3,h4,.chart-panel-title-row):first-child { margin-top: 0 }`, `.chart-panel-title-row>:is(h2,h3,h4) { margin: 0 }`; no inline `marginTop` / `margin` / `fontSize` on sections). A `.chart-grid` is a subgrid where it is a page-grid child (two panels on six columns each from 880; `--full-line` all of them) and a plain 12-column grid with the same gutter elsewhere. Chart titles and surface controls use `.chart-panel-title-row`; control styles live in `styles/controls.css`. **Account pages are on the grid (`AccountDetailSharedLayout`):** the content shell is a page grid, the strip a `page-grid` tile, and every section a tile (position, charts as `chart-grid` tiles, returns, detalle, cartola months, each credit-card table, mortgage form / sheet / scenarios / prepayments, capability forms, flows); a section made of several tiles (the card's cuotas block, the Pasivos credit-card and mortgage sections, the depto ledger block) is a `page-grid` container with one dim marker, so the same components sit on the Pasivos group pages inside `GroupInfoBase`.
- **A card's title is a pill in its bucket's colour (`DashboardCardTitleRow` `colorRgb`):** the nav node's own `color_rgb` (the colour its chart lines use, set from the panel), drawn with the shared `Pill` on a muted version of it (`mutedPillBackgroundRgb`: lightness ×0.9, chroma ×0.8 in OKLCH); small, not uppercase, the text the pill's own colour with only its lightness moved (`tintedTextOnRgb`: dark on a light pill, light on a dark one). A card with no colour keeps plain text.
- **Card numbers flash on a change (trial; `numberChangeEffect.ts`, `AnimatedNumberFlow` `changeEffect`):** when a strip card's balance or breakdown line changes in the same display unit after a settled render, the digits switch at once and the cell flashes green or red by direction (`flashOnChange`): instant on, ~200 ms hold, 2 s fade; a new change restarts it. The four P/L figures and the summary cards' balances (the page's own total in row 1 and an account page's hero, `CompactEntityCard`) do not flash; they keep the rolling digits. A currency switch, or a dimmed placeholder giving way to live figures, keeps the rolling digits. `NUMBER_CHANGE_FLASH_ENABLED = false` brings the rolling digits back everywhere.
- **Cards have no chrome and touch** (no padding, background, border or radius, no inset yet — aligning card text with the container edge is the next step; `--card-radius` only skins popovers and the modal). A strip is `.cards-strip` (`PortfolioEntityCardsStrip`: one `.cards.cards--summary` block over one `.cards.cards--detail` block; the accounts table a sibling `.cards-strip__table`), a subgrid of the content columns; each `.cards` block is **four equal columns of its own** across the strip with no gap (not a subgrid of the page columns: the gutters would split across the cards and make the outer ones narrower, misaligning the rows). A row the cards do not fill closes with a line just outside its last card (`box-shadow`), on the pixel the next row's card draws its left border on; dividers are per-card borders stripped by a **fixed 4-up count** (`nth-child(4n+1)` no left border, `nth-child(n+5)` a top border; never auto-fill), the one line between the blocks the detail block's border-top. The summary row is the same 4-up block with two cells empty. Below 880 cards are 1-up, 2-up between 600 and 879. A bare `.cards` outside a strip (the flows periods, the mortgage / credit-card summary rows) is a plain 4-column grid with the same dividers. `.chart-box`, `.chart-box--pending` and `.table-wrap` have no chrome (the pending chart frame is the title row plus the reserved height).
- **The dashboard's big-desktop rail (≥1440):** `GroupInfoBase` takes `rail` (and `tileOrder`); with it the strip and `charts` (the net-worth chart) go into `.page-main` (columns 1–8) and the rail tiles into `.page-rail` (9–12, pulled back one gutter so the two stacks touch), two independent column stacks (never shared explicit rows: a tall rail table would open whitespace in the main stack); below the rail band the tiles take their own order and span from the layout table (`PageGridTile` `wide` → `--tile-order-l` / `--tile-span-l`, `dashboardTileWide`): flows chart | Δ by class, returns across, allocation | the detalle table, then the wide tables, then the export row and the accounts tree last, full width on every tier (the export row always right above the tree). Below 1440 the two containers are `display: contents` and the tiles are page-grid items ordered by `--tile-order` = `DASHBOARD_LAYOUT[id].s.y` (`client/src/dashboardLayout.ts`, the one table of tile rectangles per tier in react-grid-layout's own shape — `GRID` is its `Responsive` props; `dashboardLayout.test.ts` asserts reading order, spans and big-desktop placement). In the rail a `.cards` block is 2-up (a `.cards--list` block — «Próximos pagos» — stays one card per row there and at 600–879; a `.cards--pair` block — the «Flujos» periods — stays 2-up below 600 too) and a parallel table shows its mobile rendering by the rail's width (`@container rail (max-width: 40rem)`). The home «Flujos» section is two tiles: `DashboardFlowsPeriods` (rail) and `DashboardFlowsChart` (main), on the same react-query entry. On the small desktop (880–1439) the periods and «Próximos pagos» share a row, half the columns each (`SMALL_PAIRS` in `dashboardLayout.ts`, `PageGridTile` `smallSpan`; the periods' cards 2-up), and below the big desktop the tiles take their reading-order index (`dashboardTileOrder`), not a `y`. Group pages have no rail (one stack, same tiles). **The detalle tables are row lists, one rendering at every width (`PerfDetailRows`):** monthly / yearly (`MonthlyPerfDetailTable`) and daily (`DailyPerfDetailTable`) rows read by symbols, not column labels (each figure names itself on hover): flows by an icon each in the text colour — expenses a shopping bag, income two stacked banknotes, contributions a coin stack with a leaning coin (the piggy bank is savings, on the home «Flujos» panel) — with the signed amount (negatives in parentheses) giving the direction; the net-worth rows' income and expenses are `income` / `expenses` on `GET /api/groups/net_worth/consolidated-monthly?installment_mode=`, from the flows overview's months; an account's units keep a → / ← arrow, the result ▲ / ▼ with its % in the sign's colour, YTD and Σ quieter. ## Per-surface display controls

- **Período/Rango are per-surface, not global.** Every chart owns a compact Período (D/M/Y) + Rango control and every perf/flows period table a Período-only control (tables always cover FULL history and paginate at every grain). State: `client/src/surfaceDisplayPrefs.ts` — `useSurfacePrefs(surfaceId, defaultPeriod, defaultRange)` persists partial `{period, range}` JSON under `nw-tracker.surface.<pageKey>.<surfaceKey>` (missing field = caller default; per page instance; deliberately no cross-tab sync). UI: `components/ui/SurfaceControls.tsx` in `ChartPanelTitleRow`/heading rows. The global toolbar (`AppDisplayPreferencesBar`) carries the display unit only; the old `nw-tracker.metricsPeriod`/`.timeRange` keys are cleared at boot. Bullets elsewhere that say "toolbar Período/Rango" mean this per-surface pair.
- **Defaults**: home value charts + group/account/Pasivos valuation = Diario+3y; every P/L combo, flows chart and the CC charts = Mensual+3y (the CC ledger surfaces are independent controls — `CreditCardLedgerSurfaces.tsx`, one implementation for the card page (`cc.<id>.*`) and the Pasivos / credit-card group section (`liab.cc.<slug>.*`): `.historial` is D/M/Y + Rango and the `.detalle` table M/Y period only; the group pages get Diario through the daily-series CC block summed over the merged ledger's masters, see «CC per-day owed + daily extras»); tables = Mensual (+ full history); proportional charts = Mensual+Todo (the Pasivos root's coverage chart, which takes that slot, Mensual+3y); rates = range-only 1y. **A Rango of N days is N days ending today, today included, on both sides:** `timeRangeCutoffYmd` = today − (N − 1), the same as the server's day windows (daily series points, flows overview day rows). Every client clip goes through `clipPointsToTimeRange` / `clipRowsToTimeRange` (no inline `>= cutoff` filters).
- **Axes.** Every value chart's Y axis starts at 0 for non-negative data and spans 0 for mixed-sign data — one helper, `buildNiceYAxis` (`client/src/components/charts/chartLayout.ts`). Two deliberate exceptions: the Rates page keeps `buildNiceYAxisPositiveBand` (a quote series is about the move; a 0-anchored UF axis is a flat line) and the wealth-percentile top-% axis is a reversed log scale that cannot contain 0. X ticks are **phased on January**: month strides are divisors of 12 (1/2/3/4/6) walked from the first month index that is a multiple of the stride, so a 4-month stride reads ene/may/sep whatever month the series starts in; the day-grid helper phases its month-first ticks the same way, and multi-year strides land on round years (even years for 2, 2015/2020/2025 for 5). Only the first-data-point push (year branch) and the appended last point may sit off-phase. Known residue: on a daily grid whose first month is partial, a tick that phases onto that month sits on the first grid day, not the 1st (`computeRegularMonthXAxisTicks` cannot tell a daily grid from a month-end series with a live last point).
- **Cards show all three periods at once** (no card period anywhere): metrics grid = Mes and Año deposits + P/L rows, a divider, then the dimmed Total row (lifetime deposits + P/L); the Día P/L sits on the balance row beside the main value, with no day deposits figure (`DashboardCardGroupMetrics.tsx`); then breakdown. There is no title balance-Δ chip / `title_delta`. Chart-inactive visibility = any-period activity.
- **Composition charts are proportional** (100%-stacked areas at every grain, own controls; no pies): server-built share series in `server/src/proportionalSeries.ts` — per date base = Σ max(value, 0) over member lines (negatives floor to 0, base 0 → null; Σ shares == 1) — emitted pre-clip as `group_allocation_proportional` + `nav_grouped_proportional`/`liab_grouped_proportional` (group payloads), `allocation_proportional` (home bundle + overview-daily) and `proportional`/`grouped_proportional` (`/api/daily-series`). Client renders via `ProportionalAreaChart` (shares are unit-invariant — keep-prev passes them through unscaled). **One level only:** the home chart stacks one level below the «big» buckets of the net_worth nav tree (`compositionBigBuckets`, `dashboardComposition.ts`: net_worth's children, where a `nav_bucket` without a `dashboard_bucket_slug` — Inversiones — is replaced by its own children; liability and reference groups skipped). Its lines are each big bucket's first-level children — a child group is one line (Σ of its `listAccountsForGroupTab` accounts), a direct account one line (name, account colour) — in nav order; label, i18n key and `color_rgb` come from the nav node and the client colours by the payload colour. Values are the dashboard's marks: monthly `slugMarkTotalsAtDatesClp` at the chart dates only (reusing the primary-lines totals for the same group), daily `accountMarkClpSeriesOnGrid` — so they agree at month-ends — computed in CLP since shares are unit-invariant. The linked credit-card netting (`cashNetOfLinkedCreditCards`) is subtracted from the savings line (`isCashSavingsNavNode`, same as the value map); the builder throws unless exactly one line carries it, if an account sits in two lines, or if a bucket account is in none. A group page's chart is always its direct children (`nav_grouped_proportional` is that single block) whatever the Agrupado toggle says, a leaf page its accounts; there is no `ungrouped` proportional block. Pasivos is separate (unchanged by this rule).
- **Value map («Mapa», `navValueMap.ts`).** A finviz-style treemap in the composition chart's slot on the dashboard and on every net_worth group page with something to tile — sub-groups or accounts of its own (leaf pages too, even with a single account; Pasivos keeps its chart); a «Composición / Mapa» select in the panel title row (stored per surface as `view` beside `<pageKey>.proportional`; the map's own Día/Mes/Año return window is `<pageKey>.map`, default Día; Rango does not apply). Nesting is the net_worth nav tree: a group with GROUP children is a frame (header strip with name + %, when there is room), a group without is the smallest tile, which carries its accounts (`leaf_accounts`): a leaf group opens into them at any depth when it holds two or more, a single account stays the group's own tile except on the page's own first level, which always opens — the page root opens into its own accounts even with one; the client decides by depth from the page root. Liability and reference groups are not in the map. **Additivity:** tile values are Σ of account rows' current values, each account claimed by one tile (a duplicate throws), so frames add up; the one non-row figure is the linked credit-card total, which the cash card nets (`cashNetOfLinkedCreditCards`) and whose footer sits on the savings card, so the SAVINGS tile carries it (checking is a sibling leaf group and stays raw) and the cash frame equals the cash card value. Every node carries its TRUE value, negatives included (a frame = Σ of all its children); a node worth ≤ 0 is left out of the payload but still counts in every ancestor (so a card bigger than savings + checking hides the whole cash bucket, and the root stays net worth). The client sizes a frame's area by its visible children; tooltips show the true value. The map shows whenever it is the selected view: during a unit switch or a refetch it keeps drawing the last data it had (`useHeldValueMap`), never swapping back to the composition chart. Size = value in the display unit; colour = the node's flow-adjusted % for the period (`row_pct` rule over the node's rows, a single row for an account tile; an empty member with no delta does not blank a group's %) against FIXED per-period bounds the server emits (day ±3%, month ±8%, year ±25%; null % = neutral). The layout is our own squarified treemap (`treemapLayout.ts`) — Recharts' `Treemap` cannot reserve a frame header — drawn by `ValueTreemap.tsx` with CSS tokens `--treemap-*`. Every frame keeps its header: a frame squarified smaller than its minimum (header + a body, and for a frame holding frames, room for their minimum too) is grown at its siblings' expense, and each node's area is its value at one global px-per-value plus the area its headers and padding take (re-measured over a few passes), so a tile inside a frame has the same area per value as one outside. A tile's label shows only when it fits whole (text measured on hidden spans): name over % from ~36 px tall, one row from ~22 px, else none; a header drops its % first, then shortens the name. The tooltip always shows value, % and P/L; a click goes to the node's route.

## Loading states (`components/ui/Loadable.tsx`, `components/charts/ChartEmptyState.tsx`)

- **No view is ever replaced by a loading screen.** Every page renders its real layout at once; while a query is pending each component renders its frame with the values it has — zero placeholders, held prior data, an empty table — and dims (`Loadable` / `loadableClass`: `.loadable.is-loading`, opacity .55, inert, `aria-busy`; nested markers never compound, and `.chart-panel-title-row` stays clickable inside a dimmed surface so a Período/Rango/view change is a new request, never blocked). The only loading text is a button label while its mutation runs; never a bare «Cargando…» paragraph, `null`, or a page re-gated on a Diario/unit change. **Eager pages, lazy charts, idle prefetch (`App.tsx`, `lazyChunks.ts`, `components/charts/lazyCharts.tsx`):** the dashboard, group, Pasivos and account pages plus the flows and panel layouts ship in the entry chunk, so a document load paints the page's own layout; the chart engine (recharts) is one lazy chunk reached only through `lazyCharts.tsx` (`chartsBundle.ts` re-exports the chart components the eager pages use), whose Suspense fallback is the chart's own frame — title row with live controls plus the pending box — so a chart slot never shows text; secondary pages stay lazy behind a `null` fallback (`v7_startTransition` keeps the previous page during in-app navigation; the flows and panel layouts wrap their `Outlet` in their own `Suspense` so a direct load keeps the h1 and tabs), and `useIdleChunkPrefetch` imports every registered chunk — charts first — in an idle callback after first paint, after which navigation and charts are synchronous (`lazyComponent` renders a loaded module directly). The entry chunk must carry no recharts. **A first-ever visit (no cached nav tree) is blank, not a message:** the sidebar shows the Net worth link and the Panel footer; the dashboard and the group / Pasivos pages (`GroupInfoBase` `coldStripShape`) draw `PlaceholderCardsStrip` — nameless cards (blank title, value and metric rows at the real rows' height, same grid and shells) in the shape `client/src/coldPageShape.ts` states (`DASHBOARD_COLD_STRIP` 2 summary + 4 bucket cards, `GROUP_COLD_STRIP` 1 summary card; a guess for the paint before the tree arrives, never routed through `requireNavCardMetrics`); a page title with no name yet (`PageTitleRow`) keeps a title's height, so the account placeholder is a blank title, not «Cuenta #id».
- **The home panels paint from the browser's last copy (`queries/persistedPayloadCache.ts`).** «Flujos» (its two closed periods, per unit and expense mode), «Próximos pagos» and «Últimos movimientos» (per unit) keep their last live payload in localStorage and show it, undimmed, until the server answers, like the strip's nav snapshot, the sidebar tree and a group page's shell. One key scheme for all of them, `nw:cache:<name>:v<version>[:<scope>…]`, the version being the payload's `schema_version` (`DTO_SCHEMA_VERSIONS` in contracts) or, for a shape the client builds itself, the client's own; older versions and keys of earlier conventions are swept at boot (`sweepPersistedPayloads`). A held payload of the other unit is never stored; an entry whose shape the client does not read (`isValid`) is ignored.
- **A background refetch never dims (`queryShowsLoading` in `queries/pageShapeReady.ts`).** A query-backed view's `loading` is `isPending || isPlaceholderData` — no data yet (a disabled query included), or the previous page / filter held — never `isFetching`, because the live-quotes stamp invalidates queries on each price move and everything would dim on every tick. `isLoading` is not the signal either: it is false while placeholder data is shown and for a disabled query. `npm run check:conventions` flags `isFetching` / `isRefetching` in `components/` and `pages/`. **A failed background refetch never hides data either (`queryLoadError`, same file):** react-query keeps the last data and sets `error` when a refetch fails; a view shows its error instead of its content only when it has no data (`queryLoadError(q)` = `q.error` while `q.data` is undefined) — a server restart must not replace a page with an error.
- **Every data component takes `loading?: boolean`** (charts, tables, sections, the CC surfaces, `PeriodReturnsWithBenchmark` with `data: … | null`) and dims its own root. A chart's empty branch is `ChartEmptyState`: while loading an empty `.chart-box--pending` at the chart's size (`boxStyle` for the fixed-height ones), otherwise the «no data» copy — loading and absence never share a message. Tables render their header with no rows while loading; the empty label is for a loaded, empty result.
- **A Diario chart never draws the monthly data.** In day mode a chart shows its pending frame — the title row with its live controls over an empty box of the chart's size (`ChartEmptyState` with `loading`) — until its own daily payload for the current unit has arrived (query neither pending nor placeholder, `queryShowsLoading`); the page passes it no points (an empty block, `null`, `[]`), never `dailyBlock ?? monthlyBlock`. Monthly and yearly modes are unaffected. Applies to the dashboard overview, composition and Δ combo, the group and Pasivos valuation / composition / coverage / P/L charts, the Pasivos mortgage combos, the card historial and the account valuation and P/L combos. The home net-worth chart shows the same pending frame in Mensual and Anual until the real bundle is in (the placeholder bundle's zero lines are not drawn, since they only flash before the lines' draw-in). A group's P/L combos stay mounted in day mode whatever their points say (`PortfolioGroupChartsSection`), so the controls can switch back.
- **Recharts is patched (`patches/recharts+3.10.1.patch`, applied by the root `postinstall: patch-package`).** A Line's first draw-in never recorded reaching the end (its final frame, elapsed 1, renders after `isAnimating` turns false, so `useAnimatedLineLength` is never asked for it, and its 4-decimal rounding can leave even that frame short of `getTotalLength()`), so the first data update redrew the right edge of every line. Changes (both builds, `es6` and `lib`): `Line.js` passes the final frame to `getVisibleLength`; `useAnimatedLineLength.js` counts elapsed 1 as full; `LineDrawShape.js` gives an unmeasured line (length 0 on first render) `stroke-dasharray: 0px 1px` (hidden) instead of `0px 0px`, which the browser draws solid, flashing every line in full before its wipe-in. Still needed in 3.11; drop the patch once Recharts fixes it, and re-check it on any Recharts upgrade (patch-package fails the install when it no longer applies). The deploy re-runs `npm ci` when `patches/` changes (`needs_ci` in `scripts/server-deploy.sh`). Separately, `LineChartPanel` keeps its plotted rows across refetches (`useStableChartRows`: unchanged rows keep their objects, a rebuild that changes nothing passes the same array).
- **Loading is not absence.** A server-stated absence (an explicit `null`, an empty list after load, a capability schema such as `movement_create`) hides the subview; a pending query must not read as one. `period_returns` is `undefined` while loading and `null` when the server says none (`useGroupInfoConsolidatedTables`, `useAccountDetailPageData`); the account placeholder takes its category and title from the cached nav row / nav node (`placeholders/accountDetailPlaceholders.ts`), so category-keyed blocks mount right at first paint; the card strip mounts on a cold cache from `buildPlaceholderNavStripDash` (zero `card_metrics_by_slug` for every nav group node, so `requireNavCardMetrics` holds). Accepted pop-ins, because the client cannot know them before the bundle: the CC/mortgage sections and perf combos of a group that turns out to have none, the capability forms. The dashboard's `chart_shape` and the group pages' `chart_buckets` are the nav-time hints for the patrimonio/perf panels and the grouped toggle, and `chart_coverage` (`groupHostsLiabilitiesCoverage`) marks the Pasivos root so the coverage chart mounts from first paint instead of the composition chart swapping out when the payload lands.
- **Keep-previous-data is scoped to the entity** (`displayUnitQueryBehaviorFor(queryKey, entityKeyLength)` in `queries/displayUnitQueries.ts`): a unit, period, range, page or filter change holds the previous payload (the page dims it; `isPlaceholderData` means held data of the SAME group/account/scope), while a different group, account or daily scope starts from its placeholder (bare `keepPreviousData` would show account A's bundle, undimmed, under account B's title). **A held prior-unit payload is never fx-converted:** a unit switch shows the target unit's own react-query data when still warm, else the dimmed zero placeholders for charts and tables — and for the CARD STRIP the previous unit's cards, dimmed and in THEIR unit, which flip to the new values once they land (the dashboard from its held bundle; the group, Pasivos and account pages through `useHeldNavStrip`, the previous unit's nav context or stored snapshot, the account hero from its held detail row — `AccountDetailPageData.stripUnit`); the target unit's stored snapshot wins when it has one; a blank strip only when neither unit has anything. The nav snapshot and nav context queries are keyed on the unit (entity length 2) so neither holds one unit's payload under another; the dashboard cards always animate. The ticker, watchlist and Flows P/L keep previous data across their unit/window changes too. Pages gate `notFound` / `loadFailed` / `<Navigate>` on the nav query having settled, never while it is pending.

## An account's value: what it holds, converted once (`docs/holdings-currency-plan.md`, `accountValue.ts`, `holdingPrices.ts`, `valueConvert.ts`, `rates.ts`)

- **Value at a date = quantity of what the account holds, converted ONCE into the display unit.** `accountHolding(id)` (`holdings.ts`): a currency (pesos, dollars; property and mortgage in UF), a stock (quote currency), a coin (dollar price series), fund cuotas (peso-priced) or a card. `accountHoldingQtyAt(id, ymd)` = quantity; `holdingPriceAt(instrument, ymd)` = unit price in its quote currency (past day: stored observation on/before, history tier; today: live quote in session, held print after close, display-session bar, newest bar; a fund's live/per-date Risky Norris proxy); `accountValueAt(id, ymd, unit)` = qty × price → `convertValue` (`valueConvert.ts` over `rates.ts`). Never build pesos and convert back. Historical stack `accountHistoricalQtyMark` (`accountMarkClpAtYmd.ts`: branches return quantities; an instrument is the asset only on days its price is on file, else fall through); `accountMarkClpAtYmd` = that in pesos.
- **Spread side = what closes the position.** Assets: foreign → CLP at bid, CLP → foreign at ask; liabilities flip (`holdingIsDebt`). UF and EUR have no spread. Stored days read `fx_daily` with bid/ask observed that day or later, else mid ∓ half `FX_BID_ASK_SPREAD_CLP`. Flows convert per event at the mid (`flowEventInUnit`, `convertTs`, `clpToUnitAtMid`), as do benchmark levels.
- **Today reads the live rate** (USD/CLP while the fx day is open, `fxForLiveMtm` in `rates.ts`). `accountTodayValue(id, slug, opts, now) → {value_clp, native_value, native_currency, side, as_of_date, priced_on}` is the one today value (dashboard row, header, today's mark, perf live row, every chart live point); other units convert the NATIVE value with `todayValueInUnit(id, v, unit)`. `priced_on` is informational only.
- **`accountValueClpToUnitAt(id, clp, ymd, unit)`** converts a peso-native account value at the account's side and re-reads a value native in another currency (`accountValueCurrency`) from its holding. `clpToUnitAt(clp, ymd, unit, {side})` is for amounts that aren't one account's value (cards netted from cash, liability totals at `side: "debt"`). Bucket/net-worth sums in a unit = Σ each account's value in that unit per day (`buildDashboardBucketDailySeriesInUnit`, daily series, overview, ATH) — never Σ pesos ÷ one rate.
- **A card's value in a unit goes through one seam, `cardValueInUnit.ts`** (owed walk in pesos at the debt side); the card phase will replace it with per-currency sub-balances. The property and mortgage are still the depto ledger's pesos (peso quantities) until the loan phase.
- **Stored valuations are in any currency (migration 260, `valuationValue.ts`).** A `valuations` row is a quantity in `currency` (any lowercase code). Generic readers convert once on the row's date at the account's side (`storedValuationInUnit`: `valuationLatest.ts`, `bookValuations.ts`, `valuationTimeseries.ts`); the historical stack (`accountMarkClpAtYmd.ts`) carries book marks in pesos, so a non-peso book mark with a carry window throws. Kind-specific readers assert their currency (`assertValuationCurrency`: card CLP anchors, AFP/Fintual peso marks). Property rows are UF appraisals, left out by every mark reader (`valuationsAreAppraisals`); the mortgage has none (migration 261; the depto ledger values it, and property/mortgage chart month-ends come from the ledger, `augmentChartDatesForDeptoAccounts`). `GET /api/accounts/:id/valuations` returns `value` + `currency`; `POST` writes pesos and refuses a property.
- **The daily cache stores quantities** (`markSeriesStore.ts` cells `{qty, asset}`); unit values are built at read from memoized day price and rate (`accountValueSeriesOnGrid`), one series for every unit. Rate rows (`fx_daily`, `fx_daily_bid_ask`, `uf_daily`) trim only accounts whose quantity is a rate-built peso figure (cards — from the row's own day —, the depto ledger, book marks), never shares, coins, cuotas or dollar ledgers (`setRateIndependentAccountsResolver`). Price rows (`equity_daily`, `fund_unit_daily`) trim their holders (which asset a day holds depends on price availability).

## Data provenance (`DataOrigin`)

API payloads must **not** use top-level `source: "db"` / `"csv"` — the client always reads SQLite. Provenance describes how data entered:

| Account | `accounts.import_key` (identity; `notes` = same string as human provenance) | `import:excel|key=mortgage`, `credit_card_master|santander|<last4>`, `import:panel|ticker=QQQ|key=…` |

## Import sources vs runtime

**Rule:** files under `cfraser/` are **import inputs only**. HTTP, dashboard, valuation, and sync read **SQLite**; missing data → error or “run import”, not a silent file fallback.

- **Depto:** one movement ledger per property (`loadDeptoLedgerForProperty(id)`, cached `depto.ledger|rows|<property id>`; `deptoLedgerForAccount` / `deptoLedgerForLoan` / `loadAllDeptoLedgers`). Pairs come from `propertyLoanPairs()` (`accountRoles.ts`: a `property` role holder and its `loan_of` account); extra properties are `import:property|key=<k>` / `import:loan|property=<k>` (`propertyAccountImportKey` / `loanAccountImportKey`; migration 299's triggers seed the roles). Every reader («Próximos pagos», valor/hipoteca overlays, mortgage sections, card pairing, real-estate mortgage rows) loops over the pairs; the lender portal reading names its loan by `lender_pattern`. The ledger joins property-account movements with **`loan_payments`** (migration 258; docs/holdings-currency-plan.md phase 4): one row per payment movement, `leg` `property` | `loan`, `loan_account_id`, cuota, origin, and the bank's figures in its own currency — `balance_after`, `min_payment`, `max_payment` in `loan_currency` (UF); `principal`, `extra_principal`, `interest`, `insurance_fire`, `insurance_life` in `payment_currency` (pesos); readers throw on any other pair. Nothing derived is stored (parts' UF = pesos ÷ UF día, 4 decimals, the pago 5; net equity; `pagado_neto_uf`; `pago_acumulado_clp`; deltas/acumulados are computed from `uf_daily`). The appraisal is a **`valuations` row of the property account in UF**, forward-filled by the ledger; a property's valuations are its appraisals (`valuationsAreAppraisals`, `valuationValue.ts`), so generic mark readers skip them and its chart samples month-ends from its first ledger row (`augmentChartDatesForPropertyAccounts`); its value is net equity (`deptoNetEquityUfBySnapshotDates`). Rows are **sequential daily balances**: order = `deptoLedgerChronoCompare` (date, then decreasing crédito restante for same-day prepago+cuota); `assertDeptoPrepagoSequencing` fails when a prepago raises the balance (regular cuotas may: grace-period capitalization); snapshot fills use exact-date cutoffs with prepagos included — never a month-end cutoff expansion or a prepago skip (one-day equity spikes, ± P/L couplets). `mortgagePaymentCreate` writes the movements (human notes, mortgage `flow_kind`) plus both `loan_payments` rows; manual-payment recompute updates in place. No `depto_snapshot`: the RE card synthesizes valor/hipoteca from the property + mortgage rows.
- **Account identity:** `accounts.import_key` (unique, nullable; migration 159) is the find-or-create key and well-known lookup (`import:excel|key=mortgage`, `import:fintual|cert|key=…`, `credit_card_master|<issuer>|<last4>`, `import:panel|…`); every creator writes it; `notes` holds the same string for humans, never read by code. Card→account resolution uses `credit_card_account_config.card_last4` (every master has a config row).

Runtime code must not use `fs.readFile*` / `readSemicolonCsv` on `cfraser/` except in `server/scripts/` and import helpers. Import-sync document coverage (`GET /api/import-sync/…`) may list files for admin tooling only.

Every 3 min the agent fetches `origin/main`; on a move it enqueues a `deploy` job (see «The job queue»; one queued, moved to the newest commit) and polls its claim ~150 s, else leaves it for the next run (stale after 15 min, so a dead agent can't drain the queue forever). Outcomes in `cfraser/deploy.log`, the job and app messages (failure = notification); `scripts/server-deploy.sh --check` dry-runs. Read-only deploy key. - Express async handlers must be wrapped in `asyncHandler` (GUIDELINES.md).

## Dashboard performance profiling

- **`npm run profile:dashboard`** (from `server/`): sequential builder timings on the test/dev DB (`NW_TRACKER_TEST_DB` or `server/data/nw-tracker.test.db`).
- **`DEBUG_PERF=1`** (or `DEBUG_VERBOSE=1`) logs `[heavy]` spans during requests.

Dropped by every explicit invalidation (`invalidateCcBillingDetail`, `invalidateMarketDataAggregations`); only requests in an invalidation→rewarm gap pay the build.
- **`GET /api/dashboard/nav-context`** (sidebar/group pages): account rows, card metrics, value map, no net-worth series; fetched on group/liabilities routes and account pages whose nav node has routable children (home uses the bundle). **Scoped** by required `?root=<nav node slug>` (`navContextScope.ts`): card metrics of the subtree and of groups its nodes host (`linked_card_slugs`), the account rows those nodes hold plus every liability account (the property card names the mortgage), the value map under the node; bucket totals, layout and liabilities breakdown whole. The Pasivos tree is searched first (net worth has a childless `liabilities` node). The client keys on the root and merges into the stored nav snapshot (`mergeNavContextIntoSnapshotCache`; never writes without one — a slice doesn't cover the tree); the warmer builds visited group pages' slices. It is requested beside the page's own requests and the strip shows as soon as it lands, dimmed until then.
- The dominant cost is usually the portfolio-group totals inside **`getDashboardValuationTimeseries`** / **`getGroupValuationTimeseries`** (`@heavy` in source).
- **JSON is serialized once and compressed** (`jsonResponse.ts`): `jsonResponseMiddleware` replaces `res.json` on `/api` with the same body, `Content-Type` and weak ETag (over uncompressed bytes, so 304s work across encodings); bodies ≥1 KB get `Vary: Accept-Encoding` and brotli (preferred on q ties; browsers offer it on HTTPS only) or gzip, never over an existing `Content-Encoding` or `no-transform`. A payload marked with `markJsonResponseCacheable` keeps bytes, ETag and compressed forms in a WeakMap keyed by the object (lives and dies with the cache entry). Marked: group and account daily-series responses (`groupDailySeriesResponse.ts`; account as `daily.series|response|account|`, dropped by API writes), `cachedGroupResponse`, the page bundle, nav snapshot/context, the account detail bundle, both card ledgers. **Only immutable cached objects may be marked** (a mutated object serves stale bytes); others are stringified per response at gzip 1 / brotli 1 (cached ones gzip 6 / brotli 5, once per build).

## UI tables — desktop/mobile sync

Parallel-renderings rule: GUIDELINES.md. Desktop columns are `<td className="desktop-only">`; mobile is `<TableMobileCard>` / `<TableMobileCardRow>` inside `<td className="mobile-only">`, usually in the same component or a companion (e.g. `CreditCardSections.tsx` + `CreditCardPurchaseMobileCard.tsx`).

**A table shows its cards whenever its desktop rendering does not fit** (`useTableFit.ts`, `Table` `fitToWidth`): below 880 px, and at any width when the desktop columns exceed the `.table-wrap` — `Table` measures after every render and wrap resize (class removed, measured, reset; synchronous, before paint, no state) and sets `.table-wrap--cards`, styled exactly like the narrow viewport (rule sets side by side). Default for every `table--parallel-mobile` table, so both renderings switch together; a fixed breakpoint can't work because a table is as wide as its data. `PeriodReturnsTable` (one markup, fixed layout, 34rem / 42rem-with-benchmark floor) flips by container query on its wrap (`period-returns`). Never fix overflow with a scroll box. A right-edge card's number-flow mask spills ~6 px, so card blocks at the content edge use `overflow-x: clip` (`.cards-strip`, home «Flujos» period cards). Check pages at 375 / 599 / 600 / 879 / 880 / 1024 / 1279 / 1280 / 1439 / 1440 / 1600 / 1920 for `.layout-main` scrollWidth = clientWidth.

**Expense line lists** (`CreditCardExpenseLinesTable.tsx`): month, facturación, «sin categoría», big-group and deposit-matched lists are one responsive list (no horizontal scroll, same rendering at every width; a container query moves pills under the merchant when narrow). A row: origin icon (`ExpenseOriginIcon` from the structured `origin`: card / bank / manual / payslip, account in a hover/tap card), date, big-group pill once set, category pill (`PillPicker`: option-pill popover, × on hover clears, «Único» inside; an unset big group is picked from the extras), merchant with note and an ⓘ card (counterparty, receipt, deposit link), amount with installment detail in superscript, and a ⋯ extras button (big group while unset, note, pieces, cuotas, delete) with a red badge when the line waits on the user. Header = three sort buttons (date, category, amount). A popover inside a `Modal` renders into its `<dialog>` (`AnchoredPopover`), since `showModal()` puts the dialog in the top layer.

**The flows list** (`FlowRows.tsx`, under `FlowsTable`'s filters): a row list, not a table. When every row fits on one line, rows are subgrids under a header — date, type pill, accounts, amount (units superscript), note (the one flexible, ellipsized column); below the container breakpoint (`flow-rows-wide` 58rem when both accounts are named, `flow-rows-narrow` 44rem on an account page) a row is three lines: date + type + amount, accounts, note. **An intra-group transfer shows once** (`assembleFlowRows`, `flowsApi.ts`): the origin's row, `internal`, unsigned, with a side-neutral type (`internalTransferFlowType`: «Traspaso <CODE>», or «Cambio de divisas» across currencies; share purchases and card payments keep their type); account/bucket filters match either side (`counterpart_bucket_slug`). A transfer leaving the group keeps its signed leg. Every row carries `from_account_*` / `to_account_*` and `money_direction` (`moneyDirectionForAccount`: by leg for transfers, else by signed amount in its own currency, then units; null only for a zero opening anchor; anything else undecidable throws). Labels naming a currency take it from the movement (`movementFlowTypeLabel(type, {currency, counter_currency})`). Accounts cell (`flowAccountsCell`): on a group/dashboard origin → target («→ account» from outside, «account →» leaving); on an account page the page's account is omitted and the arrow shows left (→) or arrived (←), then the other account.
