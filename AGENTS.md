## Language and i18n

- **UI copy via i18n (es + en)**: the UI is bilingual. All user-facing strings live in **`client/src/i18n/master.json`** — the single source of truth, same nesting as the locale files but every leaf holds both languages side by side: `{ "en": "Save", "es": "Guardar" }`. `locales/es.json` / `locales/en.json` are **generated** from it by `npm run i18n:generate -w nw-tracker-client` (`client/scripts/i18n-generate.mjs`); never hand-edit the locale files — `client/src/i18n/localeSync.test.ts` fails on any drift. The master stays nested (not flat dotted keys) because some leaf keys contain literal dots (e.g. `panelAccounts.addAccount."accountType.equity"`). Do not hardcode Spanish or English labels in components except via `t('…')` / `i18n.t('…')`.
- **Translation keys in English**: use dotted paths such as `dashboard.cards.netWorth`, `brokerage.groups.mutual_funds`. Code identifiers use English slugs (`mutual_funds`, `real_estate`); display copy lives in `master.json`.
- **Shared labels**: use helpers in `client/src/i18n/index.ts` (e.g. `brokerageGroupLabel`) so the sidebar, dashboard cards, and charts read the same keys.
- When adding UI text, add the key (both languages) to `master.json` first, run `npm run i18n:generate -w nw-tracker-client`, then reference it from code. Migrate existing hardcoded strings when touching an area.
- **UI language preference**: `client/src/languagePreference.ts` (localStorage `nw-tracker.language`), seeded once from `navigator.language` (Spanish → `es`, anything else → `en`; non-browser/vitest contexts stay `es` so label assertions are deterministic), then the stored value is authoritative. Changed from `/panel/settings` via `DisplayPreferencesContext.setLanguage` (calls `i18n.changeLanguage`, persists, and keeps `<html lang>` in sync; the context change re-renders `AppTree` top-down). The decimal separator remains an independent setting. **Do not cache `t()` results** in `useMemo`/state without the language in the deps — translate at render time.
- **Dates**: numeric dates render as ISO `YYYY-MM-DD` (timestamps `YYYY-MM-DD HH:MM`) in every language — never `dd-mm-yy` / `toLocale*` short styles, which are ambiguous across locales. Month-name labels (`dic 2026` ↔ `Dec 2026`, chart ticks `dic 16` ↔ `Dec 16`) go through `client/src/formatDateLabel.ts`, which reads `i18n.language` at call time — same no-caching rule as `t()`.
- **Enforced by `npm run check:conventions`** (root; also runs at the end of root `npm run typecheck`): flags accented Spanish in client string literals/JSX (comments exempt), `Intl.NumberFormat` outside `format.ts`, hardcoded-locale `toLocaleString` without date options, and month-name tables outside `formatDateLabel.ts` (2026-09-26: `formatYmEs` and two private copies had kept month labels Spanish in the English UI). Escape hatch: `// convention-ok: <reason>` on the line.
- **Number formatting**: all numbers (CLP, USD, UF, units, percents) share one decimal-separator convention from `client/src/numberFormatPreference.ts` (localStorage `nw-tracker.decimalSeparator`, seeded from the IANA timezone; toolbar toggle overrides). Always format via `client/src/format.ts` helpers — never `Intl.NumberFormat` / `toLocaleString` with a hardcoded locale for numbers (dates: see the Dates bullet above — ISO numerics + `formatDateLabel.ts` month names). A separator change re-renders (not remounts) the tree via `AppTree`; **do not cache formatted strings** in `useMemo`/state unless `decimalSeparator` is in the deps — memoize raw numbers and format at render time. **Typed numbers (2026-09-27):** every number field reads through `parseNumberInput` / `parseNumberInputOrThrow` (format.ts). A number that fits one convention is read that way («1500,5», «1.500.000», «1,234.56»); only a single mark followed by exactly three digits («1.500») is decided by the setting (1500 with comma decimals, 1.5 with period decimals); anything else is rejected with `common.numberInvalid`, and forms keep their own sign/range/integer rules. Prefills and placeholders use `formatNumberInput`. Never `Number()` / `parseFloat` / `.replace(/\./g, "")` on typed text, and no `type="number"` inputs (the browser parses those by its own locale). The flows amount filter (`flowsAmountFilter.ts`) also takes an amount copied from the table: a leading `$` / `US$` and the negative «($500)».

## CC chart / Pasivos convention

**"owed on that date", not billing-month totals.** Per-card chart lines, the Pasivos group Total, `accountMarkClpAtYmd`, and the net-worth dashboard Pasivos line all read stored `valuations` via `latestCreditCardValuationRowAsOf`. **Today is walked, not live-formula'd (2026-07-23):** every date — today included — is `last anchor strictly before it + evidence dated after it` (`ccOwedWalkClpAtYmd` in `ccOwedWalk.ts`, the single choke point `latestCreditCardDisplayedBalance` now uses; `as_of_date` comes back as the walked-through date so callers don't re-apply the window). The live billing formula (facturado + cupo en cuotas − cuota a pagar next mes) is a DIFFERENT framing of the same debt, so valuing today with it while history was walked dumped the whole frame gap into today's delta — ·0101 read +1x.xxx (exactly one TGR cuota, 9x.xxx ÷ 6) on a day with no purchase. Today's stamp is written from the walk too, so tomorrow's anchor is in the same frame. Billing surfaces (Balance total, detalle por mes, cupo) keep the live formula — that frame is their point. Consequence: a card's displayed balance is the evidence walk (·0781 7.xxx.xxx vs live 7.xxx.xxx), and it re-syncs to statement truth at each month-end anchor; there is no separate "Saldo pasivos" ref line (removed — Total carries the same series). The month-end points `upsertCreditCardValuationsFromLedger` writes are billing-detail `balance_total` = owed-at-cierre = **facturado + post-close plan remainder** (the plan remainder `installmentRemainingClpByCalendarMonth`, cuotas due strictly after the month — the just-billed cuota rides inside facturado only) + post-cierre window activity (charges +, PAGOs −) — evidence-based, re-synced after web-paste repairs in `mergeCcAccountFromParsedRows`. **The old `− cuota a pagar next mes` term was removed 2026-08-12:** it netted a double count that only exists when the cupo figure still CONTAINS the billed cuota (the bank's live cupo frame); against the post-close remainder actually used it sank every closed month-end anchor one billed cuota below true owed — provable at the floor (·0781 2025-01-31 anchor $2.xxx.xxx < $3.xxx.xxx of unbilled cuotas after the facturado had been paid in full), and visible as «deuda en cuotas» crossing above «saldo total» on every month whose payment landed on/before month-end (monthly view) plus the matching daily residuals. Anchors re-stamped the same day (see `server/scripts/restamp-cc-anchor-frame.ts`). **Today-stamps self-purge on contradicted evidence (2026-07-23):** `upsertCreditCardValuationsFromLedger` also stamps a `today` valuation on every CC write, freezing what the live formula said that day. Those stamps are only valid until dated evidence arrives for an earlier day — a paste of last week's purchases would otherwise leave the walk climbing through them and then snapping back, dumping the whole import into *today's* delta (·0781+·0101 read +3xx.xxx just past midnight on 2026-07-23). So the writer takes **`affectedEvidenceFromYmd`** and deletes every non-month-end stamp from that date through yesterday before rewriting (month-end rows are statement-derived and the same run re-syncs them; the purge runs before the has-points early return — removing wrong data must not depend on having new data). **Every caller that adds or removes dated evidence passes it**: the merge import (`earliestInsertedTxDate` over genuinely INSERTED lines — dedupe-skips contribute nothing, so re-pasting is idempotent — plus new `purchase_date`s and the header pagado date), line deletions (`earliestTransactionDateForLineIds`, read BEFORE deleting), and manual installment create/edit/delete (edits use min(old, new) date). Pure recomputes omit it. Trade-off: a purged stamp loses that day's live-frame correction; the walk carries from the previous anchor. Older manual audits stay relevant only for balance-convention changes (six stale ·0781 rows from the missing-PAGO era were purged 2026-07-22; four contradicted 2026-07 stamps purged 2026-07-23).

- **A card's P/L is its cost of financing (2026-07-22), loss-negative like the mortgage.** Liability accounts mark as positive debt, so every P/L surface uses `pl = prior − owed − flow` — daily series, monthly `nominal_pl`, dashboard `delta_day`, group P/L bars. For a card, P/L = **−(section-3 charges: intereses, comisiones, impuestos)** dated on the day each was charged (`ccFinancingCostDaily.ts`; the classifier is the same `isClp/UsdSection3FinancingChargeMerchant` predicate the financing chart sums, so the two agree — verified against `statementSection3ChargesClpForBillingMonth` per card, `server/scripts/verify-cc-financing-identity.ts`). Everything else that moves owed is **flow**, and it is **derived** (`flow = −Δowed + financing`), never summed from events: the stored anchors are live-formula stamps, so at a cierre the billing frame re-splits the same debt and the balance steps ~1M against a walk that saw no transaction (·0781 2026-06-19: +1.xxx.xxx) — measurement noise in the buy/pay legs, not cost. Cards therefore read `pl = 0` on ordinary days and only the bank's charges show up. **Interest inside installment cuotas is financing cost too (2026-10-05; `ccInstallmentInterest.ts`):** for a plan its statements print with a rate above 0, interest = the plan total (Σ printed cuotas) − the printed principal (every cuota line's `amount_clp`), dated on the purchase date — the owed walk adds the whole total that day, so the derived flow stays at the principal. A 0% plan that rounds a few pesos above its principal (BCI) has none, and a plan no statement has printed yet (hand-entered, from the feed) has none until one does. The dashboard's financing summary reads it in the purchase's billing month; the old annual-rate model (`annual_interest_pct`, always 0) was removed. **In «deuda en cuotas» the interest bills cuota by cuota (2026-10-05; `ccInstallmentInterestBillingEvents`):** the plan-debt walk adds such a plan's principal on the purchase date and each cuota's share of the interest at the close of the statement that bills it (projected close for one not billed yet), as the bank's owed counts it; the retirement still removes whole cuotas. Adding the total at purchase had put the unbilled interest above the owed line (·0161 PARIS 2023-02/03). The owed walk and the P/L keep the whole total on the purchase date. On the real DB: two ·0161 plans of 2023, 2x.xxx + 2x.xxx. Cost of the USD side's fx drift is **not** modeled (it is inseparable from anchor noise at daily grain). Card flows are NOT personal capital: they stay out of `/flows/deposits`, the deposits reconciliation, and the "aportes acum." companions, which is also why the `pago_tarjeta` mirror transfer's card leg emits nothing (`accountDeposits.ts` — the cash leg does emit its withdrawal). The mortgage's daily flow leg is `mortgageSheetPaymentEventsThroughDate` (depto ledger, same source as its dashboard cards).
- **One schedule framing (2026-07-13): the installment plan schedule is facturación/statement months everywhere.** `purchaseFirstDueYm` + index gives the month each cuota **bills**; per-month plan sums equal the statements' billed-cuota sums exactly, and `cuotaAPagarNextMesClp` / facturaciones read the billing month itself (never +1). Anchor precedence: cuota-01 statement month → cuota-00 preamble's statement month + 1 → stored `first_due_month` (web-paste nudge, write-once evidence) → manual guess = the purchase's **own** cycle as the bank closes it (`billingMonthContainingPurchase`; date-based so it can't drift; the next statement's evidence relocates it either way — cuota-01 pins the month, a cuota-00 preamble moves it to statement + 1). **Manual-source anchors clamp to the first pending facturación (2026-07-27):** the stored/guessed month for a plan with no statement cuota evidence advances to `last fully-closed month + 1` — an imported statement that didn't bill the plan is negative evidence, so an evidence-less manual plan can't inflate a closed month's cuota sums; statement-driven (never the calendar), so a lagging import queue keeps the date-based guess. **A facturación only closes when every statement currency the card's history carries is imported** (`lastPdfBillingMonthForAccount` / `accountRequiresUsdStatementClose` — the July-2026 USD twin arriving alone must not advance `open_billing_month` or retarget web pastes, and it settles only its OWN currency's lines in the open web-paste bucket — since 2026-09-26 `reconcileOpenWebPasteAfterPdfClose` settles per currency before the full close, because keeping the whole bucket counted the first twin's lines twice until the second arrived (the September 2026 ·0781 USD statement, imported hours before its CLP twin, billed US$x.xxx,xx for US$x.xxx,xx); a dormant never-billed USD side keeps closing on CLP alone; and a USD twin still missing once the bank has closed a LATER facturación — a later statement in either currency, a feed-observed close, or an announced close that has passed — is not coming, so the month closes on CLP alone: `pdfClosedBillingMonthsForAccount`, 2026-09-26, after every USD-quiet cycle had stayed «open» for good, the retired ·0161's CLP-only 2025 months among them, which the merged group ledger then flagged open as well. The bucket reconcile keeps the stricter per-twin check, `hasEveryStatementTwinForBillingMonth`: a CLP-only month's dollar lines still wait for a USD statement. A card that stopped billing, `creditCardBillingDetailInactive`, gets no provisional facturación rows, mirroring its detalle — ·0161's November statement announced a December close that no statement will ever follow). Web-paste-converted plans carry the issuer card_group (`'santander'`/`'BCI'`), PDF statements the parser groups (`'A'`/`'B'`/`'INTL'`) — the manual↔statement twin reconcile treats the web-paste group as compatible with any PDF group and tolerates ±2 days of purchase-date skew on indexed cuota lines (exact merchant/amount/cuotas still required). Nota-cancelled plans (full-principal NOTA DE CREDITO matched by posting **statement month** — banks backdate the transaction date, never the statement — or by a strictly-later transaction date) are excluded from every schedule aggregate via the loader's `schedulePurchases`; live cupo therefore matches the printed «cupo utilizado en cuotas». A fully **settled** ledger no longer force-actives a card (`creditCardBillingDetailInactive` requires outstanding principal, else the tail heuristic decides).
- **Cuotas por facturación (`payload.months`)**: one row per facturación event — `month` (facturación) + `pay_by_date` (statement PAGAR HASTA when closed; derived ~10th of the next month for open/projected) + `total_clp` + `debt_after_clp` (suffix sum; last row 0). Rows roll off once their pay-by passes (Chile day — the same clock that flips a fully-paid purchase from active to completed); `totals.next_calendar_month` reports the **pay** month of the next payment event. Purchase tables show `purchase_date` + `purchase_billing_month` (the bank's cycle containing the purchase date, `billingMonthContainingPurchase`), not the calendar purchase month.
- **Facturación proxy earnings are keyed by the facturación that billed the money (2026-09-26; `ccInvestmentProxy.ts`).** `facturacion_proxy` (the facturaciones table's proxy column, looked up by `billing_month`) invests each purchase from its purchase date until the pay-by of the facturación that billed it. A printed cuota is keyed by the plan schedule's month (`first_due_month` + N − 1) and withdrawn on its payment row's `pay_by_date`; a one-shot line is keyed by `facturacionMonthByStatementDate` (a stale bucket's lines → the open month) and withdrawn on that facturación's pay-by as the table shows it (`facturacionPayByIsoResolver`), so open and provisional web-paste lines take part. Superseded lines and count-less cuota purchases are left out, as the facturado leaves them out; an unparseable line date throws. Before: cuota gains sat one row late (pay-by month), bucket lines dropped out, and dd/mm/yy PDF rows were skipped.
- **Months after the open facturación are plan-only projections** (`projected: true` rows from `appendProjectedBillingDetailRows`), **pay-frame**: facturado is null (nothing billed yet) and saldo/cupo at month-end M = plan remainder after (M−1)'s close — a cycle's cuotas leave the debt on their **pay-by** (~10th of M+1), not at the close that bills them. One facturación step per month, flat from today through the open month-end, plus a trailing zero month after the final pay-by. Identity: chart month-end M = calendar-table row M's cuota + `debt_after_clp`. Closed months keep the statement frame (printed cupo; billed-unpaid cuotas ride inside facturado) and today keeps the live value — the seam is smooth because bank-frame(M) ≡ pay-frame(M+1). `latestBillingDetailRow` skips projected rows so the live «Balance total» / today's Pasivos point stays the open-month rolled balance. **The historial CHART's two lines are the daily data sampled (2026-10-05; `ccHistorialLinesAtMonthEndsClp`, passed as `linesForMonths` to `buildCcHistorialChartSeries` by the card payload and by `creditCardGroupLedgerResponse` summed over the same masters as the daily block):** «saldo total» (the owed walk) and «deuda en cuotas» (the plan-debt walk) on each month's last day, TODAY for the current calendar month, the plan tail after today (the plan debt once its last pay-by has passed); bars stay per facturación. Payment frame at every month, so the monthly and daily charts show the same numbers on the same day. Until 2026-10-05 only the cuota line was sampled (since 2026-09-26) and «saldo total» read the detalle row, whose open month was a roll-forward from the last statement that left out cuota plans bought in the cycle: converting the ·0101 payment line (1.xxx.xxx) to a plan dropped October's saldo below its cuotas. That roll-forward now adds them too (`installmentPurchasesClpAfter`, plans bought after the closed month's CALENDAR month-end — its cupo already carries the ones bought between its close and month-end). The detalle table's «cupo en cuotas» keeps the statement frame above (facturado + cupo = balance). A closed month used to plot its post-close remainder, one billed cycle below the daily line whenever the payment landed after month-end (·0901 31/08: 7,xx M monthly vs 8,xx M daily).
- **Historial bars (2026-09-26): one stacked bar per facturación**, bottom to top «Facturado CLP» (CLP facturado − the cuotas: únicos and the bank's charges, net of notas de crédito — negative when credits outweigh them, drawn below zero with `stackOffset="sign"`), «Facturado CLP (cuotas)» (the facturación's `cuota_a_pagar_clp`: the plan schedule, which equals the statement's billed cuotas) and «Facturado US$» (pesos at the rate the facturación was actually paid, see «Card dollars in pesos»; the tooltip shows «US$ X ($Y)» like the facturaciones table), one amber hue with the cuotas darkest; the tooltip reads top to bottom like the chart (saldo total, deuda en cuotas, total facturado over its segments). Built server-side in `buildCcHistorialChartSeries`; a month the plan only projects carries just its cuotas, and an open month no line has landed in yet (billing detail has it, facturaciones do not — no statement, no bucket) splits its detail facturado as CLP: with no lines there is nothing in dollars. **A group's bar is the Σ of its cards' own bars** (`memberSeries`), and the merged billing-detail row adds a projected member's cuota to a month another member has billed (`mergedTotalFacturadoClp` — the table's «≈ cuota» for that card alone), so the group table and the bars agree; neither is split again from merged facturaciones: a month one card has billed or opened while another only projects has no merged facturación carrying the second card's cuotas (the old grey «Pagos de cuotas» bar dropped ·0101's 3x.xxx from October 2026 on the Pasivos pages that way). **Day mode puts each card's bar on that card's close date** (`facturacionBarsOnCloseDates`, from the same cached bundle as the monthly bars: the facturaciones table's close, a projected month's `closeEvidenceForBillingMonth`), cards closing the same day stacked; the client runs the grid on past the plan tail to a later close, draws fixed-width 6 px segments (Recharts shrinks `barSize` to a sub-pixel day band) and lists the bars within `athTooltipIndexTolerance` rows in the tooltip. The «Coste financiero vs facturado» chart went with the old grey bar: its per-month financing cost is no longer on the card pages (the dashboard card's YTD summary still reads `buildCreditCardFinancingPlByBillingMonth`), and so did the per-purchase `extraOffsets` schedule shift it alone consumed — request param, client state and the legacy offset inputs removed end to end; stale `nw-credit-card-extra-offsets:<id>` localStorage keys are swept at boot (`DisplayPreferencesContext`).

- **Card dollars in pesos: two frames (2026-09-26; `ccFacturacionUsdRate.ts`).** As DEBT — the owed walk, the month-end anchors, the detalle and the stored balances, open-month sums, payments and the financing charges (`statementSection3ChargesClpForBillingMonth`, now in `creditCardPerformancePl.ts` and grouped by `statementDatesForFacturacion`) — a facturación's dollars are valued at its pay-by − 1 (`balanceUsdFxDateIso` / `payByFxDateIso`). The detalle read the pay-by itself until 2026-09-26, so the month-end anchors re-stamp once by up to a day's fx move (·0901: 22 rows, at most 1x.xxx). What a facturación SHOWS it cost — its row's «Facturado US$» pesos, the historial bars and its expense lines (Expenses page, facturación modal) — is the rate actually paid: the dollar-debt payments after its close and up to the next close, weighted — divisas purchases (`pago_tarjeta` transfers with a USD counter leg: the pesos that left checking, the dollars the card was credited) and traspasos de deuda (`cc_traspaso_deuda_links`); today's rate (`fxForLiveMtm`) while it is unpaid and its pay-by is still ahead (the pay-by day included); the pay-by − 1 debt rate when the pay-by passed with no payment on file (older ·0161 facturaciones paid by means the data does not record). Rows carry `usd_rate_clp` / `usd_rate_source` (`paid` | `live` | `pay_by`; a merged group row names a rate only when its members agree), and expense lines read their facturación's rate from the same cached rows (`facturacionUsdRateResolver`), so the modal adds up to the row. A dollar payment line (`isCcUsdPaymentLine`: ABONO DE DIVISAS, a PAGO / MONTO CANCELADO in dollars, a traspaso's USD leg) is printed on the statement after the facturación it pays, so it shows the pesos actually paid for it (`usdPaymentLineClpResolver`, 2026-09-27): the divisas purchase paired with it (found through the payment's evidence key, see «Checking↔CC payment mirrors»), a traspaso's CLP leg (as the owed walk values it), else the rate of the facturación it paid — the one whose (close, next close] window holds its date (`facturacionPaidOn`, the window its paid rate sums over). - **Facturado financing links (`cc_facturado_financing_links`, «Financiamiento de facturado en cuotas»; two fixes 2026-09-21).** A facturado of one card (·0101) paid through installment purchases on another (·0901) is declared as a link; `applyCcFacturadoFinancingProjection` (`ccFacturadoFinancingProjectionLines.ts`, the last step of the expenses payload) then hides the financing cuotas everywhere (`excluded`), keeps the financed purchases in their month in «Total» mode and, in «Por cuota» mode, splits each financed purchase equally over the payment's distinct cuota BILLING months as `split_only` lines dated the 28th, carrying the source amount as `installment_total_clp` so the «/$total» superscript shows. **Financing cuotas are matched by exact `purchase_key`, so a statement cuota line must carry the same with-total `installment-h:` key its plan-derived siblings do:** `installmentLedgerTotalForStatementLine` (`ccExpenseCategories.ts`, the one resolver behind both the flows builder's `installment_total_clp` stamp and `resolveCcExpensePurchaseKey`) reads the plan through the line's own `cc_installment_payments.parser_row_id` first, then identity when the matching plans carry one total (twin plans of identical purchases share theirs), then the printed `valor_cuota_mensual_clp` among same-identity plans with different totals, else the legacy no-total key (which the category/notes readers still resolve). The identity-only lookup refused the June-2026 twins (two RECAUDACION EX PLAZA LYON plans dated 2026-06-30, 1.xxx.xxx + 1.xxx.xxx = the ·0101 June facturado), so the August-billed cuota-01 lines carried the legacy key, the link saw only the Sep/Oct plan-derived cuotas and split June's Lider spend into HALVES labelled 1/2 over Sep–Oct instead of thirds over Aug–Oct. **The interest gap is Σ cuotas − the closed statement's `monto_facturado`** (`statementFacturadoClpForBillingMonth`: CLP, non-web-paste, keyed by statement month like the lines; duplicate copies collapse on their identical total, disagreeing totals throw; no closed statement → no gap line; up to one peso per cuota is rounding) — never Σ cuotas − Σ financed lines, which read the financed card's own cuotas billed that month (the ·0101 August link printed 3x.xxx of phantom «bills» over Sep–Nov) and notas de crédito as ± interest. Those cuotas stay in the financed month on their card, so the all-months total is still Σ cuotas. A facturado paid as a one-shot purchase (the RECAUDACION EX PLAZA LYON one-shots) needs no link: its `no_cuenta` category keeps it out of gastos.

- **Financing links declare themselves (2026-10-05; `ccFacturadoFinancingAuto.ts`).** After every card write (`mergeCcAccountFromParsedRows`, the feed import's end, a plan created by hand or from a tagged line) the matcher looks for a closed CLP facturado (any card, month not yet linked) that cuota purchases on ANOTHER card paid: on one day, purchases whose principals (the printed one for an interest plan, else the total) add up to it to the peso, dated after its close and up to 10 days past its pay-by — the merchant is not used. Plans get the link (`upsertCcFacturadoFinancingLink`); a feed line tagged as a cuota purchase with no count yet counts as a payment too but waits for its plan to be linked. Two fitting combinations, or a purchase fitting two facturados, are reported and left alone; an existing link is never touched. When the paid card shows no payment of that amount around the date (payment lines −3…+5 days, or a statement header naming it) a PAGO is planted in its open bucket (batch kind `cc_financing_payment`) — BCI has no daily feed, so its payment otherwise waited for the next statement while both cards counted the debt; the statement that prints the real PAGO settles the bucket line. Replayed on the real DB with the two hand-made links removed, it rebuilt both exactly (June: plans 160 + 161; August: 170) and flagged nothing else in the history.
- **Facturación closes come from the bank's own evidence, not the config cycle (2026-09-26; migration 185, `ccBillingCloses.ts`).** The bank publishes a close well before its statement, twice. **Announced:** current statements print the following cycle — Santander «PRÓXIMO PERÍODO DE FACTURACIÓN 25/08/2026 24/09/2026» (June 2026 on), BCI Lider «Próximo Período de Facturación 27/08/2026 26/09/2026» — parsed into `cc_statements.next_period_from` / `next_period_to` (`pdf_next_period_*` in `cc_statement_reconcile.py`), and the Santander statement JSON's FechaProxFact fills `next_period_to` (JSON-written statements carry it; for a PDF-owned close the JSON importer fills it when missing and reports a disagreement). The gap between a statement's period end and its printed next start is the issuer's **close-day rule** (`closeDayOffsetDays`): Santander starts the next cycle ON the close day — a purchase dated the close day bills next month (the 24/09/2026 rows sat in «por facturar» the day after the September close) — BCI the day after. **Observed:** the Santander unbilled feed always opens with a **SALDO INICIAL** row (per currency) dated at the latest close and valued at that facturación's «Monto total facturado» (verified in both currencies on the July 2026 close); the scraper keeps it apart (`saldoInicial` on each slide — it was discarded until 2026-09-26) and `import:santander-movements` records it in `cc_feed_billing_closes` (a repeat that changes the date or the amount throws). Precedence per billing month: statement → feed → announced → estimate (`closeEvidenceForBillingMonth`). **The estimate is the day of the account's latest known close carried into the month** (clamped to its length: ·0901 the 24th, ·0101 the 26th); the config cycle only estimates for a card with no close on record (2026-09-26 — the default 20 had put every projected close and daily bar four to six days early). Never «fix» the config cycle to the real close day instead: the config close is the open buckets' `statement_date` identity (`statementCloseDdMmYyyyForBillingMonth`), which must stay off the real close days or a bucket shares its date with the incoming statement. **The open month advances on the bank's close** (`lastClosedBillingMonthForAccount` = latest statement close, a later feed-observed close, or a later announced close whose next cycle has started); the months between the last statement and that close are **provisionally closed** (`provisionallyClosedBillingMonthsForAccount`): facturado = the feed's SALDO INICIAL (USD at the pay-by) when observed, else the app's estimate; the billing-detail row is statement-framed (`as_of_kind: statement`, as_of = the real close, `provisional: true`) so the next month's balance roll starts from it; facturaciones carry `is_provisional_close`, `close_date_source` and, with the bank's figure, `provisional_estimate_total_clp` (the client marks the month «provisoria» and an estimated close «≈»). **The open month's cupo subtracts what a provisional close billed** (`provisionalBilledCuotasClp` in `cupoEnCuotasForBillingMonth`): the live cupo marks a cuota billed only once a statement prints it, so until the statement arrives it still carries the provisional month's cuotas, which that month's row already bills (2026-10 ·0901 read 7,xx M against September's 5,xx M). **Not negative schedule evidence:** the manual-plan clamp keeps reading `lastPdfBillingMonthForAccount` — a close without its statement does not say which cuotas it billed. **Open buckets keep their config `statement_date`** — an identity (`cc_statements` is unique on source + date and several sums group lines by statement date, so a bucket must never share the incoming statement's date); displayed closes come from `closeDateForBillingMonth`. **Feed routing:** everything a post-close feed lists is unbilled by definition, so every row goes to the month after the observed close (`targetBillingMonth`), and bucket lines under earlier months whose one-shot key the feed still lists move forward (`moveOpenBucketLinesByDedupeKey` — close-day purchases, pending authorizations that settled after the close). The repair pass moves bucket lines from the next cycle's first day (`nextPeriodStartIsoForBillingMonth`), not from the day after the close, and creates the open bucket only when a line moves into it — it runs on every card merge, and the eager create left the retired ·0161 an empty «open» facturación each month (2026-05 → 09, which the merged group ledger then flagged open as well; the five were deleted 2026-09-26, snapshot `20260926-151347-before-retired-cc-empty-bucket-cleanup`). **Statement reconcile matches instead of deleting a date window** (`reconcileOpenWebPasteAfterPdfClose`): a bucket line on the statement (same merchant, amount, date within a day — `webPasteLineMatchesStatementLine`) is deleted; an unmatched line inside the billed cycle (up to, not including, the next cycle's first day) is deleted as a pre-auth the statement settled differently; an unmatched line outside it moves to the open facturación; a later bucket's line is deleted only when the statement bills it. The old inclusive window deleted Santander close-day purchases until the next feed re-listed them. **Stale buckets** (carried into the open month by the read paths) are only those of statement-closed months — a provisional month's bucket is its own evidence. **One rule decides which facturación a statement's lines belong to (2026-09-26):** `facturacionMonthByStatementDate` (the statement's own month; a stale bucket's, the open month). The open-month facturado and payment sums read it through `statementDatesForFacturacion`, and the expense lines' `billing_month` is stamped from it, with a `web_paste` flag for the lines the modal may delete. The facturación modal is a plain filter on that month (`flowLinesForFacturacionMonth`), so it lists exactly what the facturado counts. The client's own copy of the rule, `statementsForFacturacionMonth`, was removed: it put every earlier bucket in every later month and treated a month as closed on any one statement, which listed September 2026's CLP bucket under October while only September's USD statement had arrived. **Cross-check:** a statement for a feed-observed close must print the same date and bill exactly the SALDO INICIAL (CLP to the peso, USD to the cent) — `assertFeedClosesMatchStatements` throws inside every card merge and on every feed import. A pasted «SALDO INICIAL» row is skipped (`skipped_saldo_inicial`), never imported as a 1,xx M charge.

## Ingest API (2026-09-30; plan in `docs/ingest-split-plan.md`)

- **Two packages meet here.** `ingest/` (workspace `nw-tracker-ingest`, formerly `scraper/`) reads the outside world; the server applies what it sends and becomes the only DB writer as sources move over. They share only **`server/contracts`** (workspace `nw-tracker-contracts`): the envelope (`schema_version`, `feeder_id`, `source {channel, ref, label?, fetched_at?}`, `payload`), the result / error bodies, the kind registry `INGEST_KINDS`, a typed client (`createIngestClient`, validates before sending) and a JSON Schema export (`npm run schema -w nw-tracker-contracts`). `ingest` never imports the rest of the server; the server never imports `ingest`.
- **Kinds are canonical, never bank-shaped:** a kind says what the data means (a card's open-cycle listing, an observed close, a cuota-purchase hint); bank decoding lives in the feeder, so any feeder can produce it. One `schema_version` per kind; a change old payloads would not satisfy bumps it.
- **`POST /api/ingest/<kind>`** (`server/src/routes/ingest.ts`) checks envelope → version → payload before a handler runs (4xx `unknown_ingest_kind` / `unsupported_schema_version` / `invalid_envelope` / `invalid_payload`), then calls the kind's handler in `INGEST_HANDLERS` (`server/src/ingestHandlers.ts`; its type makes a kind without a handler a compile error, and registration throws on any mismatch) and answers `{status: applied | duplicate | conflict, kind, schema_version, message?, details?}`. `GET /api/ingest/kinds` lists what is accepted. Both registries are empty until the first source moves.
- **Access (`server/src/ingestAuth.ts`):** local connections only (the socket address, never `req.ip`); `INGEST_TOKEN` adds a required `Authorization: Bearer`, and `INGEST_ALLOW_REMOTE=1` — refused at boot without a token — lets a remote feeder in. `DEMO_MODE` refuses everything (`ingest_disabled`). Ingest bodies may be up to 32 MB (the rest of the API keeps 2 MB): a whole document set travels in one request.
- **Run protocol (2026-09-30, Phases 2a + 2b; built, switched on by `ingest/switch-schedule.sh to-server`).** The server decides WHEN and WHAT: `ingestRunScheduler.ts` ticks every 30 s on the wall clock (timers stall in sleep, the clock does not, so the first tick after a wake sees a missed slot) and `decideIngestRun` (`ingestRunPolicy.ts`, pure) picks one action: the nightly for the latest 22:00 Chile slot (answered by an `ingest_runs` row or any daily run recorded after it; skipped when a daily run finished < 60 min ago; waits for a run in flight), else the hourly poll for the latest :30 slot (skipped while a run is in flight). An hourly request may carry one bank fetch, `decideSantanderFetch`: a **catch-up** when no card feed was fetched since the latest 22:00 slot (30-min grace), none was attempted for that slot, the login is not latched and the bank was not tried in the last 35 min; else the **payday** morning fetch (`santanderPaydayFetch.ts`). Its inputs are the feeder's bank facts from the latest run report (`santander_state`: last attempt, last successful card-feed fetch, login latch, and the feeder's own catch-up / payday markers — `.santander-catchup.json` / `.santander-payday-fetch.json`, which every runner writes, so attempts on either side of a switch count) plus this scheduler's own history (an attempt = requested and not declined). Requests go to the ingest service (`INGEST_URL`, default `http://127.0.0.1:3002`); a slot the service did not take is `not_started` — the nightly is retried every tick and badges «Ingest service unreachable» once per slot, the hourly is given up **A request is idempotent per run id (2026-10-03):** the retry carries the same id, the service answers 202 again for the run it is running and `already_ran` (409) for one it finished, the server reads both — and a «busy» naming its own run — as started, and a report for a run marked `not_started` is accepted; the service answers before the run starts, and only a slot's second unreachable answer badges. On 2026-10-02 a request sent as the Mac woke timed out at 10 s while the service took it (11 s), the server read the service's «busy: run 50» as someone else's run for 20 minutes, refused the report, and asked again — run 50 ran twice, the second time into the bank's 30-minute guard. **The server records each run** when its report arrives (`completeIngestRun` → `recordDailyRun` / `recordHourlyEmailRun`, the same titles and badge rules as the shell runners' `record:*`; a dry run records nothing, a quiet hourly nothing), and a run with no report after 3 h / 90 min is `lost` and recorded as a failed run. `ingest_runs` (migrations 200–201) is the scheduler's memory, one row per (kind, slot); `GET /api/ingest/runs` lists it. **The ingest service** (`ingest/src/service/`, LaunchAgent `com.user.nw-tracker-ingest` in the GUI session) takes one run at a time (409 busy, also while a shell runner it did not start is running) and runs it with the TypeScript runners (`ingest/src/runner/`: `runNightly` / `runHourly`, the shell runners' sequences step for step — same labels, commands, gates and apply flags, verified against `daily-run.sh` / `email-run.sh` driven through a fake `npm` in 11 scenarios; output appended to `cfraser/daily-run.log` / `email-run.log` in the same format, the hourly log rotating at 5 MB). It may decline a requested bank fetch (latched login, bank tried < 35 min ago — reported `vetoed`, not an attempt), raises the desktop alert on a failed nightly, and reports steps, activity, the fetch outcome and the bank facts to `POST /api/ingest/runs/<id>/complete`, retrying ~15 min while the server is down. `INGEST_RUN_DRY=1` makes every run a dry run. `daily-run.sh` / `email-run.sh` and their check scripts remain only as the `to-launchd` fallback. **Enabling:** `INGEST_SCHEDULER_ENABLED=1` only in the INSTALLED server plist (set by the switch script, kept by `install-server-agent.sh`), never the root `.env`; the scheduler is off on any instance with `BACKGROUND_JOBS_ENABLED=0` whatever the flag says. Never run both schedulers: `switch-schedule.sh to-server` retires the two timed agents in the same step, `to-launchd` reverses it, `status` shows which is live. Rehearsed on a copy of the real DB with the service in dry-run mode: an on-time hourly, a nightly 1186 min late, and an hourly whose payday fetch the shell's marker correctly withheld.

## Global sync scheduler

- In-process scheduler (`server/src/globalSyncScheduler.ts`): polls every 15 minutes **only while any source is stale**; when all are fresh, stops polling and wakes at the earliest source `next_sync` wall time.
- **Only the user's primary app instance runs background jobs.** Any secondary dev server sharing the real DB — every `.claude/launch.json` server config (already set) or an ad-hoc `npm run dev -w nw-tracker-server` — must set **`BACKGROUND_JOBS_ENABLED=0`**: two in-process schedulers on one SQLite file double-run every due sync (duplicate `Sync` rows in `app_messages`, identical diffs) and race writes ("database is locked"). See the env bullet under Server runtime modes.
- **Crypto EOD** (`crypto_eod`): due from 23:55 Chile; `equity_daily` trade dates are **UTC** days. Source: CoinGecko daily USD (includes weekends; Yahoo skipped gaps). Due close = last **completed** UTC day at sync time (never the in-progress UTC calendar day). Stale carryover persists after midnight Chile until that day is in DB (see `cryptoEodDueUtcYmd` in `equityEodSync.ts`). Backfill: `npm run backfill:crypto-coingecko-eod -w nw-tracker-server`.
- Manual “Marcar desactualizado” calls `notifyGlobalSyncScheduler()` to start polling immediately.
- **IPC is the Banco Central's base-2023 spliced index, checked against its own monthly variation (2026-09-29; `ipcSeries.ts`, `fetchIpcMonthsVerified` in `bcentralApi.ts`).** `ipc_daily` stores the index only (`G073.IPC.IND.2023.M`, first-of-month dates, 1998 →); every fetch also reads the published variation (`G073.IPC.VAR.2023.M`) and throws unless each month's index ratio matches it within 1e-5 points (full history: 1,2e-7). Both print plain decimals and go through `parseUsNumber` — the generic `parseBcentralNumber` read «133.823492253» as 133.823.492.253, and the base-2018 series had stopped at 2023-12, so the table held 90 corrupt rows until it was reloaded. The splice is not the INE's official variation in every month: the UF, which moves with the official one-decimal variation, disagrees with the rounded spliced variation in 15 of 128 months since 2016 (base changes of 2019 and 2024, rounding edges), so a tax reajuste that must follow the SII's figures cannot assume them equal.
- **The official IPC variation lives apart, in `ipc_official_monthly` (2026-09-29; migration 196, `siiOfficialIpc.ts`).** The INE's monthly variation as the SII prints it (`sii.cl/valores_y_fechas/utm/utm<year>.htm`, one decimal) — what the UF follows and what the SII reajusta with — plus the index as printed in the base of its day (ratios across the 2019 and 2024 base changes are meaningless; reajustes chain the variations, `officialIpcVariationPctBetween`). Every month is checked against the UF (growth from the 9th of the next month to the 9th of the one after, rounded to one decimal — it matched 2016-01 → 2026-08, all 128); only the two latest months may wait for their UF, anything older throws, and a stored month whose figures change throws. Filled by `server/scripts/backfill-sii-official-ipc.ts` (from 2016: `uf_daily` starts mid-2015); the monthly `sbif_ipc` sync step fetches this year's page (and last year's until its December is stored).

- **AFC Fondo de Cesantía (CIC) is a cuota ledger priced by the Superintendencia de Pensiones' public daily valor cuota (2026-09-21; `afcCicSeries.ts`, `cuotaLedgerAccounts.ts`).** Source **`afc_cic`** reads the SP's yearly CSV (`vcfAFCxls.php?aaaa=YYYY` — semicolon, Latin-1, Chilean numbers, one row per CALENDAR day with weekends/holidays as flat carries of the prior close, history since 2002, ~15 KB a year, no auth; the parser fail-fasts on any header/row shape change) into `fund_unit_daily` series `afc_cic` (CIC column only — the FCS is the solidarity fund). - **The AFC ledger is rebuilt from the AFC documents, not derived (2026-09-22; `afcCertImport.ts` on the server, ingest's `afc/documents.ts` reading the PDFs through `unemployment_fund.documents`; `npm run import:afc-cert -- --cert=<pdf> [--cartola=<pdf> …] [--replace-excel-rows] [--drop-ids=…] [--apply]`).** The AFC prints no cuotas anywhere, and none are needed: the cuatrimestral cartola closes in cuota arithmetic against the SP series to 35 pesos, which proves the CIC is valued at the SP valor cuota, each cotización is credited at the valor cuota of its **fecha de pago**, and the AFC's commission is deducted in cuotas (the one thing the SP series does not carry). So (1) the **certificado de cotizaciones previsionales acreditadas** (every cotización with período, empleador, monto, fecha de pago; two legs per período — trabajador 0,6 % + empleador 1,6 % — closed by a `TOTAL` line the parser must reproduce) becomes ONE movement per (período, pay date) with `units_delta = monto ÷ valor cuota(pay date)`, identity = note key `AFC cotización — período YYYY-MM (pago YYYY-MM-DD)` (idempotent re-imports; a changed printed amount is a `mismatch`, never overwritten); (2) withdrawals are priced at the valor cuota of their date, except one after which the account's own next stored valuation reads 0 with nothing else moving the ledger before it — that one **closes** with exactly the cuotas held; (3) each **estado cuatrimestral** yields a true-up per printed saldo (`AFC ajuste cartola — saldo inicial|final YYYY-MM-DD`): `units = saldo ÷ valor cuota(day) − ledger through the day`, `flow_kind = cash_fee` when the ledger sits above the saldo (the commission) or `savings_earnings` below — both are P/L to every deposit reader, never capital — refused when the period's cotizaciones in the ledger differ from the cartola's «Total de cotizaciones» (the certificate import is incomplete; a true-up must not absorb missing cotizaciones as «commission»), and closing withdrawals are re-measured after the true-ups. ## Rentabilidad benchmark row (2026-10-03; migration 207, `benchmarkLevels.ts`, `benchmarkComparison.ts`)

- **The month windows (MTD → TOTAL) are chained from DAILY returns since 2026-10-04** (`periodReturnsDaily.ts`): each day's flow-adjusted `pct` of the page's own daily series (`resolveAccountDailySeries` / `resolveGroupDailySeries`, full history), from the month-end before the window's first month through today; the pesos and the window bounds stay the monthly rows'. Monthly chaining counted a month's deposits from its first day and misstated months with large mid-month flows (Acciones TOTAL 7,6% monthly vs 12,6% daily). The full-history daily series behind every Rentabilidad table are warmed in CLP after the page bundles (`rentabilidadDailyWarm.ts`: 36 scopes, ~11 s cold, ~1 s after a live-quote tick, one scope per macrotask).
- **Every Rentabilidad table (account pages, investment group pages, Inversiones) has a second row comparing it with a selectable benchmark**, default the mortgage, choice remembered per surface (`<pageKey>.returns`, `useSurfaceBenchmark`). Fetched apart from the page payloads (`GET /api/benchmark-comparison?benchmark=&unit=&account_id=|portfolio_group=`, `GET /api/benchmarks`), so a change of benchmark refetches only the row.
- **The row is a shadow portfolio:** for each window it starts with what the account or group was worth at the window start (1D/1W: the marks on the anchor day; month windows: the first month's `prior_closing`, the figure the real P/L starts from) and receives the same flows on the same days (`loadMergedDisplayDepositInflowEvents`, `flowEventInUnit` — transfers between a group's members cancel), all in the benchmark. Cells: the benchmark's own return over the window (L(end) ÷ L(start) − 1, comparable with the real time-weighted %), the shadow P/L, and Δ = the real cell's P/L − the shadow's. A window that starts empty measures from its first flow; a benchmark with no level at the start or on a flow day leaves the cell empty, never a guess. Levels are in the display unit at each day's rate (live fx today).
- **Benchmarks are rows of `benchmarks`, one per kind:** `equity_with_dividends` (`equity_daily` closes, each `equity_dividends` dividend reinvested at its ex-date close net of `withholding_pct`; SPY at 15%), `fund_unit` (a `fund_unit_daily` series; Risky Norris = `fintual_cert_risky_norris`), `index_plus_rate` (UF compounded at `rate_pct`: the mortgage at 4,95%, UF at 0, a DAP at 2% — migration 208). A level read on or before its date throws when the observation is over 10 days old (a stale series, not a weekend). A new benchmark of an existing kind is a row, not code. **`portfolio_group` (migration 209)** names one of the user's own groups (`portfolio_group_slug`; seeded Brokerage, Acciones, APV, Crypto): its level is the group's time-weighted return, each day's flow-adjusted `pct` from its own daily series chained (`chainDailyReturns`), in the display unit; offered under «Tus portafolios» in both selectors and only while the group exists. It is chained DAILY, so it differs from the group's Rentabilidad TOTAL, which chains monthly returns (every month's flows counted from day 1): Acciones 12,6% daily vs 7,6% monthly on 2026-10-04. In the prepayments comparison, payments that predate a benchmark's history are listed without an invested value and left out of both sides of the totals (`covered_payments` / `covered_from`).
- **`equity_dividends` is write-once** (Yahoo `events=div`): `stocks_nyse` fetches it with the closes for every NYSE ticker and benchmark tickers are always in that sync; a restated amount is a sync note, never overwritten. History: `npm run backfill:equity-dividends -w nw-tracker-server [-- --ticker=SPY --dry-run]`.
- Check: the SPY account against the SPY benchmark differs by tens of pesos over YTD/1A (ex-date vs pay-date reinvestment).
- **Both rows carry the money's IRR** (`real_irr_pct` / `shadow_irr_pct`, `irr.ts`): the rate that turns the window's starting value and every flow, on its date, into the end value — yearly on windows of 365 days or more, over the window on shorter ones (`irr_annualized`; annualizing a day is noise). Solved by a grid scan plus bisection; null when no rate or several rates fit (e.g. a shadow the same withdrawals leave below zero: Brokerage TOTAL against the mortgage). It replaced a Modified Dietz money-weighted %, which inflated on long windows with large flows both ways (826% on Brokerage TOTAL).
- **The mortgage page's «Prepagos vs invertir»** (`mortgagePrepaymentComparison.ts`, `GET /api/mortgage-prepayment-comparison?account_id=&benchmark=&unit=`) follows every peso paid above the minimum cuota (`depto_payments.amortizacion_ext_clp` on the `mortgage` rows: the `prepago` rows and the extra in each regular payment) to today two ways: prepaid, at the `mortgage` benchmark; invested the same day in the selected benchmark (default SPY, `account.<id>.prepayments`). Δ = invested − prepaid; totals carry both IRRs. Before tax; the insurance that shrinks with the balance is left out.

## Daily series — calendar-day grid deltas (`dailySeries.ts`)

- **`getBucketDailySeries(accounts, { unit, days, now?, includeAccounts? })`** (`server/src/dailySeries.ts`): one point per **Chilean calendar day** ending today (`chileWallClockAt(now).ymd`; `days: 0` = since `portfolioStartYmd`, `DAILY_SERIES_MAX_DAYS` 7400 is a sanity bound, not a product cap — full-history daily is a user choice, 2026-07-21). Values are true levels via `bucketValueInUnitAt` (→ `accountMarkClpAtYmd`) — each account's mark is flat on its own closed days (weekend/holiday), so **per-account market-calendar attribution falls out of level deltas** (a `.SN` line moves on Chilean days, USD stocks on NYSE days, crypto/UF every day) with no session-window bookkeeping. Each point carries **`market_day`** (`isNyseTradingDay || isChileBusinessDay`; false = weekend/shared holiday — the detalle table dims those rows). Flows use the same deposit-event accounting as `netDepositFlowBetween`, bucketed per `(prev_day, day]` (bulk `loadMergedDisplayDepositInflowEvents` — USD-cash included since 2026-08-04). `pl = delta − flow`; missing legs → null, never a fake 0. Grid helper: `chileCalendarDaysListEndingAt` (in-file; the old `nyseSessionsListEndingAt` was removed).
- **Money without a value gives no return (2026-10-04; `unvaluedMemberDays`).** A bucket sums only the members that have a mark that day, so a member whose money arrived before its first valuation (the AFP's 2017-06-12 contributions, valued from 2017-06-30) read as the money in without its value: −79% on 06-12 and +358% on 06-30 on Retiro/Inversiones, which collapsed a daily-chained TOTAL to 3,55%. A run of unmarked days that money entered and that ends in a mark — and the day the mark appears — now has `pl` and `pct` null (flat in a chain). Never-valued (not yet open) and no-longer-valued (closed) members are not flagged.
- **Liquidation-edge conventions (2026-08-04):** (1) **USD-cash deposits are event-based, native-frame** — `loadUsdCashCapitalSortFlows` (`equityBrokerageCapitalFlows.ts`) emits every balance-affecting non-interest movement as a deposit event (USD sign = `signedUsdDeltaForAccountMovement`, so Σ event USD ≡ balance − interest by construction); the CLP frame is per event, never a re-priced aggregate: compra counter legs at their real pesos, equity legs (`stock_buy`/`stock_sell`/`dividend_payout`) mirror the stock side's attribution exactly (intra-bucket transfers net to the peso), legless USD at the event date's sell rate. **A wire shared by same-day buys is split pro rata (2026-09-28; `wireProRataFlows`):** with exactly one CLP→USD conversion on the cash account that day, no buy equal to it, and the day's buys needing at least its dollars, each buy carries `wire pesos × buy / Σbuys` at face plus the dollars the wire did not cover (USD already held, e.g. a swept dividend) at the reference rate — the last buy takes the rounding, so the pieces add up to the wire; one buy larger than the wire is the old wire + residual composite. Before, two buys from one wire both fell to the reference rate while the wire came in at its real pesos, so the conversion spread read as a −100% month on the cash account (Racional USD 2026-07) instead of sitting in the stocks' cost. The old balance−interest re-pricing (flowsDeposits window deltas, valuationTimeseries dep maps, dailySeries telescoping, `usdCashMonthlyPerfRows` netFlow) is gone — a no-event window reads 0 deposits in both frames; fx moves on held USD land in P/L like equities. CLP ledger cash and checking accounts follow the same rule since 2026-09-27: the group consolidation sums their merged deposit events per month through `ledgerCashNetFlowBetween` (events load once per account via `netDepositFlowWindows`), and `valuationTimeseries` has no CLP-cash balance − interest branch any more, so the aportes line, both performance tables, the card and the daily series read the same events. In pesos the events sum to balance − interest on every day, so only the USD frame moved: fx moves on pesos held are USD P/L (the consolidated checking P/L used to read 0 in every closed month). These monthly rows (USD cash included) give the first month P/L = close − flow, as the account performance builder does. (2) **`pct_month` is sign-guarded** (`flowAdjustedPct(nominal, prior, netFlow, close, eps)` in `periodReturns.ts`, `flowAdjustedPctMonth` until 2026-09-27 — accountPerformance's closed months, live current-month row and first months, both consolidations, the dashboard pcts (closing at the row's current value), the daily series `pct`, the 1D/1W cells and the equity position's return on deposited all use it). **A period that ends at zero** (`|close| ≤ eps`) on a net withdrawal divides by `prior` (2026-09-27): the start frame's `prior + netFlow` is then exactly `−nominal`, so every sale that emptied an account read −100% however small the loss; withdrawing exactly the prior close reads 0%, ending at zero with no prior close (bought and sold inside the period) reads null, and ending at zero on a net deposit keeps −100% (everything at work was lost, never below −100%). **Zero is the unit's coin** (`ZERO_CLOSE_EPS`: 1 peso, 0,01 USD, 0,0001 UF; `flowAdjustedPct` takes the unit) on every grain: a close, prior or start base at or below it is no capital, so a one-peso dust balance reads null instead of dividing the day's fx move by a peso. **Group periods carry each member's zero close** (`endChargedFlow` / `groupStartFrameFlow`): a member that ends at zero on a net withdrawal has it charged at the period end, capped at the group's own net withdrawal so a transfer between members is not counted twice — in `consolidateGroupMonthlyPerf` (rows carry `end_charged_flow`, summed by the yearly rollup), the net-worth / inversiones bucket sums (re-capped), the daily series and the 1D/1W cells; a period where no member empties is unchanged: when `prior + netFlow ≤ eps` (a liquidation withdraws intra-month gains too) the denominator falls back to `prior` — otherwise a close-at-0 month reads exactly −100% by the identity `nominal = −(prior + netFlow)` and poisons every chained Rentabilidad window. (3) **Daily chart lines clip as units** (`trimDailyLineEdges`): a never-held-in-window line nulls its `deposits_acum` too, aggregated bucket lines re-trim after summing, and the daily payload carries **`chart_end_ymd`** (mirror of the monthly block's) when every account line ended — the client trims valuation-chart points only (`buildDailyValuationBlock`); `points` stay full-length for P/L bars and the detalle table. ## Open-month CC bucket — truncated merchant duplicates

- The unbilled month is written by **two sources describing the same transaction differently**: the nightly scraper feed (`import:santander-movements` → `importCcWebPasteLines`, source `cc_santander_fetch`) carries the bank's full merchant string on settled rows, while a manual paste from Santander's web table — and, since 2026-08-28, the feed's own pending-authorization rows — carries it cut at **exactly 15 characters**. The one-shot dedupe key is `merchant | amount | date`, so the two never collide — and the bank usually restates the transaction a day later when it settles, so the dates differ too. Both rows survive and the open month over-reports.
- **`removeTruncatedMerchantDuplicateLines`** (`ccTruncatedMerchantDedupe.ts`) runs after every web-paste/feed write and drops the shorter re-listing once its fuller twin exists — two signatures, both scoped to `import:web-paste%` sources (a PDF statement is the bank's settled record and never carries a truncated or pending merchant), both requiring the same amount to the cent in the same currency, and **identical merchants never match** (two genuine charges of the same amount days apart are real spending; the one-shot key already handles true duplicates). It only fires when BOTH rows exist, so a paste — or a pending row — whose fuller twin has not arrived is untouched. (1) **Truncated** (`isTruncatedMerchantOf`): shorter merchant EXACTLY at the 15-char truncation width AND a strict prefix of the longer one, transaction dates within `RESTATEMENT_WINDOW_DAYS` (4 — a manual paste carries the authorization date, the settled feed row may carry the next day). ## Checking / cuenta vista ledger anchor

- A checking account's balance is **derived from movements**, not stored, so a synthetic **anchor** movement (`import:cartola|anchor|<period>|saldo final`, dated before the first real movement) carries the opening balance that makes the walk land on the latest cartola's `saldo_final_clp`. `ensureCheckingLedgerAnchor` re-derives it whenever an import advances the latest cartola period.
- **The derivation MUST use the same accounting as the balance reader** — `sumClpThroughDate` → `signedClpDeltaForAccountMovement` (matches `account_id OR from_account_id OR to_account_id`, signs each leg per account, and applies `flow_kind` semantics). Anything else silently produces an anchor that is internally consistent but disagrees with what the app displays.
- **Bank posting day (2026-09-30; migration 199, `movementBankPostings.ts`).** `occurred_on` is the best evidence of when money moved (a payment receipt, a broker mail, a card's credit date); `movement_bank_postings(movement_id, account_id, posted_on)` keeps the day a bank document filed it on one account when that differs — after Santander's 14:00 cutoff the next workday, sometimes next month. One row per (movement, account), because a corriente↔vista transfer has a posting on each side; sparse (no row = posted on `occurred_on`). **Every reader that reconciles against a bank document reads `COALESCE(posted_on, occurred_on)` through `BANK_POSTING_JOIN_SQL` / `BANK_POSTED_ON_SQL`**: the anchor derivation and the month table (`nonAnchorClpFlowTotals`), `checkingMovementBalanceAtMonthEnd` (`sumClpThroughBankPostedDate`), the timeline months, the xlsx/cartola dedupe (`partialMovementSupersededByCartola`, `findMatchingCartolaMovementNoteInDb`, the cartola import's count) and `findMatchingInternalTransferLegId` — a leg with a known posting matches only that day, one without matches the business-day window, across months too. Everything else reads `occurred_on`. **Writers** — whatever learns a bank date records it (`recordBankPosting`, which throws when the movement does not touch the account): a bank import deduped against a transfer leg (`claimTransferLegForBankRow`), a hand transfer that supersedes an imported bank row, a receipt re-date, a Fintual promotion, both mirror conversions (each deleted leg's date). This replaced the month-boundary rule that made every mail-sourced writer wait for the bank row (or keep the bank date) when the next business day fell in the next month — the receipt, Fintual retiro and Racional deposit deferrals, the mirror-pair checking-straddle block, the card-payment converter's same-month filter — because a transfer dated in month M whose bank row sat in M+1's cartola shifted the anchor by its amount. The migration backfilled 134 postings from `movement_mirror_merges`, the synthetic-transfer confirmations and re-dated rows; on the real DB that brought 13 checking months onto their printed saldo final and left the anchors and every display value unchanged. Regression: «bank posting day» in `checkingCartolaBalances.test.ts`.
- **Forward-posted rows count from today; history keeps bank dates (2026-09-06).** Santander dates an after-cutoff wire at the next workday and its feed lists the row early (a Sunday import carried a Monday-dated credit), so the ledger can hold movements dated after Chile today. One rule, `displayLedgerCutoffYmd` (`movementTransfer.ts`): a display read at a date before today is strict (`≤ date`), a read at today or later has NO upper bound — a movement we already know about counts now and keeps counting when its bank date arrives, so a value never steps twice. Applied at exactly two choke points: the ledger balance readers (`checkingMovementBalanceClpAt`, `clpCashBalanceClpAt`, `usdCashBalanceUsdAt` → every mark/live/consolidation caller inherits it) and the merged deposit-event timeline (`buildMergedDepositMap` re-dates such events to today and keeps the bank date as `posted_on`), so every flow-adjusted P/L — daily series, 1D/1W strip, dashboard day/month/year cells, the live month row, aportes lines — reads 0 for the row on every day it is shown; the old "skip events dated > today" caps (`flowsDeposits.ts`, `accountDeposits.ts`) were removed because with the balance counting the row they would have produced the phantom in the other direction. The day rollover is what moves the row: Sunday's live point carried it, Monday's rebuild of Sunday (strict, never cached while it was today) no longer does and Monday carries it — including across a month boundary (the old month's live «Mes» totals include it on the 31st; its closed row, built later, does not). **Reconciliation stays strict:** `nonAnchorClpFlowTotals` / the cartola anchor derivation and `checkingMovementBalanceAtMonthEnd` (cartola month table) compare against a bank document that is as-of its printed period end; the deposit-match candidate loaders in `checkingCartolaLoaders.ts` (expense↔deposit links, the deposits reconciliation, checking gastos/inflows pairing) read `loadMergedDepositInflowEventsBankDated` — pairing a fund deposit with the wire that funded it is a statement about real dates, and re-dating would have broken every far-future test fixture too; and the balance cache key carries the cutoff actually applied so a today-value is never served as that date's history. Listings keep the bank date: `AccountMovementApiRow.forward_posted` badges the row («ya en el saldo»). Equity unit walks are not covered (no feed produces forward-dated trades).
- **The bank's own charges are `cash_fee` (2026-10-05; `checkingBankCharges.ts`).** The plan's maintenance fee («COM.MANTENCION PLAN»), the línea de crédito interest and the overdraft tax are stored as `cash_fee` by both checking importers, decided from the bank's description at import: the deposit loaders skip the kind, so they are the account's P/L (a loss) instead of withdrawals, which is the only P/L a peso checking account has. Gastos still list them. The 55 rows imported before were tagged by `server/scripts/tag-checking-bank-charges.ts`.
- **Bug fixed 2026-08-06**: `sumNonAnchorMovementsClpAt` summed `MOVEMENT_CLP_LEG_SQL` over `WHERE account_id = ?`. A transfer row carries the account in `from_account_id`/`to_account_id` with **`account_id` NULL**, and `NULL = ?` never matches — so every transfer leg was invisible (and the CLP leg is unsigned, so an outbound transfer would have counted as an inflow anyway). On the real cuenta vista that hid 260 legs worth −1x.xxx.xxx: the anchor derived to −1x.xxx.xxx instead of +1.074 and the account read −1x.xxx.xxx instead of 0. It stayed latent for months because the anchor is only re-derived when a new cartola advances the period — an unrelated import is what detonated it. Regression test: «cartola-derived anchor with transfer legs» in `checkingCartolaBalances.test.ts`. **When touching any balance/anchor helper, check whether transfer rows (account_id NULL) are in scope.**

- **One source for a checking account's movements (2026-10-06; `listCheckingMovements` in `checkingCartolaLoaders.ts`).** Expenses, income, deposit matching, payslip pairing and income overrides ask for an account's inflows or outflows, never for a document: the function returns the cartola's rows plus the daily «últimos movimientos» rows its cartola has not replaced yet (one superseded but not pruned is left out, so nothing counts twice), and nothing else — not the anchor, not a hand-made adjustment like 12419. Before, income and the matcher's withdrawal pools read cartola rows only, so a month's credits (the salary landing on the 30th) were missing from income until its cartola arrived a week or more later, while gastos already read both. When the cartola supersedes a daily row, `prunePartialMovementsSupersededByCartola` moves what hangs off it by id — the payslip link and the income override — onto the official row (`carryMovementKeyedIncomeState`; both reference movements without a cascade, so a link left behind would fail the import). Which document a row came from is still read from its note in that one function and in the import-side key mechanics (stable purchase keys, the transfer-leg dedupe); a structured source column would retire that.

## Historical mirror pairs + movement search

- **Mirror pairs** (`/panel/mirror-pairs`): two pre-transfer-model single-leg rows (retiro + same-amount depósito on different accounts, inflow 0–5 days after outflow) are converted into one transfer row dated the **outflow day**; original legs (ids, dates, amounts, units, notes) live in the **`movement_mirror_merges`** table keyed by the transfer movement (ON DELETE CASCADE; the transfer note is a human summary) and conversion is undoable (`undoMirrorConversion` — a server-side function; its HTTP route was removed 2026-09-05, the UI never called it). Candidates: `listMirrorPairCandidates` (`server/src/movementMirrorPairs.ts`) — high confidence = unique both directions + within the cartola business-day window (`bankDateMatchesTransferDate`) + no month straddle; month-straddle pairs are ambiguous (converting moves one side's money into the other month on every display) but never blocked — each deleted leg's date stays as the transfer's posting day on its account (the old checking-inflow block went 2026-09-30, see «Bank posting day»). Excluded legs: flow_kind/USD legs, both-legs-cuotas, dap either side, afp/afc **inflows** (pre-tax payroll), deposits already in `expense_deposit_links`/`checking_gap_deposit_mirrors`/`payroll_work_earnings`, Buda/ahorro-split notes. Rejections persist in `movement_mirror_pair_rejections` (migration 155; ids cascade on full rebuilds). **Link-established pairs**: 1:1 `expense_deposit_links` rows (auto/manual, `checking-cartola:` keys resolved via `movementForCheckingPurchaseKey`, amounts equal) surface as `linked: true` high-confidence candidates — the link is the evidence, no window applies; the link row cascades away at conversion. Multi-allocation/partial links, synthetic links, and Buda-note deposits stay out. One transfer carries one `units_delta` (abs; cuota readers use `transferLegUnitsThroughDate`). **Month-precision legs** (cuenta_ahorro_vivienda — sheet records mm-yyyy only; movements dated conventional month-end): the pairing window is the whole month ± 7 days across the boundary (`monthPrecisionPairAllowed`) instead of the day-gap rule, the bank-window requirement is waived, and the converted transfer takes the **real-day (checking) leg's date** — so cartola re-import dedupe matches same-day and checking anchors are untouched (the checking-straddle hard-block is skipped when the out leg is month-precision). Conversion is balance- and aportes-neutral: the aportes/monthly-P&L reader (`loadTransferLegSignedFlowEvents` in `accountDeposits.ts`) buckets each side of a merged transfer on the day **that side's valuation evidence actually moves**, or flow and value are measured in different frames and the gap lands in P/L. **Month-precision legs keep their original `movement_mirror_merges` date** (their marks sit in the sheet month, not the transfer month) — that is what keeps a cross-month ahorro conversion from creating a −X/+X monthly-P&L couplet. **Every other leg uses the transfer's own date**, because balances and `transferLegUnitsThroughDate` both key off the movement: dating a real-day leg at its original settlement day instead produced a phantom ±X P/L couplet across the 1–3 day settlement gap (fixed 2026-07-24 — a checking → Fintual traspaso showed a phantom P/L couplet on 2026-04-21/23 that cancelled within the month but dominated the daily view; 101 legs across 137 gapped merges were affected). Month-precision kinds live in `monthPrecisionAccountKinds.ts` (`accountIsMonthPrecisionDated`), import-free so both `accountBucket.ts` and `flowsCheckingGastos.ts` can read them. Converted cartola credits leave the income pool (a correction) and mirror-merge transfers into checking self-resolve in the deposits reconciliation. **Amount and date cannot tell same-day siblings apart (2026-09-28):** the greedy pick between two same-amount debits of one day is only the lower id, and three historical conversions absorbed the wrong bank row that way (a wire to another bank or a PREVIRED payment instead of the traspaso beside it, one of them through an auto deposit link that had picked the earlier of two wires), while twelve more paired a debit with an unrelated same-amount credit (ATM withdrawals, wires to another bank, a third party's transfer). So every ambiguous candidate carries its competing legs (`out_alternatives` / `in_alternatives`), the panel shows them with their notes, and any of them converts in its place (`resolveMirrorPairRef`); an **auto** `expense_deposit_links` pair with a same-amount competitor in the window is ambiguous (a manual link stays high); a credit the user classified as income (`checking_income_movement_overrides` income kind / force-include) and a checking debit the user categorized as spending (a `cc_expense_unique_purchases` category outside unclassified / deposits / internal transfer / no_cuenta, or a `cc_expense_line_splits` split) are never legs. Repair: `server/scripts/repair-mirror-merge-legs.ts --plan=<json> [--apply]` (report-first, IMMEDIATE, idempotent; plan items `swap` a wrongly absorbed leg for its sibling, `undo` a non-transfer — both restore the original rows under their ORIGINAL ids so id-keyed splits and legacy `checking-mv:` keys resolve again, and an undo records the pairing as a rejection — or `reject` a never-converted pairing; month-end balances and checking anchors are verified unchanged inside the transaction).
- **Checking↔CC payment mirrors (2026-07-22):** a checking «Traspaso a T. Crédito»/PAGO TARJETA debit pairs with the card's payment evidence — a payment line (legacy formats; `isCcPaymentMerchant`, exactly PAGO / MONTO CANCELADO / ABONO — the one rule every payment reader shares since 2026-09-26, when this matcher and the cuota retirement dropped their own SQL `LIKE`) or the statement's `monto_pagado_anterior` header (current format; its date read through `requireHeaderPagoIso`, which throws unless ISO) — by exact amount within ±4 days — the debit may sit on any account under Checking accounts (`accountIdsUnderCheckingAccounts`, the asset leaves under the checking bucket, whatever their kind; until 2026-10-05 only the cuenta corriente, which left twelve 2019–2024 card payments from the cuenta vista unpaired) (`ccPaymentMirrors.ts`; candidates in the /panel/mirror-pairs «Pagos de tarjeta» section, POST `/api/movement-mirrors/convert-cc-payments`). - **A closed month's month-end anchor adds what a later facturación bills (2026-10-06; `unbilledAtMonthEndAdjustmentsClp` in `ccBillingBalances.ts`).** The statement frame (facturado + cupo) covers what the statement billed; the month-end anchor adds every charge and payment dated on or before the calendar month-end that a LATER facturación bills, or none yet — chosen by billing (`facturacionMonthByStatementDate`, so a provisional month's bucket is billed by its month and a stale bucket by the open one), not by a date window starting the day after the close. The stream also carries the dated header-payment legs now (`cc_header_payment_legs`), which neither the walk nor the anchors subtracted before. The daily walk keeps its date window from its anchor (`postCloseLiveBalanceAdjustmentsClp`). Re-stamp: `scripts/restamp-cc-anchor-frame.ts`. - **A statement billed what it printed, credit included; a backdated line enters at its statement's close (2026-10-07; `statementHeaderFacturado`, `normalizedPostCloseLines`).** The import kept only a positive «Monto total facturado a pagar», so a period that ended in credit — ·0161's peso statement of 2018-06-25 (−2xx.xxx) and six dollar ones in credit (2017–2022) — read as «no header», fell back to its lines and left the credit out of the month-end anchor, while the walk counted it: the anchor and the walk from the previous one disagreed by the credit, one month up and the next down. The import, the statement JSON writer and every billing reader (`facturadoFromStatement`, the slot totals, `usdToClpAsDebt`) now take the printed figure whatever its sign; 0 is «nothing billed», only a missing header falls back to the lines (`scripts/backfill-cc-printed-facturado.ts` wrote the 13 stored rows). A line dated two cycles or more before the statement that bills it (a nota de crédito carrying its purchase's date: −4xx.xxx dated 22/02/2018 on the June statement, −3xx.xxx dated 18/06/2020 on August's) takes that statement's close as its date in the post-close stream, so the walk and the anchors count it in the same month (the anchors' own «backdated» exception went). On ·0161 the sum of |anchor − walk| over its 113 month-ends went 3,79 M → 0,83 M; what is left is a peso residue unrelated to credits (2019-07, 2021-11, 2020-02/03, 2018-11, 2024-01, each 50–113k).
- **Dollar header payments (migration 218).** A header leg has a currency and `amount`: old international statements print the period's abono only in the header («ABONO REALIZADO», no line: ·0161 2017-10-24 −249,86 and 2020-01-23 −78,40). `scripts/link-cc-usd-header-abono-legs.ts` (report-first) writes the gap between the header abono and the statement's negative lines (refunds count, traspasos do not) as a dollar leg, dated on the one checking «Compra de Divisas» debit of the period whose implied rate is plausible (which the converter then pairs), else on the previous pay-by. The walk values a dollar leg at its statement's debt fx; the cuota retirement reads peso legs only.
- **A dollar payment is valued at the debt fx of the facturación it paid (2026-10-07; `normalizedPostCloseLines`).** The month-end anchor values a facturación's dollars at its pay-by − 1; the payment that clears them (an ABONO DE DIVISAS / dollar PAGO line, a dollar header leg) is printed on the next statement, and valued at that statement's fx it read the month's fx move as owed: ·0161 2021-11, 3.xxx,xx USD at 839 against the debt at 803, −1xx.xxx between the anchor and the walk. The stream values it at the debt fx of the latest dollar statement that closed before it (the pairing `facturacionPaidOn` uses); a linked traspaso keeps its CLP twin's pesos. ·0781's anchor/walk disagreement 207k → 59k, ·0161 0,83 M → 0,51 M; what ·0161 still has above 50k is missing documents: the 2017-07/08 and 2018-10 dollar statements were never mailed, and the 2020-01..03 dollar statements have no text layer (their OCR'd headers do not add up). Those are estimated (`scripts/estimate-cc-missing-usd-statements.ts --plan=cfraser/cc-usd-estimate-plan-0161.json`): the three missing statements are written as `import:estimate|…` with one «COMPRAS INTERNACIONALES (ESTIMADO)» charge each (the gap between the printed balances either side) and their «ABONO DE DIVISAS» on the checking divisas debit that paid them (dollars = the debit's pesos at the day's dólar × 1,021, the median spread of 114 paired divisas payments); the three scans get their header abono from their own printed totals, an estimated charge for what the scan misses (6,09 / 2,29 USD) and dated dollar legs. ·0161 has no anchor/walk disagreement above 50k left (Σ 0,24 M).
- **Statements from outside the PDF corpus are named `import:<kind>|…`** (`isCcStatementPdfSource`): web pastes, the Santander statement JSON, the 2019 statements rebuilt from mails (`import:santander-mail|`), the CMR card's mailed PDFs (`import:cmr|`). - **Undated header payments get dated legs (2026-10-05; migration 213, `cc_header_payment_legs`).** The parser dates a statement's «monto pagado período anterior» only when exactly one body line carries it, so a period paid in several transfers, or by a debit the card printed no line for, left the header undated — invisible to the cuota retirement, which reads dated payments only: ·0161's facturaciones looked 5,9M unpaid by 2023 and its cuotas retired 3–7 months late, the «deuda en cuotas» line sitting above owed. ## Data provenance (`DataOrigin`)

## Import sources vs runtime

**Rule:** files under `cfraser/` are **import inputs only**. HTTP, dashboard, valuation, and sync read **SQLite**; missing data → error or “run import”, not a silent file fallback.

- **Depto:** runtime reads the **movement ledger** — `loadDeptoLedgerFromMovements()` joins property-account movements with **`depto_payments`** (one row per movement: cuota + the ~17 payment fields; UF-day/deltas/acumulados/analytics re-derived from `uf_daily`). Rows are **sequential daily balances** (2026-07-21): ledger order = `deptoLedgerChronoCompare` (date, then decreasing crédito restante for same-day prepago+cuota pairs), the loader fail-fasts via `assertDeptoPrepagoSequencing` (a prepago must not raise the balance — regular cuotas may, grace-period capitalization is real), and the snapshot fills use exact-date cutoffs with prepago rows included (the first-of-month → month-end cutoff expansion and the prepago-skip are gone; they created one-day equity spikes on every 1st and ±19.7M P/L couplets around prepagos in the daily view). Nov-2024 cuota 9 ↔ prepago 1 balances were repaired in the live DB (`scripts/repair-depto-prepago1-sequencing.ts`, applied 2026-07-21). `mortgagePaymentCreate` writes the movements (human notes, mortgage `flow_kind` in the column) plus both `depto_payments` rows; manual-payment recompute updates the table in place (the old `depto_dividendos_sheet_rows` staging was dropped in migration 158). No `depto_snapshot`: the dashboard RE card synthesizes valor/hipoteca from the property + mortgage account rows (same path as the demo).
- **CC installments:** `import:cc-parsed` / PDF → `cc_installment_*` / `cc_statements`; no runtime CSV.
- **CC parse is incremental too (2026-08-10).** The per-PDF parse cache's identity is **(PDF bytes sha256, parser version) only** — the old `mtime_ns`/size veto produced permanent false misses after ns-level timestamp drift (backup/copy round-trips), re-parsing 4 statements nightly. On a cache hit the PDF is **never read**: the readability peek (full OCR for image-only scans) and the one-shot qpdf repair attempt run on cache-miss files only, and the hit path validates the cached meta (`require_statement_meta`) instead of re-deriving it via `pdftotext -layout`/OCR — cached meta was finalized by `parse_one_pdf` under the same version hash. Nightly `parse:cc-pdfs` went **~11 min → ~1s** (301 hits). Corollary: two different downloads of the SAME facturación filed under different filenames make the incremental import ping-pong that statement's row between the two source names on every run — exact-duplicate downloads are quarantined under a `duplicates/` folder inside the card slot (excluded via `is_excluded_cc_pdf_path`, same mechanism as `pending-review/`). A statement re-downloaded after its close arrives named by its pay-by date; the parse reads the real close and skips it as an already-parsed copy, and it belongs in the slot's `duplicates/`. An old parse stored such copies as their own closes; `server/scripts/remove-cc-duplicate-download-statements.ts` (report-first) finds and removes any left.
- **CC statement import is incremental (2026-08-05).** The import (`card.parsed_statements` since 2026-10-02; `import:cc-parsed` by hand) skips any statement whose parsed rows are unchanged since its last import — no re-import, no re-reconcile. Each statement carries an `import_fingerprint` (migration 171): a hash of the exact CSV records it imported from, written by `importCcStatementsMerge` itself, because only that loop knows which row the statement resolved to (the close-date fallback can match a row filed under a different `source_pdf` when a statement is re-downloaded — a fingerprint keyed by the CSV tuple would never land and the statement would re-import forever). `ccStatementFingerprint.ts` is deliberately a leaf module (its own record type + key helper) so the importer can depend on it without a cycle. Effect on the nightly run: **9,9s → 0,55s**, and one unresolvable legacy statement no longer aborts the whole import. The gate is only ever a *skip*: a statement that does import still gets the full reconcile. **`--full` forces the from-scratch pass** (`import:cfraser-inbox -- --full` passes it through). It was run once at setup — worth doing deliberately after a parser change, but not on a schedule, since a statement whose parse changed re-reconciles itself.
- **CC statement source ownership (2026-08-05, «JSON leads, PDF import guarded»):** `cc_statements` is UNIQUE on (account_id, card_group, source_pdf, statement_date), so one facturación arriving from two sources would duplicate the ledger. Ownership is period-level over (statement close, currency), and **the PDF outranks the JSON** (2026-08-06; `ccStatementJsonSource.ts`). The Santander statement-JSON importer (`npm run import:santander-statements [-- --apply]`, ingest: decoded and sent as `card.statement`; server: `cardStatementApply.ts` over `santanderStatementImport.ts`) skips PDF-owned closes (report-only cross-check — the diff that has already caught real PDF data loss) and writes unowned ones through `mergeCcAccountFromParsedRows` with a stable `import:santander-json|<currency>|<close>` source id; and an incoming PDF for a JSON-owned close **supersedes** it inside `mergeCcAccountFromParsedRows` — the JSON statement rows are deleted (lines cascade) and the PDF is written in their place, with those closes reported as `json_closes_superseded_by_pdf`. The superseded statements' keys are added to `replaceStatementKeys` so the fail-fast reconcile does not count their lines against the incoming PDF. **Why not first-writer-wins:** the JSON is the fast writer (available the day a facturación closes) but not the authoritative document — the international endpoint is dateless with all-NULL headers, so a JSON USD statement carries lines only. Since the real PDF now arrives by e-mail a day or two later, first-writer-wins would have dropped it forever and pinned the ledger to the thinner source. The nightly cross-check pairs JSON rows with ledger lines by normalized merchant + absolute amount and then, for leftovers, by amount + merchant prefix (`pairStatementLines`, reported apart as «matched by prefix»): the PDF layout can glue the charge-type column onto the merchant — «SEG AUTO SANTANDER COMPRAS P.A.T.» for the JSON's «SEG AUTO SANTANDER» (19 stored lines since 2023 carry that padded column; the parser was left alone because a version bump re-parses the corpus). JSON statements are real statements everywhere else: they count toward facturación close and open-web-paste supersede via `isPdfStatementSource` (= not web-paste), participate in traspaso links, and their line dedupe keys live in a `json|`-prefixed key space (stable across re-imports so replacement and category restore work). Import refuses (fail-fast) when the bank's Cuenta→master mapping disagrees with the card registry's plastic routing (`assertNoCardRoutingConflict`) and skips a dateless international response that merely re-serves an older cycle's rows (`usdStatementIsStaleEcho` — the intl RESPUESTA is all nulls, so USD statements carry line data only and headers stay NULL). **A facturación's two currencies pair on (account, NumExtracto) (2026-09-27; `assembleSantanderStatementBatch`, `ingest/src/santander/statementJson.ts`):** the international file takes its close, pay-by, next close and titular card only from the national of the SAME extracto (from the staged name `<Cuenta>-extracto-<NNN>-…` or a capture's `requestBody.INPUT.NumExtracto`; neither, or `extracto-0`, throws); one without a twin is reported «unpaired», never dated from another close; the batch throws only when ambiguous (one extracto with two closes or two differing copies, two extractos claiming one close). Writes go per (account, close). `--apply` moves a superseded facturación (not its account's newest extracto) whose every statement verified into `santander-statement-json/archive/`; dirty groups stay («KEPT»). The pairing's third pass matches a merchant differing only in rendering (`matched_by_rendering`: a trailing 4-digit terminal code only the JSON prints, «KIOSCO 1234» / «KIOSCO»; punctuation, «ABC] 12» / «ABC! 12»). Before this the grow-only dir's first facturación transition (extracto 022 → 023) made the 2026-09-26 nightly throw «Two national closes for account … in one batch».

- **Fintual retiros are synthesized from the mail (2026-08-19).** A «Pagamos tu retiro» e-mail names the exact amount, payment date, goal and cuota count, so `import:fintual-emails` writes the goal→checking transfer immediately even when the checking credit is not imported yet — a morning retiro otherwise strands its NAV drop in the day's P/L until the 22:00 xlsx import (the hourly e-mail poll can see the mail but can never fetch the bank leg). One row only, whichever side lands first: an already-imported credit is still **promoted in place** (`fintualWithdrawalPairing.ts`), and a synthesized transfer relies on the checking importers' existing `superseded_by_transfer` skip (`findMatchingInternalTransferLegId` — signed amount + posting-window match) to absorb the bank's later listing, in both the daily xlsx and the monthly cartola. Each synthesis is recorded in **`fintual_synthetic_retiro_transfers`** (migration 177, message-id-keyed — UNIQUE, so a duplicate-guard miss cannot write one mail twice; `fintualSyntheticRetiros.ts` is a leaf module so the checking importers can stamp it without a cycle), and the skip stamps `confirmed_on` — the only trace the bank ever listed the money, since the skip inserts nothing. `import:fintual-emails` exits non-zero (→ failed step → notification) when a synthesis is unconfirmed past paid_on + 2 Chile business days: the promised wire never appeared in any bank feed, and a phantom credit would otherwise be silently absorbed by the next checking-anchor re-derivation. A retiro paid on the month's last business day is synthesized too (the month-boundary deferral went 2026-09-30): the credit that lands next month brings its posting day, see «Bank posting day»; a promoted credit keeps its bank date the same way. **A retiro to the Fintual balance (2026-09-29):** the mail then reads «tus $X pesos chilenos quedaron disponibles para invertir en Fintual … equivalente a N cuotas» (no bank, no parenthesised count); the classifier sets `paid_to: "fintual"` and the import writes goal → «Fintual CLP» (`import:panel|kind=clp|key=fintual_clp`, Efectivo) with the cuotas — no synthesis record, no checking pairing. ## Server runtime modes (local vs hosted demo)

One binary, env-driven (`server/src/httpSecurity.ts`, root `.env` loaded at boot):

- **The primary instance runs as a LaunchAgent (2026-09-30): `com.user.nw-tracker-server`** (`server/com.user.nw-tracker-server.plist`, installed by `server/scripts/install-server-agent.sh`, which refuses while the port is taken). `tsx src/index.ts` without watch, KeepAlive, log `cfraser/server.log`. Restart after a code change with `launchctl kickstart -k gui/$(id -u)/com.user.nw-tracker-server` (the user's shell alias `nw-server-restart` bootstraps it when not loaded). Its scheduler will own the nightly ingest runs (see `docs/ingest-split-plan.md`), so it must not depend on an open terminal.

- **`HOST`** — bind host; default `127.0.0.1` (keeps the unauthenticated local API off the LAN). Hosted demo (Render) sets `HOST=0.0.0.0`.
- **`CORS_ALLOWED_ORIGINS`** — comma-separated allowlist; defaults to Vite dev/preview origins (`localhost:5173`/`4173`). Never use a reflect-any-origin CORS config — any website could read the API.
- **`DEMO_MODE` is the only access-control switch — there is no login.** The hosted demo used to sit behind a shared-password `/login` page (any syntactically valid email + one public password, logged to `demo_auth_logins`); recruiters reached the gate and left without trying it, so the whole mechanism was removed 2026-07-24 (`AUTH_PASSWORD`, `SESSION_SECRET`, `nw_session`, `/api/auth/*`, the client `AuthContext`/`LoginPage`). Every deployment is now unauthenticated: local mode is bound to `127.0.0.1`, and the public demo is protected by being **read-only** instead — `demoReadOnlyMiddleware` (`server/src/httpSecurity.ts`, mounted only when `DEMO_MODE=1`) answers `403 { error: "demo_read_only" }` to any `/api` request that is not GET/HEAD/OPTIONS, and the client maps that sentinel to the localized `demo.readOnly` message (`client/src/api.ts`). The one exempt mutation is the analytics beacon (`DEMO_PAGEVIEW_PATH`). **Do not put real data behind `DEMO_MODE`** — it is an open door with a read-only latch, not authentication.
- **`DB_BACKUP_ENABLED` / `DB_BACKUP_KEEP` / `DB_BACKUP_DIR` / `DB_BACKUP_DIR_KEEP`** — daily auto-snapshot of the DB while the server runs (`dbBackupScheduler.ts`; default on, keep 14 local `auto-daily` snapshots, optional second copy dir keeping 60). `DB_BACKUP_DIR` points at `~/Documents/backups/nw-tracker` (set in root `.env`). Manual `npm run db:snapshot` labels are never pruned.
- **`CACHE_WARM_ENABLED`** — proactive dashboard cache warmer (`dashboardCacheWarmer.ts`; default on, `0` disables). Rebuilds the page-bundle caches in the background at boot, at 00:05 Chile (day-rollover clear), when `data_version` shows an external write, and debounced (30s) after in-process invalidations — so no interactive request pays a cold aggregation build. The warmed object itself is the served response (`dashboard.page_bundle|<unit>` in the aggregation cache), not just its inner aggregations. CC billing detail lives in the aggregation cache (`cc.billing_detail|<accountId>`; day/data_version fresh + invalidated by CC write hooks), not rebuilt per request.
- **`BACKGROUND_JOBS_ENABLED`** — umbrella for the four in-process schedulers (`server/src/backgroundJobsEnv.ts`, applied at boot after demo-mode defaults): `0` defaults `GLOBAL_SYNC_ENABLED` / `LIVE_QUOTES_SYNC_ENABLED` / `DB_BACKUP_ENABLED` / `CACHE_WARM_ENABLED` to `0`; an explicitly set per-job flag wins. Set on every `.claude/launch.json` server config so agent-spawned dev servers never run syncs/backups against the shared DB — only the user's primary app instance does (see Global sync scheduler).
- Express async route handlers must be wrapped in `asyncHandler` — see GUIDELINES.md «Async route handlers must be wrapped».

## Schema baseline (fresh DBs)

`initSchema()` executes `server/src/schemaBaseline.ts` — the full schema dumped from the live DB (as of migration 155), all `IF NOT EXISTS`. On a brand-new DB it marks migrations ≤ 155 as pre-applied. **Migrations ≤ 155 were squashed into the baseline 2026-07-07 and their files deleted** (personal-data ones also purged from git history; copies of everything live outside the repo in `~/Documents/backups/nw-tracker/{removed,squashed}-migrations/`). The only pre-baseline files kept are the 8 reference-row seeds in `BASELINE_REFERENCE_DATA_MIGRATIONS` (db.ts) — idempotent category/uniqueness seeds the schema-only baseline skips, which still run on fresh DBs. A recorded-but-missing file is harmless to the runner (the live DB keeps all 155 ids in `schema_migrations`), so numbering gaps are expected; post-baseline migrations (156+: fintual flow_kind, depto_payments + movement_mirror_merges + staging drop, accounts.import_key) apply normally everywhere. A migration may pair with a `POST_MIGRATION_HOOKS` entry in `db.ts` (pure TS module, runs inside the migration transaction — see `legacyNoteBackfills.ts` for 157). Tables dropped by a migration must ALSO be removed from the baseline, or every boot resurrects an empty shell via `IF NOT EXISTS`. When squashing again: `npx tsx scripts/regenerate-schema-baseline.ts --last <newest-migration>` (from `server/`), then delete the newly-covered files (keep the reference seeds). Migration SQL is naively split on `;` (no string-literal lexing) — no triggers or `;`/`--` inside literals; use a post-migration hook in `db.ts` for those.

## Server verbose logging

- **`DEBUG_VERBOSE=1`** — enables all channels below (stderr).
- **`DEBUG_HTTP=1`** — `[api] -->` / `[api] <--` for every incoming Express request (method, path, status, ms).
- **`DEBUG_HTTP_OUT=1`** — `[http-out]` for outbound `fetch` (BCentral, Yahoo, the Superintendencia de Pensiones, Fintual sync).
- **`DEBUG_DB=1`** — `[db]` for SQLite `prepare`/`exec` slower than **`DEBUG_DB_SLOW_MS`** (default 20). **`DEBUG_DB_ALL=1`** logs every statement.
- **`DEBUG_PERF=1`** — `[heavy] …ms` for labeled expensive work (`server/src/heavyWork.ts`).

## Dashboard performance profiling

- **`npm run profile:dashboard`** (from `server/`): sequential timings for dashboard builders on the test/dev DB (`NW_TRACKER_TEST_DB` or default `server/data/nw-tracker.test.db`).
- **`DEBUG_PERF=1`** (or **`DEBUG_VERBOSE=1`**) on the server logs `[heavy] …ms` spans for labeled work (`server/src/heavyWork.ts`) during HTTP requests.
- Home page: **`GET /api/dashboard/page-bundle`** — one client call replaces the old 5-way fan-out. The whole bundle response is served from the aggregation cache (`dashboard.page_bundle|<unit>`, built by the warmer; cached value is the in-flight promise so concurrent cold requests share one build). Every explicit invalidation drops it — `invalidateCcBillingDetail` and `invalidateMarketDataAggregations` are the two funnel points — so a warm request is ~5ms; only requests landing in an invalidation→rewarm gap pay the full build.
- Nav strip (sidebar / group pages): **`GET /api/dashboard/nav-context`** — accounts + liabilities + overview in one call (client fetches only on group/liabilities routes and account detail when the nav node has routable children; home uses `page-bundle` only).
- Dominant cost is usually the portfolio-group totals aggregation inside **`getDashboardValuationTimeseries`** / **`getGroupValuationTimeseries`**; `@heavy` marks those entry points in source.

## Server Vitest (SQLite)

- Vitest uses **`server/data/nw-tracker.test.db`**, never `nw-tracker.db`. Both are gitignored (`server/data/*.db`).
- **`NW_TRACKER_TEST_DB`** is set in `server/vitest.config.ts` (`test.env`) and in the server **`npm run test`** script so it is present before `db.ts` loads.
- **`server/src/vitest.globalSetup.ts`**: when `nw-tracker.test.db` is missing, generates the **lean synthetic preset** (`generate-demo-data.ts --preset=test`) — tests must not depend on personal data. Delete `nw-tracker.test.db` to rebuild; the file is never refreshed automatically, so a stale pre-synthetic dev-DB copy on disk silently keeps being used (symptom: suites failing on missing `demo:*` fixture accounts or real-data invariants — delete the test DB). Escape hatch: `NW_TRACKER_TEST_FROM_DEV=1` copies the local `nw-tracker.db` instead (reproducing an issue against real data).
- **`server/src/vitest.setup.ts`** → **`server/src/test/vitestDbSeed.ts`**: ensures an isolated Santander CC master `credit_card_master|santander|vitest-fixture` (never a real card) for merge/import tests.
- Override the test file with `NW_TRACKER_TEST_DB` (absolute path, basename under `server/data/`, or `:memory:`). Vitest uses `pool: "forks"` with one sequential fork (`fileParallelism: false`) — better-sqlite3 segfaults nondeterministically in worker threads at teardown, killing the run after a few files; parallel forks would race migrations on the single SQLite file.
- To remove Vitest fixture rows from **`nw-tracker.db`** (e.g. after running tests against the wrong DB): `sqlite3 server/data/nw-tracker.db < server/scripts/cleanup-cc-vitest-pollution.sql`.
